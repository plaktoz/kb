The /reflect Loop — Making Agents Better Over Time

Module 4 — Autonomous Runs and Continuous Improvement · Lesson 11 of 12 · ~25 min
Source github.com/michael-denyer/pstack-claude — reflect SKILL.md
The /reflect skill mines conversations for durable learnings and routes them into concrete skill edits, closing the feedback loop that makes the agent system improve over time.

What /reflect does — and why it matters

Every conversation an agent has is a data point. A tool call that required three retries, a judgment call that produced a suboptimal branch, an entire approach that was never considered — these are the raw material of improvement. Left unexamined, they repeat. Examined systematically, they become skill edits that make every future agent in the organisation behave better.

/reflect is pstack's mechanism for doing that work. It mines the conversation transcript through three independent review lenses, synthesises findings into structured categories, performs a structural check, and then — only with explicit human approval — routes accepted learnings into the appropriate part of the skill system.

/reflect creates a feedback loop: each conversation can surface patterns, the synthesiser filters signal from noise, the human approves what is worth keeping, and skills update — so future agents behave better in exactly the situations where past agents struggled.

When /reflect triggers — and when it skips

/reflect is triggered when the user says reflect or /reflect. It is not triggered automatically at the end of every session. This is intentional: the skill skips trivial conversations and topics that were already handled correctly.

The most important filter is this: one-offs are not learnings. A single unusual incident does not warrant a skill edit. Patterns that recur across conversations, or gaps that would affect any future agent tackling the same kind of work, are the candidates worth filing.

It is tempting to treat every suboptimal moment in a conversation as a learning to encode. The skill explicitly rejects this. Filing a one-time quirk as a rule creates brittle, over-fitted skills that constrain agents in situations the rule was never designed for. Durable learnings generalise — one-offs do not.

The six-step loop

When /reflect runs, it executes six steps in sequence. Steps two and three involve parallel subagents; all other steps are performed by the parent agent or a single synthesiser agent.

Step 1 — Locate the transcript

Before any review can happen, the parent agent must find its own session transcript. It does this using a dedicated finder script rather than relying on the user to supply the transcript manually. This makes the process reliable and removes a friction point that might otherwise cause the reflect step to be skipped.

Step 2 — Three-lens parallel review

Three subagents run simultaneously, each examining the transcript through a distinct lens. Running them in parallel means the review takes no longer than the slowest single lens rather than the sum of all three.

Lens What it examines
Judgment Decision quality — where did the agent choose a suboptimal branch, misread context, or apply the wrong heuristic?
Tooling Tool usage patterns — which tool calls were inefficient, redundant, or called in the wrong order?
Divergent Alternative approaches — what entirely different strategy was never considered, and would it have been better?

Each lens produces its own set of candidate findings. Findings from all three feed forward to the synthesiser in step 3.

Step 3 — Synthesise: Accepted, Rejected, Backlog

A fourth agent consolidates the three sets of findings and sorts them into three categories. The synthesiser also spot-verifies citations — checking that each finding actually corresponds to something that occurred in the transcript rather than a hallucinated reference.

  • Accepted — a durable learning worth encoding as a skill edit. It generalises beyond this conversation and would improve future agent behaviour in similar situations.
  • Rejected — a finding that does not hold up under scrutiny: it is a one-off, it contradicts existing guidance, or the citation does not check out.
  • Backlog — worth preserving but not yet ready to become a skill edit. Either the pattern needs more evidence, or the finding belongs in the structural track (see step 4).

Step 4 — Structural check

Before any Accepted finding moves toward a skill edit, the skill asks a clarifying question: could this learning be enforced via a lint rule, a script, or a flag rather than natural-language guidance in a skill file?

If the answer is yes, the finding moves to Backlog rather than becoming a skill edit. This matters because a machine-enforceable rule is more reliable than prose guidance — it fires every time the condition is met, regardless of whether the agent remembered to read the relevant skill section. Skill prose is reserved for guidance that genuinely requires judgment.

Step 5 — Human approval (required, no exceptions)

The most critical guardrail in the entire reflect process: skill changes are never auto-applied. The user explicitly approves which changes to implement. The rationale is stated directly in the skill: skill changes affect every future agent in the organisation.

Once the user approves, routing depends on the scale of the change:

  • Small edits — the parent agent applies them directly to the relevant skill file.
  • Substantive changes — routed to plugin-dev:skill-development for a full draft, test, and iterate loop before the change lands.
  • New skills — always created via plugin-dev:skill-development, never written ad hoc by the parent agent.

Step 6 — Summary

After the approved changes are applied, /reflect produces a summary covering three things: what changed and where, what was filed to backlog and why, and what was dropped along with the reasons for rejection. This summary is the audit trail that makes the feedback loop legible over time.

Why this creates genuine continuous improvement

The loop is effective because each stage removes a different category of noise before anything reaches a skill file. The three-lens review surfaces what a single pass would miss. The synthesiser filters the lens outputs for signal. The structural check moves machine-enforceable rules out of natural-language skill prose. Human approval prevents any single conversation's edge cases from distorting org-wide behaviour. And the routing logic ensures that larger changes go through the same deliberate process as new skill development — not a shortcut.

The result is a system where the agent organisation can genuinely learn — not by accumulating undifferentiated instructions, but by improving in targeted, verified, human-approved increments.

Check your understanding

Why does /reflect require human approval before applying any skill changes?

Read a recent agent conversation transcript — or recall one from memory. Apply the three-lens review manually:

  1. Judgment lens — what decisions were suboptimal? Where did the agent choose the wrong branch or misread context?
  2. Tooling lens — what tool calls were inefficient, redundant, or called in the wrong sequence?
  3. Divergent lens — what alternative approach was never considered? Would it have been better?

From your findings, write one Accepted learning — a pattern that generalises and would improve future agents in similar situations. Then write one thing that belongs in Backlog instead, and explain why it is not ready to become a skill edit yet.

Paste your three lens findings and your Accepted learning into a new Claude conversation and ask: "Does this generalise beyond the single conversation I reviewed, or is it a one-off? If it is a one-off, what would need to be true for it to become a durable learning?"
