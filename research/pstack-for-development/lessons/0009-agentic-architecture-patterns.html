Agentic Architecture Patterns Mapped to pstack

🕑 ~20 min prompt chaining · orchestrator-workers · evaluator-optimizer · parallelization/voting · ACI · tool design principles
Primary source anthropic.com/engineering/building-effective-agents — Anthropic’s engineering guide to building effective agents: four architectural patterns, why coding agents work well, ACI principles for tool design, format guidance, and a framework caution.

Not all agentic work is shaped the same way. Some tasks decompose into a fixed sequence of predictable steps. Others fan out across an unpredictable surface area. Still others demand iterative refinement against a measurable quality bar. Using the wrong architecture for the shape of the problem is one of the most common reasons agents produce mediocre results even when the underlying model is capable.

Anthropic’s engineering team has identified four architectural patterns that cover most agentic work. Each maps directly to a pstack primitive. This lesson explains the patterns, maps them, and then examines the tool-design discipline — called the Agent-Computer Interface — that determines whether any architecture actually performs.

The Four Architectural Patterns

1. Prompt Chaining

Prompt chaining decomposes a task into a fixed sequence of steps, where each LLM call consumes the output of the previous one. It is the right choice when the subtasks are known in advance and trading higher latency for better accuracy on each step is worthwhile. The tradeoff is explicit: you give up speed in exchange for determinism and auditability at every stage of the chain.

In pstack terms, this maps directly to a Playbook — the bug-fix playbook, the feature playbook, and the other named workflows are each a prompt chain with a fixed set of obligatory steps.

2. Orchestrator-Workers

In this pattern a central LLM dynamically breaks down a task and delegates subtasks to worker LLMs. The orchestrator decides at runtime how many workers to spin up and what each one is responsible for. Anthropic recommends this when the scope of the problem cannot be predicted upfront — their canonical example is situations where “the number of files that need to be changed” is unknown before investigation begins.

In pstack this is /swarm: the coordinator analyses the task surface, slices it into independent units, and fans out to worker agents in parallel.

3. Evaluator-Optimizer

One LLM generates an artifact; a second LLM evaluates it and returns feedback; the first LLM revises. This loop continues until the evaluator is satisfied or a maximum iteration count is reached. It is effective when iterative refinement yields measurable quality gains — that is, when you have a clear rubric the evaluator can apply consistently.

In pstack this is /arena: a single artifact is repeatedly improved through a generate-evaluate-revise cycle.

4. Parallelization (Sectioning and Voting)

Parallelization covers two distinct shapes. Sectioning runs independent subtasks simultaneously to reduce wall-clock time. Voting runs the same task multiple times with the same or different models and uses agreement across outputs as a confidence signal — the result you trust is the one multiple independent runs converge on. Voting is particularly valuable when a single run could plausibly produce a subtly wrong answer that looks correct.

In pstack this is /swarm in its race shape: N candidates compete on the same task and the strongest result wins by agreement.

Why Coding Agents Work Especially Well

Coding tasks are a natural fit for agentic architectures for one structural reason: solutions are verifiable via automated tests. The agent can run the test suite after every change and use the results as direct feedback. This closes the loop that most other domains leave open. Output quality is objectively measurable, and the agent can iterate against that measurement without human intervention at each step.

This is why the Evaluator-Optimizer pattern works particularly well in coding contexts: the evaluator does not need to make a subjective judgment. It runs the tests and reads the results. The feedback signal is clear and consistent.

ACI — Agent-Computer Interface

Architecture determines the shape of the work. The quality of individual tool definitions determines whether agents can execute within that shape without making avoidable errors. Anthropic calls this discipline the Agent-Computer Interface — by analogy to the Human-Computer Interface, it is the layer where the agent and its computational environment meet.

The Anthropic team building a SWE-bench coding agent reported that they spent more time optimizing their tools than the overall prompt. That inversion of priorities is the central lesson of ACI: getting the tool layer right matters more than getting the system prompt right.

The Three ACI Principles

1. Write tool descriptions like a great docstring for a junior developer.

The model reads your tool descriptions the same way a junior developer reads documentation: if the description is vague, examples are absent, and edge cases are unaddressed, the model will misuse the tool in exactly the ways a junior developer would. Include example usage, the expected input format, and the edge cases the caller is responsible for handling. Treat every tool definition as documentation that will be read by someone with no other context.

2. Poka-yoke your arguments.

Poka-yoke is a manufacturing concept meaning “mistake-proof.” Applied to tool design, it means designing the argument surface so that mistakes are structurally harder to make. If a function could be called with ambiguous or invalid combinations of arguments, redesign the interface so those combinations are impossible or immediately obvious as errors. Do not rely on the model to choose correctly when the interface itself invites incorrect choices.

3. Require absolute filepaths.

When an agent changes its working directory during a task — which coding agents do routinely — relative filepaths silently resolve to different locations. The tool call succeeds; the file it touches is not the one you intended. Requiring absolute filepaths eliminates this class of error entirely. Test tools extensively with varied inputs, observe failure modes, and iterate on the definition until the common failure modes are gone.

The Anthropic team building a SWE-bench agent spent more time optimizing their tools than the overall prompt. ACI — the quality of tool definitions — is where most of the leverage in an agentic system lives, not in the system prompt.

Format and Framework Guidance

Output format choices affect how reliably a model can produce correct output. Anthropic offers three concrete guidelines:

  • Keep formats close to what models have seen in natural text. The further a format deviates from the training distribution, the more likely the model is to produce subtle errors.
  • Avoid formats that require accurate counting. Token and character counting is unreliable; if correctness depends on counting, redesign the format.
  • Prefer markdown over JSON for code. Code embedded in JSON requires escaping that adds error surface. Markdown is closer to what models have seen and produces fewer formatting mistakes.

On the question of frameworks: extra abstraction layers obscure prompts and responses, making it harder to observe what the model is actually receiving and producing. Anthropic recommends preferring direct API usage and reducing abstraction layers before moving to production. The cost of abstraction is debugging opacity; pay that cost consciously, not by default.

There is also a token-level consideration: give the model enough tokens to reason before committing to an output. Forcing a conclusion before reasoning is complete produces lower-quality outputs than allowing the model to work through the problem first.

Using an agentic framework does not make your system more reliable. Extra abstraction layers hide what prompts the model is actually seeing and what responses it is producing, which makes debugging significantly harder. Frameworks are a convenience for development; they are a liability for production observability. Prefer direct API usage and remove abstraction layers before shipping.

Three Core Principles

Anthropic distills their agent-building guidance into three principles that apply regardless of which architecture you choose:

  1. Simplicity. The simplest architecture that solves the problem is almost always the right one. Complexity has a compounding cost in debugging, observability, and failure diagnosis.
  2. Transparency. Show planning steps explicitly. An agent that reasons internally and then produces an output is harder to debug than one that externalises its reasoning at each step.
  3. Thorough ACI. Tool design is the primary leverage point. Invest disproportionately in descriptions, argument ergonomics, and testing with varied inputs before assuming the architecture is the bottleneck.

Quick check

According to Anthropic, why should agent tools require absolute filepaths?

Pick one tool you have built or used in an agent workflow — a file-editing tool, a shell-runner, a search function, anything. Apply all three ACI principles from the Anthropic article:

  1. Write the description as you would a great docstring for a junior developer — include example usage, edge cases, and input format requirements.
  2. Identify one argument that could be misused or passed ambiguously, and describe how you would poka-yoke it.
  3. If the tool accepts any path argument, confirm it requires an absolute filepath. If it does not, rewrite the argument contract so that it does.
Ask your AI tutor: “I have a tool that does X. Which of the three ACI principles would improve it most, and what would the improved description look like?” — then compare the tutor’s description against what you wrote in the exercise.
