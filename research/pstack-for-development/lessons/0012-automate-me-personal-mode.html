/automate-me — Building Your Personal Mode

Module 4 of 4 ~20 min Lesson 12 / 12
Primary sources flaviocopes.com/pstack  ·  github.com/michael-denyer/pstack-claude — docs/reference.md

pstack exposes two distinct tools for making the skill system smarter over time: /reflect, which mines your recent session for improvements to shared org skills, and /automate-me, which reads your transcripts and drafts a personal mode skill tailored to your specific recurring patterns. They improve different layers of the stack and are designed to be used at different moments.

This lesson covers both tools, the approval loop that keeps skill changes safe, the discipline of distinguishing a durable pattern from a one-off preference, and the full continuous improvement system that connects individual sessions to a better-behaved future org.

Skill changes affect every future agent in the org. A change that looks right in isolation can silently degrade unrelated workflows once it is live. This is why neither /reflect nor /automate-me apply changes automatically — every proposed change requires human approval before it reaches the shared skill set.

/automate-me

/automate-me reads your recent transcripts, identifies patterns that are specific to how you work, and drafts a personal mode skill based on those observations. The output is a candidate skill definition that you then review. You approve it, adjust it, or discard it — nothing is applied without that step.

The pstack-claude reference describes it as: "Draft a personal skill from recent transcripts." That framing is deliberate — it is a draft, not a deployment. The human review step is where you decide whether the pattern is genuinely reusable or merely a coincidence across a few sessions.

New skills that survive review are created through plugin-dev:skill-development, the dedicated skill authoring workflow. You do not bypass that process just because the origin was an automated transcript analysis.

/reflect — Improving Shared Org Skills

/reflect operates at a different scope. After a difficult or particularly instructive task, it proposes improvements to the shared skills that every agent in the org uses. Like /automate-me, it requires approval before any change is applied.

The reflect loop produces three categories of proposals:

  • Accepted — small edits that apply directly once approved.
  • Rejected — patterns that did not hold up under review.
  • Backlog — substantive changes that require the full plugin-dev:skill-development draft-test-iterate cycle before they are ready to ship.

Each conversation can seed the loop: reviewers surface patterns, a synthesizer filters signal from noise, a human approves the survivors, the relevant skills update, and every future agent in the org behaves accordingly.

/reflect does not auto-apply any change, even one that looks unambiguously correct. The rule is firm: skill changes affect every future agent in the org. A reflex to skip approval for "obviously safe" edits is precisely the mistake the approval gate is designed to prevent. One-offs are not learnings — a pattern that appeared in a single session may evaporate in the next, and encoding it as a shared skill would degrade all future sessions that do not match that one-time context.

Skill vs Preference — What Is Worth Encoding

The hardest judgement in personal skill authoring is separating a durable, reusable pattern from a one-off preference. The /reflect skill makes this explicit: "One-offs are not learnings." That principle applies equally to personal mode authoring.

A useful test before encoding a pattern:

  • Frequency: has this pattern appeared across multiple independent sessions, or only once?
  • Generality: would this pattern apply to the next ten tasks of this type, or only to a specific one-time context?
  • Stability: would you still want this behaviour six months from now, or is it shaped by a current project constraint that will change?

If a pattern fails any of these tests, note it but do not encode it. The skill set works because it is a curated signal. Noise in the skill set means every future agent starts from a noisier baseline.

What the Skill System Contains

To calibrate what belongs in a skill, it helps to understand the scope of what already exists. pstack (Lauren Tan's original) contains 23 workflow skills, 21 engineering principles, and 22 task playbooks. pstack-claude exposes 31 public slash commands across 54 skill directories.

That is a large, deliberate collection built up over time. A personal skill you author should complement the existing structure — it should encode something about how you work that the shared skills do not already cover.

When Personalisation Is Durable

A personal skill is durable when it encodes a constraint or preference that is genuinely stable across your work — not a reaction to one project, one deadline, or one difficult task. Examples of durable personal patterns include: a consistent ordering preference for how you want research summarised, a domain-specific terminology convention you enforce in every codebase you touch, or a verification habit you run at the end of every session regardless of context.

Examples that are not durable: a scratchpad location you used during one sprint, a verbosity level you wanted for one particular deliverable, or a workaround for a tool limitation that may be fixed in the next version.

Common Mistakes to Avoid

Mistake Why it fails
Listing skills instead of stating goals and constraints Agents work best from intent, not from a prescribed tool list — listing skills locks in a method rather than an outcome.
Vague finish conditions for autonomous runs An agent with no clear stopping criterion will continue past the intended scope or halt at the wrong point.
Parallel writers sharing one working directory Concurrent writes to the same path produce collisions that corrupt both outputs.
Accepting a green build as behavioural proof Tests passing confirms compilation and existing assertions — it does not confirm that the agent behaved as intended on new inputs.
Using Orchestrate for tasks one agent can finish in a session Orchestration adds coordination overhead; single-agent tasks run faster and with fewer failure modes when handled directly.

Authoring a Personal Skill via plugin-dev

When a pattern clears the durable/reusable bar and human review approves it, the creation path runs through plugin-dev:skill-development. That workflow follows the same draft-test-iterate loop used for all new skills: draft the SKILL.md, test it against real sessions, iterate on the trigger and behaviour definitions, then promote it.

A SKILL.md has three essential fields:

  • name — the slash command that invokes the skill.
  • trigger — the condition or phrase that activates it.
  • behaviour — what the agent does when triggered, expressed as a goal or constraint, not as a step list.

Check your understanding

What does /automate-me produce when you run it?

Think about your own recent agent usage. Identify three recurring patterns — things you find yourself asking for or adjusting repeatedly across sessions.

  1. For each pattern, decide: is this a durable, reusable pattern worth encoding, or a one-off preference that should be skipped?
  2. For the strongest candidate, draft the SKILL.md frontmatter:
    • name — the slash command
    • trigger — the condition or phrase that activates it
    • behaviour — what the agent does, expressed as a goal or constraint
Paste your three patterns and your SKILL.md draft into a new Claude chat and ask: "Apply the one-offs-are-not-learnings test to each pattern. For the one I drafted a SKILL.md for, is the trigger specific enough to fire reliably and is the behaviour expressed as a goal rather than a step list?"
