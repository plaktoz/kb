Arena — Multi-Model Competition

Module 3 of 4 ~25 min Lesson 6 / 12
Primary source github.com/michael-denyer/pstack-claude — plugins/pstack/skills/arena/SKILL.md

Arena is pstack's answer to a specific class of decision risk: the moment when a single attempt at a non-trivial artifact would lock in the wrong shape. Rather than hoping one model produces the best design, Arena spawns multiple independent candidates in parallel, scores them against a shared rubric, and synthesises the winner with the best ideas from the losers.

It is triggered by /arena, "arena this," or "throw it in the arena."

Pick the base candidate by extensibility, not by feel. A candidate that scores lower overall but has a cleaner extension seam is often the stronger foundation — the graft step will import the missing ideas from the other candidates anyway.

When to Use Arena

Arena is the right tool when one attempt at a non-trivial artifact would lock in the wrong shape. Typical cases include API contracts, data-model designs, architectural decision records, and any artifact where two developers with different instincts might reach meaningfully different — and both defensible — answers.

When to avoid it: if the work is purely generation-bound (writing a large body of text that is already well-specified), spawning the same model multiple times produces equivalent diversity at lower cost. Arena earns its overhead only when model family differences are likely to surface distinct structural approaches.

Arena is not a solution for an under-specified brief. If candidates produce wildly divergent outputs, that is a signal that Phase 1 (Frame) was not precise enough — the correct response is to reframe and re-run, not to average the outputs together. Averaging divergent proposals produces an incoherent hybrid that inherits the weaknesses of all candidates and the strengths of none.

The Six-Phase Competition Pattern

ARENA: 6-PHASE COMPETITION PATTERN
──────────────────────────────────────────────────────────────
  Frame: define artifact + 3-6 criterion rubric
      │
      ▼
  Fan Out: spawn N candidates simultaneously (opus/fable/sonnet)
  ┌──────┬──────┬──────┐
  │ C-1  │ C-2  │ C-3  │   (each: artifact + rationale)
  └──┬───┴──┬───┴──┬───┘
     │      │      │
     └──────┼──────┘
            ▼
  Cross-Judge: readonly judge (different model family)
  scores each candidate against rubric
            │
            ▼
  Pick: strongest base (by extensibility, not feel)
            │
            ▼
  Graft: walk losers → pick 1-2 ideas each → integrate
            │
            ▼
  Verify: test synthesized result
  ┌─────────┴────────────┐
  PASS                 FAIL
  Ship it           Re-frame or
                    fix missed graft
──────────────────────────────────────────────────────────────
  Convergence → ship. Divergence → reframe the brief.
──────────────────────────────────────────────────────────────

Phase 1 — Frame

Define exactly what artifact is being produced. Build a rubric of 3–6 criteria — these must be concrete enough that an independent judge can score against them without consulting the author. Assign runners (the competing models) and give each a separate output path so their work cannot cross-contaminate.

Phase 2 — Fan Out

Spawn all subagents simultaneously using run_in_background: true. Each candidate produces two things: the artifact itself and a rationale explaining the key design decisions. The default model pool is opus, fable, and sonnet.

Phase 3 — Cross-Judge

Spawn a separate, readonly judge model — from a different model family where possible — to score each candidate against the rubric. The judge sees the rubric and the artifacts but does not know which model produced which candidate. This removes the bias that comes from self-evaluation.

Phase 4 — Pick

Score criterion-by-criterion and compare your assessment against the cross-judge's scores. Select the base candidate on extensibility: which one is easiest to build on if you need to add or change one thing later? A candidate that scores lower overall but has a cleaner foundation is often the stronger choice.

Phase 5 — Graft

Walk each losing candidate and identify one or two ideas per candidate that are worth porting into the winner. Integrate them manually, not by paste — copy-pasting tends to carry implicit assumptions that do not fit the base candidate's structure. The synthesis note must name the base, every grafted idea, what was rejected and why, and the verification result.

Phase 6 — Verify

Test the synthesized result as you would any artifact. If it fails, the correct response is either to re-frame the Frame phase (if the rubric was missing a criterion) or to fix the graft that was missed. A passing Verify step ends the run; the artifact and synthesis note together constitute the output.

Reading the Convergence Signal

Signal Meaning Action
Convergence — candidates agree on shape The brief was well-specified; all reasonable approaches reach the same structure Ship — no grafting needed
Divergence — candidates wildly disagree Phase 1 (Frame) was under-specified; the problem was ambiguous Reframe the brief; do not average the outputs

Convergence is a quality signal, not a failure. When three models from different families all reach the same structural answer, you have strong evidence that the shape is correct. Skip grafting and ship.

Arena vs Swarm

Arena and Swarm are both multi-agent patterns but they solve different problems. Arena optimises for quality on a single artifact: the output is one thing, improved by competition. Swarm optimises for coverage across an aggregated report: the output is many parallel findings combined into one document.

Use Arena when the shape of a single artifact is uncertain. Use Swarm when you need to cover a large surface area that no single agent context can hold.

Check your understanding

When Arena candidates wildly diverge, what should you do?

Design an Arena run for a real pending decision in your codebase. Write out all four components below.

  1. Artifact definition — what exactly is being produced? Be specific enough that a model you have never talked to would know what to build.
  2. 4-criterion rubric — one criterion per line; each must be scoreable by an independent judge without additional context.
  3. Model assignment — which models would you use as runners, and which model (from a different family) would you assign as cross-judge?
  4. Verify step — what does passing verification look like for this specific artifact? Be precise enough that "tests are green" would not qualify.
Paste your exercise answer into a new Claude chat and ask: "Review my Arena design — is my rubric specific enough for a cross-judge to score without context, and does my Verify step go beyond 'tests pass'?"
