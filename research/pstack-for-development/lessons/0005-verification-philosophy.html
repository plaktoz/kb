Verification Philosophy — Prove It Works

Module 2 — Core Interface · Lesson 5 of 12 · ~15 min
Source github.com/michael-denyer/pstack-claude — poteto-mode SKILL.md
The "Prove It Works" principle is one of 21 enforced by poteto-mode.

Why "the build passed" is not enough

Every developer has shipped a change where the build was green, the tests passed, and lint reported nothing — and still broken behaviour reached production. The problem is not that CI lied. The problem is that CI was never asked the right question.

pstack enforces a simple rule: verification must match what changed. A passing build tells you the compiler is happy. It does not tell you that the new CLI flag behaves correctly, that the refactored UI flow still works end-to-end, or that the database value you wrote can actually be read back. Those questions require different evidence.

"The build passed" is a statement about compilation, not about correctness. Real verification runs or inspects the actual artifact that changed — not a proxy for it. 
PSTACK VERIFICATION HIERARCHY
──────────────────────────────────────────────────────────────────
  ❌ Insufficient proof:
     "The build passed"
     "Tests are green"
     "Lint is clean"

  ✓ Required proof (match what changed):
     CLI change      → run the real command
     UI change       → walk the changed flow
     Performance     → compare actual traces (before/after)
     Storage change  → read the value back from storage
     Behavior change → demonstrate against real artifact

  HOW TO WRITE A DONE CONDITION:
  ──────────────────────────────────────────────────────────────
  /poteto-mode <what you observed or want>
  Done means <something the agent can run or inspect>.
  Keep <existing behavior that must not change>.
  ──────────────────────────────────────────────────────────────

Insufficient proof: the three familiar lies

pstack explicitly rejects three phrases as sufficient evidence that a change is correct:

  • "The build passed" — proves compilation succeeded, nothing more.
  • "Tests are green" — proves the existing test suite did not regress, but says nothing about behaviour the tests do not cover.
  • "Lint is clean" — proves style conformance, not correctness.

None of these statements answers the question: does the changed thing actually do what it is supposed to do? That question requires running or inspecting the changed artifact directly.

It is tempting to treat a broad test suite as a verification substitute. Tests are valuable — but they verify what the test author anticipated. Change-type matching requires verifying what you just changed, which the existing suite was written before your change existed.

Required proof: match the verification to the change

The correct verification step depends on the kind of change made. Each change type has a natural form of evidence:

Change type Required verification
CLI change Run the real command and observe the output.
UI change Walk the changed flow from start to finish.
Performance change Compare actual traces before and after the change.
Storage change Read the value back from storage after writing it.
Behavior change Demonstrate the new behavior against the real artifact.

The pattern is consistent: go to the real place the change lives, and exercise it. Do not accept a report from a system that was not designed to observe your specific change.

Writing a done condition

pstack formalises verification through the done condition — a concrete, inspectable statement of what the agent must demonstrate before the task is considered complete. The format has three parts: 

/poteto-mode <what you observed or want>
Done means <something the agent can run or inspect>.
Keep <existing behavior that must not change>.

The Done means clause is where the verification philosophy becomes operational. It must name something the agent can actually run or inspect — not a feeling, not a build status, not a test summary. A well-written done condition rules out ambiguity before the work begins.

A concrete example

For an autonomous refactoring run that removes an old API, a correct done condition reads: 

Done means zero old callers, every parser fixture passes,
and the old API is deleted.

This is verifiable: the agent can grep for old callers, run the parser fixtures, and confirm the deleted file is absent. None of those checks reduce to "the build passed".

Autonomy, reversibility, and when to pause

pstack's verification philosophy connects directly to how autonomy is granted. The rule is:

  • Reversible work proceeds without asking — the agent acts and verifies against the done condition.
  • Irreversible or high-impact actions always pause: force-pushes to shared branches, deploys, data deletion, and customer messages.

Session overrides like "going to bed" or "run until done" extend autonomy for the session — but they do not remove the pause requirement for the destructive categories above. Verification is the agent's permission to proceed; a done condition that cannot be checked forces a pause.

Check your understanding

A teammate changes a CLI flag. What counts as required proof the change works?

Think of three past tasks where you (or an agent) accepted "tests are green" as sufficient proof. For each:

  1. Name the change type (CLI / UI / performance / storage / behavior).
  2. Write the correct verification step that would have caught a real regression.

Then pick one of the three tasks and write a complete /poteto-mode prompt for it, including a Done means clause and a Keep clause.

Paste your three verification steps and your /poteto-mode prompt into a new Claude conversation and ask: "Does my Done means clause name something you can actually run or inspect, or is it still a proxy?"
