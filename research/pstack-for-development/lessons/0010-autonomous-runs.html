Autonomous Runs — Overnight Execution

🕑 ~20 min autonomous-run playbook · done condition design · decision log · session overrides · rollback guards · when to pause vs proceed
Primary source github.com/michael-denyer/pstack-claude — poteto-mode SKILL.md — the canonical autonomy contract for /poteto-mode: what proceeds automatically, what always stops, and how session overrides like “going to bed” extend that contract for overnight runs.

Most agent tasks take minutes. Autonomous runs are different: you hand the agent a goal, set the conditions, and walk away for hours. That shift in time horizon demands a different kind of contract between you and the agent — one that is precise enough to let work proceed without interruption, but principled enough to stop before anything irreversible goes wrong.

/poteto-mode ships with exactly that contract. This lesson dissects it: the autonomy rules that govern each action, the pause triggers that override everything else, the session overrides that extend autonomy, and the done condition structure that tells the agent unambiguously when to stop.

The autonomous run contract is not a trust setting — it is a decision protocol. The agent does not ask whether it can proceed; it evaluates whether the action is reversible and whether it hits a known pause trigger. Everything else runs automatically. The protocol replaces constant check-ins with one upfront, well-formed prompt.

The Autonomy Rules

poteto-mode applies a simple two-part test to every action it considers:

  1. Is the action reversible? Reversible work — edits, commits, branch creation, refactoring inside a fresh worktree — proceeds automatically. External actions that can also be reversed proceed the same way. No confirmation needed.
  2. Does it hit a pause trigger? Four categories always stop the agent regardless of any session override: force-pushes to shared branches, deploys, data deletion, and customer messages. These are not configurable. They are hard stops.

Outside those four categories, the agent does not ask. It decides, acts, logs the decision, and moves on.

A common misconception is that “full autonomy” means the agent never stops. It does not. Session overrides like “going to bed” or “run until done” extend autonomy for reversible work, but the four pause triggers — force-push, deploy, data deletion, customer message — remain hard stops even under the most permissive session override. Autonomy is selective, not total.

Session Overrides

By default, poteto-mode may surface clarifying questions mid-task. Session overrides suppress that behaviour for the duration of the run. Two canonical phrases extend autonomy:

  • “I am going to bed.” — signals that no human is available to answer questions; the agent must make all reversible decisions independently.
  • “Run until done.” — removes the pause checkpoints for reversible steps; the agent runs the full task without surfacing intermediate status requests.

These overrides appear directly in the prompt, not as configuration flags. They are part of the autonomous run contract you author, not a system setting you toggle.

Alongside the override, you pair /loop until done — which keeps re-invoking the task until the done condition is satisfied, or until the agent reaches a genuine dead end and stops to explain it.

Done Condition Design

A done condition is what replaces you as the judge of completion. For an autonomous run it must be something the agent can run or inspect without asking — not a qualitative judgment, not a human review step.

The canonical format is:

/poteto-mode <what you observed or want>
Done means <something the agent can run or inspect>.
Keep <existing behaviour that must not change>.

Each clause does specific work:

  • /poteto-mode <goal> — states the observable starting condition or the end-state you want, plainly.
  • Done means — a verifiable criterion the agent can evaluate autonomously. It must be runnable or inspectable: a test suite output, a grep result, a file count, a lint pass. Not “the code looks clean.”
  • Keep — invariants the agent is explicitly forbidden from breaking. These act as a rollback guard: if the keep clause is violated, the change is not done.

The Decision Log

When working autonomously, the agent makes choices you were not present for. The decision log is how you review those choices after the fact.

You request it in the prompt: “Keep a decision log.” The agent then commits a record of each non-trivial choice alongside the code changes it made — what it decided, what alternatives it considered, and why it chose as it did.

This is not a courtesy — it is the review mechanism. Because the owner reviews every subagent diff independently, the decision log is what makes that review meaningful rather than purely reactive.

Rollback Guards

A rollback guard is a specific, inspectable condition you embed in the Keep clause or as an explicit instruction that, if violated, tells the agent (and you) that the run went wrong and the changes should be reverted.

Rollback guards work because autonomous runs operate in a fresh worktree. All work is reversible until it is pushed to a shared branch — which is a pause trigger and therefore never happens automatically. The worktree isolation means the worst outcome of a bad autonomous run is a branch you delete, not a corrupted main.

A useful rollback guard names a concrete invariant you can check: an integration test suite, a particular fixture, an API contract. If the guard fails, the done condition cannot be met, and the agent stops and explains rather than force-completing.

Candor Over Agreement

One principle governs what the agent does when it genuinely cannot proceed: “No is an acceptable answer.” This is explicitly part of the poteto-mode contract. The agent is expected to stop and explain a real dead end rather than push through with a degraded or incorrect solution just to report completion.

This matters especially for autonomous runs because you are not present to catch a wrong-direction decision early. An agent that candidly reports a dead end saves you from a large, broken diff to unpick. An agent optimising for apparent completion hands you that diff silently.

Anatomy of a Complete Autonomous Run Prompt

The following is the canonical example from the poteto-mode skill: 

/poteto-mode I am going to bed. Migrate every caller to the new parser in a fresh worktree.
Done means zero old callers, every parser fixture passes, and the old API is deleted.
Keep a decision log. Do not ask before committing.
/loop until done. If you reach a real dead end, stop and explain it.

Breaking it down line by line:

  • Line 1 — session override (“going to bed”) plus the goal stated as a migration scope. “Fresh worktree” is the rollback guarantee.
  • Line 2 — three-part done condition: zero old callers (grep verifiable), fixture suite pass (runnable), old API deleted (file check). All inspectable without human judgment.
  • Line 3 — decision log requested; confirmation for commits explicitly waived.
  • Line 4 — loop instruction with explicit dead-end handling: the agent may stop, but only to explain, not to silently stall.

What Is Not in pstack

The poteto-mode skill ships with pstack-claude. Some tools referenced in broader pstack documentation — /deslop, control-cli, and control-ui — come from a separate package (cursor-team-kit) and are not included in pstack-claude. Advanced shipping playbooks also assume GitHub and Graphite as the delivery stack; teams without those tools will need to adapt those playbooks.

Quick check

Which action will always pause a poteto-mode autonomous run, even when “going to bed” is set?

Skill exercise — write a complete autonomous run prompt. Pick a real refactoring task you could hand to an agent tonight. Write a full autonomous run prompt that includes all five parts below. Then, in the final line, identify which specific action in your task would trigger a pause even under full autonomy.

  1. Goal — the scope of the refactoring, stated as an observable starting condition or desired end-state.
  2. Done means clause — a verifiable condition the agent can run or inspect without asking you. Name the exact artifact or command.
  3. Keep clause — at least one invariant the agent must not break. This is your rollback guard.
  4. Decision log instruction — explicitly request the log so you can review choices made while you were away.
  5. Pause trigger identification — state which single action in this task would cause a hard stop even with a full session override active.

Once written, check: can the agent verify your “Done means” clause without asking you? If it requires your judgment, rewrite it as something runnable or file-inspectable. That gap is the most common mistake in first-draft autonomous run prompts.

Ask your AI tutor: “For the refactoring task I described, is my Done means clause something you could evaluate without asking me — and does my rollback guard cover the most likely failure mode?”
