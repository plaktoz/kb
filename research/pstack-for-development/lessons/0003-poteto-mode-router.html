poteto-mode — The Central Router

Module 2 · Lesson 3 of 12 · ~20 min
Primary source github.com/michael-denyer/pstack-claude — poteto-mode/SKILL.md
poteto-mode is not a task executor. It is a dispatcher. Every incoming task is evaluated against a routing table of signals, then handed off to the playbook or sub-skill that owns that type of work. The quality of that routing decision determines the quality of the entire run.

What poteto-mode does

poteto-mode is the central router for pstack. When a task arrives, poteto-mode reads it, identifies the dominant signal, and dispatches to the matching playbook or sub-skill. It does not try to do the work itself. Its job is to make the right routing decision and then get out of the way.

The routing table has two layers. The first layer maps signals to specific sub-skills that activate immediately when a pattern is detected. The second layer maps task types to the playbook that owns that class of work. A single incoming task may trigger a signal match first; if no signal fires, the task type determines the playbook.

Signal routing: eight fast dispatches

Signal routing fires before task-type routing. These eight patterns short-circuit the classification process when a distinctive marker is present.

Signal Destination Why it fires first
Nontrivial change or architecture /how skill High-risk changes need a plan before any code moves
Empirical question (behavior, timing) Prototype playbook Uncertainty about runtime behavior requires measurement, not reasoning
Code crossing function boundaries /architect skill Cross-boundary changes need structural coordination
Parallel fan-out needed /swarm skill Fan-out work should not be serialized
Contested design choice /interrogate skill Unresolved trade-offs need structured challenge before commitment
Any prose surface /unslop skill All written output benefits from the unslop pass
PR status request Babysit playbook PR monitoring is a distinct workflow with its own polling loop
Landing a green stack Shipping playbook Merging and deploying a passing build is a discrete procedure

Task-type routing: eight playbooks

When no signal fires, poteto-mode classifies the task by type and selects the matching playbook. Each playbook contains the full procedure for that class of work, including which model to use by default.

Task type Playbook Model default
Read-only question investigation.md --
Reported defect bug-fix.md fable
Measured slowness perf-issue.md fable
New behavior feature.md opus
Structure refactor refactoring.md opus
Throwaway sketch prototype.md --
Long autonomous task autonomous-run.md --
Multi-day program orchestrate.md --

Feature work and refactoring default to opus because they require the most judgment. Bug fixes and performance issues default to fable, which handles targeted, high-precision changes. The hardest individual changes also go to fable.

Autonomy rules

poteto-mode enforces a clear autonomy boundary. Reversible work and external read actions proceed without asking. Four categories always require a pause:

  • Force-pushes to shared branches
  • Deploys
  • Data deletion
  • Customer messages

This boundary can be extended during a session. When a developer says "going to bed" or "run until done," poteto-mode treats that as an explicit grant to proceed through the full run without interruption.

Enforced principles

poteto-mode enforces 21 operating principles. Six are essential to understand before using the system:

Laziness Protocol

Bias toward deletion and the smallest viable change. More code is a liability. The right answer is usually less.

Prove It Works

Verify real artifacts, not proxies. A passing test is not the same as observed behavior in the running system.

Guard the Context Window

Route bulk work to subagents. The main context window is a scarce resource. Long file reads, multi-file operations, and sweeping searches belong in subagent calls, not the primary thread.

Never Block on the Human

Proceed on reversible work and present results. Do not stop to ask questions that the work itself will answer.

Attack the Premise

When repeated fixes fail, challenge the shared assumption. The bug may not be where everyone believes it is.

Foundational Thinking

Define types and structures before writing logic. Code built on unclear data models accumulates the wrong complexity.

Subagent configuration

When poteto-mode delegates to subagents, it passes subagent_type: "pstack:poteto-agent". Subagents run in background by default. Context is passed as file pointers, not inlined content. This keeps the main context window clean and preserves its capacity for the work that actually requires reasoning.

Reply rules

poteto-mode's outputs follow four rules that apply to every response:

  • Short declarative sentences
  • No long-dash characters
  • Frame impact for the end user and the next maintainer before discussing implementation details
  • Every claim carries evidence or an explicit label: measured, inferred, or guess
poteto-mode is not a catch-all for anything unclear. If you hand it an underspecified task, it will still route it somewhere based on the closest signal match. Vague tasks produce routing decisions that may be technically correct but practically wrong. Sharpen the task description before invoking poteto-mode, not after.
