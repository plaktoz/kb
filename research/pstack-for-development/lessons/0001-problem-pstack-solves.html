The Problem pstack Solves

🕑 ~15 min context amnesia · green build fallacy · agent-as-engineer framing · done conditions
Primary source flaviocopes.com/pstack/ — pstack exists because agents “keep forgetting” guidance on investigation, design, testing, and communication; the fix is structured, durable skill files.

You ask an AI agent to fix a bug. It makes changes, runs the tests, reports back: “All tests are passing.” You merge the pull request. Three hours later a colleague tells you a core feature is broken. The tests were green — but the change was wrong.

This is not a one-off. It is the default mode of AI-assisted development, and it has a name: the green build fallacy. pstack is the structured skill system built to break that pattern.

Context Amnesia — the Root Problem

Every time you start a new agent session — or cross a context window boundary in a long one — the agent loses the accumulated guidance you gave it. How to investigate unfamiliar code. How to design cleanly. How to test thoroughly. How to communicate findings. That knowledge evaporates.

Agents keep forgetting this guidance. And without it they fall back on surface heuristics: make the diff small, make the tests pass, report done. The result is a stream of plausible-looking, low-quality outputs — each individually defensible, none collectively trustworthy.

pstack solves this with durable skill files — structured SKILL.md definitions that load guidance into the agent at the moment a task begins, so the agent never has to remember what it was told last session. pstack is a Cursor plugin for rigorous AI agent work created by Lauren Tan (@poteto), and it works in Claude Code, Codex, and other coding agents via these SKILL.md files.

The core problem pstack solves is not a capability gap — it is a memory gap. Agents are capable of rigorous investigation, careful design, and real verification. They just keep forgetting to do it. Durable skill files make forgetting structurally impossible.

The Green Build Fallacy

The green build fallacy is the mistake of accepting “tests are green” as sufficient proof that a change works. It is the most common failure mode in AI-assisted development because it is the natural stopping point for an agent optimising for task completion.

A green build tells you that the code compiles and that the assertions in your test suite pass. It says nothing about whether the change is complete, whether it preserves existing behaviour, or whether the tests themselves are adequate evidence for the goal you had in mind.

pstack's answer is the done condition: an explicit, agent-runnable statement of what “finished” looks like that you write before work begins. Done conditions force you to name the real evidence you want — and force the agent to produce it.

Green tests do not equal a working change. An agent can make all existing tests pass by deleting behaviour those tests don't cover, stubbing dependencies, or leaving the root cause untouched. pstack demands evidence the agent can actually run or inspect — not just a test summary.

Agent-as-Engineer Framing

pstack's philosophy is “less code, higher quality, and verification.” That phrase captures a deliberate shift: the agent is not a fast typist executing your instructions — it is an engineer accountable for producing finished, verified work.

This reframing changes what you ask for. Instead of “add a retry mechanism to the fetch call,” you write a goal with an explicit done condition and a list of behaviours that must survive the change. The agent is then responsible for the full engineering loop: investigation, design, implementation, and verification.

pstack ships 23 workflow skills, 21 engineering principles, 22 task playbooks, and 2 specialised subagents — all oriented around this framing. The primary entry point, /poteto-mode, acts as a router: it reads your goal, selects the right playbook, creates a task list, delegates to appropriate models, and demands evidence before reporting success.

Done Conditions

A done condition is the core primitive that makes the agent-as-engineer framing operational. The format is: 

/poteto-mode <goal> / Done means <something agent can run or inspect> / Keep <existing behaviour that must not change>

Each part has a specific role:

  • goal — what you want the agent to accomplish, stated plainly.
  • Done means — a concrete, inspectable or runnable criterion the agent must satisfy before declaring success. Not “tests pass” — something with real evidence value.
  • Keep — existing behaviour the agent is explicitly forbidden from breaking. A guard against silent regressions.

Investing thirty seconds in a done condition before starting a task eliminates the most common failure mode: an agent that reports success because it has no way to measure failure.

Quick check

What does the green build fallacy describe?

Part 1 — the bad prompt. Write a vague, instruction-style task prompt you might currently give an AI agent. Keep it to one or two sentences. Do not include a done condition or a guard on existing behaviour.

Part 2 — the pstack rewrite. Rewrite that same task using the /poteto-mode structure: /poteto-mode <goal> / Done means <something runnable> / Keep <existing behaviour>.

Compare the two. The first leaves the agent to decide what “done” means. The second gives it a runnable criterion and a guard — that is the structural shift pstack is built around.

Ask your AI tutor: “What is one done condition I could write for a feature I am working on right now?” — then check whether it names something the agent can actually run or inspect.
