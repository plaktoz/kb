Investigation Primitives — /how and /why

Module 2 — Core Interface · Lesson 4 of 12 · ~15 min
Primary Source github.com/michael-denyer/pstack-claude — plugins/pstack/skills/how/SKILL.md

Every non-trivial codebase investigation starts with one of two questions: how does this work? or why was it built this way? pstack treats these as fundamentally different queries that warrant different strategies. /how is the skill for mechanical understanding — code walkthroughs, subsystem explanations, and ownership queries such as "where should this live?" /why is the skill for historical reasoning — searching Git history, tickets, documentation, and team chat to surface the original intent behind a decision.

This lesson focuses on /how: how it classifies question complexity, what it does differently for simple versus complex questions, how it structures its output, and when to hand off to /why instead.

For complex questions, /how does not hand your question to a single agent. It first decomposes the question into 2–4 distinct angles, then launches parallel read-only explorer subagents — one per angle — before a synthesis agent consolidates their findings into a single structured output. Simple questions skip all of this and go straight to a single-pass explanation.

Complexity Classification

Before any exploration begins, /how classifies the question into one of two tiers. The classification is intentionally conservative: when in doubt, take the simple path.

Tier Trigger Approach
Simple Single module or narrow question One read-only subagent handles both exploration and explanation in a single pass
Complex Multi-file subsystem or cross-cutting feature Decompose into 2–4 angles → parallel read-only subagents (model: opus) → synthesis agent (model: opus)

Simple path

One read-only subagent handles both exploration and explanation in a single pass. This is the default: efficient and sufficient for any question that fits within a single module or a well-bounded narrow scope. The output already arrives structured into the standard sections — it is not a raw dump of notes.

Complex path

The question is first decomposed into 2–4 distinct angles (for example: data flow, state management, public interface, error handling). Each angle becomes the brief for a separate read-only explorer subagent, all running simultaneously using the opus model. When all explorers complete, a dedicated synthesis subagent — also running on opus — consolidates their findings into a single coherent explanation.

Output is delivered with light edits only. Substantial rewrites of the explorers' findings are explicitly prohibited. The synthesis agent's job is integration and coherence, not reinterpretation.

The result is an explanation fit for a senior engineer building a mental model, not line-by-line annotation of every function.

Output Sections

Regardless of which path is taken, /how structures its response into up to five named sections. Sections that do not apply to the specific question are dropped rather than left empty.

Section Answers
Overview What is this? A one-paragraph orientation for someone new to the subsystem.
Key Concepts What are the important abstractions, terms, or invariants you need to hold in mind?
How It Works Walkthrough of the mechanics — data flow, control flow, state changes.
Where Things Live Which files, directories, or modules own which responsibilities? (Also answers ownership queries: "where should this live?")
Gotchas Non-obvious behaviours, edge cases, or common mistakes for this subsystem.

Knowing the section structure helps you write better prompts. If your real question is an ownership query — "where should this new feature live?" — you can direct /how to focus on Where Things Live. If you want to understand a subtle bug, target Gotchas.

/how vs /why vs /teach

The three commands address distinct question types and draw on entirely different evidence bases.

Command Question type Evidence sources
/how "How does X work?" / "Where should this live?" Current codebase — files, modules, call graphs
/why "Why was this built this way?" / "What problem does this solve?" Git history, tickets, documentation, team chat
/teach "Help me deeply understand X" Both: mechanics from /how combined with history from /why

Motivation questions — "why was this built?" — are explicitly redirected by /how to /why. This is intentional: the current codebase contains what was built, not the reasoning behind the choices that shaped it.

/how cannot explain historical intent. If you ask "why does this use Redis instead of Postgres?", /how will redirect you to /why. The codebase reflects the outcome of past decisions — not the trade-offs, constraints, or alternatives that were weighed at the time. Use /why when your real question is about motivation; use /teach when you want both mechanics and history in a single run.

Check Your Understanding

On the complex path, which model does /how assign to the parallel explorer subagents?

Pick a subsystem you actively work on. In the text area below, write two prompts:

  1. A /how prompt for that subsystem (e.g. "how does the retry pipeline handle dead letters?").
  2. A /why prompt for a design decision within it (e.g. "why does the retry system use exponential backoff?").

For each prompt, predict which complexity path /how would take and explain your reasoning. Then identify which output section (Overview / Key Concepts / How It Works / Where Things Live / Gotchas) would most directly answer your actual question.

Ask Claude: "I wrote a /how prompt for [your subsystem]. Can you predict whether it will take the simple or complex path, and which output section I should read first for my actual question?"
