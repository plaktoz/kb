What Is PayloadCMS?

~12 min Module 1 — Foundations
Primary Source
payloadcms.com/docs/getting-started/what-is-payload

Official introduction to what Payload is — a TypeScript-first, code-first CMS/backend that auto-generates APIs and admin UI from a single config file.

What Is a Headless CMS?

A traditional CMS — think WordPress or Drupal — bundles two concerns together: a backend that stores and manages content, and a front-end presentation layer that decides how that content looks in a browser. These two halves are tightly coupled. Changing the front end often means touching the back end, and vice versa.

A headless CMS separates those concerns. The backend handles content storage and exposes it through APIs (typically REST or GraphQL). Any front end — a Next.js website, a React Native app, a digital signage board — consumes those APIs however it likes. The CMS is "headless" because it has no opinion about the display layer: the head (the front end) has been removed.

This separation gives development teams flexibility. You can redesign your website without touching your content model. You can publish the same content to a website and a mobile app simultaneously. You can swap out your front end framework years from now without migrating your content database.

What Does "Code-First" Mean?

Most GUI-based CMS tools let you define content types through a web interface: click "Add Field", type a label, choose a field type, save. This is intuitive for non-developers, but it has a hidden cost — your schema lives in a database, not in your codebase. It is hard to version-control, hard to review in a pull request, and hard to reproduce across environments.

Code-first inverts this. In Payload, you define your entire schema in a single TypeScript file: payload.config.ts. This file lives in your repository, gets committed to version control, and serves as the single source of truth for your data model. Every field, every collection, every access rule is declared as code.

The payoff is significant. Schema changes go through normal code review. You can spin up a new environment and have the exact same content structure instantly. Your IDE provides autocomplete and type-checking across your schema definitions. And because the config is just TypeScript, you can apply programming constructs — loops, conditionals, shared constants — to eliminate repetition.

Payload's Architecture: Five Layers

Everything in Payload flows from one source: payload.config.ts. Define your schema there and Payload auto-generates the APIs, the admin panel, and the authentication system. There is no separate setup for each layer — they derive directly from your config.

Layer What It Does How It Is Created
Schema Defines collections (like database tables), globals (singleton records), and individual fields with types and validation rules. You write it in payload.config.ts — this is the only layer you author directly.
APIs REST endpoints, a GraphQL schema, and a Local Node.js API are all available for querying and mutating your data. Auto-generated from your schema. Add a new collection and all three APIs immediately reflect it.
Admin UI A fully functional, React-based admin panel with list views, detail forms, and rich-text editing. Auto-generated from your schema. Field types determine which UI components render in the panel.
Auth Built-in authentication — login, sessions, password reset — plus access control at the document level and down to individual fields. Configured in your collection definitions. No third-party auth library required for basic use.
Storage File upload handling with automatic image resizing, format conversion, and focal-point cropping for responsive images. Enabled by adding an upload collection to your config and specifying image size presets.

Primary Use Cases

Payload positions itself not just as a CMS but as a general-purpose backend framework. The four primary categories it targets are:

  • Headless CMS: Power a marketing site or blog. Authors manage content through the Admin UI; your Next.js front end fetches it via the REST or GraphQL API.
  • Enterprise App Builder: Model complex business data — users, orders, workflows — using collections and globals, then build custom admin views on top.
  • E-Commerce backends: Define products, variants, inventory, and orders in code. The Local API lets your Next.js server actions query Payload directly without an HTTP round-trip.
  • Digital Asset Management (DAM): Centralise images, videos, and documents with upload collections, metadata fields, and access-controlled delivery.

Notable enterprise features include SSO integration, AI auto-embedding for semantic search, publishing workflows with draft/preview support, visual editing, and A/B testing capabilities.

Self-Hosting and Database Support

Payload runs inside your Next.js project as a first-class dependency — it is not a separate service you call over the network. This means you deploy one application, not two. Your Next.js server actions can call the Payload Local API directly in-process, with zero HTTP overhead and full TypeScript type safety.

Payload supports three databases out of the box: MongoDB, PostgreSQL, and SQLite. You pick the adapter that suits your infrastructure and the same payload.config.ts schema works with all three. Because there is no Payload cloud service you must use, you retain complete ownership of your data. Deploy on a VPS, a container platform, or any Node.js-compatible cloud provider.

Core insight: You define your schema exactly once in payload.config.ts, and Payload derives three APIs (REST, GraphQL, Local), a full admin panel, and an auth system from that single file. There is no separate wiring step for each layer — the config is the entire contract.
Common misconception: Payload is not a hosted SaaS product or a WordPress plugin — it is a TypeScript library that lives inside your codebase. You own the schema, the data, and the deployment. This also means there is no "install and click" setup: you need a Node.js environment and at least basic TypeScript familiarity to get started.
