Hooks — Server-side Lifecycle Logic

~14 min Module 2 — Core Building Blocks
Primary Source
payloadcms.com/docs/hooks/overview

Official overview of the Payload hooks system — covering hook types, execution model, context, and best practices for running server-side logic at lifecycle points.

What Are Hooks and Why Do They Matter?

When Payload receives a request — say, a create or update operation on a collection document — it does not simply write data to the database and return. It runs through an ordered lifecycle: validation, access checks, field processing, persistence, and response. Hooks are named insertion points along that lifecycle where you can attach your own async functions.

A hook function receives a context object describing the operation in progress and can do anything: mutate the incoming data before it is saved, call a third-party API after a save completes, send an email when a document is published, queue a background job, or block the operation entirely with an error. Because hooks run entirely on the server, they never appear in the client bundle — sensitive credentials, database calls, and business logic all stay server-side.

This is the mechanism Payload provides instead of model callbacks or event emitters. If you want to stamp an audit field, synchronise data to another service, or enforce a business rule that goes beyond simple field validation, hooks are the place to do it.

The Four Hook Types

Payload organises hooks by scope. Each scope corresponds to a different level of your config:

Type Defined in Typical use
Root Hooks The top-level payload.config.ts Application-wide error handling, global request instrumentation
Collection Hooks A collection's hooks key beforeChange, afterChange, beforeRead, afterRead, beforeDelete, afterDelete on that collection's documents
Global Hooks A global's hooks key Same lifecycle events as Collection Hooks but for singleton global documents
Field Hooks An individual field's hooks key Transforming or validating a single field's value in isolation

Collection Hooks are the most common starting point. You attach an array of functions under the hook name — beforeChange, afterChange, beforeRead, afterRead — and Payload calls them in array order at the matching lifecycle moment.

Execution Model: Async vs. Fire-and-Forget

Every hook function can be async. Whether Payload waits for it depends on whether the function returns something:

  • Returns a Promise (async function with a return value): Payload awaits the Promise before moving to the next step. This is the right choice when the rest of the operation depends on what your hook does — for example, when you are stamping a field that must exist on the saved document.
  • Returns nothing: Payload does not wait. The hook fires, the request continues immediately. This is useful for side effects that do not affect the saved data — logging to an analytics service, triggering a webhook, sending an email — where delaying the response would hurt the user experience.

The practical rule: if the hook modifies data and must have that modification reflected in the persisted document, return data. If the hook is purely a side effect, return nothing and let it run in the background.

Hook Context

Each hook receives a context object (req.context or the context argument, depending on hook type) that persists across all hooks within a single request. You can write arbitrary keys onto this object to pass information between hooks or to signal that a step has already run.

The most important use of context is breaking infinite loops. An afterChange hook that calls payload.update() inside itself will trigger another afterChange, which triggers another update, forever. Setting a flag on context and checking it at the top of the hook stops the cycle: 

afterChange: [
  async ({ doc, req, context }) => {
    if (context.alreadyProcessed) return doc
    context.alreadyProcessed = true
    // Safely call payload.update() or do other work here
    return doc
  },
],

Best Practices

Practice Why
Avoid expensive logic in beforeRead / afterRead These hooks run on every read request — list views, detail views, API calls. A slow operation here multiplies across every page load.
Prefer beforeChange / afterChange for heavy work These run only on create and update operations, so expensive calls (external API, image processing) fire far less often.
Use Hook Context to prevent infinite loops Any hook that triggers another Payload operation on the same collection risks recursion. A context flag stops the cycle on the second pass.
Offload long-running tasks to the jobs queue The jobs queue frees up the request to continue processing without waiting. A hook can enqueue a task and return immediately.

Blocking Operations with APIError

Sometimes a hook should stop the operation entirely — for example, if a rate limit has been exceeded, if a required external service is unavailable, or if a business rule is violated that field-level validation cannot express. Throwing an APIError inside a hook causes Payload to abort the operation and return the error as an HTTP response with the status code you supply: 

import { APIError } from 'payload'

beforeChange: [
  async ({ data, req }) => {
    const allowed = await checkRateLimit(req.user.id)
    if (!allowed) {
      throw new APIError('Rate limit exceeded. Try again later.', 429)
    }
    return data
  },
],

The first argument is the human-readable message; the second is the HTTP status code. Use standard codes: 400 for bad input, 403 for access denied, 429 for rate limiting, 500 for unexpected server errors.

Core insight: Whether Payload waits for your hook is determined entirely by whether the hook returns a value. Return data (or doc) and Payload awaits the Promise before continuing — your mutation lands in the saved document. Return nothing and the hook runs as a fire-and-forget side effect, never blocking the response.
Two gotchas to avoid: First, any hook that calls payload.update() on the same collection it belongs to will trigger itself again — always guard with a context flag (if (context.alreadyProcessed) return) to break the loop. Second, beforeRead and afterRead fire on every single read, including list views with dozens of documents. Putting a database query or HTTP call inside them will visibly slow every page in the admin panel.

Skill Exercise

Write a beforeChange hook for a posts collection that automatically sets a publishedAt field to the current ISO timestamp when status changes from draft to published. The hook should only stamp the date on the first transition — if the document is already published, it should leave publishedAt untouched.

Start from this skeleton and complete it:

// collections/Posts.ts
export const Posts = {
  slug: 'posts',
  hooks: {
    beforeChange: [
      async ({ data, originalDoc }) => {
        // Your logic here



        return data
      },
    ],
  },
  fields: [
    { name: 'status', type: 'select', options: ['draft', 'published'] },
    { name: 'publishedAt', type: 'date' },
    // ... other fields
  ],
}
