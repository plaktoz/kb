Collections — Modeling Repeatable Content

~15 min Module 2 — Core Building Blocks
Primary Source
https://payloadcms.com/docs/configuration/collections

What Are Collections?

A collection is a group of documents that share a common schema. Think of it as a database table paired with a configuration object that tells Payload how to handle every aspect of those documents: their data shape, who can access them, how they version, and how they appear in the admin panel.

Payload automatically generates three APIs from every collection you define — a Local API for server-side Node.js calls, a REST API over HTTP, and a GraphQL API. You write the config once and all three surfaces appear automatically, with no additional wiring required.

Collections are ideal for content that repeats across many instances: blog posts, products, users, orders, uploaded media, or comments. If you only ever need a single document — a site-wide navigation menu, global app settings — reach for a Global instead. (Globals are covered in Lesson 6.)

Required Properties

Every collection must include exactly two required properties:

  • slug — a unique, URL-friendly string identifier. Payload uses the slug to construct API routes (/api/products), derive database table names, and reference the collection inside hooks and relationship fields. Keep it lowercase and kebab-case.
  • fields — an array of field definitions describing the document's data structure. Each field maps to a database column (SQL adapters) or a document property (MongoDB). Without fields, your collection stores no meaningful data.

Everything beyond slug and fields is optional — you layer in capability as your use case demands it.

Configuration Options

The table below covers the most commonly used top-level options beyond the two required properties:

Option Purpose
access Controls who can create, read, update, and delete documents. Accepts functions that return a boolean or a Payload query constraint object.
hooks Lifecycle event handlers that run server-side at defined points — beforeChange, afterRead, beforeDelete, and others.
auth Enables user authentication for this collection, auto-generating login, logout, token refresh, and password-reset endpoints.
versions Turns on document versioning. Set to { drafts: true } to add a publish workflow where documents start as unpublished drafts.
upload Configures file upload support, adding MIME type handling, image resizing, and a storage adapter to the collection.
timestamps Automatically adds createdAt and updatedAt fields to every document. Set to false to disable both.
orderable Enables drag-and-drop document reordering in the admin List View via fractional indexing — useful for manually curated content sequences.

Admin Panel Options

The admin key inside a CollectionConfig controls how Payload presents the collection in the admin panel. None of these options affect the generated APIs — they are purely presentation-layer settings.

  • useAsTitle — the name of the field whose value Payload uses as the document's human-readable label in the List View, breadcrumbs, and relationship pickers. Without it, documents are identified only by their auto-generated ID.
  • defaultColumns — an array of field names that appear as columns in the List View by default. Users can change their personal column configuration, but this sets the initial state everyone sees.
  • listSearchableFields — the fields the admin search input queries when a user types in the List View. The Payload docs stress that you should index each of these fields in your database for acceptable query performance.
  • pagination — configures the default page size and the page-size options available in the List View footer.
  • enableListViewSelectAPI — a performance optimization that fetches only the currently visible columns rather than full documents. Pair it with forceSelect to guarantee critical fields are always included in that reduced query.

Example: A Posts Collection

Here is a complete, minimal posts collection demonstrating the required properties and several optional ones working together: 

// collections/Posts.ts
import type { CollectionConfig } from 'payload'

export const Posts: CollectionConfig = {
  slug: 'posts',
  admin: {
    useAsTitle: 'title',
    defaultColumns: ['title', 'status', 'updatedAt'],
  },
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'content', type: 'richText' },
    {
      name: 'status',
      type: 'select',
      options: ['draft', 'published'],
      defaultValue: 'draft',
    },
  ],
  versions: { drafts: true },
}

Notice the TypeScript import: CollectionConfig from 'payload' gives you full editor autocomplete and catches misspelled option names at compile time. Typing your collection configs is a best practice that pays dividends immediately when your config file grows.

Best Practices

  1. One file per collection. Keep each collection in its own file — e.g. collections/Posts.ts — and import it into your main payload.config.ts. This keeps the config file short and makes individual collections easy to locate and reason about in isolation.
  2. Index every field in listSearchableFields. Payload will not warn you when a search field lacks an index. The search box will simply grow progressively slower as documents accumulate. Add the database index immediately after wiring up searchable fields.
  3. Single-document content belongs in a Global. If a collection will always have exactly one document, stop and use a Global instead. Collections carry overhead — list views, pagination, bulk operations — that is pure waste for singleton content.
  4. Use forceSelect with enableListViewSelectAPI. The select optimization reduces data fetched per row, but it can silently omit fields your custom components depend on. List those fields in forceSelect so they are always included in the partial query.
  5. Override the Edit View with admin.components.edit.*. When the default edit form does not fit your editorial workflow, swap in a custom React component at the field level, section level, or full-page level using Payload's component override system.
Key Insight

A single CollectionConfig object is all Payload needs to generate a full CRUD API across three transports (Local, REST, GraphQL) and a fully functional admin UI. Every option you add — access control, versioning, search, uploads — enriches all three surfaces simultaneously. Write the config once; everything else is derived.

Common Mistake

Placing useAsTitle at the top level of the config instead of inside the admin object. Payload will silently ignore it, and every document in the list will show its raw ID instead of a readable title. Always nest admin panel options under the admin key.

Skill Exercise

Write a complete CollectionConfig object for a products collection. Requirements:

  • At least 4 fields: name (text, required), price (number), description (textarea or richText), and status (select with options active and archived)
  • useAsTitle set to the name field
  • Draft versioning enabled via versions: { drafts: true }
After writing your config, verify three things: (1) both slug and fields exist at the top level; (2) useAsTitle is nested inside the admin object, not at the top level; and (3) your versioning value is { drafts: true } — an object — rather than the bare boolean true, which enables versioning without the draft workflow.
