Component Overrides — Replacing Admin UI Pieces

~14 min Module 3 — Admin UI Customization
Primary Source
https://payloadcms.com/docs/admin/components

Why Payload Uses Path Strings Instead of Imports

Every other configuration system you have worked with likely accepts direct imports — you write import MyButton from './components/MyButton' at the top of the file and pass the variable. Payload deliberately does not work that way for admin components.

Instead, you register components as path strings inside admin.components. Payload reads those strings at startup and resolves the file and export itself. The reason is architectural: your Payload config runs on the server, and directly importing a React component there would pull client-side code into the server bundle. Path strings keep the two bundles cleanly separate — Payload can decide when and where to load each component without you worrying about the bundler boundary.

Key Insight

You never import custom admin components into payload.config.ts. You register them as path strings. This is the single most unusual thing about Payload's customisation API, and understanding it is what makes everything else fall into place. Payload's build tooling reads those strings and wires the components into the admin bundle for you.

Component Path Syntax

A component path is a string that tells Payload where to find the file and which export to use. Three forms are supported:

Pattern Example When to use
Default export '/src/components/MyButton' The file uses export default
Named export (hash) '/src/components/MyButton#MyButton' The file uses a named export; append #ExportName
Object form { path: '/src/components/MyButton', exportName: 'MyButton' } Same as hash syntax but type-safe and readable in long configs

The hash shorthand (#ExportName) is the most compact and most commonly seen in documentation examples. The object form with explicit path and exportName properties is preferable when you are also passing clientProps or serverProps, since you need the object form to attach those additional keys.

Gotcha

Component paths must be absolute from your project root, not relative to the config file. Write '/src/components/MyButton', not './components/MyButton'. A relative path will silently fail to resolve at build time, and you will see either a missing component or an unhelpful bundler error rather than a clear message about the path format.

The Four Categories of Overridable Components

Payload divides overridable components into four scopes. Understanding the scope tells you where in the config the override lives.

1. Root Components

Root components are top-level elements of the admin panel that exist independently of any collection or global — the navigation bar, the logout button, the dashboard, the global header and footer, and the before/after slots that wrap the main content area. They are configured directly under admin.components in the root Payload config. 

// payload.config.ts
admin: {
  components: {
    logout: {
      Button: '/src/components/MyLogoutButton#MyLogoutButton',
    },
    Nav: '/src/components/MyNav',
  },
}

2. Collection Components

Collection components are scoped to a specific collection. Override slots include the list view, the edit view, the save button, and various before/after injection points around the form. They live inside the collection definition's own admin.components key. 

// collections/Posts.ts
{
  slug: 'posts',
  admin: {
    components: {
      edit: {
        SaveButton: '/src/components/CustomSaveButton#CustomSaveButton',
      },
    },
  },
}

3. Global Components

Global components work the same way as collection components but apply to a global document rather than a collection. The same slot names are available and the config key is also admin.components, this time inside the global definition.

4. Field Components

Field components override how individual fields render in the admin UI — their label, their input element, their description, or the entire field block. These are covered in depth in the next lesson; the override syntax follows the same path string pattern.

Server Components, Client Components, and Auto-Props

Because Payload's admin panel is built on Next.js App Router, your custom components can be either server components or client components. Payload supports both.

Server Components (default)

Any component without a 'use client' directive is treated as a server component. It renders on the server, can use async data fetching, and is never sent to the browser as JavaScript. Server components receive two props automatically:

  • payload — the fully-initialised Payload instance, giving you access to the Local API, collections, globals, and config directly inside the component.
  • i18n — the internationalisation object, so your component can surface translated strings that match the admin panel's current locale setting.

Client Components

Add 'use client' as the first line of the file and the component becomes a client component. It runs in the browser, can use React hooks like useState, useEffect, and Next.js's useRouter. Client components still receive payload and i18n automatically, but the payload object in client context is a limited client-safe version — it does not give you access to the full server API. 

// src/components/MyLogoutButton.tsx
'use client'
import { useRouter } from 'next/navigation'

export function MyLogoutButton() {
  const router = useRouter()
  return (
    <button onClick={() => {
      // perform logout logic
      router.push('/login')
    }}>
      Sign out
    </button>
  )
}

Passing Custom Props with clientProps and serverProps

Sometimes your component needs data from outside itself — a label string, a feature flag, an API endpoint. Rather than hardcoding that data into the component file, you can pass it from the config using the clientProps and serverProps keys on the component object.

Property Purpose Constraint
clientProps Props forwarded to a Client Component Must be JSON-serialisable (strings, numbers, plain objects — no functions)
serverProps Props forwarded to a Server Component Can include non-serialisable values since they never cross the network

To use either, switch to the object form of the component path so you have a place to attach the extra keys: 

admin: {
  components: {
    logout: {
      Button: {
        path: '/src/components/MyLogoutButton',
        exportName: 'MyLogoutButton',
        clientProps: {
          redirectPath: '/login',
          label: 'Sign out',
        },
      },
    },
  },
}

Inside the component, those values arrive as regular React props alongside the automatically-injected payload and i18n.
