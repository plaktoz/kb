Custom Field Components

~15 min Module 3 — Admin UI Customization
Primary Source
payloadcms.com/docs/admin/components

Official documentation for component overrides in the Payload admin panel — covers field-level slots, the useField hook, and client component requirements.

What Are Field Component Overrides?

Every field Payload renders in the admin panel has a default UI — a text input, a toggle, a date picker, and so on. These defaults are chosen based on the field's type. But sometimes the default control is not expressive enough for your use case. A color value stored as a hex string should ideally show a colour swatch, not a plain text box. A rating stored as an integer should probably render as stars, not a bare number spinner.

Payload's field component overrides let you replace any part of that default UI without changing the underlying data model. You declare a path to a React component in your field's admin.components object, and Payload swaps in your component wherever that field appears. Your data type, validation, and API shape stay exactly the same — only the visual presentation changes.

This is a clean separation of concerns: the schema owns the data contract, the component owns the render. You can iterate on the UI independently of the rest of the collection definition.

The Override Slots Available

The admin.components object on a field definition accepts overrides for eight distinct slots. Most customisations touch only one or two of them:

Slot What It Controls Typical Use
Field The entire input UI in the document edit form Replace a text box with a colour picker, star rating, or rich selector
Cell How the field value appears in list view table cells Render a coloured badge instead of raw hex text
Filter The filter control when searching/filtering the list view Provide a dropdown of known values rather than a free-text input
Label The label rendered above the input in the edit form Add a tooltip icon or custom layout alongside the field name
Error The validation error message displayed below the input Style errors to match your brand or add contextual help links
Diff How the field's changes look in the version history diff view Render colour values as swatches side-by-side instead of hex strings
beforeInput UI inserted immediately before the existing input element Prefix label, unit badge, or helper text without replacing the input
afterInput UI inserted immediately after the existing input element Live preview, character counter, or copy-to-clipboard button

The most common override by far is Field — it replaces the entire input UI. The others let you make surgical changes around the existing input rather than rebuilding it from scratch.

Registering a Custom Field Component

To attach a custom component to a field, add it to admin.components in the field definition. The value is a string path pointing to the component file and its named export, separated by a #: 

{
  name: 'color',
  type: 'text',
  admin: {
    components: {
      Field: '/src/components/ColorPicker#ColorPicker',
    },
  },
}

The path before # is the module path (relative to your project root). The part after # is the named export. Payload resolves this at build time and passes the component into the admin bundle. You do not need to import anything in your collection config — the string reference is enough.

You can override multiple slots in the same field by adding more keys to admin.components. For example, providing both Field and Cell means your custom UI appears both in the edit form and in the list view.

How the useField Hook Works

When Payload renders your custom Field component, it does not pass the current value as a plain prop. Instead, it expects you to reach into Payload's internal form state yourself using the useField hook from @payloadcms/ui.

useField accepts an options object with a path property. The path is the field's name — or a dot-separated path for nested fields. It returns two things: value (the current stored value) and setValue (a function to write a new value back into the form). 

import { useField } from '@payloadcms/ui'

const { value, setValue } = useField<string>({ path })

When you call setValue, Payload marks the form as dirty and stages the new value for submission — exactly as if the user had typed into the default input. Your component never deals with form submission, validation, or save logic directly. useField is the single bridge between your custom React UI and everything Payload manages internally.

The path prop itself is automatically passed to your component by Payload. You declare it in your component's props and forward it straight to useField — no manual wiring required.

Core insight: useField is the bridge between your custom UI and Payload's form state. You supply { path } (the field name), get back value and setValue, and your component stays completely decoupled from form submission and validation logic.

Full Example: The ColorPicker Component

The ColorPicker is the canonical example in Payload's documentation because it shows the complete pattern in about ten lines. Here is the field definition followed by the component:

Field definition in your collection:

{
  name: 'color',
  type: 'text',
  admin: {
    components: {
      Field: '/src/components/ColorPicker#ColorPicker',
    },
  },
}

Component file at src/components/ColorPicker.tsx:

'use client'
import { useField } from '@payloadcms/ui'

export function ColorPicker({ path }: { path: string }) {
  const { value, setValue } = useField<string>({ path })
  return (
    <input
      type="color"
      value={value || '#000000'}
      onChange={e => setValue(e.target.value)}
    />
  )
}

Walk through the pattern step by step. The component receives path as a prop — Payload injects this automatically. It passes path to useField, which returns the current stored hex value and a setValue callback. The native <input type="color"> element renders the browser's colour picker and calls setValue whenever the user picks a colour. The fallback '#000000' handles the case where the field has not been set yet.

Notice what is absent: no useState, no useEffect, no form submit handler. Payload's form state management handles all of that. The component's only job is translating between the browser's colour picker event and useField's setValue.

The beforeInput and afterInput Pattern

Replacing the entire Field slot gives you maximum control but also maximum responsibility — you must replicate any behaviour from the default input that you still want. Sometimes a lighter touch is preferable.

beforeInput and afterInput let you inject custom UI immediately before or after the existing input element without replacing it. The original input keeps working exactly as before; your component simply adds content around it. 

{
  name: 'slug',
  type: 'text',
  admin: {
    components: {
      afterInput: '/src/components/SlugPreview#SlugPreview',
    },
  },
}

A slug preview component using afterInput could read the current value via useField and display a live URL preview below the text box — without touching the input itself. The same approach works for character counters, unit labels, helper links, or copy buttons.

As a rule of thumb: use Field when the default input control is fundamentally wrong for your data (a colour, a star rating, a map pin). Use beforeInput or afterInput when the default input is fine but you want to add supporting context around it.

Required: Custom field components that use React state, event handlers, or the useField hook must be Client Components. Add 'use client' as the very first line of the file. Omitting it causes a server-rendering error because hooks are not available in React Server Components.
