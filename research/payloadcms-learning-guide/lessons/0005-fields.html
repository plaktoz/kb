Fields — Building Your Content Schema

~16 min Module 2 — Core Building Blocks
Primary Source
https://payloadcms.com/docs/fields/overview

What Is a Field?

Fields are the atomic building blocks of any Payload schema. Every collection and global has a fields array, and that array governs what data can be stored, how it is validated, how it appears in the Admin Panel, and who can read or write it.

Payload provides 20+ field types organized into three distinct categories: data fields, presentational fields, and virtual fields. Understanding which category a field belongs to tells you immediately whether it writes to the database, and how to use it.

Key Insight

Every field that stores data requires a name property — that name becomes the database column and the key in your JSON response. Presentational fields have no name and write nothing to the database; they exist only to organize the Admin UI. Getting this distinction right early prevents a lot of confusion about why some field changes appear in your data and others do not.

Data Fields

Data fields are the most common type. They read from and write to the database. Each one requires a name property that identifies the column, and Payload maps the field type to an appropriate database column through its adapter layer (SQLite, Postgres, or MongoDB).

Field Type Purpose
textSimple string input
textareaMulti-line string input
numberNumeric values
emailValidates proper email format
checkboxBoolean true/false
dateDate picker that saves a timestamp
selectDropdown/picklist selector
radioSingle-choice radio button group
richTextExtensible rich text editor (Lexical by default in Payload 2)
codeCode editor that saves a string
jsonJSON editor interface for arbitrary JSON blobs
arrayRepeating content with nested fields — each row is a sub-document
blocksBlock-based content where each block type defines its own nested schema
group (named)Nests fields inside a keyed object in the database
tabs (named)Tabbed layout where each named tab creates a key in the stored document
relationshipLinks to documents in one or more other collections
uploadReferences a locally uploaded file or image from an upload collection
pointGeographic coordinates stored as a GeoJSON point

Here are three data field definitions showing common configurations:

// Inside a CollectionConfig.fields array

{
  name: 'title',
  type: 'text',
  required: true,
},
{
  name: 'publishedAt',
  type: 'date',
  admin: {
    date: {
      pickerAppearance: 'dayAndTime',
    },
  },
},
{
  name: 'category',
  type: 'select',
  options: [
    { label: 'Tutorial', value: 'tutorial' },
    { label: 'News',     value: 'news' },
    { label: 'Opinion',  value: 'opinion' },
  ],
},

Notice that each field has a name and a type. The name maps directly to the column name in your database and the key in the API response. Field-specific options like options for select or pickerAppearance for date live inside the field definition or inside its admin sub-object.

Nested data: array, group, and blocks

Three data field types let you nest other fields within them. The key differences are:

  • array — a list of repeating rows, each with the same shape (e.g., a list of team members with name and role)
  • group (named) — a single object nested under a key (e.g., seo containing metaTitle and metaDescription)
  • blocks — like array but each row can pick from a set of different block types, each with its own schema (e.g., a page builder with text, image, and CTA blocks)
// array: repeating rows with the same shape
{
  name: 'tags',
  type: 'array',
  fields: [
    {
      name: 'label',
      type: 'text',
    },
  ],
},

// group: a single nested object under a key
{
  name: 'seo',
  type: 'group',
  fields: [
    { name: 'metaTitle',       type: 'text' },
    { name: 'metaDescription', type: 'textarea' },
  ],
},

Presentational Fields

Presentational fields do not write to the database. They exist purely to organize the Admin Panel layout — arranging fields side by side, collapsing infrequently-used sections, or injecting fully custom components into any part of the edit form.

Field Type Purpose
rowArranges its child fields horizontally side by side in the Admin Panel
collapsibleWraps child fields in a collapsible accordion component
tabs (unnamed)Tabbed layout where tabs have no name key — nothing extra is stored in the database
group (unnamed)Groups fields visually without adding any key to the stored document
uiBlank slate for fully custom React components with no built-in input

A row wrapping two text fields looks like this:

{
  type: 'row',
  fields: [
    {
      name: 'firstName',
      type: 'text',
    },
    {
      name: 'lastName',
      type: 'text',
    },
  ],
},

The row itself has no name — it is invisible to the database and to the API. Only firstName and lastName are stored and returned. The row is purely a layout instruction for the Admin Panel.

The ui field type is the most flexible: you register a custom React component path in admin.components.Field and Payload renders it inside the form with no database backing at all. This is useful for custom dashboards, inline documentation, or interactive tools embedded in the edit view.

Virtual Fields

Virtual fields are computed or derived at runtime and never persisted to the database on their own. Payload supports three forms of virtual fields, each with a different mechanism for populating the value.

Variant How it works
join field type Enables two-way data binding between collections — the joined side is queried and attached to the document at read time, not stored inside the document itself
virtual: true Marks any data field as virtual; the value must be supplied by a hook (e.g., an afterRead hook that computes a full name from separate firstName and lastName fields)
virtual: 'dot.path' Auto-resolves data from a related field path — for example, virtual: 'author.name' automatically reads the name from the linked author record when the document is fetched 
// Virtual field populated by an afterRead hook
{
  name: 'fullName',
  type: 'text',
  virtual: true,
  // Value set in an afterRead hook:
  // ({ doc }) => { doc.fullName = `${doc.firstName} ${doc.lastName}` }
},

// Virtual field auto-resolved from a linked relationship
{
  name: 'authorName',
  type: 'text',
  virtual: 'author.name', // reads .name from the linked Authors record
},

// Join field: shows all Posts linked to this Author record
{
  name: 'posts',
  type: 'join',
  collection: 'posts',
  on: 'author', // the relationship field in the posts collection
},

Virtual fields are especially useful when you want to expose computed or aggregated data through the API without storing redundant values in the database. Because they are not stored, they also cannot be queried directly in the database — you cannot filter by a virtual field value.

Key Universal Field Options

These options are available on most data fields regardless of type. Understanding them unlocks the majority of customization you will need day to day.

Option Description
defaultValue A static value or a function receiving { user, locale, req }. Sets the field's initial value when a new document is created in the Admin Panel or via the API.
validate Custom validation function. Must return true on success or an error string on failure. Runs on both the server and in the Admin Panel before save.
hooks Field-level lifecycle callbacks — beforeChange, afterRead, etc. — scoped to this single field rather than the entire document.
access Field-level permission control. Overrides collection-level access for this field alone. Useful for hiding sensitive fields from non-admin users.
admin.condition A function (data, siblingData) => boolean. Conditionally shows or hides the field in the Admin Panel based on the values of other fields. The field still exists in the schema; it is only hidden in the UI.
admin.components Swap in custom React components for specific rendering slots: Field (the input itself), Cell (list view column), Filter, Label, Error, Diff, beforeInput, and afterInput.

Here is a field that uses validate and admin.condition together to make a date field conditionally required:

{
  name: 'scheduledAt',
  type: 'date',
  admin: {
    // Only show this field when the status field equals 'scheduled'
    condition: (data, siblingData) => siblingData.status === 'scheduled',
  },
  validate: (value, { data }) => {
    if (data.status === 'scheduled' && !value) {
      return 'A scheduled date is required when status is "scheduled".'
    }
    return true
  },
},

Note that admin.condition controls only the visibility of the field in the Admin Panel — it does not make the field conditionally required by itself. You pair it with validate to enforce the business rule server-side.

Custom components via admin.components

The admin.components option lets you replace any rendering slot of a field with your own React component, registered by file path (not by import). For example, to use a custom color picker instead of the default text input for a color field: 

{
  name: 'color',
  type: 'text',
  admin: {
    components: {
      Field: '/src/components/ColorPicker#ColorPickerField',
    },
  },
},

The path syntax is 'file/path#ExportName'. Server Components are the default; add 'use client' at the top of your component file for interactive inputs that need browser APIs or React state.

Reserved Field Names

Payload reserves a handful of field names for its own internal use. Defining a custom field with any of these names will conflict with Payload's internals and cause data corruption or runtime errors.

Warning — Forbidden Field Names

Never use these as your own field name values: __v, salt, hash, file.

Additionally, status is reserved when you are using Postgres with drafts enabled — Payload uses it internally to track draft state. Using any reserved name will either silently overwrite Payload's internal data or produce runtime errors that are difficult to trace back to a naming collision.

Skill Exercise — ~8 min

Write the fields array for a posts collection that models a full blog post. It must include all six of these properties using the correct field type for each:

  • title — a short string
  • author — a link to a record in the authors collection
  • tags — a repeating list where each item has a string label
  • heroImage — a reference to an upload in the media collection
  • publishedAt — a date and time picker
  • body — a rich text editor

Write TypeScript/JavaScript object syntax. Use the correct type value for every field — refer to the data fields table above if needed.

Ask your tutor: "Why does Payload split fields into three separate categories — data, presentational, and virtual — instead of using a single flat list with flags?" The answer reveals how the adapter pattern cleanly separates UI concerns from persistence concerns, and why that makes swapping databases possible without changing your field definitions.
