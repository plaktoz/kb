Globals — Singletons and App-wide Settings

~10 min Module 2 — Core Building Blocks
Primary Source
payloadcms.com/docs/configuration/globals

Official documentation for Globals — how to define them, how they differ from Collections, and when to reach for each one.

What Is a Global?

A Global in Payload is similar to a Collection in that it has its own schema of typed fields, its own access control rules, and its own automatically generated APIs — Local, REST, and GraphQL. The critical difference is that a Global corresponds to exactly one document. No list view, no pagination, no "create another." Just a single record in the database.

The canonical use cases are app-wide singletons: a header navigation structure, a site-wide banner alert, localized string tables, or a global settings object that controls feature flags. These are things where your application always needs exactly one version, and there is no meaningful concept of "multiple instances."

Because Globals are defined in payload.config.ts just like Collections, they benefit from all the same code-first advantages: version control, TypeScript autocomplete, environment parity, and no surprises between staging and production.

Defining a Global with GlobalConfig

You define a Global by creating an object that satisfies Payload's GlobalConfig type, then registering it in your config under the globals array. The shape is intentionally similar to a Collection — a slug and a fields array — with the key difference that there is no timestamps toggle for auto-generating multiple documents.

Below is the canonical example from the docs: a site navigation Global that stores an array of link objects, each with a label and a URL. 

import type { GlobalConfig } from 'payload'

export const SiteNav: GlobalConfig = {
  slug: 'site-nav',
  fields: [
    {
      name: 'links',
      type: 'array',
      fields: [
        { name: 'label', type: 'text', required: true },
        { name: 'url',   type: 'text', required: true },
      ],
    },
  ],
}

Once registered in payload.config.ts under globals: [SiteNav], Payload auto-generates the Admin UI panel for editing it, plus the REST endpoint GET /api/globals/site-nav and equivalent GraphQL and Local API access.

Globals vs. Collections — Side by Side

The distinction often trips up newcomers because the configuration syntax looks almost identical. The meaningful difference is purely about cardinality: how many documents will this config produce?

Globals Collections
Document count Exactly one document Zero to unlimited documents
Best for App-wide singletons Repeatable content types
Admin UI Single edit form, no list view List view + per-document edit form
API shape GET/POST /api/globals/slug GET /api/slug, GET /api/slug/:id
Versioning Supported Supported
Hooks Supported Supported
Access Control Unique per Global Unique per Collection
Examples Nav, banners, site settings Blog posts, users, products

Versioning Globals

One underappreciated feature is that Globals support Payload's full versioning system — including drafts and publishing workflows — just like Collections do. This is especially useful for things like a site-wide promotional banner that you want to schedule, preview, and then publish at a specific time without pushing code.

Enable versioning on a Global by adding a versions key to your GlobalConfig object, exactly as you would on a Collection. The version history for the Global's single document becomes navigable in the Admin UI.

Core rule: Use a Global when your app needs exactly one instance of something; use a Collection when you need multiple documents of the same type. The Payload docs state it plainly — "if you have more than one Global that share the same structure, consider using a Collection instead."
Common mistake: Developers sometimes create a Global for every piece of editable text — "homepage hero," "about page header," "contact page intro." This leads to a proliferation of single-field Globals. If the content follows a consistent structure across multiple pages, it almost always belongs in a Collection (e.g., a pages collection) where each page is its own document. Globals are for truly app-wide, genuinely one-of-a-kind data.
