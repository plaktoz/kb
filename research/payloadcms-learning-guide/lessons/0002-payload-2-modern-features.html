Payload 2.0 — What Changed and Why It Matters

~10 min Module 1 — Foundations
Primary Source
https://payloadcms.com/blog/payload-2-0

A Ground-Up Architectural Rethink

Payload 2.0 is not a feature drop — it is a deliberate redesign of how the framework's internal layers connect. The Payload team identified three areas where tight coupling was creating problems: the database driver, the admin panel bundler, and the rich-text editor. Swapping any one of them previously meant patching internals. Version 2.0 solves this by introducing a formal abstraction boundary called the adapter pattern.

The result is a framework that keeps its stable, code-first API on the surface while letting the layers underneath evolve independently. For developers, this means fewer breaking upgrades and real choices about tooling.

Key Insight

The adapter pattern is the structural reason that everything else in Payload 2.0 is possible. Postgres support, Vite bundling, and the Lexical editor each exist as adapters — pluggable modules that satisfy a shared interface. Adding a new database or editor in the future requires writing a new adapter, not forking the framework.

Postgres Support via Drizzle ORM

For the first time, Payload supports a fully relational database. Install the @payloadcms/db-postgres package and pass it as the db adapter in your config — MongoDB remains the default, so existing projects are unaffected.

Under the hood, the Postgres adapter uses Drizzle ORM. This has concrete consequences for how your schema looks at the database level:

  • Arrays create real tables. In MongoDB, an array field lives inside a document as a JSON array. In Postgres, Payload generates a proper join table, which means you can query individual array items efficiently.
  • Relationships maintain ordering. The adapter tracks position so that ordered relationship fields round-trip correctly.
  • Direct Drizzle access. You can reach the raw Drizzle client at payload.db.drizzle for custom queries without leaving the Payload request context.
Caveat

Postgres support shipped as beta in Payload 2.0. The schema generation and migration tooling were still stabilising at launch. If you were adopting Payload for a production project at the time of the 2.0 release, MongoDB remained the safer, battle-tested default.

The Lexical Rich Text Editor

Payload 1.x used Slate.js for its rich text fields. Slate served well for basic editing but had limitations in extensibility. Payload 2.0 replaces it with Lexical, Meta's open-source editor framework.

What the switch delivers to content editors:

  • A "/" command menu — type a slash to insert headings, lists, embeds, or custom blocks.
  • A popup toolbar — appears on text selection for inline formatting without hunting for a fixed toolbar.
  • Drag-and-drop reordering of blocks and elements within the editor canvas.
  • Inline block embedding — you can place any collection block you have already defined directly inside rich text content, closing the gap between structured data and prose.

For developers, Lexical exposes a node-based plugin architecture. Because it ships as a Payload adapter, you can also swap it out entirely if you need a different editing experience in a specific field.

Database Migrations and Transaction Support

Payload 2.0 introduces first-class TypeScript migration support through seven new CLI commands. The most commonly used are:

Command What it does
payload migrate:create Generates a new TypeScript migration file from schema changes
payload migrate Runs all pending migrations against the connected database
payload migrate:down Rolls back the most recently applied migration

A push mode is available for local development: instead of writing a migration file, Payload synchronises the database schema directly from your current config. This keeps development fast — you iterate on collections without managing migration files until you are ready to commit a schema change.

On the transaction side, Payload now wraps database operations in transactions automatically where appropriate. If you need to participate in a transaction from a custom hook, the identifier is available at req.transactionID, letting you coordinate multiple writes as a single atomic unit.

Other Notable Features in 2.0

Live Preview

Editors can preview content changes in real time directly inside the Payload admin UI, without publishing or switching to a separate browser tab. The preview iframe updates as fields are edited, shortening the feedback loop between writing and seeing the rendered result.

Vite Bundler Support

Webpack remains available as the default admin bundler. Vite is now a supported alternative. Switching to Vite is a single adapter change in your config and typically delivers faster hot-module replacement during admin customisation work.

Image Cropping and Focal Point Selection

Upload management now ships with built-in cropping tools and focal point controls enabled by default. Content editors can set a focal point directly in the admin panel, which downstream image-processing utilities can read to crop consistently across different aspect ratios.

Draft Query Performance

The draft querying system was fully refactored. In Payload 1.x, querying collections with many draft versions could become slow. The 2.0 rewrite delivers consistent performance regardless of how many draft documents exist in a collection.

Monorepo and Cross-Database Testing

Payload's own codebase migrated to a PNPM monorepo structure. Integration tests now run against both MongoDB and Postgres on every commit, which means database-specific bugs surface before they reach users rather than after.
