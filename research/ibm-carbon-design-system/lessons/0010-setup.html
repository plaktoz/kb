Setting Up Carbon in a React Project

~15 min Module 4 — Building with Carbon · Lesson 10 of 12
Source
Carbon Design System — Official Tutorial: "Getting Started with @carbon/react" (carbondesignsystem.com)
Key result: Going from a blank Next.js project to a working Carbon application requires three package installs, two file changes (rename globals.css to globals.scss and add @use '@carbon/react'), and a single import statement — the entire setup is five commands and two edits.

Prerequisites and what you will need

Before you install Carbon, you need a React project to install it into. The official Carbon tutorial is written against Next.js, so that is what this lesson uses. You should be comfortable creating a Next.js app with create-next-app, navigating its directory structure, and editing files. You do not need prior Carbon experience — that is what this module is for — but familiarity with JSX and basic npm or yarn package management is assumed.

On your machine you will need Node.js (18 or later is a safe choice for modern Next.js), and either npm or yarn as your package manager. The official Carbon tutorial uses yarn, so the commands below follow that convention. If you prefer npm, simply substitute npm install for yarn add in each command — the package names are identical.

The three packages you are about to install serve distinct roles. @carbon/react is the main component library — it contains every Carbon component (buttons, modals, data tables, notifications, and so on) compiled for React. sass is the Dart Sass compiler, which Carbon requires to compile its stylesheets; this is not optional. @carbon/icons-react is the icon library, separate from the main component package so you only pay the bundle cost when you actually use icons.

Installing the packages

Start by scaffolding a fresh Next.js project. The create-next-app scaffolder will ask you several questions about TypeScript, ESLint, and the App Router — answer according to your preferences. If you are following along with the official Carbon tutorial, accepting the defaults works fine.

# Create a Next.js project (if starting fresh)
npx create-next-app@latest my-carbon-app

Once scaffolding completes, move into the new directory and install the three Carbon packages. The versions pinned below are the ones used in the official Carbon tutorial (@carbon/react@1.33.0, sass@1.63.6) — installing these exact versions avoids any surprise breaking changes if you are following the tutorial step by step. In a real project you would ordinarily install the latest stable versions.

# Install Carbon component library
yarn add @carbon/react

# Install Dart Sass (required for Carbon styles)
yarn add sass

# Install Carbon icon library
yarn add @carbon/icons-react

After these three commands your package.json will list all three packages as dependencies. The sass package in the npm registry is Dart Sass — the same compiler the Carbon team uses internally. Dart Sass is required because Carbon's stylesheets use the modern @use and @forward module syntax that older LibSass does not support. If you accidentally install the legacy node-sass package instead, the Sass compilation step will fail with module resolution errors.

Configuring Sass

Installing the packages is only the first half of setup. Carbon's styles are written in Sass, which means your project needs to know how to compile them. Next.js supports Sass out of the box once the sass package is installed, but you still need to wire up the Carbon stylesheet import. This requires two file changes.

The first change is a rename. Find app/globals.css in your project (or styles/globals.css depending on how you answered the scaffolding questions) and rename it to globals.scss. This tells Next.js to treat the file as Sass rather than plain CSS, which is what allows the @use directive you are about to add to work.

The second change is to update the import in your layout file. Open app/layout.js (or app/layout.tsx for TypeScript projects) and find the import that references globals.css. Change the file extension from .css to .scss so it points to the renamed file:

// Before
import './globals.css';

// After
import './globals.scss';

Now open globals.scss and add the Carbon stylesheet import at the top of the file. This single line is what triggers Dart Sass to compile all Carbon component styles into your project's output CSS:

@use '@carbon/react';

This loads every Carbon component's styles — all of them, in one directive. For most projects starting out, this is exactly what you want: zero configuration, full coverage. As your project matures and you want to optimize bundle size, you can switch to importing only the styles for components you actually use. To scope styles to a single component — the button, for instance — replace the broad import with a targeted one:

/* Load styles for a specific component only */
@use '@carbon/react/scss/components/button';

The targeted import approach requires you to add one @use line per component type. This is worth the extra effort for large production applications where every kilobyte matters, but it is an optimization you should reach for after your application is working, not before.

Importing and using your first component

With the packages installed and Sass configured, you are ready to use Carbon components in your JSX. Carbon exports all of its components from the top-level @carbon/react package, so a single named import gives you access to whichever component you need. To render a button:

import { Button } from '@carbon/react';

export default function MyPage() {
  return (
    <main>
      <Button kind="primary">Get started</Button>
    </main>
  );
}

The kind prop controls the button's visual variant. Carbon defines several button kinds: "primary" (the main call-to-action, filled with the interactive color), "secondary" (an outlined variant for secondary actions), "tertiary" (transparent with a border), "ghost" (no border, minimal visual weight), and "danger" (for destructive actions). All are available as named values on the same kind prop — no separate component imports needed.

Icons work slightly differently. The icon library is a separate package (@carbon/icons-react), and icons are imported from a path within that package, not from @carbon/react directly. Each icon is a React component you pass as a prop to the Carbon component that accepts it:

import { Add } from '@carbon/react/icons';

export default function MyPage() {
  return (
    <Button kind="primary" renderIcon={Add}>
      Add item
    </Button>
  );
}

The separation between component and icon imports is intentional. Icons are a large catalog — hundreds of items — and bundling them all with the component library would significantly increase the initial install footprint. By keeping them in a separate package with individual named exports, tree-shaking can eliminate every icon you do not use, so your final bundle only includes the icons your code explicitly imports.

The theming wrapper: providers.js

Carbon ships with four built-in themes: "white" (light, default background), "g10" (light gray), "g90" (dark gray), and "g100" (near-black, the darkest option). These map to the IBM Design Language's official light and dark palettes. Wrapping your application — or sections of it — in a <Theme> component activates the corresponding set of design tokens, changing colors, border tones, and interactive states throughout the subtree in one step.

The official tutorial pattern is to create a providers.js file that centralizes theming alongside other global layout wrappers. The Theme component controls the active token set, and the Content component provides the correct padding and background color for the page body. A typical providers.js looks like this:

import { Theme, Content } from '@carbon/react';

export default function Providers({ children }) {
  return (
    <>
      <Theme theme="g100">
        {/* Navigation components go here */}
      </Theme>
      <Content>{children}</Content>
    </>
  );
}

In this pattern, the navigation area (header, side nav) is wrapped in <Theme theme="g100">, giving it the dark shell treatment that is characteristic of IBM products. The main page content lives inside <Content>, which uses the default theme. You can nest <Theme> components at any level of the tree — wrapping a sidebar in "g10" while keeping the main canvas in "white" is perfectly valid and is how Carbon achieves its signature two-tone layouts.

Once you have created providers.js, import it into your root layout.js and wrap your page output with it. Every page your application renders will then have access to Carbon's theme tokens, and the correct background and text colors will apply automatically to all Carbon components in the tree.

TypeScript notes

If your Next.js project uses TypeScript, there is one additional configuration step. Not all Carbon components are fully typed yet — the library is large and type coverage is an ongoing community effort. Without the following setting, TypeScript's type checker may surface errors from within Carbon's own source files when you run a build. These are not errors in your code; they are gaps in Carbon's type declarations. The fix is to tell TypeScript to skip type checking inside node_modules:

// tsconfig.json
{
  "compilerOptions": {
    "skipLibCheck": true
  }
}

Add "skipLibCheck": true to the compilerOptions object in your tsconfig.json. This option is a standard escape hatch for exactly this situation — third-party libraries that are not yet fully typed. It does not affect type checking of your own code; TypeScript continues to check everything you write. It only suppresses errors originating inside node_modules.

Beyond this single setting, Carbon's TypeScript experience is generally good. Components accept typed props, and your editor will provide autocompletion for valid kind values, icon names, and theme strings. As the Carbon community fills in the remaining type gaps over time, the need for skipLibCheck will diminish — but for now it is the recommended approach in the official documentation.

Framework-specific guides

This lesson walked through setup using Next.js, which is the framework the official Carbon tutorial targets. Carbon also publishes dedicated Sass integration guides for Remix, Gatsby, Vite, and Webpack. Each guide covers any framework-specific configuration differences — for example, Vite handles Sass imports slightly differently from Next.js, and Gatsby has its own gatsby-config.js patterns for global style injection. If you are building on one of these frameworks instead of Next.js, consult the corresponding guide on the Carbon documentation site before following this lesson's file-change instructions literally.

Regardless of framework, the core sequence is the same: install @carbon/react, install sass, add @use '@carbon/react' to your global stylesheet, and import components from @carbon/react. The framework guides only change where and how you hook in the global stylesheet — the component API is identical across all setups.

Key Insight
The @use '@carbon/react' directive in your global Sass file is not optional decoration — it is the step that triggers Dart Sass to compile Carbon's component styles into your project's output CSS. Without it, your Carbon components will render without any visual styling: no colors, no spacing, no interactive states. Every other step in setup can be done in any order, but this one line must be present before Carbon components will look correct.
Common Error
Two setup mistakes account for most "Carbon components look unstyled" reports. The first is forgetting to rename globals.css to globals.scss — if the file extension stays .css, Next.js will not invoke the Sass compiler, and the @use directive will be silently ignored. The second is forgetting to add @use '@carbon/react' to the renamed file entirely. Check both before reaching for other debugging steps: the file must be named .scss, and it must contain the @use import.
