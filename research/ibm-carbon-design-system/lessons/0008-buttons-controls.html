Buttons and Controls

~15 min Module 3 — Component Library in Depth · Lesson 8 of 12
Source
Carbon Design System — "Button" component documentation (carbondesignsystem.com)
Key result: Carbon defines five button variants arranged in a strict emphasis hierarchy. Every layout should contain at most one primary button; remaining calls to action descend in emphasis through secondary, tertiary, ghost, and danger variants. Labels follow a verb + noun formula, icons appear to the right of labels, and alignment shifts between left (full-page) and right (wizard/dialog) depending on context.

The five variants and their emphasis hierarchy

Carbon's button system is built around a single organizing idea: every button on a screen occupies a specific position in a visual hierarchy, and that position should be communicated through the button's visual weight. There are five variants, each carrying a distinct level of emphasis. Together they form a vocabulary for expressing how important an action is relative to every other action on the same screen.

The hierarchy runs from most to least prominent: Primary → Secondary → Tertiary → Ghost → Danger. Danger sits outside the main descending hierarchy because its emphasis is specialized — it signals destructive intent rather than general importance. A danger button should be visually unmistakable, but it should never be confused with the principal call to action.

Understanding the variants is only half the job. The other half is understanding how to use them together. Carbon makes an important observation: "You don't necessarily need to use the buttons in the order that their labels imply." This means you should choose variants based on the visual hierarchy you need for the screen, not based on a mechanical mapping of variant name to action name. A "Back" button in a wizard uses secondary styling not because back is inherently secondary, but because the primary action in that context is "Next" or "Submit."

Variant Emphasis Intended purpose
Primary Highest The principal call to action on a screen — use only once per page
Secondary High Negative actions such as Cancel or Back; always paired with a primary button
Tertiary Medium Less prominent, independent, or grouped actions that complement the primary
Ghost Low Least emphasis; supplementary actions, cancel in informal contexts, or inline actions within dense layouts
Danger Specialized Destructive actions only — Delete, Remove, Stop; signals irreversibility, not general importance

The one-primary-per-screen rule and why it matters

Carbon is explicit: each page should have only one primary button. All remaining calls to action should use lower-emphasis variants. This constraint is not arbitrary — it flows directly from how visual attention works. When a user lands on a screen, their eye is drawn to the most visually prominent element. A primary button's high-contrast filled style is designed to capture that attention and guide the user toward the single most important action available. If two or more buttons compete for that top position, the hierarchy collapses and users must read every button label to determine what the screen wants them to do.

In practical terms, the rule forces a design decision that is often uncomfortable but always clarifying: what is the one thing this screen exists to accomplish? A form submission screen exists to submit the form — that is the primary action. A confirmation dialog exists to confirm or cancel — the destructive confirmation is primary (and in that specific case, it may be styled as a danger button that carries primary weight within the dialog). A search results page may exist to let users refine their search, open a result, or export — but only one of those can be the top-level intent, and the button hierarchy makes that intent visible without a word of instruction.

Violating the one-primary rule produces a predictable failure mode: the user pauses, scans, and hesitates. Every additional primary button increases the cognitive cost of using the screen. In user research, screens with multiple primary buttons consistently generate more errors and longer task completion times than equivalent screens with a clear hierarchy. The rule is not a stylistic preference — it is a usability guarantee that Carbon's component constraints help enforce.

Label rules: verb + noun, sentence case, no truncation

A button label is a promise. It tells the user what will happen the moment they click. Carbon's labeling guidance is designed to make that promise as precise and readable as possible. The core formula is verb + noun: pair an action word with the object of that action. "Save file." "Delete record." "Submit form." "Add user." This pattern works because it leaves no ambiguity about what the button does — the verb describes the action and the noun specifies what is affected. Avoid noun-only labels ("Settings", "Profile") that describe destinations rather than actions; those belong on links, not buttons.

Labels must be written in sentence case — capitalize only the first word and proper nouns. "Save changes" is correct; "Save Changes" is title case and incorrect; "SAVE CHANGES" is all-caps and doubly incorrect. All-caps labels are particularly problematic: they reduce readability (words are harder to distinguish), they can inadvertently read as shouting, and they force users to parse individual letters rather than whole-word shapes. Carbon's sentence case requirement is consistent with its broader typography guidance and with WCAG readability best practices.

Labels within the button are always left-aligned inside the button container. When a label is too long to fit on one line, it should wrap rather than truncate. Truncation with an ellipsis is never acceptable for button labels — it hides information that users need to make an informed click decision. If a label regularly overflows the available space, that is a signal to shorten it (can you make the verb + noun more concise?) or to reconsider the button's size tier rather than to hide the text. Limit button groups to 2–3 actions; if you have more than three actions to present, use a menu button (an overflow control that reveals additional options) rather than proliferating individual buttons.

Icon placement and icon-only button requirements

Icons in Carbon buttons always appear to the right of the label text. This is the opposite of many other design systems and is worth memorizing explicitly. The rationale is rooted in reading direction: in left-to-right interfaces, the eye reads the label first and then encounters the icon as a reinforcing visual. Standard buttons use 16px icons; large expressive buttons use 20px icons. Do not mix icon sizes within a button group, and do not use non-standard sizes that fall outside these two values.

Icon-only buttons — buttons that display an icon with no visible label text — are permitted in Carbon but carry a strict requirement: they must always have a tooltip. The tooltip exposes the action name that the icon represents. Without this tooltip, icon-only buttons are inaccessible: screen reader users cannot determine the button's purpose, and sighted users who do not recognize the icon are equally blocked. The tooltip is not optional decoration; it is the required accessible name of the button. If you are building an icon-only button and feel the tooltip would be redundant or obvious, that is not a justification for omitting it — it is still required.

There is one important exception: danger buttons cannot be icon-only. Because danger buttons trigger destructive, often irreversible actions, Carbon requires that their intent always be made explicit through visible text. An icon alone — even a universally recognizable trash-can icon — is insufficient for a button that will delete a record, stop a process, or remove a user. The text label is the safeguard that ensures the user has read and understood the action before triggering it. Pair an icon with a label on danger buttons; never omit the label.

Alignment rules: page designs vs. wizards and dialogs

Button alignment in Carbon depends on context. In full-page designs, the primary button is left-aligned. This follows the natural reading gravity of the page: important content and actions sit at the left edge, where the eye returns at the start of each new line. A left-aligned primary button in a form, for example, is visually anchored to the content it submits and reads as part of the same left-to-right flow as the form fields above it.

In wizards and dialogs, the convention inverts: the primary button is right-aligned. This reflects a different spatial metaphor. Wizards are step sequences, and "forward" is to the right — the primary action (Next, Submit, Confirm) lives at the right edge of the footer, while the secondary action (Back, Cancel) lives at the left. This right-aligned convention is so widely adopted in modal dialogs and multi-step flows that deviating from it will feel unfamiliar to users even if they cannot articulate why. Respecting this pattern is an act of respecting user muscle memory.

One additional grouping rule applies regardless of context: buttons within a group should share the same width. Mismatched button widths in a group create visual noise that distracts from the content. If one button's label is substantially longer than another's, consider whether the labels can be made more parallel — both the same approximate length — or whether the buttons should be laid out differently to avoid the size mismatch.

Loading states and inline feedback

Carbon buttons support an inline loading state that provides feedback during asynchronous operations. When a user clicks a button that triggers a process — a form submission, a data export, a long-running API call — the button can transition to a loading state that shows a spinner or progress indicator inline within the button's own footprint. This design eliminates the need for a separate full-page loading overlay for actions that originate from a button click.

A critical rule accompanies the loading state: the button must be disabled while loading is in progress. This prevents double-submission — the most common failure mode in submit-button interactions. If the button remained active during the loading state, a user who clicks again (either impatiently or by accident) would trigger a second action before the first completes. Disabling the button during loading is both a usability safeguard and a data integrity measure, particularly important for operations like payments, record creation, or any action with side effects.

The inline loading pattern is intentionally scoped to the button that triggered the action. It signals "something is happening as a result of what you just did" without disrupting the rest of the screen. Once the operation completes, the button returns to its normal state (or, in some flows, transitions to a success state momentarily before resetting). This contained feedback model is consistent with Carbon's broader philosophy of giving users precise, contextually appropriate information rather than blunt full-screen interruptions.

Key Insight
The entire Carbon button system is an argument about hierarchy. Every rule — one primary per screen, descending emphasis variants, size consistency within groups, left vs. right alignment — serves the same underlying goal: the most important action on any given screen should be immediately, unambiguously obvious to any user who glances at it. When the hierarchy is correct, users do not need to read every button to know what the screen wants them to do. When the hierarchy breaks down, cognitive load rises and errors follow.
Common Violation
The two most frequent button violations in real product work are (1) placing multiple primary buttons on a single screen — often because a designer wants to give equal prominence to two competing actions — and (2) writing labels that are nouns, all-caps, or truncated rather than using the verb + noun formula in sentence case. Both violations erode the hierarchy that makes buttons work. If a screen has more than one primary button, it means the design has not yet committed to a single principal action — that is an information architecture problem, not a styling one.

Button spec audit: identify violations and rewrite correctly

A designer has placed these five buttons on a single page:

  1. Primary — label: "SUBMIT" (all caps)
  2. Primary — label: "Cancel"
  3. Ghost — label: "Delete record"
  4. Danger (icon-only) — no tooltip provided
  5. Two buttons of different sizes in the same group

Identify every violation in the spec above and rewrite it correctly — specifying the correct variant, label format (including casing), and any missing requirements for each button. There is at least one violation in every item.
