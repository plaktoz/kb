IBM Carbon Design System — Typography & Spacing
Covers type tokens, IBM Plex typeface families, productive vs expressive token sets, the mathematical spacing scale, and the Stack component for consistent layout rhythm.

IBM Plex and the typeface foundation

Carbon's typographic foundation is built on IBM Plex, an open-source typeface family released by IBM in 2017. Plex was designed from scratch to reflect IBM's personality — analytical, precise, and human — while remaining highly legible across product interfaces and editorial contexts alike. Because it is open-source, IBM Plex is free to use in both commercial and personal projects.

IBM Plex comes in three stacks that cover the full range of design needs:

  • IBM Plex Sans — the primary UI typeface. Clean, modern, and optimised for screen reading at a wide range of sizes. Used for almost all body copy, labels, headings, and interactive elements in Carbon components.
  • IBM Plex Serif — a transitional serif suitable for long-form editorial content, articles, and contexts where a more classical voice is desired. Not commonly used in data-dense product screens.
  • IBM Plex Mono — a monospaced variant for code samples, technical values, and numeric data that benefits from character alignment. Used in code editors, terminal output, and data tables wherever fixed-width rendering matters.

Carbon recommends three weight tiers: Light (300) for large display sizes where heavy ink feels overwhelming, Regular (400) as the everyday workhorse for body copy and secondary labels, and SemiBold (600) for headings, section titles, and UI labels that need hierarchical emphasis. SemiBold works well for short strings like section headers but becomes tiring and harder to read in long paragraphs — use Regular there instead. Italics in Carbon have a specific, limited role: emphasis within prose, titles of works, technical terms on first introduction, and captions. Avoid italics as a stylistic decoration; use them only when the semantic meaning requires it.

Color in type follows the same purposeful logic. Running body text stays in neutral Carbon text tokens — never styled blue or otherwise coloured without reason. Blue is reserved for interactive, primary action elements such as links and buttons. Coloured type appears in narrowly defined contexts: error messages, warning banners, inline code, and status indicators. Using colour in typography decoratively undermines the signal-to-noise ratio of the entire interface.

Type tokens: productive vs expressive

Rather than hard-coding font sizes, Carbon abstracts typography into type tokens — named references that encapsulate a complete typographic configuration including font size, line height, font weight, and letter spacing. This means that when you apply a token like $heading-03, you get a consistent, tested combination of properties rather than assembling them ad hoc. This is the core mechanism that keeps text visually coherent across an entire product suite, even when different teams contribute different components.

The token system is divided into two semantically distinct sets distinguished by their naming suffix:

  • Productive type tokens (e.g. $label-01, $body-compact-01, $heading-03): Condensed, fixed-size configurations optimised for task-focused product interfaces — dashboards, forms, data tables, and toolbars. Sizes do not change across breakpoints. Productive tokens prioritise information density and scanning speed. The -01 suffix signals this set.
  • Expressive type tokens (e.g. $display-01, $heading-06): Larger, more dramatic configurations that respond across breakpoints, growing at wider viewports to fill editorial layouts, landing pages, and marketing surfaces. The -02 suffix signals this set. Expressive heading sizes are not fixed — they scale responsively to create visual impact that would feel out of place in a compact product UI.

The distinction matters in practice. If you are building a settings panel, a data grid, or a form, you almost always want productive tokens: they keep the interface tight and functional. If you are building a hero banner, a docs landing page, or a promotional section, expressive tokens deliver the visual weight and typographic drama appropriate to that context. Mixing the two carelessly — for example, using an expressive display token inside a compact modal — creates jarring size inconsistencies that break the visual rhythm of the product.

The underlying scale from which all tokens are derived starts at 12px (denoted y₀ = 12) and follows a mathematical formula to generate consistent hierarchical size steps. This means every step up in the scale represents a deliberate, proportional increase rather than an arbitrary jump. The mathematical consistency is what allows diverse tokens — from small label text to large display headings — to feel like they belong to the same visual system.

The spacing scale and why it uses multiples of 8

Carbon's spacing system is built on multiples of 2, 4, and 8 pixels. This is not arbitrary. Most screen resolutions divide cleanly by 8, meaning 8px increments align perfectly to subpixel rendering boundaries on retina and high-DPI displays. Interfaces built on an 8px grid look sharper because they avoid the slight blurring that occurs when a fractional pixel boundary falls between physical pixels. The base grid also makes mathematical relationships between elements predictable: doubling a spacing value (for example, moving from 16px to 32px) communicates a meaningful jump in visual weight or separation, while halving suggests finer control.

The practical benefit for designers and developers working together is a shared vocabulary. When a designer annotates a comp with "32px below the heading", both parties know that maps to $spacing-07. No translation needed, no divergence in implementation. The tokens replace raw CSS values entirely — you write margin-bottom: $spacing-07 instead of margin-bottom: 32px, and the design intent is preserved as a named reference rather than a magic number.

Notice how the scale grows: steps 01–05 advance by 2px, 2px, 4px, and 4px — fine granularity at small sizes where precision matters most. From step 05 onward the gaps grow larger — 8px, 8px, 8px, 8px — until the very top of the scale where jumps become dramatic to support major layout decisions. This graduated density mirrors how human perception works: we are more sensitive to spatial differences at small scales (the difference between 2px and 4px is very noticeable) and less sensitive at large ones (the difference between 80px and 96px reads as roughly equivalent).

Applying spacing tokens in practice

Spacing tokens are used as direct replacements for CSS margin and padding values. In Sass, this looks exactly like using a variable:

// Single-side padding
.cds--card {
  padding: $spacing-05; // 16px on all sides
}

// Mixed margins (top, right, bottom, left)
.cds--section-heading {
  margin: $spacing-07 $spacing-04 0 $spacing-04; // 32px top, 12px sides, 0 bottom
}

// Gap between stacked elements
.cds--form-group {
  margin-bottom: $spacing-06; // 24px below each form group
}

A key design principle behind the scale is that more space signals higher importance and stronger focus. Elements with generous whitespace around them attract the eye and communicate that they are primary focal points. Conversely, tightly packed elements read as related, secondary, or subordinate. When you increase the margin above a section heading from $spacing-07 (32px) to $spacing-09 (48px), you are telling the reader: this is a significant transition, not a minor sub-topic.

Proximity implies relationship; distance implies separation. This gestalt principle is at the heart of why tokens are chosen deliberately rather than guessed. Two labels 4px apart ($spacing-02) feel like parts of the same unit. Two sections 64px apart ($spacing-10) feel like distinct chapters. When your spacing tokens reflect the actual hierarchy of your content, users can scan and navigate without having to read every word.

Tokens are not responsive by default — $spacing-07 is always 32px regardless of screen size. However, it is an accepted pattern to step the scale up or down at breakpoints when the design demands it. For example, you might use $spacing-09 (48px) for vertical section gaps on large displays and step down to $spacing-07 (32px) on mobile. This is done explicitly in your responsive styles rather than being automatic, giving you precise control over the layout at every viewport size.

The Stack component

Carbon includes a Stack component that brings the spacing scale directly into layout without requiring manual margin declarations on every child element. Instead of styling each item individually, you wrap a group of related items in a Stack and set a single gap property using a spacing scale value. Stack handles the rest — applying equal spacing between every child in the group, in either a vertical (column) or horizontal (row) orientation.

This is especially useful for form fields, button groups, notification stacks, and list layouts where you want uniform rhythm without the fragility of collapsing margins. Classic CSS margin collapsing can make margin-based spacing unpredictable when adjacent elements have different margins. Stack sidesteps this entirely by using CSS gap under the hood, which does not collapse.

// Stack children vertically with $spacing-05 (16px) between each
<Stack gap={5}>
  <FormLabel />
  <TextInput />
  <HelperText />
</Stack>

// Stack children horizontally with $spacing-03 (8px) between each
<Stack orientation="horizontal" gap={3}>
  <Button kind="primary">Save</Button>
  <Button kind="secondary">Cancel</Button>
</Stack>

The gap prop accepts a number corresponding to the spacing scale step — so gap={5} maps to $spacing-05 (16px). This keeps the same token vocabulary consistent whether you are writing Sass, CSS-in-JS, or React JSX. The Stack component removes an entire category of spacing bugs by making it impossible to accidentally use an off-scale value: if the gap prop accepts only integers mapping to defined tokens, there is no way to sneak a raw pixel value past code review.

Key Insight

Spacing and type tokens are not just organisational conveniences — they are the mechanism by which design decisions survive translation from mockup to code. When every developer on a team reaches for $spacing-05 instead of 16px, the design system gains a single source of truth: change the token once, update the entire product. The same logic applies to type tokens. This is the compounding value of a token-based system over time.

Watch Out

Using arbitrary pixel values — margin-top: 14px, padding: 22px — instead of spacing tokens is one of the most common ways to break the visual rhythm of a Carbon interface. These "magic numbers" are invisible to the design system: they do not respond to theme changes, they do not communicate design intent, and they diverge silently over time as components are updated. Even a value that looks close to a token value (14px instead of $spacing-04 at 12px or $spacing-05 at 16px) introduces an inconsistency that accumulates across hundreds of components. Always use the nearest token and discuss with your designer if the token does not fit.
