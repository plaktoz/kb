What Are Design Tokens, and Why Do They Exist?

Imagine you are building a large product — dozens of components, hundreds of screens, multiple teams working in parallel. Every button, every input field, every heading needs a color. The naive approach is to hard-code hex values directly into each component: #0f62fe for a primary button, #161616 for body text, #e0e0e0 for a border. That approach works fine until the day you need to support a dark mode, or your brand guidelines update the primary blue, or a new accessibility audit demands higher contrast. Suddenly you are hunting through thousands of lines of CSS or styles code, changing hex values one at a time, and praying nothing was missed.

Design tokens solve this problem by introducing a layer of indirection. Instead of writing #0f62fe, you write $interactive. Instead of #161616, you write $text-primary. Each token is a named, role-based identifier that maps to a concrete value underneath — but crucially, that mapping can change depending on context (for example, which theme is active) without you touching any component code. The component stays the same; only the token's resolved value changes.

Carbon's token system is built on the IBM Design Language palette of neutral grays and a core blue. Neutral grays form the dominant surface tones throughout all themes, while IBM's core blue (#0f62fe in light themes) drives primary interactive elements. Tokens layer on top of this palette as semantic, role-based names, so a designer or developer never needs to remember exact hex codes — they need to know the role a color plays, and pick the token for that role.

The Ten Core Token Groups

Carbon organizes its color tokens into ten named groups. Each group covers a distinct role in the UI, and tokens within a group share that role while varying by state or emphasis. Understanding the groups is the foundation of working with Carbon color — once you know which group a color belongs to, you know roughly which token to reach for.

The ten groups are: Background, Layer, Field, Border, Text, Link, Icon, Support, Focus, and Skeleton. Background tokens set the page-level canvas. Layer tokens control the surfaces stacked above it — cards, panels, modals. Field tokens handle form input backgrounds. Border tokens draw dividers, outlines, and separators. Text tokens govern all written content. Link tokens are specifically for navigational anchor text. Icon tokens color iconography. Support tokens carry semantic meaning: error, success, and warning states. Focus tokens define the visible keyboard-focus ring. Skeleton tokens drive loading placeholder animations.

Token Group Role Example Tokens
Background Page-level canvas color $background, $background-hover
Layer Raised surfaces: cards, panels, modals $layer-hover, $layer-active
Field Form input backgrounds $field-01, $field-hover-01
Border Dividers, outlines, separators $border-subtle, $border-strong
Text All written content $text-primary, $text-secondary
Link Navigational anchor text $link-primary
Icon Iconography fill and stroke $icon-primary
Support Semantic state colors $support-error, $support-success, $support-warning
Focus Keyboard focus ring $focus
Skeleton Loading placeholder animations $skeleton-background

Notice that some groups have only a handful of tokens while others — like Text or Layer — have many, covering different emphasis levels and interactive states. The token naming convention is consistent: group name first, then a qualifier. $text-primary is primary-emphasis text; $text-secondary is de-emphasized text. $border-subtle is a low-contrast divider; $border-strong is a higher-contrast edge. This predictability means you can often infer a token name before looking it up.

The Four Built-In Themes and Layering Logic

Carbon ships with four production-ready themes. Two are light and two are dark. The light themes are White (base color #ffffff) and Gray 10 (base color #f4f4f4). The dark themes are Gray 90 (base color #262626) and Gray 100 (base color #161616). Each theme maps every token to a concrete palette value. When you switch themes, every token resolves differently — but the semantic meaning of each token stays identical. $text-primary is always "the primary text color for this theme," whether that resolves to near-black in a light theme or near-white in a dark one.

Switching between themes at runtime — for inline dark/light mode — is straightforward because token names never change. A component written against tokens simply re-renders correctly when the theme changes. This is the practical power of the token abstraction: theme switching is a data change, not a code change.

Within any given theme, Carbon uses a layering model to create visual depth. In light themes, layers alternate between the two light palette values — White and Gray 10. The page background might be White, a card surface above it uses Gray 10, and a popover or modal above that returns to White. In dark themes the logic inverts: each additional layer becomes one step lighter. The darkest base sits at the bottom; every panel or surface elevated above it is slightly lighter, communicating hierarchy through luminance. This alternating or stepping pattern means components designed for layer 1 also look correct in layer 3 without modification — the tokens handle the value swapping.

Interaction State Tokens

A well-designed color system must account for more than the "enabled" (default) state of a component. Users hover, click, focus, and select elements constantly. Each of these interactions deserves a visually distinct response so that the interface feels alive and communicates clearly what is happening. Carbon's token system has dedicated tokens for every major interaction state, paired with a consistent visual logic for how much each state changes from the enabled baseline.

The five interaction states beyond "enabled" are: Hover, Active, Selected, Focus, and Disabled. Each follows a predictable pattern:

  • Hover — the cursor is over an element but it has not been pressed. The color shifts a half-step lighter or darker from the enabled value. Token example: $layer-hover, $background-hover.
  • Active — the element is being pressed or activated. The color shifts a full two steps lighter or darker — a noticeably larger change than hover, so press feedback feels distinct. Token example: $layer-active.
  • Selected — the element has been chosen in a selection context (e.g., a tab, a list item). One full step lighter or darker from enabled. Token example: $layer-selected.
  • Focus — keyboard focus ring. In light themes the ring uses Blue 60; in dark themes it uses White. There is often a companion $focus-inset token that draws a thin buffer border inside the focus ring, improving contrast on colored backgrounds. Token: $focus.
  • Disabled — the element is unavailable for interaction. Disabled colors are drawn exclusively from the gray family, and no contrast ratio requirements apply to disabled states, because the intent is to show unavailability rather than readable content.

Having discrete tokens for each state means teams never need to compute derived colors manually. If a designer or developer reaches for a hex value to shade a hover state by hand, they have stepped outside the system — and they lose the guarantee that their chosen shade is consistent with every other hover state across the product. Token-based interaction states are what make a Carbon application feel cohesive and intentional even when built by many different teams.

WCAG Contrast Requirements and How Carbon Meets Them

Accessibility is not an afterthought in Carbon — it is built into the token system itself. Carbon's color tokens are designed to satisfy the Web Content Accessibility Guidelines (WCAG) contrast requirements by default when used correctly. The two key thresholds from WCAG 2.1 are: text smaller than 24px (or bold text smaller than 18.66px) must achieve a 4.5:1 contrast ratio against its background, and large text (24px and above) as well as non-text graphics must achieve at least 3:1.

When you use $text-primary on a $background surface, or $text-secondary on a $layer-01 surface, Carbon has pre-verified that those token pairings meet the required ratio across all four themes. This pre-verification is only guaranteed when you stay within the token system. If you reach for a raw hex value — say, placing a mid-gray text color you picked yourself on a white background — you lose that guarantee entirely and must run your own contrast audit.

Focus states have their own minimum: 3:1 contrast between the focus ring and adjacent colors. In practice, Carbon often exceeds this minimum. The $focus-inset token adds a white (or dark) buffer border between the focus ring and the element's own background, which prevents the ring from visually merging into a same-colored surface. This pattern is especially important on interactive elements that appear on colored backgrounds — without the inset buffer, a blue ring on a blue button would be invisible. The layered approach of $focus plus $focus-inset makes the keyboard focus indicator robust across all theme contexts.

Disabled states are the one explicit carve-out: since disabled elements are intentionally unavailable and carry no readable information, WCAG does not require contrast compliance for them. Carbon's disabled tokens therefore use muted grays that communicate "unavailable" without meeting the active-state contrast thresholds. Everything else in the system — text, icons, links, support indicators — is designed to comply when tokens are used as intended.

Key insight

Design tokens are semantic roles, not color values. When you write $layer-hover, you are saying "the hover state of a raised surface in whatever theme is active." The token system is what makes theme switching free — no component code changes, only the token-to-value mappings change.

Common misconception

Avoid using raw hex values from the IBM Design Language palette directly in components — for example writing color: #0f62fe instead of color: $interactive. Even if the hex is "correct" today, it will not respond to theme switching, will not be recognized by Carbon's theming tools, and may fail accessibility checks in dark contexts. Always reference a token by name; never a palette hex.
