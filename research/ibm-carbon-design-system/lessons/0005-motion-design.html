Motion Design

Module 2 — Layout, Motion, and Accessibility Lesson 5 of 12 ~12 min
Source
IBM Carbon Design System — Motion Guidelines
Carbon's motion documentation covers two motion styles (productive and expressive), three easing curve types, six duration tokens ranging from 70ms to 700ms, and guidelines for motion sensitivity and accessible animation.

Why motion matters in UI design

Motion in a user interface is far more than decoration. When used well, animation communicates meaning: it tells the user where an element came from, where it went, and how one state relates to the next. Carbon articulates this purpose precisely — motion guides users "from here to there, now to next, start to finish." Without motion, state changes appear as abrupt cuts that force users to reconstruct context for themselves. With thoughtful motion, the interface narrates its own transitions.

Carbon defines four qualities that purposeful motion must have. It should be purposeful — every movement carries intent and reinforces the message of the interface rather than distracting from it. It should be responsive — animation reacts immediately to user input, signalling that the system is alive and listening. It should be meticulous — the timing and easing of each element are carefully chosen rather than copied from a default. And it should be unobtrusive — motion never draws so much attention to itself that it competes with the content the user came to see.

These four qualities exist in tension. Expressive motion that delights users in a marketing context becomes obtrusive in a dense data dashboard where users are trying to work quickly. Understanding this tension — and resolving it by matching the motion style to the context — is the central skill this lesson develops.

Productive vs expressive motion

Productive motion is subtle, efficient, and task-focused. It is designed for interfaces where users are in flow — accomplishing a goal, scanning data, entering input. Productive motion keeps itself small and quick, using shorter duration tokens and understated easing curves. The aim is to provide just enough feedback to confirm a state change without interrupting the user's cognitive momentum. Examples include button hover and active states, dropdown menus opening and closing, data table rows expanding, toggle switches flipping, and form validation messages appearing inline.

Expressive motion is vibrant, highly visible, and attention-capturing. It is reserved for significant moments in the user journey — transitions that mark a meaningful change of context. Carbon explicitly instructs designers to "reserve expressive motion for occasional, important moments." Examples include full-page transitions to a new route, primary call-to-action confirmations, onboarding celebrations, and prominent notification toasts that carry system-level information. Because expressive motion commands attention, overusing it defeats its own purpose: if every action triggers expressive animation, nothing feels significant.

The distinction between the two styles maps onto the productive-versus-expressive vocabulary already seen in Carbon's type token system. Just as expressive type styles are reserved for headlines that need visual weight, expressive motion styles are reserved for moments that need emotional emphasis. In both cases, the productive variant is the default and the expressive variant is the deliberate exception. When in doubt, start with productive motion — it is almost always the safer, more professional choice for business software.

Style Character Typical contexts Duration range
Productive Subtle, efficient, task-focused Buttons, dropdowns, toggles, data tables Faster (70–150ms typical)
Expressive Vibrant, visible, attention-capturing Page transitions, primary actions, notifications Slower (240–700ms typical)

Easing curves explained

Easing curves define the velocity profile of a transition — how fast the animation accelerates and decelerates over its duration. A linear curve moves at a constant speed from start to finish, which feels mechanical and unnatural because physical objects in the real world almost never move that way. Carbon's motion system, by contrast, is grounded in the "physics of a light-weight material": elements should accelerate quickly and decelerate gently (or the reverse), matching the intuitions users bring from everyday experience with real objects.

Carbon defines three functional easing curve types, each available in both a productive and an expressive variant. The standard curve is for elements that remain visible throughout the entire transition — moving from one position or state to another within the same view. The entrance curve is for elements entering the visible area from outside — they start fast (already in motion as they cross the boundary) and ease to a stop. The exit curve is for elements leaving the visible area — they start from rest, accelerate, and leave the frame quickly. Using the wrong curve type for a given interaction — say, applying an entrance curve to an element that never leaves the screen — produces motion that feels physically implausible and subtly wrong to users even if they cannot articulate why.

Carbon explicitly warns against certain curve characteristics: no bounce, no stretch, and no sudden-stop curves. Bounce and stretch introduce springy elastic motion that conflicts with the "light-weight material" metaphor and tends to read as playful or frivolous in professional contexts. Sudden stops — linear or near-linear curves — feel abrupt because real objects do not halt instantaneously. If you are tempted by a bouncy easing from a general animation library, Carbon's answer is to use a standard curve with a slightly longer duration instead.

Type Purpose Productive CSS Expressive CSS
Standard Element visible throughout cubic-bezier(0.2, 0, 0.38, 0.9) cubic-bezier(0.4, 0.14, 0.3, 1)
Entrance Elements entering view cubic-bezier(0, 0, 0.38, 0.9) cubic-bezier(0, 0, 0.3, 1)
Exit Elements leaving view cubic-bezier(0.2, 0, 1, 0.9) cubic-bezier(0.4, 0.14, 1, 1)

In practice, you will use these values via Carbon's Sass motion mixins rather than writing cubic-bezier() values by hand. But understanding the underlying values helps you recognise when a colleague's custom animation is straying outside the system — and helps you explain, concretely, why it looks off.

Duration tokens

Carbon provides six duration tokens, named along a fast–moderate–slow scale. Each token has a specific millisecond value and an intended use case. The naming follows the same -01 (subtler) and -02 (more prominent) convention seen elsewhere in the Carbon token system: within each speed tier, -01 is the shorter, quieter variant and -02 is the longer, more noticeable one.

The guiding principle for choosing a duration is that animation duration should scale with the size of the visual change. A button changing colour involves almost no spatial displacement — it deserves the shortest token available (duration-fast-01, 70ms). A full-panel expansion that reshuffles a large section of the layout involves substantial spatial movement — it warrants one of the slower tokens (duration-slow-01, 400ms or duration-slow-02, 700ms). Applying a long duration to a tiny microinteraction makes the interface feel sluggish; applying a short duration to a large layout shift makes elements appear to teleport rather than travel.

Token Value Use case
duration-fast-01 70ms Buttons, toggles — the smallest state-change microinteractions
duration-fast-02 110ms Fades — elements cross-fading in place without spatial movement
duration-moderate-01 150ms Small expansions — dropdowns, tooltips, short accordion panels
duration-moderate-02 240ms Toasts and system communication — visible enough to be noticed
duration-slow-01 400ms Large expansions — side panels, full-height drawers, page sections
duration-slow-02 700ms Background dimming — modal scrim overlays, gradual context shifts

Notice that the slower tokens are not reserved only for expressive motion. A large sidebar panel expanding is a productive interaction — it is task-focused and part of normal workflow — yet it appropriately uses duration-slow-01 because the spatial change is large. The speed tiers describe the size of the visual change, not the emotional register of the moment. The motion style (productive vs expressive) and the duration token are two independent axes that you apply together.

Motion sensitivity and accessibility

Not every user experiences animation the same way. For people with vestibular disorders, certain motion patterns — particularly large-scale translations, parallax effects, and sustained looping animations — can trigger vertigo, nausea, or disorientation. The prefers-reduced-motion CSS media query gives these users a way to signal their preference to the browser, and Carbon's motion guidance requires that this signal be respected.

The practical rule is straightforward: always provide a static alternative for users with motion sensitivity. In most cases this means wrapping animated properties in a @media (prefers-reduced-motion: reduce) block that either eliminates the animation entirely or replaces it with a simple opacity fade at a very short duration. A dropdown that normally slides open should simply appear when reduced motion is preferred. A page transition that normally sweeps in from the side should cut directly to the new content. The information conveyed by the interface must not depend on the animation; the animation should only enhance an experience that already works without it.

Beyond motion sensitivity, lower-powered devices — older mobile phones, constrained embedded browsers — may render complex animations poorly, producing jank that undermines the very sense of responsiveness the animation was meant to create. Carbon's guidance to provide static alternatives applies equally here: an animation that degrades to jank is worse than no animation at all. If you are building for a wide hardware spectrum, err toward shorter durations and simpler easing, and test on real constrained devices rather than relying solely on desktop browser tooling.

Key insight
The productive/expressive distinction is not about how much effort an animation takes to build — it is about how much attention it should command. Productive motion should disappear into the background of the user's awareness. Expressive motion earns the right to be noticed by being reserved for genuinely significant moments. When every interaction feels significant, none of them do.
Common mistake
Applying expressive motion to every interaction. It is tempting to use the more dramatic, slower easing curves throughout a UI because they feel more polished in isolation. In practice, pervasive expressive animation makes an interface feel slow and overwrought — users cannot work at their natural pace because the interface keeps demanding their attention. Expressive motion loses its meaning the moment it is no longer exceptional. Default to productive motion everywhere, then consciously decide which two or three moments per screen truly warrant the expressive treatment.
