How to think about components as a system, not a grab-bag

A newcomer to Carbon can open the component documentation and feel overwhelmed. Forty-nine components. Dozens of variants. Countless configuration options. It is tempting to treat the library as a flat catalog — to search for something that visually resembles what you need and drop it into your design. This grab-bag approach to component selection is exactly what leads to incoherent user interfaces, where things technically work but feel assembled from unrelated sources rather than designed as a unified whole.

The right mental model is to treat Carbon's components as a system of interlocking parts, each with a defined role. Every component was created to solve a specific class of problem. A Modal exists because sometimes you need to interrupt the user with a decision they must make before continuing. A Data Table exists because users often need to scan, sort, and act on large sets of structured records. A Notification exists because the application needs to communicate a system-level event without hijacking the entire screen. When you understand a component's intended purpose, you stop asking "which component looks right?" and start asking "which component is designed to solve this problem?"

Carbon's 7-category taxonomy is the key to this shift. The categories are not arbitrary filing labels — they describe what a component does in the interface architecture. UI Shell components frame the page. Input and Navigation components let users act on the application. Data Display and Feedback components communicate results and system state. Overlays and Content components handle contextual and supplementary information. Knowing which category a component belongs to tells you something meaningful about when and how to use it. This lesson maps all 49 components across those 7 categories so you can navigate the library by intent rather than by appearance.

UI Shell — the structural frame of every Carbon app

The UI Shell is the skeleton that every other component lives inside. It consists of three structural pieces: the Header, the Left Panel (also called SideNav), and the Right Panel. Together they define the persistent chrome of your application — the parts of the interface that remain stable while content in the main body changes. The UI Shell is not optional decoration; it is the scaffolding from which the rest of the interface hangs.

The Header occupies the top of the application and carries global-level elements: the IBM product logo or wordmark, the product name, global navigation links, and utility icons such as search, notifications, and the user profile menu. Its position at the top of the visual hierarchy signals to users that it controls things that span the entire application rather than a single screen. Carbon's Header is designed to collapse gracefully on smaller viewports, ensuring the global navigation remains accessible without consuming precious screen space on mobile devices.

The Left Panel (SideNav) provides the primary navigation structure within a product. Where the Header holds global controls, the SideNav holds product-level navigation — the tree of sections, features, and settings that a user navigates within one application. The Right Panel is a more specialized structural element, typically used for contextual panels, filters, or supplementary information that relates to the content in the main area. When you are starting the architecture of a new Carbon application, these three UI Shell components are the first decisions you make — they establish the spatial grammar that every subsequent component decision will relate to.

Inputs & Controls and Navigation — interacting with the app

With the structural frame established, the next two categories — Inputs & Controls and Navigation — cover everything that lets a user act on the application. They are the tools of agency: the components a user reaches for to give the system information, to move through it, and to invoke operations upon it.

Inputs & Controls is Carbon's largest category, with 13 components. It encompasses every mechanism by which a user provides data or makes a choice. Text Input and Number Input capture free-form typed values. Checkbox, Radio Button, Toggle, and Select handle constrained choices with varying degrees of mutual exclusivity. Dropdown handles longer lists of options in a compact form. Date Picker provides structured date entry with calendar assistance. Search enables free-text query entry. File Uploader handles binary content submission. Slider captures numeric values along a range. Accordion is somewhat atypical in this category — it is a disclosure pattern that expands and collapses sections of content, and Carbon groups it here because it often wraps form fields. Together these components cover virtually every data-entry scenario a product team is likely to encounter. The critical discipline is matching the right input to the nature of the data: a Toggle for binary on/off state, a Radio Button group when exactly one option must be chosen from a small set, a Dropdown when the choice set is longer than about five items.

Navigation covers how users move through the application and understand where they are. Breadcrumb provides wayfinding context in hierarchically structured content. Tabs organize related content into parallel views that the user can switch between without leaving the page. Pagination divides large datasets into digestible pages. Progress Indicator shows a user's position in a multi-step workflow. Tree View exposes hierarchical data structures — like file systems or organizational charts — as navigable trees. Menu, Menu Buttons, and Overflow Menu all handle command invocation: ways to expose actions without dedicating permanent screen space to every possible operation. Choosing among these navigation components requires understanding how your content is structured: Tabs for parallel alternatives, Breadcrumb for deep hierarchies, Pagination for long lists, Progress Indicator for sequential processes.

Data Display and Feedback & Status — showing results and progress

If Inputs and Navigation are about what users do to the application, Data Display and Feedback & Status are about what the application communicates back to users. These categories close the loop in the user-interface dialogue.

Data Display contains 6 components for presenting structured information. Data Table is Carbon's most powerful and configurable data presentation component — it supports sorting, filtering, batch actions, inline editing, and pagination, making it the right choice whenever users need to work with a set of structured records rather than just view them. Structured List handles simpler read-only key-value information with less overhead than a full Data Table. Contained List and List handle simpler enumerations. Tag communicates categorical labels on items — status, type, category — in a compact visual form that works well alongside other content. Tile is a versatile card-like container that groups related content into a visually bounded unit, particularly useful in dashboards and content feeds. The distinction between these components often comes down to structure and interactivity: Data Table when users need to act on rows, Structured List for read-only tabular data, Tile for mixed content blocks.

Feedback & Status addresses one of the most critical responsibilities in UI design: telling users what the system is doing and what has happened. Loading and Inline Loading communicate that an operation is in progress — the difference between them is scope. Loading is a full-screen or prominent spinner for operations that block the entire interface. Inline Loading is a subtle indicator for operations contained within a single element, like a button that is waiting for a server response. Progress Bar communicates how far along a known-length operation is, giving users a concrete sense of elapsed and remaining time. Notification communicates system-level events — successes, warnings, errors, and informational messages — across four distinct severity levels. Getting Feedback & Status right is often the difference between an application that feels responsive and trustworthy and one that feels broken and opaque.

Overlays & Popovers and Content & Layout — contextual and supplementary elements

Overlays & Popovers covers the 4 components that float above the main page surface to deliver contextual content or require user decisions. Modal is the most disruptive — it blocks the entire background and demands user attention before the underlying application can be interacted with again. Use Modal when a decision genuinely requires the user's focused attention and cannot be deferred: confirming a destructive action, completing a focused data entry task, displaying a critical warning. Overusing Modal is one of the most common friction sources in application design; if the content does not require blocking the user, a less disruptive component is almost always the right choice.

Popover, Toggletip, and Tooltip are the lighter members of this category, all providing contextual information near a trigger element without blocking the page. The distinctions among them are subtle but important. Tooltip is non-interactive and appears on hover, making it suitable only for supplementary labels and definitions — never for interactive content. Toggletip appears on click and can contain more complex content. Popover is the most capable of the three, supporting rich interactive content within its floating panel. Choosing among them comes down to whether the content needs to be interactive (Popover), clickable-to-show (Toggletip), or purely informational on hover (Tooltip).

Content & Layout contains 5 components that handle supplementary and structural content within the main body of a page. Form wraps inputs and controls with semantic structure, layout, and validation messaging. Link provides accessible anchor behavior. Code Snippet displays code samples with appropriate monospace styling and copy-to-clipboard functionality. Content Switcher lets users toggle between two or three views of the same content area — similar to Tabs but for smaller, more compact switching contexts. AI Label is a distinctive Carbon component that identifies content generated by AI systems, giving users a consistent signal that they are reading AI-produced output. This category handles the content layer of a page: not the global chrome (UI Shell), not the data structures (Data Display), but the inline and supplementary elements that give meaning to the page's text and code.

Key Insight
Choose components by purpose, not by appearance. Every Carbon component belongs to a category that describes its role in the interface architecture. Before reaching for a component, ask what the interface needs to do at that moment — frame the page, collect user input, display data, communicate system state, surface contextual information — and let the answer point you to the right category. A component chosen because it "looks right" without asking what it is designed to do will almost always create problems downstream.
Common Mistake
Reinventing components that already exist. The most frequent anti-pattern teams encounter with Carbon is building a custom solution for a problem that one of the 49 components already solves. Custom tooltips that lack keyboard accessibility, ad hoc notification banners that miss error severity levels, hand-rolled data tables without sort or filter — these all represent duplicated effort and almost always ship with worse accessibility, keyboard behavior, and visual consistency than the Carbon equivalent. Before writing a custom component, spend ten minutes verifying that Carbon does not already provide one that fits. It usually does.
