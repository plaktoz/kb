How Carbon's Theming System Works

Carbon's theming system is built on a single core principle: tokens are the only stable surface you should touch when customizing appearance. A token is a named design decision — background, text-primary, interactive — that maps to a specific value in a given theme. Change the token once, and the new value propagates automatically across every component that references it. This is the correct, supported way to customize Carbon.

The alternative — writing raw CSS overrides that target component class names directly — is explicitly discouraged. Component class names are implementation details, not a public API. They can change between Carbon releases without notice. A product that relies on direct CSS overrides will regularly break during upgrades, requiring manual patching of every affected selector. Token overrides, by contrast, are guaranteed to remain semantically stable: the token background will always control the surface color, regardless of what internal class structure changes underneath.

Tokens also nest internally. For example, the $interactive token references $blue-60 under the hood. When you override a high-level token like $interactive, you do not need to know or touch the low-level palette value it resolves to. This layered architecture keeps customization ergonomic while preserving the system's coherence. The full list of available tokens is published in the @carbon/themes package on GitHub, organized into four categories: Color, Spacing, Typography, and Global (which covers border widths, layer usage, and similar structural properties).

Using the Four Built-In Themes

Carbon ships with four built-in themes out of the box: White (the default light theme), Gray 10 (a softer light variant), Gray 90 (a dark theme), and Gray 100 (the darkest variant, suited to high-contrast dark interfaces). These four themes cover the most common light and dark mode use cases without requiring any custom token work. Each theme is a complete, coherent token set — switching between them changes not just background colors but the entire cascade of interactive, text, border, and layer tokens simultaneously.

To switch from the default White theme to a different built-in theme, you use the Sass @use ... with syntax at the top of your stylesheet. The following example applies the Gray 100 dark theme across your entire application: 

@use '@carbon/react/scss/theme' with ($theme: themes.$g100);

This single declaration is all that is required to switch the entire token set. No component code changes are needed. Because every Carbon component reads from the same token layer, the theme change flows through automatically. The four available theme variables from the themes namespace are $white, $g10, $g90, and $g100. White is the default, so you only need to declare it explicitly if you are overriding a parent stylesheet that has set a different theme.

Creating Custom Themes with Sass Token Overrides

When none of the four built-in themes fit your product's brand, you can create a custom theme by providing a token map to the same $theme parameter. You only need to specify the tokens you want to override — all other tokens continue to resolve to the values defined in the base theme you are building on top of. This makes partial overrides safe and minimal: you change what matters for your brand, and Carbon handles the rest.

The following example creates a custom theme that overrides the background surface, the primary text color, and introduces a product-specific custom token: 

@use '@carbon/react/scss/theme' with (
  $theme: (
    background: #e2e2e2,
    text-primary: #1a1a1a,
    custom-token-01: #000000
  )
);

A few details are worth understanding here. First, the with keyword is a Sass module configuration feature introduced in Sass modules (the @use system). It lets you pass named configuration values to a module at the point it is loaded — you can only do this once, at the top of the first file that imports the module. This is different from overriding a variable after the fact, and it is how Carbon intentionally exposes its configuration surface. Second, custom tokens like custom-token-01 can be defined in the same map — they become part of your product's token vocabulary and can be used alongside Carbon's built-in tokens in your own component styles. Third, the four token categories — Color, Spacing, Typography, and Global — cover everything Carbon controls. The complete token reference in the @carbon/themes package on GitHub documents every token name, its semantic meaning, and the value it resolves to in each built-in theme.

IBM Voice: What Makes It Distinct

IBM's content voice is defined by a set of characteristics that distinguish it from both bland corporate language and overly casual marketing copy. The core positioning is: persuasive, not poetic. IBM products communicate with data, logic, and directness rather than with metaphor or emotional appeal. The voice is confident without boasting, simple without being condescending, and always oriented toward outcomes the user cares about rather than features the product wants to advertise.

IBM's content guidelines describe the voice as treating users as intellectual equals. This has a practical implication: you do not explain obvious things at length, you do not hedge every statement with qualifications, and you do not pad content with filler phrases. If a task requires three steps, you list three steps clearly. If an error has a specific cause, you name the cause. Specificity is a form of respect. Vagueness — "something went wrong," "an error occurred," "please try again" — forces the user to do investigative work the product should have done for them.

The distinction between voice and tone is important here. Voice is the persistent character of the product: clear, fact-focused, direct, and confident. It does not change from screen to screen. Tone adapts to context. A voice can be consistently IBM while the tone in an error message is terse and the tone in an onboarding welcome screen is warmer. The voice is a constant; the tone is a setting you adjust for the emotional register of each moment.

Tone Adaptation by Context

Understanding tone adaptation requires thinking about what users are experiencing at each moment. Error messages arrive when something has gone wrong — the user is typically frustrated or confused. The correct tonal response is economical and direct, often phrase-based rather than full sentences. "File not found. Check the path and try again." is better than "We're sorry, but it seems like the file you were looking for could not be located at this time." The shorter version respects the user's time and gets them back on track faster. It is not cold — it is efficient.

Onboarding flows have a different emotional context. The user is new, possibly uncertain, and deciding whether this product is worth their investment of time. Here, the tone can be warmer and use fuller sentences with friendly explanations. "Welcome to the dashboard. This is where you'll find all your active projects." gives a first-time user spatial orientation without being patronizing. It is still the IBM voice — clear, direct, factual — but the tone is open and welcoming rather than terse.

IBM's content guidelines frame this as a "conversation" between the product and the user — a dialogue that works alongside visuals and interactions rather than competing with them. Good content writing does not comment on what the interface already shows visually. It adds context, guides action, or acknowledges what just happened. A button labeled "Save file" does not need a tooltip explaining "clicking this button saves the current file" if the action is already clear from context. Words earn their place by doing work that visuals and interactions cannot do on their own.

UI Label Rules in Practice

Carbon's content guidelines specify a precise format for button labels, menu items, and form actions: the {verb} + {noun} pattern. The verb states the action; the noun names the object being acted on. "Save file." "Delete record." "Upload document." "Export report." This format is unambiguous and scannable. A user glancing at a toolbar does not need to read full sentences — they need to know what will happen and what it will happen to, in that order.

Capitalization follows sentence case: only the first word is capitalized. "Get started" not "Get Started". "Upload document" not "Upload Document". Title case — capitalizing every significant word — is a common mistake that makes interfaces feel more formal than IBM's voice intends, and it introduces inconsistency as teams disagree about which words count as "significant." Sentence case is simpler, more consistent, and aligns with how users read natural language.

A few additional label rules round out the system. Text should never be truncated with an ellipsis — if a label does not fit, the container should expand or the label should be rewritten. Overflow text wraps. Text within buttons and form labels is left-aligned, not centered or right-aligned. All-caps labels — a legacy pattern from early UI design — are prohibited. They are harder to read and convey an unintentionally aggressive or shouting tone that conflicts with IBM's conversational voice. When accessibility intersects with content, the rules compound: form inputs require either a visible label or an aria-label, and error messages must tell users both what happened and what to do next — not just that an error occurred.

Key insight

Always use token overrides to customize Carbon — never override component CSS directly. Token overrides propagate changes coherently across all components that reference the token, keep your customizations upgrade-safe, and work with Carbon's theming architecture as intended. Direct CSS overrides target implementation details that can change at any Carbon release, breaking your product silently during upgrades.

Warning

Overriding component styles directly with raw CSS — for example, targeting .cds--btn--primary to change a button's background color — bypasses the token system entirely. This approach breaks upgrade safety because Carbon component class names are internal implementation details, not a stable public API. After a Carbon minor version bump, those selectors may no longer exist or may no longer target the element you expect. It also breaks system coherence: a direct override applies only to the specific element you targeted, while every other component that shares the same token remains unchanged, creating visual inconsistency across your UI.
