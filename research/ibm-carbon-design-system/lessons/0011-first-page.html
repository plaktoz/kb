Anatomy of a Carbon app: Shell, Theme, Content

A complete Carbon application is built from three cooperating structural layers. The UI Shell provides the persistent navigation frame — the top header bar, optional side navigation panel, and global action bar. The Theme wrapper establishes a design token context so that every Carbon component inside it reads its colors, background values, and interactive states from the same coherent token set. The Content component wraps the main page body, adding the standard spacing and background that Carbon's design guidelines specify for content areas.

Understanding how these three layers compose is the prerequisite for building any Carbon page. They are not optional refinements — they are the structural skeleton. Without the Shell, users have no way to navigate between sections of your application. Without the Theme wrapper, Carbon components fall back to their default token values, which may not match the palette the rest of your UI expects. Without Content, the main body of the page will lack the standard padding and background that Carbon's visual language prescribes.

In practice, you will typically create a providers.js (or equivalent layout file) that composes all three layers in a single place. This makes it easy to apply a consistent Shell and theme across every page of your application without duplicating the wrapper structure in each route. The Shell lives inside the Theme so it inherits the correct token values; the Content wrapper sits outside the Theme so it can use its own background token. This asymmetry is intentional and worth understanding before you write your first layout file.

Building the TutorialHeader with UI Shell components

Carbon's UI Shell is composed from a family of focused, composable React components, all exported from @carbon/react. The outermost wrapper is HeaderContainer, which manages the open/closed state of the side navigation panel and passes it down through a render prop. Inside the render prop, you place the Header element, which renders the top bar and accepts an aria-label that identifies the application to assistive technologies.

Within Header, you place HeaderName for the branded application title (the IBM product name prefix goes in the prefix prop), HeaderNavigation for the primary link set, HeaderGlobalBar for icon actions such as notifications and user settings, and SideNav for the collapsible panel that mirrors the top navigation on small screens. Each of these components has a clear, single responsibility, and together they assemble a complete, accessible navigation shell with almost no custom CSS required.

Icons in the global bar come from the separate @carbon/icons-react package. The import path changed in recent Carbon versions: rather than importing from a standalone package, you import icons from @carbon/react/icons. Each icon component accepts a size prop (commonly 20) that sets its SVG dimensions. Wrapping each icon in a HeaderGlobalAction component provides the correct button affordance, keyboard focus ring, and hover state — you should never render a raw icon as a bare clickable element.

One important implementation detail: use Next.js Link inside HeaderMenuItem and SideNavMenuItem rather than plain anchor tags. Carbon's shell components handle the visual styling, but the routing behavior — including client-side navigation without a full page reload — comes from the framework's Link component. Mixing raw anchors with Next.js routing causes unnecessary full-page reloads that degrade perceived performance. 

import {
  Header,
  HeaderContainer,
  HeaderName,
  HeaderNavigation,
  HeaderMenuItem,
  HeaderGlobalBar,
  HeaderGlobalAction,
  SideNav,
  SideNavItems,
  SideNavMenuItem,
} from '@carbon/react';
import { Switcher, Notification, UserAvatar } from '@carbon/react/icons';
import Link from 'next/link';

const TutorialHeader = () => (
  <HeaderContainer
    render={({ isSideNavExpanded, onClickSideNavExpand }) => (
      <Header aria-label="Carbon Tutorial">
        <HeaderName href="/" prefix="IBM">
          Carbon Tutorial
        </HeaderName>
        <HeaderNavigation aria-label="Carbon Tutorial">
          <HeaderMenuItem>
            <Link href="/repos">Repositories</Link>
          </HeaderMenuItem>
        </HeaderNavigation>
        <HeaderGlobalBar>
          <HeaderGlobalAction aria-label="Notifications">
            <Notification size={20} />
          </HeaderGlobalAction>
          <HeaderGlobalAction aria-label="User Avatar">
            <UserAvatar size={20} />
          </HeaderGlobalAction>
          <HeaderGlobalAction aria-label="App Switcher">
            <Switcher size={20} />
          </HeaderGlobalAction>
        </HeaderGlobalBar>
        <SideNav aria-label="Side navigation" expanded={isSideNavExpanded}>
          <SideNavItems>
            <SideNavMenuItem>
              <Link href="/repos">Repositories</Link>
            </SideNavMenuItem>
          </SideNavItems>
        </SideNav>
      </Header>
    )}
  />
);

The providers.js theming wrapper

In a Next.js application using Carbon, it is common practice to centralize the theming and shell composition in a single file — typically named providers.js or placed in the root layout. This file imports Theme and Content from @carbon/react alongside your TutorialHeader component, then wraps them around the application's child content.

The Theme component accepts a theme prop whose value is one of Carbon's four built-in themes: white, g10 (light gray), g90 (dark gray), or g100 (near-black). Wrapping TutorialHeader inside <Theme theme="g100"> applies the near-black palette to the shell while leaving the page body free to use a different theme. This layered approach is what allows Carbon products to display a dark top bar with a light content area — a common pattern in IBM enterprise applications.

The Content component is placed outside the Theme wrapper in the example below. This is deliberate: Content should inherit the ambient theme of the page body rather than the shell's dark theme. It renders a <main> element with Carbon's standard content padding and background, giving the page body its structural foundation. All route-level page components passed as children will be rendered inside this Content wrapper. 

import { Theme, Content } from '@carbon/react';
import TutorialHeader from '@/components/TutorialHeader/TutorialHeader';

export default function Providers({ children }) {
  return (
    <>
      <Theme theme="g100">
        <TutorialHeader />
      </Theme>
      <Content>{children}</Content>
    </>
  );
}

Responsive layout with Grid and Column

With the Shell and Theme in place, the next step is building the page content itself. Carbon's layout system is built around two React components: <Grid> and <Column>. The Grid establishes a row container governed by Carbon's 2x grid rules — 4 columns at small (320px), 8 at medium (672px), and 16 at large (1056px). Each Column inside the grid declares how many columns it should span at each breakpoint using the sm, md, and lg props.

The most important pattern to memorize is full-width: lg={16} md={8} sm={4}. These values match the maximum column count at each breakpoint, so the column spans the entire available width regardless of viewport size. This is the correct choice for hero banners, full-bleed section backgrounds, and any container that should always occupy the full page width. Pairing this with the fullWidth prop on Grid additionally removes the outer margin, allowing content to reach the viewport edges.

For two-column layouts, split the columns evenly at each breakpoint: each column gets lg={8} md={4} sm={4}. At large, each column occupies half of the 16-column grid. At medium, each column occupies half of the 8-column grid. At small, each column uses all 4 available columns — meaning both columns stack vertically, filling the full width on mobile screens. This stacking behavior is automatic and is the correct pattern for mobile-first responsive design.

For more complex compositions, the Column component also supports an object syntax for individual breakpoints, allowing you to specify both a span and an offset in one expression. An offset shifts the column to the right by the specified number of columns, leaving empty space before the content. This is useful for centering a narrower column within a wider grid without needing extra wrapper elements or CSS margin hacks. 

import { Grid, Column, Breadcrumb, BreadcrumbItem, Button,
  Tabs, Tab, TabList, TabPanels, TabPanel } from '@carbon/react';

// Full width at all breakpoints — hero banner pattern
<Grid className="landing-page" fullWidth>
  <Column lg={16} md={8} sm={4} className="landing-page__banner">
    {/* hero content */}
  </Column>
</Grid>

// Two equal columns at large, stacked at small
<Grid>
  <Column lg={8} md={4} sm={4}>Left</Column>
  <Column lg={8} md={4} sm={4}>Right</Column>
</Grid>

// With offset at large — center a column within the grid
<Column md={4} lg={{ span: 8, offset: 7 }} sm={4}>
  Offset content
</Column>

Styling with Sass tokens

Carbon components are styled internally with design tokens, but your custom page-level CSS should also draw from the same token vocabulary whenever possible. Carbon ships its Sass variables through a set of namespaced modules that you import with @use. The key modules are spacing, type, breakpoint, and theme. Importing them makes Carbon's full token scale available to your stylesheet as Sass variables, ensuring your custom styles stay consistent with the system.

The spacing tokens follow Carbon's 8px mini-unit scale, prefixed with $spacing- and numbered from 01 (4px) up through 13 (96px). A common landing page pattern uses $spacing-05 (16px) for top padding and $spacing-06 (24px) for side padding on banner sections. The theme tokens — such as $layer-01 — give you access to Carbon's semantic color system so your background colors automatically adapt when users switch between light and dark themes.

One practical advantage of using Sass tokens over raw pixel values is that your styles automatically stay in sync when Carbon updates its token definitions. If IBM revises the spacing scale or adjusts a background color in a future Carbon release, your stylesheet picks up the change without any modifications to your own code. This is the same benefit that Carbon component consumers receive — tokens decouple intent from specific values. 

@use '@carbon/react/scss/spacing' as *;
@use '@carbon/react/scss/type' as *;
@use '@carbon/react/scss/breakpoint' as *;
@use '@carbon/react/scss/theme' as *;

.landing-page__banner {
  padding-top: $spacing-05;
  padding-bottom: $spacing-07 * 4;
  padding-left: $spacing-06;
}

.landing-page-background {
  background-color: $layer-01;
}

Accessibility: ARIA labels for duplicate nav elements

A subtle but important accessibility requirement arises when you place multiple navigation landmarks on the same page. In HTML, both <nav> and elements with role="navigation" are landmark regions — assistive technology users can jump between landmarks quickly using keyboard shortcuts or rotor menus. When two or more navigation landmarks exist on the same page, they must each carry a distinct aria-label so screen reader users can tell them apart and navigate to the right one.

In a typical Carbon landing page, this situation arises because two different components both render <nav> elements. The Breadcrumb component renders a <nav> for the breadcrumb trail at the top of the page content. The TabList component inside a Tabs group also renders a <nav> element. Without distinct labels, a screen reader would announce both as simply "navigation," leaving the user unable to distinguish between them.

The fix is straightforward: pass a unique, descriptive aria-label to each component that will render a navigation landmark. Carbon's Breadcrumb component passes its aria-label directly to its internal <nav> element. The TabList component similarly forwards aria-label to its container. The labels you choose should describe the purpose of each navigation region — "Page navigation" for the breadcrumb and "Tab navigation" for the tab list are clear and unambiguous choices. 

// Breadcrumb — renders a <nav> element, needs a unique aria-label
<Breadcrumb noTrailingSlash aria-label="Page navigation">
  <BreadcrumbItem>
    <a href="/">Getting started</a>
  </BreadcrumbItem>
</Breadcrumb>

// TabList — also renders a <nav> element, needs a different aria-label
<TabList className="tabs-group" aria-label="Tab navigation">
  <Tab>About</Tab>
  <Tab>Design</Tab>
  <Tab>Develop</Tab>
</TabList>
Key Insight

The structural trinity of a Carbon application — Shell, Theme, Content — should be the first thing you set up before building any page-level layout. The Shell (HeaderContainer and its children) provides navigation. The Theme wrapper establishes the token context that gives every Carbon component inside it consistent colors and interactive states. The Content wrapper frames the page body with the correct padding and background. Once this skeleton is in place, adding pages becomes a matter of composing Grid and Column inside Content — the structural decisions are already made. Trying to add theming or the Shell after the fact is significantly harder than wiring them up correctly at the start.

Common Pitfall

Forgetting to add aria-label attributes when multiple navigation landmarks appear on the same page is one of the most common accessibility oversights in Carbon applications. It is easy to overlook because the visual result looks identical — the labels exist only in the accessibility tree. Components like Breadcrumb and TabList both render <nav> elements, and without distinct labels, screen readers announce them identically. Before shipping a page, run an automated accessibility scan (such as axe or IBM Equal Access Checker) and verify that every landmark region has a label that meaningfully distinguishes it from all others on the same page.
