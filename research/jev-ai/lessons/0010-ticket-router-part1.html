Build the Support Ticket Router — Part 1: Classify

Module 4 Lesson 10 of 12 ~45 min
Learning objective After this lesson, you will have a working support ticket classifier that calls system_one with all three output types — Choice, Score, and Noul — in a single request, and you will be able to read the structured response to drive routing decisions based on confidence.
Primary source
typesafe-sdk-python — Typesafe AI on GitHub

Step 1 — Sign Up & Get Your API Key

Before writing any code, you need a Typesafe API key. The key is the only credential the SDK needs; everything else is configured in code.

  1. Go to console.typesafe.ai and create an account.
  2. Navigate to /keys in the console and generate a new key.
  3. Export it as an environment variable so the SDK can pick it up automatically: 
    export TYPESAFE_API_KEY="your-key-here"
  4. To make this permanent across terminal sessions, add the same line to your ~/.zshrc (or ~/.bashrc) and reload: 
    echo 'export TYPESAFE_API_KEY="your-key-here"' >> ~/.zshrc
source ~/.zshrc
Never paste your API key directly into source code or commit it to a repository. The SDK reads TYPESAFE_API_KEY from the environment automatically — you only need to set the variable once and the key stays out of your codebase entirely.

Step 2 — Install the SDK

The Typesafe SDK requires Python 3.10 or later. Install it with pip: 

pip install typesafe-sdk

Verify the install by importing the three types you will use in this lesson: 

python -c "from typesafe_sdk import Choice, Score, Noul; print('OK')"

If you see OK printed, you are ready to build the classifier.

Step 3 — The Complete Classifier Code

Create a file called router.py and paste in the following. This is the complete, working classifier — no placeholders, no stubs. 

import os
from typesafe_sdk import Choice, Score, Noul, TypeSafeClient

TICKETS = [
    "I was charged twice for my subscription last month.",
    "The app crashes when I try to upload a file larger than 10MB.",
    "How do I change my username?",
    "I need to cancel my account immediately, this is urgent!",
]

with TypeSafeClient() as client:
    for ticket in TICKETS:
        response = client.system_one(
            state={"message": ticket},
            questions={
                "department": Choice(
                    instructions="Which department should handle this ticket?",
                    criteria={
                        "billing": "Payment issues, charges, refunds, subscriptions",
                        "technical": "Bugs, crashes, errors, performance problems",
                        "account": "Account settings, passwords, cancellations",
                        "general": "General questions and inquiries",
                    },
                ),
                "urgency": Score(
                    instructions="How urgent is this ticket? (0 = not urgent, 5 = critical)",
                    criteria=["0: routine question", "3: frustrated customer", "5: data loss or billing emergency"],
                ),
                "is_vip": Noul(
                    instructions="Does this ticket suggest a high-value or long-term customer?",
                ),
            },
        )

        dept = response.answers["department"]
        urgency = response.answers["urgency"]

        if dept.confidence > 0.8:
            action = f"AUTO-ROUTE → {dept.choice.upper()}"
        else:
            action = f"HUMAN REVIEW (confidence: {dept.confidence:.2f})"

        print(f"\nTicket: {ticket[:60]}...")
        print(f"  Department : {dept.choice} (confidence: {dept.confidence:.2f})")
        print(f"  Urgency    : {urgency.score:.1f}/5")
        print(f"  VIP signal : {response.answers['is_vip'].noul:.2f}")
        print(f"  Action     : {action}")

Run it with:

python router.py

Step 4 — Understanding the Code

State design

The state argument is a plain Python dict passed to system_one. In this example it holds a single key, "message", but it can hold anything — user metadata, account tier, previous ticket history. Packing everything into one dict means Jev receives the full context in a single structured object, with no need for long prose preambles in the instructions.

Question design

The questions dict defines three independent outputs in one call:

  • Choice ("department") — asks Jev to select one key from a labelled dict of options. Each key maps to a short description that provides grounding for the decision.
  • Score ("urgency") — asks Jev to return a numeric value, calibrated by the criteria list. The anchor examples (0, 3, 5) give the model a concrete scale to reason against.
  • Noul ("is_vip") — returns a float between 0 and 1. It is the simplest output type: no discrete choices, no numeric scale, just a continuous signal representing how strongly the answer is “yes.”

All three questions are resolved in a single network call. There is no need to call the API once per output type.

Reading answers

Answers come back under response.answers, keyed by the same names you used in questions. For a Choice answer, the two fields you will use most are .choice (the selected key as a string) and .confidence (a float from 0 to 1). For a Score answer, the value is at .score. For a Noul answer, the value is at .noul.

Confidence check

The line if dept.confidence > 0.8 is the routing gate. When Jev is highly confident about the department, the ticket flows straight to that team without human involvement. When confidence falls below the threshold, the ticket is flagged for human review rather than silently misrouted. This single check converts a classification result into an actionable, auditable decision.

Pass structured JSON to state= so Jev has all context in one object. A dict is easier to extend later than a long freeform instructions string — add fields like "account_age" or "plan_tier" without rewriting your question definitions.

What to Expect

When you run python router.py against the four bundled tickets, you should see output that looks roughly like this: 

Ticket: I was charged twice for my subscription last month....
  Department : billing (confidence: 0.97)
  Urgency    : 4.0/5
  VIP signal : 0.31
  Action     : AUTO-ROUTE → BILLING

Ticket: The app crashes when I try to upload a file larger than...
  Department : technical (confidence: 0.95)
  Urgency    : 3.2/5
  VIP signal : 0.18
  Action     : AUTO-ROUTE → TECHNICAL

Ticket: How do I change my username?...
  Department : account (confidence: 0.92)
  Urgency    : 0.8/5
  VIP signal : 0.09
  Action     : AUTO-ROUTE → ACCOUNT

Ticket: I need to cancel my account immediately, this is urgent!...
  Department : account (confidence: 0.88)
  Urgency    : 4.5/5

Exact numbers will vary between runs — Jev’s outputs are not perfectly deterministic — but the department assignments and relative urgency scores should be consistent. A ticket that is genuinely ambiguous may drop below the 0.8 threshold and trigger the HUMAN REVIEW branch instead of auto-routing.

Lesson summary
  • The Typesafe SDK is installed with pip install typesafe-sdk; your API key is read from the TYPESAFE_API_KEY environment variable automatically.
  • system_one accepts a state dict and a questions dict, resolving all output types — Choice, Score, and Noul — in a single API call.
  • Packing context into state= as structured JSON keeps question definitions clean and makes the schema easy to extend without rewriting instructions.
  • Each answer type exposes a purpose-built attribute: .choice and .confidence for Choice, .score for Score, and .noul for Noul.
  • A single confidence threshold (dept.confidence > 0.8) converts the classification result into an auto-route or human-review decision without any additional logic.
Stuck or curious? Ask: “What happens if I lower the confidence threshold to 0.6?” or “How would I add a fourth output type to capture customer sentiment?” — both questions set up exactly what Part 2 builds on.
