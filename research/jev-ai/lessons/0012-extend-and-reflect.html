Four Ways to Extend Your Router

Your ticket router from Lessons 10 and 11 is already a working System One pipeline. The four extensions below each add a distinct capability. Pick at least one and implement it — the skill exercise at the bottom asks you to write a short retrospective on what you learned.

1. JSON Output

Instead of printing results to the terminal, accumulate them into a list and write a structured JSON file. This makes your router output consumable by downstream services without any parsing.

import json

results = []

# Inside the loop, replace the print statement:
results.append({
    "ticket": ticket,
    "department": dept.choice,
    "confidence": dept.confidence,
    "urgency": response.answers["urgency"].score,
    "action": action,
})

with open("results.json", "w") as f:
    json.dump(results, f, indent=2)

The resulting file can be read directly into a database, a dashboard, or a downstream routing queue — the router is now a service component, not just a script.

2. stdin Input

Accept a single ticket from the command line so you can test routing decisions without editing the source file. This turns the router into an interactive tool.

import sys

ticket = sys.argv[1] if len(sys.argv) > 1 else input("Enter ticket: ")

Run it as python router.py "My payment failed twice" to get an instant routing decision, or run with no arguments to be prompted interactively.

3. Escalation Logic

Combine the urgency score and the department confidence to trigger automatic escalation. This is a concrete example of decision-gating: rather than acting on the raw model output, you build a rule that fires when confidence and urgency pull in opposite directions.

urgency_score = response.answers["urgency"].score

if urgency_score >= 4 and dept.confidence < 0.7:
    action = "🚨 ESCALATE — high urgency, uncertain routing"

This pattern — act confidently above the threshold, escalate below it — is the core idiom for integrating Jev into production workflows where human oversight is still required.

4. LLM Comparison with system-one-adapter-python

The system-one-adapter-python package lets you run the exact same router code against a frontier LLM instead of Jev by swapping a single import. This is the cleanest way to benchmark accuracy and cost side by side.

pip install system-one-adapter-python
# Change this one line to route through an LLM instead of Jev:
from system_one_adapter import TypeSafeClient  # instead of typesafe_sdk

Everything else — your questions, your response parsing, your escalation logic — stays identical. Run both versions on the same batch of tickets and compare the outputs. The accuracy difference (and cost difference) is your empirical trade-off data.

What Jev Is Good At vs. Bad At

Jev’s design makes it exceptionally fast and cheap for a well-defined subset of AI tasks. Outside that subset, it is the wrong tool. The table below is a practical decision boundary.

Well-suited for Jev Not suited for Jev
Classification and routing Reasoning and multi-step planning
Scoring and confidence ranking Code generation
Extracting structured values from unstructured text Explanations and justifications
AI-powered “smart if-statements” Free-form text generation
Map-reduce over large datasets Creative tasks
Real-time sub-100ms applications Open-ended dialogue
LLM guardrailing and judging Any task requiring a natural-language reply

Two real-world demos illustrate the extremes of Jev’s range. The Doom bot runs at roughly 10 queries per second against live game state — continuously classifying enemy positions, health levels, and movement choices — at an operating cost of approximately $7 per hour. The Wikiracing demo uses high-cardinality selection to navigate Wikipedia by choosing the most relevant link at each page, demonstrating that Jev handles large choice sets efficiently, even when the answer space is wide-open.

When to Choose Jev Over an LLM

Use this decision guide before reaching for either tool on a new task.

Choose Jev when all of the following are true:

  • The output is a typed value — a category, a score, a boolean, a ranked choice — not a paragraph of text.
  • Calibrated confidence matters: you need to know not just what the answer is, but how sure the model is.
  • The task will run at high volume, in real time, or inside a tight cost budget.
  • The decision is well-defined enough to write a clear question schema for.

Choose an LLM when any of the following is true:

  • The output must be a natural-language explanation, a code snippet, or creative content.
  • The task requires chaining multiple reasoning steps before arriving at a conclusion.
  • The question schema cannot be specified in advance because the output shape varies per input.

Use both together when: an LLM generates an answer that then passes through a Jev guardrail — e.g. the LLM drafts a support reply and Jev scores it for policy compliance before it is sent. This is the most powerful hybrid pattern: System Two reasoning paired with System One gating.

Jevons Paradox in practice: Do not think of Jev as replacing LLM costs. Think of it as enabling automation use cases that were previously too expensive to exist. The Doom bot, the Wikiracing navigator, inline guardrailing at every token — none of these were economically viable at LLM pricing. A 444× cost reduction does not merely save money; it expands the surface of what is worth automating at all.
Always validate Jev’s accuracy on your specific use case before deploying. The accuracy/cost trade-off is real: Jev is not a lossless substitute for an LLM on structured tasks — it trades some accuracy headroom for massive speed and cost gains. Use system-one-adapter-python to run a direct comparison on your own data before committing to either tool in production.

Lesson summary
  • You built a full System One pipeline end to end: from understanding the reliability problem in Lesson 1, through the three primitives, to a working multi-question ticket router with confidence-gated escalation.
  • Jev excels at classification, scoring, structured extraction, and real-time decision-gating — and is the wrong tool for reasoning, code generation, or any task requiring natural-language output.
  • Speculative Fan-Out lets you add extra questions to an existing call at near-zero marginal cost, because the parallel sampler answers all questions in a single query.
  • system-one-adapter-python lets you swap Jev for a frontier LLM by changing one import line, making empirical accuracy benchmarking straightforward.
