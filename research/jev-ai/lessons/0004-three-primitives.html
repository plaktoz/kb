The Three Primitives — Choice, Score, Noul

Module 2 — The Jev API Lesson 4 of 12 ~15 min

Learning objective Understand the three question types the Jev API supports — Choice, Score, and Noul — and learn how to design atomic, well-scoped questions that take full advantage of parallel, isolated evaluation.

Meet the Three Primitives

Every call to Jev is built from three primitives. Each one represents a different shape of judgment: selecting from a list, rating on a scale, or making a binary determination. Together they cover the vast majority of classification, routing, and scoring decisions found in production pipelines.

Type Returns Includes Confidence? Best for
Choice Chosen label, probabilities per option Yes Routing, classification, category selection
Score Numeric rating, probabilities per level Yes Urgency, severity, quality assessment
Noul Float between 0 and 1 No Binary signals, presence/absence checks

Choice supports cardinality up to 255 using a two-stage system: Jev first scores all candidates, then selects from the top scorers. Score takes a rubric — a plain-language description of what each numeric level means. Noul is the simplest primitive: it returns a 0–1 float expressing the probability that something is true. It is also the only primitive that does not return a confidence score alongside the answer.

Code Examples

Choice — select from a list

Pass a list of candidate labels. Jev returns the best match, the full probability distribution across all options, and a confidence score. 

result = jev.ask(
    state="User reported a billing error on account #1234.",
    questions=[
        Choice(
            "What is the primary issue category?",
            choices=["billing", "technical", "account-access", "other"]
        )
    ]
)

# result.answer        → "billing"
# result.probabilities → {"billing": 0.91, "technical": 0.05, ...}
# result.confidence    → 0.87

Score — rate against a rubric

Provide a rubric that anchors each numeric level in plain language. Jev returns the most likely score, the probability distribution across all levels, and a confidence score. 

result = jev.ask(
    state="I've been a customer for five years and this is unacceptable.",
    questions=[
        Score(
            "How urgent is this ticket?",
            rubric="1 = routine inquiry, 5 = severe account-impacting issue"
        )
    ]
)

# result.answer        → 4
# result.probabilities → {1: 0.02, 2: 0.05, 3: 0.12, 4: 0.64, 5: 0.17}
# result.confidence    → 0.71

Noul — true/false as a float

Noul asks a yes/no question and returns the probability of "yes" as a float between 0 and 1. Unlike Choice and Score, no confidence score is returned. 

result = jev.ask(
    state="I was charged twice and my account is locked.",
    questions=[
        Noul("Is the customer expressing frustration or urgency?")
    ]
)

# result.answer → 0.94  (0–1 float; no confidence score)

Mixing all three in one call

All three primitives can be combined in a single API call. Jev evaluates each question in parallel and in isolation against the same state — a key property explained in the next section. 

result = jev.ask(
    state="I was charged twice and my account is locked.",
    questions=[
        Choice(
            "What is the primary issue?",
            choices=["billing", "account-access", "technical", "other"]
        ),
        Score(
            "How urgent is this ticket?",
            rubric="1 = low priority, 5 = critical, needs immediate action"
        ),
        Noul("Is the customer expressing frustration or urgency?")
    ]
)

# results[0].answer → "billing"    (+ probabilities + confidence)
# results[1].answer → 4            (+ probabilities + confidence)
# results[2].answer → 0.94         (float only; no confidence)

Parallel Evaluation and Context-Rot

When you bundle multiple questions into one call, Jev evaluates each question independently and in parallel against the same state. The questions do not "see" each other — there is no cascading context where an earlier answer influences a later one.

This is the opposite of how LLMs handle multi-part prompts. With an LLM, every additional instruction or question extends the context window and can subtly degrade performance — a phenomenon sometimes called context-rot. With Jev, adding questions has minimal latency impact because each is scored independently rather than sequentially. The state itself can be a plain string, a JSON object, or an array, so you can pass in whatever structured context your questions require.

Design each question as an atomic gut-check: a judgment a knowledgeable person could make in seconds without weighing other factors. The more isolated and well-scoped each question is, the more reliable and interpretable the result — and the more freely you can add or remove questions without affecting the others.
Combining multiple concerns into one question — for example, "Is this ticket urgent and related to billing and from a high-value customer?" — undermines both accuracy and interpretability. Ask each concern separately, then combine the answers with logic in your own code. When priorities shift, change a coefficient in your code rather than rewriting a question.

Atomic Question Design in Practice

The discipline of atomic question design follows a single rule: one question, one concern. If you find yourself using "and", "or", or "given that" inside a question, that is a signal to decompose. Complex multi-factor decisions should be broken into separate questions whose answers are combined with your own logic.

For example, a question like "Is this ticket both urgent and from a premium subscriber?" mixes urgency with account tier. Split it into two:

  • Noul("Is this ticket urgent?")
  • Noul("Is the customer on a premium plan?")

Your code then combines the results — and because the combining logic lives in code rather than inside a question, changing priorities is a matter of updating a condition or coefficient, not reprompting and re-testing the model. This separation also makes the system easier to audit: you can inspect what Jev returned for each individual signal before understanding how the routing decision was made.

Lesson summary
  • Choice selects from a list of up to 255 options and returns the chosen label, a probability distribution, and a confidence score.
  • Score rates state against a plain-language rubric and returns a numeric answer, a probability distribution, and a confidence score.
  • Noul answers a yes/no question as a 0–1 float; it is the only primitive that does not return a confidence score.
  • All three can be mixed in one API call and are evaluated in parallel and in isolation — adding questions has minimal latency impact and avoids context-rot.
  • Design questions atomically: one concern per question. Combine answers with logic in your own code so that shifting priorities means changing a coefficient, not rewriting a question.
