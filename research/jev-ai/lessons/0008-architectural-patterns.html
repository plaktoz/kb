The Four Architectural Patterns

Module 3 ~20 min Lesson 8 of 12
Learning objective Identify and apply Jev's four architectural patterns — Speculative Fan-Out, Confidence-Gated Routing, Composite Scoring, and Intent Routing — and understand how each pattern composes atomic decisions into reliable system behavior.
Primary source
docs.typesafe.ai/patterns — TypeSafe AI documentation on the four production architectural patterns.

In the previous lesson you learned how confidence scores give you a second axis of information beyond the answer itself. This lesson shows you what to do with that axis. TypeSafe documents four named patterns that cover the most common ways engineers compose Jev's primitives into production systems.

The underlying principle is simple: rather than asking one large, multi-factor question, you decompose your decision into discrete atomic questions and let code determine how those answers combine. Complex system behavior emerges from simple, composable pieces.

1. Speculative Fan-Out

Core idea: Send all the questions you might need — including speculative ones you are not sure you will use — in a single API call. After the call returns, write code that decides which answers to act on based on what other answers say.

When to use it: Anytime the questions you need depend on preliminary answers, or when you want to save a round-trip by anticipating the next branch. It is especially useful when the cost of extra questions is marginal.

Benefits: Cost, Speed. Because all questions are evaluated in parallel and in isolation, extra questions cost almost nothing. You pay for context once and get all answers back together.

# Send the main question plus speculative follow-ups in one call
result = client.system_one(
    context=ticket,
    questions=[
        choice("category",    ["billing", "technical", "account"]),
        choice("billing_sub", ["duplicate_charge", "wrong_amount", "missing_refund"]),
        choice("tech_sub",    ["login", "performance", "data_loss"]),
    ]
)

# Code decides which sub-answer to use — not the model
if result.answers["category"].value == "billing":
    sub = result.answers["billing_sub"].value
elif result.answers["category"].value == "technical":
    sub = result.answers["tech_sub"].value
else:
    sub = None

The speculative questions (billing_sub, tech_sub) are always evaluated but only consulted when the routing answer makes them relevant. This avoids a second round-trip to ask the follow-up after you know the category.

2. Confidence-Gated Routing

Core idea: Use confidence as a second decision axis alongside the answer value. The answer tells you what; the confidence tells you how certain. Route high-confidence results to automated action and low-confidence results to a human.

When to use it: Anytime the cost of acting on a wrong answer is asymmetric — meaning some mistakes are more expensive than others. This is the safety pattern.

Benefits: Reliability, Safety. You get autonomous throughput on the easy cases while preserving human oversight for the genuinely ambiguous ones.

result = client.system_one(context=message, questions=[
    choice("intent", ["refund", "upgrade", "cancel", "other"]),
])

answer = result.answers["intent"]

if answer.confidence >= 0.92:
    # High confidence — act autonomously
    auto_route(answer.value)
elif answer.confidence >= 0.70:
    # Medium confidence — flag for review with suggested action
    queue_for_review(answer.value, answer.confidence)
else:
    # Low confidence — escalate without a suggestion
    escalate_to_human(message)

The thresholds are plain code constants. You tune them by running your system against a labeled sample and observing where errors concentrate — no prompt rewriting required.

3. Composite Scoring

Core idea: Ask several independent Score questions, each measuring a different dimension, then combine them in code with custom weights to produce a single decision score.

When to use it: Decisions that have multiple contributing factors that are genuinely independent — for example, urgency, sentiment, and complexity might each affect how you prioritize a ticket without being the same underlying thing.

Benefits: Cost, Reliability, Speed. Each dimension is a clean, focused question. The weights live in code as numeric coefficients, so adjusting priorities means changing a number — not rewriting a prompt.

result = client.system_one(
    context=ticket,
    questions=[
        score("urgency",    "How time-sensitive is this issue? (0 = none, 1 = critical)"),
        score("sentiment",  "How negative is the customer's tone? (0 = neutral, 1 = very negative)"),
        score("complexity", "How technically complex is this issue? (0 = simple, 1 = complex)"),
    ]
)

a = result.answers
priority_score = (
    0.5 * a["urgency"].value +
    0.3 * a["sentiment"].value +
    0.2 * a["complexity"].value
)

# Weights are a one-line change — no prompt edit needed
tier = "P1" if priority_score > 0.75 else "P2" if priority_score > 0.45 else "P3"

The key discipline here is that each Score question must measure exactly one thing. If you find yourself writing criteria that mention two factors, split it into two questions.

4. Intent Routing

Core idea: Classify the user's intent first, then direct traffic to the appropriate downstream handler. Each handler only deals with one intent type, making it simpler and easier to test.

When to use it: Almost always — this is the most common pattern and a natural starting point for any new Jev-based system. It maps directly onto the routing tables most engineers already think in.

Benefits: Cost, Speed. Handlers stay simple because they receive pre-classified input. The routing question is cheap and fast.

result = client.system_one(
    context=user_message,
    questions=[
        choice("intent", ["search", "create", "update", "delete", "help"]),
    ]
)

handlers = {
    "search": handle_search,
    "create": handle_create,
    "update": handle_update,
    "delete": handle_delete,
    "help":   handle_help,
}

handler = handlers[result.answers["intent"].value]
handler(user_message)

Intent Routing is often combined with Confidence-Gated Routing for production safety: route with high-confidence intents automatically, and send low-confidence ones to a disambiguation step or human review before the handler runs.

Pattern Summary

Pattern Core idea Primary benefits Best combined with
Speculative Fan-Out Ask all questions upfront; code picks which answers to use Cost, Speed Intent Routing (send sub-questions alongside intent)
Confidence-Gated Routing Use confidence as a second axis to gate autonomous action Reliability, Safety Intent Routing (safety wrapper around any routing decision)
Composite Scoring Combine independent dimension scores with code-side weights Cost, Reliability, Speed Confidence-Gated Routing (gate on composite confidence)
Intent Routing Classify intent first; dispatch to a dedicated handler Cost, Speed Confidence-Gated Routing (add safety to the dispatch step)
Complex system behavior from simple atomic decisions. Each pattern is built from the same primitives — Choice, Score, Noul — composed by ordinary code. You never need a more complex prompt; you need a better decomposition. The intelligence of your system lives in how you combine answers, not in asking the model to hold multiple factors in mind at once.
Do not try to ask one complex multi-factor question. A question like "Is this message urgent, negative, and complex?" conflates three independent signals into one answer, making the result uninterpretable and impossible to weight. Decompose every multi-factor judgment into separate atomic questions and combine the answers in code where you can inspect, test, and tune each factor independently.

Skill exercise

Pick one of the four patterns and sketch a mini-system design that uses it. Write your design in plain text or ASCII diagram form. Include all four components:

  • State — what data object are you working with?
  • Questions — what does your Jev call ask? (question type, text, options/criteria)
  • Confidence threshold — where do you draw the line between auto-action and escalation?
  • Routing logic — what happens at each branch of your decision?
Lesson summary
  • Speculative Fan-Out sends all questions — including speculative follow-ups — in one call and lets code decide which answers to use, saving round-trips at near-zero extra cost.
  • Confidence-Gated Routing adds a safety layer by using confidence as a second decision axis, enabling autonomous action on high-confidence answers while escalating uncertain ones to humans.
  • Composite Scoring measures each relevant dimension as a separate Score question and combines them with numeric weights in code, making the weighting transparent and tunable without prompt changes.
  • Intent Routing is the most common pattern: classify intent first, then dispatch to a dedicated handler — often paired with Confidence-Gated Routing for production safety.
  • All four patterns share the same design principle: decompose complex decisions into discrete atomic questions and compose their answers in code.
