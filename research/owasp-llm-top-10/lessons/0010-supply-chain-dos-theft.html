LLM05 — Supply Chain Vulnerabilities

A traditional web application has a supply chain: npm packages, OS libraries, third-party APIs. An LLM application has all of that plus several layers unique to machine learning: pre-trained model weights, fine-tuning datasets, model-hosting platforms, vector databases, and plugins that extend the model’s capabilities at runtime. Each layer is a separate attack surface that the developer implicitly trusts every time the app starts up.

OWASP LLM05 defines five supply chain components that carry distinct risks:

Component Example Attack vector
Python dependencies transformers, langchain, openai Compromised package on PyPI; typosquatting; malicious version update
Pre-trained model weights Hugging Face model repository Backdoored weights; hidden triggers embedded during training
Plugins and extensions Code interpreter, browser, calendar plug-in Malicious plugin granted access to user data or downstream actions
Third-party APIs Embedding API, search API, translation API API provider changes terms, leaks data, or injects content into responses
Training datasets Web-scraped corpora, licensed datasets Data poisoning during training; backdoor triggers that activate on specific inputs

Three Real Incidents

OWASP LLM05 documents three concrete incidents that illustrate how supply chain compromises reach production LLM systems.

Incident 1 — Vulnerable Python library exploited in OpenAI data breach. A Python package used in the OpenAI development pipeline contained a known vulnerability. Attackers exploited it to breach internal systems — the first publicly attributed data breach involving OpenAI. The entry point was not the LLM itself; it was an ordinary dependency that happened to sit in the same environment.

Incident 2 — Poisoned PyPI package exfiltrating model developer data. A malicious package was published to PyPI under a name closely resembling a legitimate ML utility. Developers working on model fine-tuning installed it and inadvertently allowed it to exfiltrate training data, model hyperparameters, and environment variables including API keys. The attacker needed no access to the model platform — only a plausible package name.

Incident 3 — Backdoored Hugging Face model spreading misinformation. A model uploaded to Hugging Face appeared to perform its advertised summarization task but contained embedded backdoor behavior: specific trigger phrases in the input caused the model to generate misinformation instead of accurate summaries. Downstream developers who used the model via the Hub’s one-line API inherited the backdoor without any visibility into the weights they were running.

Insider threats apply across the entire supply chain, not just your own organization. A disgruntled employee at a model hosting provider, a dataset vendor, or a plugin API company can introduce a compromise that reaches your users. Terms-of-service changes are a softer version of the same problem: a vendor quietly updating their T&C to opt user inputs into training data can expose your users’ private conversations without any code change on your end.

LLM05 Mitigations

The two most structurally distinctive mitigations for LLM supply chains — ones that go beyond standard software supply chain hygiene — are the SBOM and model signing.

Software Bill of Materials (SBOM). An SBOM is a machine-readable inventory of every component in your application: Python packages and their versions, model identifiers and checksums, plugin manifests, and API endpoint contracts. You cannot audit what you cannot enumerate. An SBOM makes the full dependency graph visible so that when a vulnerability is disclosed in any component you can immediately answer the question: “Do we use this? Which version? In which service?”

Model signing. Code signing for model weights. A model registry (internal or external) attaches a cryptographic signature to each model artifact at publication time. Before loading weights, the inference server verifies the signature against a trusted public key. This prevents a compromised artifact — whether from a storage breach, a MITM during download, or a malicious contributor — from silently replacing a known-good model.

The SBOM covers all five supply chain layers listed above. Model signing specifically addresses the layer most unique to LLMs: pre-trained weights, which are opaque binary files with no equivalent in traditional web development. Think of the SBOM as the inventory and model signing as the tamper-evident seal.

Additional mitigations from OWASP LLM05: vet suppliers and review their privacy policies before integration; apply anomaly detection on the behavior of supplied models (unexpected output distributions may signal backdoor triggers); continuously monitor all third-party components for newly disclosed vulnerabilities.

LLM04 — Model Denial of Service

Denial of service against a web server traditionally means flooding it with network connections or HTTP requests until its bandwidth, CPU, or thread pool is exhausted. The attacker’s resource expenditure is modest; the defender’s is large. LLM DoS shares this asymmetry but exploits a completely different attack surface: the context window.

Every token processed by an LLM costs real compute, and that compute scales with context length. An attacker who sends requests that force the model to process a large number of tokens — whether by submitting very long inputs, by triggering recursive context expansion through clever prompting, or by flooding with many concurrent requests just below the context limit — inflates the provider’s (or operator’s) cost per request. The attacker pays for one HTTP request; the operator pays for thousands of tokens of compute.

LLM DoS is economically different from traditional server DoS. A traditional attack degrades availability while costing the attacker bandwidth. An LLM DoS attack degrades both availability and inflates the operator’s cloud bill — silently, because cost accrual is invisible until the monthly invoice. A well-designed LLM DoS campaign can cause significant financial damage before any alert fires.

Four Attack Scenarios

OWASP LLM04 documents four representative attack patterns:

Scenario 1 — Automated prompt flood. A script sends a continuous stream of complete, semantically valid requests. Each request is individually legitimate; the attack is in the volume. Because LLM API rate limiting is often configured per-account rather than per-IP, a single leaked API key can sustain the flood at high throughput.

Scenario 2 — Recursive context expansion. A crafted prompt instructs the model to expand its own output repeatedly: “For each point you make, list three sub-points, and for each sub-point list three supporting examples.” A short input generates an exponentially growing response, consuming tokens in both the generation and any downstream re-injection step.

Scenario 3 — Variable-length floods near the context limit. Requests are constructed to be just under the model’s maximum context length. This maximizes per-request compute cost while staying within the bounds that would trigger an outright rejection. Systems that enforce a hard token cap per request are largely immune; systems that accept “up to the limit” by default are highly vulnerable.

Scenario 4 — Leaked admin token abuse. If an attacker obtains an admin-level API token (via prompt injection, insider leak, or credential exposure in a public repository), they can submit requests at volumes and with parameters far beyond what normal users can reach. Admin tokens that bypass rate limiting are the highest-impact variant.

Degraded performance is not the same as outright unavailability. A model that begins responding slowly, returning truncated outputs, or timing out occasionally may be under a low-rate DoS that costs money and erodes user experience without triggering any availability alert. Monitor token consumption per request and per user over time, not just error rates.

LLM04 Mitigations

Because the context window is the attack surface, mitigations must operate at the token level, not just at the network level:

  • Input size validation — reject or truncate requests that exceed a defined token budget before the model processes them.
  • Per-request resource caps — enforce a maximum number of tokens that can be consumed in any single inference call (both input context and generated output).
  • API rate limiting per user and per IP — prevent any single identity from submitting requests at a rate that would degrade service for other users.
  • Cap queued actions — in agentic pipelines where the model can queue follow-up tasks, limit the total number of actions in flight to prevent runaway expansion.
  • Strict context window enforcement — never silently accept inputs that exceed the window; always fail fast with a clear error rather than silently truncating context in ways that change model behavior unpredictably.

LLM10 — Model Theft

A trained LLM represents significant intellectual property: months of compute, proprietary fine-tuning data, and the accumulated engineering effort of alignment and evaluation. Model theft — the unauthorized acquisition of model weights or equivalent functional knowledge — is a category of attack with no direct analogue in traditional software security.

OWASP LLM10 identifies five theft vectors:

Infrastructure breach. Misconfigured cloud storage (e.g., a public S3 bucket), unprotected model registries, or weak access controls on the inference server’s file system can expose weights directly. This is the highest-bandwidth exfiltration path: a single download yields the complete model.

Insider threat. An engineer with legitimate access to model artifacts copies them to personal storage. Unlike a code repository where diffs are visible, a binary file copy may generate no audit event unless object-level logging is explicitly configured.

API extraction attack. An attacker systematically queries the model’s public API with a carefully designed set of inputs, harvests the outputs, and uses them to train a “shadow model” that approximates the original’s behavior. The attacker never touches the weights; they reconstruct equivalent functional knowledge from observable input-output pairs. This attack is unique to LLMs and scales with API accessibility.

Supply chain failure. A component in the model’s own supply chain (a fine-tuning platform, a dataset vendor, a model-hosting provider) is compromised and the weights are exfiltrated through that channel.

Side-channel attack. Inference timing, power consumption, or memory access patterns can leak information about model architecture and parameters to an attacker with physical or low-level access to the inference hardware. Less common in cloud deployments but relevant for on-premise models.

The API extraction attack deserves particular attention because it requires no infrastructure access whatsoever. Any model exposed via a public API is theoretically extractable given sufficient query budget. The attacker’s cost scales with the number of queries needed to achieve acceptable shadow-model fidelity; the defender’s cost is the compute billed for those queries. Rate limiting is both an LLM04 and an LLM10 control.

Model Watermarking

Watermarking is the LLM10-specific detection and attribution mechanism. A watermark embeds a statistical signature into the model’s outputs — either during training (training-time watermark) or at inference time (output watermark). The signature is imperceptible in individual responses but detectable with a statistical test across a corpus of outputs.

If a stolen or extracted model is used commercially, the watermark persists in its outputs and can be used to attribute the theft to the original model. Watermarking does not prevent theft but it does two important things: it deters theft by raising the risk of attribution, and it provides forensic evidence after an incident.

LLM10 Mitigations

  • RBAC and least privilege for model repositories — only production inference services should have read access to weights; developer access should require explicit approval and time-limited credentials.
  • Network restriction — model weight storage should be inaccessible from the public internet; access only via private network or VPN with MFA.
  • Centralized model registry — all model versions tracked in a single inventory with checksums, access logs, and retention policies; no ad hoc copies in personal cloud storage.
  • API rate limiting and DLP — rate limiting slows extraction attacks; data loss prevention tooling on API outputs can detect unusual bulk query patterns consistent with systematic extraction.
  • Model watermarking — embed statistical signatures for post-incident attribution.
  • Adversarial robustness monitoring — detect queries that look like extraction probes (e.g., systematically varied inputs designed to map the model’s decision boundary) and trigger alerts or automated throttling.
  • Audit logging — log all access to model artifacts, including internal reads, with tamper-evident storage so insider exfiltration is detectable after the fact.

Synthesis — The Infrastructure Risk Cluster

LLM05, LLM04, and LLM10 form a cluster of infrastructure and economic risks that are distinct from the input-side and output-side vulnerabilities covered in earlier lessons. They share a common thread: each exploits the gap between how the system is assumed to be used and how it can be used when access controls, monitoring, and supply chain hygiene are treated as secondary concerns.

Several controls address multiple risks simultaneously:

Control LLM05 Supply Chain LLM04 Model DoS LLM10 Model Theft
API rate limiting Primary mitigation Slows extraction attacks
SBOM + model signing Primary mitigation Supports audit trail
RBAC + least privilege Limits supplier blast radius Prevents admin token abuse Primary mitigation
Audit logging Detects anomalous supplier behavior Surfaces cost anomalies Forensic evidence for insider theft
Monitoring and anomaly detection Detects backdoor triggers Detects silent cost inflation Detects extraction probe patterns
If you implement one cluster of controls, you get partial coverage across all three vulnerabilities. A mature LLM security posture treats supply chain hygiene, resource governance, and model asset protection as a unified infrastructure practice rather than three separate checklists.

Knowledge Check

According to OWASP LLM04, what makes LLM Denial of Service economically different from traditional server-based Denial of Service?

Skill exercise: You are deploying a production customer-facing chatbot that uses a third-party pre-trained model downloaded from Hugging Face, a Python SDK (e.g., transformers or langchain), and a hosted third-party embedding API.

List the three highest-risk supply chain components in this system and, for each one, name the specific control you would apply before going to production. Be concrete: name the control type (e.g., “model signing”, “SBOM scan in CI”, “API vendor privacy policy review”) and explain in one sentence why it addresses that component’s specific risk.

When reviewing a supply chain risk, ask: if this component were silently compromised right now, how long would it take you to notice? For a backdoored model, the answer might be “never” without behavioral anomaly detection. For a poisoned Python package, the answer might be “only after a security advisory” without an SBOM and continuous vulnerability scanning. The gap between compromise and detection is the window of exposure — and each control you add narrows that window.
