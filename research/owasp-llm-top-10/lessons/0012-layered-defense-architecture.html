Defense in Depth: Why One Control Is Never Enough

Every security control has failure modes. Input filters can be bypassed with obfuscated syntax. System-prompt instructions can be overridden by sufficiently crafted user or document content. An allowlist can be incomplete. Relying on a single line of defense means a single bypass grants full access to the system's capabilities.

Defense in depth is the architectural answer: stack independent controls so that circumventing one layer does not hand the attacker a win. In LLM systems this matters more than in conventional software because the attack surface is linguistic — a model that processes natural language cannot make hard syntactic distinctions between instructions and data the way a SQL parser separates queries from literals. Each layer below compensates for what the layer above cannot guarantee.

Bypassing Layer 1 does not mean the attacker wins if Layers 2 through 5 are intact. Each layer is designed to catch what the previous layer missed. A well-designed LLM system forces an attacker to defeat all five layers simultaneously — a dramatically harder task than defeating any one.

The NVIDIA 5-Layer Defense Model

NVIDIA's AI Red Team distilled their prompt-injection research into a five-layer model. The layers are ordered by where in the request-response cycle each control fires — from the moment input arrives to the moment an external service is called. Each layer addresses a different threat category.

Layer 1 — Input Validation

The first line of defense intercepts requests before they reach the model. This includes pattern matching for known injection templates (Ignore previous instructions, role-play overrides, base64-encoded payloads), length and character-set enforcement, and prompt structure integrity checks. Because this layer runs before the LLM, it consumes no model tokens and adds minimal latency. Its limitation is that it is signature-based: novel or obfuscated injections that do not match known patterns pass through.

Layer 2 — Trust Boundary Enforcement

This layer addresses a structural property of LLM context windows: they are composed of text from multiple contributors — the developer-written system prompt, retrieved documents from a RAG store, tool outputs, and the user's query. The LLM cannot prove which contributor is trustworthy; it processes all text in the context window as a single stream.

NVIDIA's key insight here is stark: "Control and data planes are not separable when working with LLMs — every LLM output must be treated as hostile territory." The correct posture is to apply the lowest privilege level across all contributors. If a retrieved document could have been tampered with, the entire context window must be treated as if it could have been tampered with. Trust is the minimum across contributors, not the maximum.

Layer 3 — Output Sanitization

Even if injected content reaches and influences the LLM, damage can still be contained by treating all model output as potentially malicious before passing it downstream. Output sanitization means: stripping or escaping HTML and script tags before rendering in a browser, refusing to forward LLM-generated URLs without validation, blocking model-generated commands from being executed directly, and applying content-policy filters to responses before they reach the user or a dependent system. This layer is the last catch before LLM output causes real-world effects.

Layer 4 — Hardened External Service Integration

When an LLM calls an external API or plugin, the call should be constructed by code, not assembled from LLM-generated text. NVIDIA's prescriptions: use strict parameterization (never string-interpolate model output directly into API calls), apply least-privilege service contexts (the API key used for a read operation should not have write permissions), and enforce type and content checks on every parameter before it leaves the system. An LLM that can write to a database or send emails should only ever be able to do so through a tightly constrained wrapper that validates every field independently.

Layer 5 — Architectural Minimalism

The final layer is a design-time control: minimize what the LLM can reach. Every external resource the model can access is both an attack surface (injection can arrive through it) and a blast-radius multiplier (a successful compromise can propagate through it). NVIDIA's specific guidance:

  • Avoid connecting LLMs to external resources when the use case does not require it.
  • Restrict plugins to the minimum functionality needed — a search plugin should not also be able to write files.
  • Multi-service chains require rigorous security review at each hop.
  • Authorization-requiring plugins should generally not be invoked after other plugin calls because cross-plugin authorization creates compounded complexity that is difficult to reason about and audit.
A common misconception is that architectural minimalism is a "nice to have" that can be addressed after the product ships. In practice, the blast radius of a successful injection is determined at design time, not at runtime. A chatbot wired to five internal APIs from day one is structurally more dangerous than one connected to none — and unwiring APIs after the fact often requires significant rearchitecting of features users already depend on.

The Cloudflare AI Gateway: Infrastructure as a Control Plane

Architectural minimalism (Layer 5) is not only about reducing connections — it is also about ensuring the connections that do exist are observable and controlled. The Cloudflare AI Gateway is a concrete implementation of this idea: a proxy that sits between your application and any upstream LLM provider (OpenAI, Anthropic, Google Gemini, and others), acting as an intermediary control plane.

Because all requests and responses pass through the Gateway, it can enforce security and operational policies that would otherwise require instrumentation inside every application component. Key capabilities:

  • Rate limiting per user or IP — prevents denial-of-service attacks that exhaust token budgets or overwhelm upstream providers. This directly addresses LLM04 (Model Denial of Service).
  • Request logging — every prompt and response is logged, enabling anomaly detection, incident forensics, and compliance auditing. Unusual patterns (sudden spike in token usage from one user, identical prompts arriving from many IPs) become visible.
  • Caching — repeated identical requests return a cached response, reducing the number of calls that reach the upstream model and thereby shrinking the upstream exposure surface.
  • Request retry and fallback routing — if an upstream provider is unavailable or returns an error, the Gateway can automatically retry or route to a fallback model, maintaining availability without manual intervention.
  • Analytics for token usage and cost — makes the cost surface visible, which is also a security surface: unexpectedly high token consumption is a signal of abuse or a runaway agent loop.

A practical advantage is that integrating the Cloudflare AI Gateway requires minimal code changes — the application simply routes its API calls through the Gateway endpoint instead of directly to the provider. The security and observability controls are activated at the infrastructure layer, not scattered across application code.

An AI Gateway does not replace application-layer controls (Layers 1–4). It provides a perimeter: rate limiting, logging, and routing enforcement that sits outside the application and cannot be bypassed by application-layer vulnerabilities. Think of it as the equivalent of a WAF (Web Application Firewall) for LLM traffic.

Why Architectural Minimalism Is a Security Primitive

The principle of least privilege — give a component only the permissions it needs to do its job — is foundational in conventional system security. In LLM systems, the same principle applies but with a twist: the LLM's "job" is defined in natural language and can be redirected by injection. This means the blast radius of a successful attack is not a property of the attacker's skill; it is a property of the system's design.

Consider two RAG chatbots answering questions about a knowledge base. Bot A has read access to the knowledge base only. Bot B has read access to the knowledge base, write access to the same database, and the ability to send emails. Both bots are equally vulnerable to an indirect injection attack in a retrieved document. But the consequences are entirely different: in Bot A, the worst the attacker can do is get the bot to produce misleading answers. In Bot B, the attacker can corrupt the database and exfiltrate data over email.

The difference between Bot A and Bot B was made at design time. Every capability, plugin, or API connection added to an LLM application is a decision that expands the blast radius of all future vulnerabilities — including vulnerabilities not yet discovered.

How the Layers Map to OWASP LLM Vulnerabilities

Each layer of the defense model targets a distinct class of vulnerabilities from the OWASP LLM Top 10. The table below shows the primary mapping. Some layers address multiple categories because the same control (for example, hardened API integration) limits several different attack paths.

Layer Name Primary Threat Addressed OWASP Category
1 Input Validation Known injection patterns reaching the model before any context is built LLM01 — Prompt Injection
2 Trust Boundary Enforcement Compromised contributor text in the context window (indirect injection via RAG, tool output, or multi-agent handoff) LLM01 — Prompt Injection (indirect variant); LLM06 — Sensitive Information Disclosure
3 Output Sanitization Hostile or malformed content in model output that is passed to a browser, downstream system, or user without inspection LLM02 — Insecure Output Handling
4 Hardened Service Integration Over-privileged API access; parameter injection through model-generated text assembled into API calls LLM07 — Insecure Plugin Design; LLM08 — Excessive Agency
5 Architectural Minimalism Expanded blast radius from unnecessary resource connections; compounded cross-plugin authorization complexity LLM08 — Excessive Agency; LLM04 — Model Denial of Service

Notice that LLM01 (Prompt Injection) appears at both Layer 1 and Layer 2. Direct injection (user-supplied) is primarily addressed by Layer 1. Indirect injection (content arriving through retrieved documents, tool outputs, or agent messages) is addressed by Layer 2, because the injection does not originate in the user input stream and may pass cleanly through input validation.
