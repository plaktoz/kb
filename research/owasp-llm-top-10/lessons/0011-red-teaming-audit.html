What Is LLM Red Teaming?

Traditional penetration testing finds exploitable bugs in software. LLM red teaming does something different: it systematically probes an AI system with adversarial inputs before deployment in order to quantify vulnerability risk. The goal is not just to find failures, but to measure how reliably the system fails under deliberate attack — and to surface that risk in terms that developers and security teams can act on.

The promptfoo documentation describes the core purpose as follows: LLM red teaming gives teams a structured way to stress-test prompt defenses, output filters, plugin permissions, and data access controls before a system reaches real users. It shifts LLM security from a reactive posture (waiting for incidents) to a proactive one (measuring attack surface before release).

The distinguishing feature of LLM red teaming is the combination of automated adversarial input generation with human creativity. Automated tools can cover known vulnerability patterns at scale; human red teamers devise novel attack vectors that automation has not yet catalogued. Neither alone is sufficient.

Red teaming applies across the full OWASP LLM Top 10 surface. A single exercise can probe for prompt injection (LLM01), insecure output handling (LLM02), training data leakage (LLM03), excessive agency (LLM08), and more — giving teams a unified view of risk rather than point-in-time checks against individual vulnerabilities.

Model-Layer vs. Application-Layer Threats

One of the most useful distinctions in LLM red teaming is the split between threats that target the model itself and threats that target the system built around it. Conflating the two leads to misallocated remediation effort: hardening the model does not fix application architecture flaws, and vice versa.

Model-layer threats

Model-layer attacks target intrinsic properties of the LLM. The attacker is trying to make the model do something its training or alignment was designed to prevent. Examples include:

  • Prompt injection and jailbreaks — crafted inputs that override system instructions or bypass safety guidelines.
  • Hallucination exploitation — prompts that reliably cause the model to fabricate authoritative-sounding false information, used to mislead downstream consumers.
  • Training data extraction — prompts that induce the model to reproduce verbatim text from its training corpus, potentially leaking PII or proprietary content that was memorised during pre-training.

Application-layer threats

Application-layer attacks target the infrastructure, integrations, and data flows wrapped around the model. The model itself may behave correctly; the vulnerability lives in how the system is assembled. Examples include:

  • Indirect injection via RAG — adversarial instructions embedded in retrieved documents that reach the model as “trusted” context (covered in Lesson 4).
  • PII leakage via RAG — the retrieval pipeline returns private records that the querying user was not authorised to see.
  • Unauthorized tool access — the model invokes a plugin or API action that exceeds its intended permission scope.
  • Data exfiltration — an attacker manipulates the system into encoding sensitive context into an outbound URL or response that the attacker controls.
It is tempting to treat model-layer hardening — fine-tuning, RLHF, content filters — as a sufficient security strategy. Application-layer threats are not addressed by any amount of model-level hardening. A model that correctly refuses a jailbreak can still exfiltrate data if the application grants it unfiltered tool access and no outbound request inspection.

The Five-Step Red Team Methodology

The promptfoo red team documentation describes a five-step process that applies whether the exercise is manual, automated, or a hybrid of both.

Step 1 — Define strategy and vulnerability priorities

Before generating any inputs, the team decides which vulnerabilities matter most for the specific deployment. A customer-facing support bot has a different threat model than an internal code-review assistant. The output of this step is a prioritised list: which OWASP categories to probe, what severity thresholds will block release, and what data the model has access to.

Step 2 — Generate adversarial inputs

Adversarial inputs are produced in two ways: automated generation using tools like promptfoo (which can produce thousands of variations of known attack patterns) and human creativity (red teamers who devise novel framing, multi-turn sequences, or context-specific attacks that automation has not modelled). The combination achieves both breadth and depth.

Step 3 — Execute in a production-like environment

Red team inputs must be run against the full system stack — not against the base model in isolation. That means the same system prompt, the same retrieval pipeline, the same plugins and tool access, and the same output post-processors that will exist in production. Testing the model in isolation gives a false sense of security because most application-layer threats only emerge when the full system is assembled.

Step 4 — Analyze results

Results are evaluated using two complementary methods. Deterministic metrics check for exact strings, regexes, or schema violations in outputs. Model-graded metrics use a secondary LLM (or a specialised evaluation model) to judge whether a response was harmful, compliant, or evasive. Combining the two captures both objective failures and nuanced policy violations that resist simple pattern matching.

Step 5 — Remediate and re-test

Each identified vulnerability is mapped to a control (system prompt change, permission reduction, output filter, architecture fix) and the same adversarial input is re-run to confirm the fix holds. Re-testing is essential because a mitigation applied for one attack vector can introduce a regression elsewhere. The cycle — attack, fix, verify — continues until risk falls below the defined threshold.

The 12-Item Audit Checklist

The table below maps each control area to its primary OWASP LLM category. During a red team exercise, each row is a testable claim: the adversarial test should confirm that the control holds under deliberate attack, not merely under normal usage.

# Check OWASP Category
1 System prompt separated from user input; untrusted content wrapped in distinct delimiters LLM01
2 All LLM output treated as untrusted before rendering or passing downstream LLM02 / LLM10:2026
3 Training and fine-tuning data sources vetted, versioned (DVC), and anomaly-scanned LLM03 / LLM05:2026
4 Input size limits enforced; rate limiting per user/IP at API gateway LLM04 / LLM06:2026
5 SBOM maintained; all model dependencies and plugins pinned and signed LLM05 / LLM04:2026
6 PII and sensitive data scrubbed from training pipelines; access-controlled in RAG LLM06 / LLM02:2026
7 All plugins use parameterized inputs; SQL injection and SSRF protections applied LLM07
8 LLM tools operate under least privilege; high-impact actions require human confirmation LLM08 / LLM03:2026
9 AI outputs in decision-critical workflows have human review and source verification LLM09 / LLM07:2026
10 Model repositories are RBAC-gated; API call patterns monitored for extraction attempts LLM10
11 Red team exercises conducted pre-deploy and integrated into the CI/CD pipeline All
12 Comprehensive audit logging of all LLM requests and tool/plugin invocations All

Integrating Red Teaming into CI/CD

A one-time pre-launch red team exercise is valuable but insufficient. LLM systems change continuously: prompts are updated, models are upgraded, plugins are added, and retrieval corpora evolve. A vulnerability that was absent at launch can be introduced by any of these changes. The solution is to treat red team tests the same way software teams treat unit tests — run them automatically on every deployment.

Tools like promptfoo support this directly. A red team configuration file defines the adversarial test suite: the attack categories, the prompts, and the pass/fail criteria. That file is checked into source control alongside the application code. A CI/CD pipeline step runs the full suite against every candidate deployment, and the build fails if the attack success rate exceeds the defined threshold. 

# Example: promptfoo red team step in a CI pipeline (conceptual)
npx promptfoo redteam run \
  --config redteam.yaml \
  --output results.json \
  --fail-threshold 0.05   # fail build if >5% of adversarial inputs succeed
Checklist items 11 and 12 reinforce each other. Continuous red teaming (item 11) surfaces new failures; comprehensive audit logging (item 12) provides the forensic trail to understand how and when each failure occurred. Together they create a feedback loop: attacks are detected, logged, root-caused, and re-tested in the next CI run.

CI/CD integration also enforces accountability. When red team tests are automated and their results are visible in the deployment pipeline, security regressions cannot ship silently. A new model version that jailbreaks more easily than its predecessor will fail the build — before it ever reaches production users.
