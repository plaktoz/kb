Overreliance & Hallucination Risks

~12 min Module 3: Output, Trust & Infrastructure LLM09 / LLM07:2026
Source OWASP LLM09 — Overreliance — LLMs can generate authoritative-sounding but factually incorrect content (hallucination), leading to security breaches, supply chain compromise, or disinformation when that output is trusted and acted upon without oversight.

What Hallucination Actually Is

The word "hallucination" is borrowed loosely from neuroscience, but in the context of language models it describes something precise: the model produces output that is fluent, confident, and coherent — and factually wrong. It is not a bug in the sense of an exception being thrown. It is the model doing exactly what it is designed to do: predicting the most plausible next token given everything in its context window.

The model has no oracle. It has no live database to query, no ability to verify claims against reality, and no mechanism that signals uncertainty at inference time in a way that the consumer can reliably detect. When a model generates a package name, an API endpoint, a statute citation, or a clinical fact, it is doing pattern completion — not retrieval from a verified source. The output looks the same whether the answer is correct or fabricated.

Hallucination is not the model "lying." It is the model pattern-completing without verifiable grounding. The fluency of the output provides no signal about its accuracy. High confidence and high error rate can coexist in the same response.

This matters for security because downstream systems, developers, and users often treat LLM output as a reliable lookup. When an LLM is integrated into a workflow that takes automatic action on its output — installing a package, filing a document, executing a query — unverified hallucinations can cause real damage.

The Three OWASP Attack Scenarios

OWASP LLM09 identifies three concrete scenarios that show how overreliance on LLM output translates into security incidents.

Scenario 1 — Disinformation at scale

A bad actor deliberately seeds misleading information into the sources used to fine-tune or retrieval-augment an LLM-powered news outlet. The model synthesises and publishes plausible-sounding articles that contain false claims. Because the outlet has no independent fact-checking step, and because the model's output reads as authoritative prose, the disinformation propagates at machine speed. The attack exploits not a code vulnerability but the editorial trust placed in the model.

Scenario 2 — Package hallucination attack

A developer asks an LLM coding assistant for help with a task and the model suggests an npm or pip package that does not exist — but the name is plausible, follows naming conventions, and fits the context perfectly. The developer does not verify the package before running npm install or pip install. An attacker who monitors for hallucinated package names (or who prompted the model specifically to elicit a fake name) has already registered that package name in the public registry with malicious code inside. The install succeeds, and the malicious package runs in the developer's environment.

Package hallucination is not a hypothetical. Researchers have demonstrated that LLMs consistently suggest non-existent package names and that squatting on those names is a viable supply chain attack. The gap between "the model sounds sure" and "the package exists and is safe" is exactly where the attack lives.

This is why package hallucination bridges two separate risk categories: it starts as LLM overreliance (LLM09) and ends as a software supply chain compromise. The developer's implicit trust in the model's suggestion is the attack vector. The malicious registry package is the payload.

Scenario 3 — AI-generated code merged without review

A development team uses an LLM assistant to generate production code and merges the output without a security-focused review pass. The generated code may use insecure defaults (e.g., verify=False in an HTTP client, a hardcoded secret, or a deprecated cryptographic primitive), reference an incorrect library version with a known CVE, or implement authentication logic that looks correct but has a subtle flaw. Because the code is syntactically valid and passes functional tests, it reaches production. The security gap is not visible until an attacker finds it.

Why AI-Generated Code Requires Security Review

LLM coding assistants are trained on large corpora of public code, which includes both secure and insecure patterns, deprecated APIs, and code written before security best practices were established. The model cannot distinguish between a secure pattern and a legacy anti-pattern by looking at code frequency in training data — both appear as valid completions. As a result, LLM-generated code tends to reflect the average of its training distribution rather than current security standards.

Three failure modes are especially common in LLM-generated code:

Failure mode Example Why LLMs produce it
Insecure defaults TLS verification disabled, debug mode left on Common in tutorials and quick-start examples in training data
Outdated patterns MD5 for password hashing, eval() for parsing Older code vastly outnumbers newer code in training corpora
Incorrect library versions Pinning a version with a known CVE Model has no live CVE feed; version knowledge is frozen at training cutoff
A mandatory human security review of LLM-generated code is not optional caution — it is the structural control that compensates for the model's inability to distinguish current best practice from historical anti-pattern.

The Mitigation Stack

OWASP LLM09 recommends a layered mitigation approach. No single control is sufficient; the goal is to build independent verification steps at every layer where the model's output could cause harm if it were wrong.

Self-consistency and voting

For any fact-sensitive query, ask the model the same question multiple times with slight rephrasing and compare the answers. Genuine factual knowledge tends to produce consistent responses; hallucinated details often vary across runs. Majority voting across responses can surface uncertainty that a single answer hides. This technique is especially useful for detecting unstable claims in generated code or cited sources.

Chain-of-thought prompting

Asking the model to "think step by step" or to explain its reasoning before giving an answer does two things: it can improve accuracy on complex tasks by surfacing intermediate reasoning, and it makes the reasoning inspectable. A reviewer can catch a hallucinated premise in the chain of reasoning before it propagates to the conclusion. This is a mitigation for complex or multi-step answers, not a substitute for external verification.

Mandatory human review for security-critical outputs

The human-in-the-loop control is the most reliable mitigation for high-stakes outputs. Any LLM output that will be executed, deployed, published to users, or used to make consequential decisions should pass through a qualified human reviewer before action is taken. The reviewer is specifically looking for security issues that the model cannot self-detect: insecure defaults, suspicious package names, unverified claims, and logic errors in generated code.

Cross-checking against trusted external sources

For factual claims — package names, API signatures, regulatory citations, medical facts — verify against an authoritative external source before acting. This means checking npmjs.com or pypi.org before installing a suggested package, querying official documentation before using a generated API call, and consulting original sources before citing a statistic the model produced.

AI-content labeling and responsible interfaces

When LLM output is presented to end users, label it clearly as AI-generated. Content filters can reduce the rate of harmful outputs, but labeling serves the downstream human: it signals that independent verification is appropriate before acting on the content. Interfaces that present LLM output as if it were human-reviewed editorial content create the conditions for large-scale overreliance.

Skill Exercise: LLM Coding Assistant Policy

Your dev team has adopted an LLM coding assistant for daily work. Write a brief policy — 3 to 5 bullet points — covering:

  • When human security review is mandatory before merging LLM-generated code
  • How to verify any package name suggested by the assistant before installing it
  • How to handle security-sensitive suggestions (auth logic, crypto, secrets management)

Your policy should be specific enough that a new team member could follow it without ambiguity. Avoid vague directives like "be careful" — name the specific check or step required.
