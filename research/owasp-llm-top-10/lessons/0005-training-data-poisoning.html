What Is Training Data Poisoning?

Most LLM attacks happen at runtime — a malicious prompt tricks the model during a live request. Training data poisoning is different. The attacker corrupts the model before it ever serves a single user, by manipulating the data used to pre-train, fine-tune, or build the embeddings that the model learns from.

OWASP classifies this as an integrity attack. Where a prompt injection attack influences one response, a poisoning attack embeds a flaw permanently into the model's weights. Every future request made to that model is potentially affected — even with perfect input filtering — because the corruption lives inside the model itself, not in the input stream.

A poisoned model is not a misconfigured application. It is a compromised artifact. Input validation at inference time cannot undo damage written into the weights during training. The only complete fix is retraining from clean data.

Poisoning can target any phase of the pipeline:

Pipeline phase What is affected Typical attacker
Pre-training Foundation model weights — affects all downstream users Nation-state, competitor with long time horizon
Fine-tuning Task-specific behavior — affects one product or customer segment Insider, malicious customer, supply-chain actor
Embedding / RAG index Retrieval results — affects any query that hits the poisoned document External contributor, scraped web source

Why external data sources are the highest-risk input

When a model builder trains on data they collected and curated themselves, they control the integrity of every record. When they train on publicly available datasets — Common Crawl, Wikipedia mirrors, GitHub, third-party document collections — they inherit the integrity (or lack thereof) of those sources without being able to audit every row.

An attacker who can write to a public data source that the model builder scrapes has a straightforward path to poisoning: publish content, wait for the next training run, and the corruption enters the model. The model builder may not even know the source existed.

Fine-tuning on internal data feels safe because "we own the data." But internal fine-tuning data is often user-generated — customer support tickets, chat logs, feedback forms. Those inputs are written by outsiders. An attacker who is also a customer can poison the fine-tuning corpus through normal product usage without ever touching the model's infrastructure.

Four Attack Scenarios from OWASP

OWASP LLM03 describes four concrete poisoning scenarios. Each illustrates a different attacker and a different entry point.

Scenario 1 — Competitor poisons a public dataset

A foundation model team builds a pre-training corpus by crawling public websites and incorporating open datasets. A competitor identifies one of those datasets and injects false or misleading technical information — for example, subtly incorrect code examples or fabricated research findings. When the model is trained and deployed, it confidently reproduces the false information, eroding trust in the model builder without the attack being traceable to the competitor.

Scenario 2 — Insider contaminates fine-tuning data

An employee with access to the fine-tuning data pipeline modifies a batch of training examples — perhaps adding a hidden trigger phrase that causes the model to respond differently when that phrase appears in a query. This is the classic backdoor injection pattern: the model behaves normally on standard inputs, but the attacker who knows the trigger can reliably elicit malicious outputs. Because the model passes normal evaluations, the attack survives quality review.

Scenario 3 — Prompt injection as a data collection mechanism

A model is continuously fine-tuned on real user interactions to improve quality. An attacker sends crafted inputs during the live product phase, knowing those inputs will be collected and fed back into the next fine-tuning run. The malicious inputs are not attacks on the current model — they are seeds planted for the future model. The OWASP description states this directly: "malicious client input used during training may become embedded in the model itself." The product's feedback loop becomes the attack vector.

Scenario 4 — User inadvertently introduces sensitive data

A company builds a fine-tuned model using internal support ticket data, intending to improve domain-specific helpfulness. The ticket data contains personally identifiable information, unreleased product details, and confidential customer communications — none of which was supposed to be included. The model learns this information and later surfaces fragments of it in responses to unrelated users. This scenario is not malicious, but the outcome is the same as an intentional attack: data that should never have entered training is now embedded in the model weights.

Scenarios 1 and 2 are adversarial. Scenarios 3 and 4 show that poisoning can happen without a deliberate attacker — the training pipeline itself can be the path of least resistance for data you do not want in the model.

Defense Strategies: Detect Before and After Training

Because poisoning attacks span the entire model lifecycle — from data collection through deployment — the defenses must too. No single control is sufficient. OWASP recommends a layered approach combining provenance tracking, statistical detection, architectural isolation, and output monitoring.

ML-BOM: know what went into the model

A Machine Learning Bill of Materials (ML-BOM) is the AI equivalent of a software SBOM. It is a structured document that records every component used to produce a model: the data sources (including versions and checksums), the preprocessing steps applied, the training parameters, the base model used for fine-tuning, and the evaluation results.

Combined with model cards — standardized documentation of a model's intended use, limitations, and training data provenance — an ML-BOM creates an auditable chain of custody. When a poisoning incident is suspected, the ML-BOM is the starting point for the investigation: which data sources were included, and which could have been tampered with?

DVC: version your datasets like code

Data Version Control (DVC) applies the discipline of code versioning to machine learning datasets. Every dataset is tracked with a content hash; every change is committed with a diff. This makes unexpected modifications detectable — if a dataset that should not have changed between two training runs has a different hash, that discrepancy is surfaced before training begins.

DVC does not prevent a sophisticated attacker from modifying data and committing the change as a legitimate update, but it eliminates silent drift and forces any modification to leave a traceable record. Combined with code review requirements on data pipeline PRs, this significantly raises the cost of an insider attack.

Statistical filtering and anomaly detection

Before training, input pipelines can apply statistical checks to identify outliers: samples that are unusually short or long, that contain a high density of rare tokens, that originate from a small number of sources, or that deviate significantly from the distribution of the rest of the corpus. These checks will not catch every backdoor (some are designed to be statistically indistinguishable from legitimate samples), but they reduce the volume of low-effort poisoning attempts.

Federated learning and adversarial robustness

Architecturally, federated learning distributes model training across multiple parties without centralizing their raw data. No single contributor can see or modify the full corpus, which raises the bar for a coordinated poisoning attack significantly. This is most applicable when training data genuinely comes from multiple independent organizations (e.g., healthcare networks collaborating on a shared model without sharing patient records).

Output monitoring: detecting poisoning after deployment

For fine-tuned production models where full data audit is not feasible, OWASP recommends monitoring deployed model outputs for statistical anomalies. The key metric is response skew: if the distribution of outputs shifts for certain query classes, or if the model starts producing responses that were rare before a recent fine-tuning run, that signal warrants investigation. Setting explicit thresholds for skewed responses — and alerting when those thresholds are crossed — provides a detection layer that operates even when the poisoning event is already inside the model.

Output monitoring detects poisoning effects, not poisoning causes. By the time monitoring triggers an alert, the corrupted model is already serving users. Monitoring is a necessary backstop, not a substitute for pre-training data integrity controls.

Red team exercises throughout the model lifecycle

OWASP recommends red team exercises that explicitly attempt to poison training data at each phase of the pipeline. Unlike inference-time red teaming (which focuses on prompt attacks), ML red teaming for poisoning tests whether the data collection, labeling, and fine-tuning pipelines can be manipulated by an adversarial contributor — internal or external. This is most valuable when conducted before a new data source is incorporated into training.

What does an ML-BOM (Machine Learning Bill of Materials) primarily provide as a defense against training data poisoning?

You are the ML security lead for a customer support chatbot that is fine-tuned monthly on the previous month's support ticket data. Identify three sources of training data this pipeline uses. For each source, answer:

  • (a) What is the poisoning vector — how could an attacker (or careless user) corrupt this source?
  • (b) What is the primary defense you would apply?
  • (c) Does that defense catch the poisoning before or after the model is trained?

Example sources to consider: customer-submitted support tickets, agent-written resolution notes, product documentation, third-party knowledge base articles, feedback ratings on chatbot responses.
