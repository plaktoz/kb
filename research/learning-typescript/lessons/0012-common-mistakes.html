1. Never Use Capitalized Primitive Types

Coming from Java, you instinctively write String for text, Integer for numbers, Boolean for true/false. In TypeScript the equivalent-looking names String, Number, and Boolean exist but they mean something completely different — and using them is almost always wrong.

The lowercase versions (string, number, boolean) are TypeScript's primitive types. They describe the actual values you work with: "hello", 42, true.

The capitalized versions (String, Number, Boolean) are the JavaScript wrapper object types. They represent boxed objects created via new String("hello"). In practice you almost never create these objects, and they behave surprisingly: 

// Don't — String (capital S) is the wrapper object type
function greet(name: String): string {
  return `Hello, ${name}`;
}

greet("Alice");        // OK by accident — primitive is assignable to wrapper
const s: string = new String("Bob");  // ERROR: String is not assignable to string
                                       // (wrapper object is NOT a primitive)
// Do — always use lowercase primitives
function greet(name: string): string {
  return `Hello, ${name}`;
}

greet("Alice");        // OK
greet(new String("Bob"));  // ERROR at call site — catches the mistake early

The same rule applies to Number/number, Boolean/boolean, Symbol/symbol, and BigInt/bigint. Use the lowercase form. Always.

Rule of thumb: if it looks like a Java class name, it is probably the wrong type in TypeScript. Use string, number, and boolean (all lowercase) for every primitive value.

2. any vs unknown — One Disables Type Checking Entirely

When you do not know the type of a value, TypeScript gives you two escape hatches: any and unknown. They look similar but behave very differently.

any is a complete opt-out. The type checker stops watching that value — you can assign it to anything, call methods on it, index into it, pass it anywhere. No errors. No safety. It is contagious: once a value is any, everything downstream of it also becomes unchecked. 

// Don't — any disables all checking
function process(input: any) {
  input.toUpperCase();       // No error — even if input is 42
  input.nonExistentMethod(); // No error — TypeScript has given up
  const n: number = input;   // No error — assignable to anything
}

unknown is the safe alternative. It says "I don't know the type yet" but it requires you to narrow the value before you can use it. The type checker stays engaged the whole time. 

// Do — unknown forces explicit narrowing before use
function process(input: unknown) {
  input.toUpperCase();       // ERROR — cannot call method on unknown
  input.nonExistentMethod(); // ERROR — correctly caught

  if (typeof input === "string") {
    input.toUpperCase();     // OK — narrowed to string inside the branch
  }

  if (typeof input === "number") {
    const doubled = input * 2;  // OK — narrowed to number
  }
}
any feels like Java's Object but is actually worse: Java's Object still enforces that methods exist; any disables all type checking in both directions. You can assign any to a number variable without error, which Java would never allow with Object.

3. Use void for Callback Return Types — Not any

When you accept a callback whose return value you do not care about, annotate it as returning void, not any. The two look interchangeable but they carry different semantics. 

// Don't — any for a callback's return allows any return type
type Listener = (event: MouseEvent) => any;

// Do — void says "the return value will be ignored"
type Listener = (event: MouseEvent) => void;

void means "the caller will not use the return value." This is looser than undefined — it allows the callback to return something (TypeScript just ignores it). This enables a useful pattern: passing a value-returning function where a void-returning callback is expected. 

// forEach expects (value: number) => void
// push returns a number — but that's fine, the return is ignored
const src = [1, 2, 3];
const dst: number[] = [];
src.forEach(n => dst.push(n));  // OK — push returns number, void discards it

If you used any instead of void, callers could accidentally rely on the return value and TypeScript would not warn them.

4. Do Not Mark Callback Parameters Optional Unless They Truly Won't Be Passed

It might seem defensive to mark a callback's parameters optional — "the callback might not receive all its arguments." But this is almost always wrong, and it causes problems for callers. 

// Don't — marking the callback parameter optional
type Handler = (err?: Error, data?: string) => void;

// Now callers must handle undefined even when you always pass both
function callHandler(h: Handler) {
  const err = new Error("oops");
  const data = "result";
  h(err, data);  // TypeScript types err and data as Error | undefined inside h
                 // even though you always pass them — misleading
}
// Do — parameters are required unless callers genuinely omit them
type Handler = (err: Error, data: string) => void;

// Callers can still pass a function that ignores some args —
// in TypeScript, extra parameters are safely dropped
const simple: Handler = (err) => console.error(err.message);  // OK

The rule from the TypeScript handbook: if a callback parameter will always receive a value when the callback is called, declare it required. Optional parameters on callbacks tell callers "prepare for undefined" when they do not need to.

5. Order Overloads from Most Specific to Most General

TypeScript picks the first matching overload when resolving a call. If you place a broad overload before a narrow one, the narrow one is never reached — callers always get the general signature, even when the specific one would be more accurate. 

// Don't — general overload comes first; specific one is unreachable
function create(x: string | number): string | number;
function create(x: string): string;
// TypeScript always picks the first overload for string input — returns string | number

// Do — most specific overload first
function create(x: string): string;
function create(x: number): number;
function create(x: string | number): string | number {
  return typeof x === "string" ? x.toUpperCase() : x * 2;
}

const a = create("hello");  // inferred as string
const b = create(42);       // inferred as number

6. Prefer Union Types Over Overloads When the Return Type Is the Same

Overloads are most useful when the return type changes based on the argument type. When the return type is the same regardless, a union type in a single signature is cleaner, easier to read, and easier to maintain. 

// Don't — overloads when return type doesn't change
function format(x: string): string;
function format(x: number): string;
function format(x: string | number): string {
  return String(x).trim();
}

// Do — single signature with a union parameter
function format(x: string | number): string {
  return String(x).trim();
}

The same principle applies to arities. If you have two overloads that differ only in whether an optional parameter is present, use an optional parameter instead: 

// Don't — separate overloads for optional param
function log(message: string): void;
function log(message: string, level: string): void;
function log(message: string, level?: string): void { /* ... */ }

// Do — single signature with optional param
function log(message: string, level?: string): void { /* ... */ }

7. Java Developer Pitfall Reference

The following table collects the nine most common mistakes Java developers make when moving to TypeScript, with a broken example and the corrected version side by side.

Mistake Wrong code Right code
Capitalized primitives — Java capitalizes types, TypeScript does not function f(s: String) {} function f(s: string) {}
Overusing any — feels like Java's Object but disables all checking function parse(x: any) { x.foo(); } function parse(x: unknown) { if (typeof x === "object" && x !== null && "foo" in x) { /* narrow first */ } }
Assuming private is enforced at runtime — Java's private is truly private; TypeScript's is compile-time only class A { private x = 1; } (accessible via (a as any).x) class A { #x = 1; } (true runtime privacy via JS private fields)
Expecting implements to infer parameter types — Java infers from the interface; TypeScript does not class C implements I { method(x) { } } — x is implicitly any class C implements I { method(x: ParamType) { } } — annotate explicitly
Structural typing surprises — Java uses nominal typing; TypeScript uses shape Expects new Dog() to be incompatible with Cat if they share shape Accept that { bark(): void } satisfies Dog — shape is all that matters
Forcing OOP everywhere — Java requires classes; TypeScript does not class MathUtils { static add(a: number, b: number) { return a + b; } } function add(a: number, b: number): number { return a + b; }
Forgetting types are erased at runtime — Java reflection works at runtime; TypeScript generics are gone if (value instanceof MyGenericClass<string>) {} — runtime error or invalid syntax Check shape manually: typeof value === "object" && "items" in value
Not enabling strict: true — no equivalent decision in Java; TypeScript is loose by default { "compilerOptions": {} } — implicit any, no null checks { "compilerOptions": { "strict": true } } — catches null bugs and implicit any
Using class type parameters on static members — Java also disallows this, but the error is less obvious in TypeScript class Box<T> { static empty(): Box<T> {} } — T not in scope on static class Box<T> { static empty<U>(): Box<U> {} } — static needs its own type parameter

8. Reading TypeScript Error Messages

TypeScript error codes follow a consistent numbering pattern. Knowing the ranges helps you triage errors faster:

  • 2xxx — Semantic errors: The most common category. Type mismatches, missing properties, incorrect argument types, undefined references. If you see a four-digit code starting with 2, you have a type system disagreement.
    Examples: TS2322 (type not assignable), TS2345 (argument type mismatch), TS2339 (property does not exist).
  • 7xxx — Implicit any: TypeScript could not infer a type and fell back to any. Usually means a missing annotation or a missing strict: true in tsconfig.
    Examples: TS7006 (parameter implicitly has any type), TS7031 (binding element implicitly has any type).

TypeScript's error messages can be verbose and deeply nested. The VS Code extension Pretty TypeScript Errors reformats them into plain-language explanations, highlights the exact mismatch, and links to the relevant handbook section. It is highly recommended for beginners and experienced developers alike.

Always enable strict: true in your tsconfig.json. It activates strictNullChecks, noImplicitAny, strictPropertyInitialization, and five other checks. This single setting catches roughly 80% of the mistakes described in this lesson automatically — before you even read an error message.
