Function Types and Overloads

Module 3 ~20 min call signatures · overloads · void · rest · destructuring
Primary source TypeScript Handbook — More on Functions — implementation signature is invisible to callers; prefer union types over overloads; void means "I don't care about the return value"; over-constraining generics is a common mistake.

1. Function Type Syntax

A function type in TypeScript is written as a parameter list followed by a fat arrow and a return type. This form appears in type aliases, interface properties, and inline annotations: 

// Standalone type alias
type Greet = (name: string) => string;

// Inline annotation on a variable
const greet: (name: string) => string = (name) => `Hello, ${name}`;

// Optional parameter — add ? after the name
type MaybeGreet = (name?: string) => string;

// Default value — only in the implementation, not the type
const hi = (name = "world"): string => `Hi, ${name}`;

TypeScript infers the return type from the implementation body, so you rarely need to annotate it explicitly. Annotate the return type when you want to make a contract explicit or catch mistakes at the declaration site rather than at every call site.

2. Call Signatures in Object Types

Functions are objects in JavaScript. When a function also carries properties, describe it with a call signature inside an object type or interface: 

// Object type with a call signature
type DescribableFunction = {
  description: string;
  (someArg: number): boolean;  // call signature — no fat arrow, uses colon
};

function doSomething(fn: DescribableFunction) {
  console.log(fn.description + " returned " + fn(6));
}

// Construct signature — for callable constructors
type SomeConstructor = {
  new (s: string): SomeObject;
};

// Some objects (like Date) can be called or constructed:
interface CallOrConstruct {
  (n?: number): string;
  new (s: string): Date;
}

The call signature syntax uses a colon (:) between parameters and return type, not a fat arrow. This is the only place where the two forms differ.

3. Overloads: When One Signature Isn't Enough

TypeScript overloads let a single function name accept inputs of different shapes. The mechanics look like this: write two or more overload signatures above the function body, then write an implementation signature below them that is broad enough to handle all the cases. 

// Two overload signatures (visible to callers)
function makeDate(timestamp: number): Date;
function makeDate(m: number, d: number, y: number): Date;

// Implementation signature (NOT visible to callers)
function makeDate(mOrTimestamp: number, d?: number, y?: number): Date {
  if (d !== undefined && y !== undefined) {
    return new Date(y, mOrTimestamp, d);
  }
  return new Date(mOrTimestamp);
}

makeDate(12345678);         // OK — matches first overload
makeDate(5, 5, 5);          // OK — matches second overload
makeDate(1, 3);             // Error — matches neither overload

The implementation signature is intentionally hidden. Even though it has optional parameters, callers cannot pass two arguments and expect it to work — TypeScript checks against the overload signatures, not the implementation. You must have at least two overload signatures above the body; a single overload signature alone is not valid.

Reach for overloads only when the shape of parameters genuinely changes between call forms — not just the types. If the differences can be expressed with a union type, that is almost always cleaner. Overloads add cognitive overhead: every caller must mentally filter which overload applies, and every maintainer must keep the implementation signature consistent with all overload signatures above it.

4. Prefer Union Types Over Overloads

Most real-world overload patterns are better written as a single signature with union types. Compare these two versions of a len function: 

// Overloaded version — more verbose, harder to reason about
function len(s: string): number;
function len(arr: any[]): number;
function len(x: any) {
  return x.length;
}

// Union type version — simpler, exactly as type-safe
function len(x: string | any[]): number {
  return x.length;
}

// The union version even accepts a union-typed argument directly:
len(Math.random() > 0.5 ? "hello" : [1, 2, 3]);  // OK with union, Error with overloads

The union version is strictly better here: it accepts a value whose type is string | number[] without TypeScript complaining, because the single overload already covers both. The overloaded version rejects that call because neither individual overload matches a union-typed argument.

5. void vs undefined

void and undefined are different types. undefined is a concrete value — the function literally returns undefined. void is a signal to callers that the return value is not meant to be used; TypeScript enforces this at the call site, not inside the function body. 

// undefined — function must return the value undefined
function mustReturnUndefined(): undefined {
  return;          // OK
  return undefined; // OK
  return 1;        // Error
}

// void — function's return value will be ignored by caller
function returnsVoid(): void {
  return;          // OK
  return undefined; // OK
  return 1;        // Also OK — TypeScript allows this for contextual void
}

// Difference at assignment:
const f: () => void = () => true;  // OK — return value is ignored
const v: void = f();               // v is void — you can't use it as boolean
void does not mean "returns nothing." It means "the caller is not expected to use the return value." TypeScript imposes void as a constraint on the caller, not on the implementation. A () => void function is free to return a value; TypeScript simply prevents the caller from treating that value as meaningful.

6. Why void Enables the forEach Pattern

The Array.prototype.forEach callback is typed as (value: T) => void. This is intentional: forEach ignores whatever the callback returns, so the type says so. The payoff is that you can pass any function as a callback, even one that returns a value, without a type error: 

const src = [1, 2, 3];
const dst: number[] = [];

// Array.prototype.push returns number (the new array length)
// But forEach's callback is typed as (value: number) => void
// So TypeScript accepts push as the callback without complaint
src.forEach(el => dst.push(el));  // OK — push's return value is discarded

// If forEach required () => undefined instead, this would be an error:
// src.forEach(el => dst.push(el));  // Would fail: number is not assignable to undefined

This is the reason the TypeScript team chose void over undefined for callback return types throughout the standard library. It keeps the type system practical: existing functions with return values can be used as callbacks without wrapping them in a () => { fn(); } shell.

7. Rest Parameters and Spread

Rest parameters collect any number of arguments into an array. In TypeScript, the array type must be annotated: 

// Rest parameter — typed as array
function multiply(n: number, ...m: number[]): number[] {
  return m.map(x => n * x);
}

const result = multiply(10, 1, 2, 3);  // [10, 20, 30]

Spreading an array into a function call has a subtle gotcha. TypeScript infers [1, 2] as number[], not as the tuple [number, number]. Math.atan2 takes exactly two arguments, so spreading a number[] fails: 

// Spread gotcha — inferred as number[], not [number, number]
const args = [8, 5];
Math.atan2(...args);  // Error: A spread argument must either have a tuple type
                      // or be passed to a rest parameter

// Fix 1: as const — infers [8, 5] as readonly [8, 5]
const args2 = [8, 5] as const;
Math.atan2(...args2);  // OK

// Fix 2: explicit tuple annotation
const args3: [number, number] = [8, 5];
Math.atan2(...args3);  // OK

8. Destructuring Parameters with Types

When a function accepts an object and you want to destructure it in the parameter list, the type annotation goes after the destructuring pattern — not inside it: 

// Named type — preferred for reuse
type Point = { x: number; y: number };

function printPoint({ x, y }: Point): void {
  console.log(`(${x}, ${y})`);
}

// Inline annotation — fine for one-off use
function sum({ a, b, c }: { a: number; b: number; c: number }): number {
  return a + b + c;
}

// Default values work inside the destructuring pattern, as in plain JS
function greet({ name, greeting = "Hello" }: { name: string; greeting?: string }): string {
  return `${greeting}, ${name}`;
}

A common mistake is putting the type annotation inside the braces ({ x: number } as a destructuring default), which JavaScript interprets as renaming the property to "number" rather than typing it. Always keep the type annotation outside the destructuring pattern.

9. Common Mistakes with Generics in Functions

Three patterns look reasonable but cause real problems:

Over-constraining a generic

// Bad — extends any[] widens the return type to any[]
function firstElement1<T extends any[]>(arr: T): any {
  return arr[0];
}

// Good — T inferred exactly, return type is T
function firstElement2<T>(arr: T[]): T | undefined {
  return arr[0];
}

firstElement2(["a", "b", "c"]);  // returns string | undefined  ✓

Unnecessary generic (type param appears only once)

// Bad — T is not doing any work; just use the type directly
function greet<Str extends string>(s: Str): void {
  console.log("Hello, " + s);
}

// Good — no generic needed
function greet(s: string): void {
  console.log("Hello, " + s);
}

Optional callback parameters

// Bad — marking the callback param optional causes downstream errors
function myForEach(arr: number[], callback: (arg: number, index?: number) => void) {
  // Inside, TypeScript thinks index might be undefined when it's always provided
  for (let i = 0; i < arr.length; i++) {
    callback(arr[i], i);
  }
}

// If the caller expects to use index:
myForEach([1, 2, 3], (a, i) => {
  console.log(i.toFixed()); // Error: i is possibly undefined — but it's always a number!
});

// Good — don't mark it optional if it will always be passed
function myForEach(arr: number[], callback: (arg: number, index: number) => void) { ... }
