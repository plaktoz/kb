What TypeScript Actually Is

~15 min Module 1 — Foundations · Lesson 1 of 13
Primary Source TypeScript Handbook — Introduction — typescriptlang.org/docs/handbook/intro.html

TypeScript is a static typechecker

TypeScript is a tool that checks your code for type errors before it ever runs. This is called static type checking: the analysis happens at compile time, not at runtime, so whole classes of bugs are caught while you are still writing code — not after a user triggers them in production.

Think of tsc (the TypeScript compiler) as a strict proofreader that reads your .ts files and reports every place where a value is used in a way that contradicts how you declared it.

The superset relationship: all valid JS is valid TS

TypeScript is a strict superset of JavaScript. This means every valid JavaScript file is also a valid TypeScript file — you can rename app.js to app.ts and it will compile without changes.

TypeScript adds optional type annotations on top of JavaScript syntax. You layer in as much or as little type information as you need. The language is designed so that adoption can be gradual. 

// Plain JavaScript — also valid TypeScript
function greet(name) {
  return "Hello, " + name;
}

// TypeScript with an added type annotation
function greet(name: string): string {
  return "Hello, " + name;
}

How it compiles: tsc and type erasure

You run the TypeScript compiler with the command tsc yourfile.ts. It reads the .ts source, checks for type errors, and then outputs a .js file.

The critical thing to understand is type erasure: every type annotation you write is completely removed from the output. The resulting .js file contains no TypeScript-specific syntax at all — it is plain JavaScript that any browser or Node.js runtime can execute. 

// greet.ts (TypeScript source)
function greet(name: string): string {
  return "Hello, " + name;
}

// greet.js (compiled output — types are gone)
function greet(name) {
  return "Hello, " + name;
}
TypeScript's types exist only in your editor and at compile time. They are completely invisible to the JavaScript runtime. Types cost zero bytes at runtime — they are erased before your code ever executes.

tsc outputs .js even when there are type errors

By default, tsc is forgiving: it reports type errors in the terminal but still produces a .js output file. This is a deliberate design choice. TypeScript assumes you know what you are doing; it warns you but does not refuse to compile.

You can opt into stricter behavior by passing --noEmitOnError to tsc, which stops output when errors exist. Many real-world projects enable this flag in their tsconfig.json to enforce a clean compile before shipping.

What TypeScript catches before runtime

Because TypeScript knows the shape of your values at compile time, it can catch a wide range of mistakes:

  • Typos in property names — accessing user.nmae when the property is name
  • Wrong API usage — passing a number where a function expects a string
  • Incorrect assumptions — calling a method on a value that might be undefined

None of these errors require running the program. TypeScript surfaces them instantly as you type, directly in your editor.

TypeScript type checking is not the same as JavaScript validation at runtime. Once your code compiles and runs, all type information is gone. If external data (from an API, a form, or user input) arrives in an unexpected shape, TypeScript cannot catch that — you still need runtime validation for data that crosses a trust boundary.
