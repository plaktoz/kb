1. Generic Functions

The syntax for a generic function in TypeScript will look immediately familiar to a Java developer: a type parameter in angle brackets, a name by convention, the same constraint vocabulary. The structural difference is placement — in Java the type parameter comes before the return type, while in TypeScript it follows the function name: 

// Java
public static <T> T identity(T value) {
    return value;
}

// TypeScript — type parameter after the function name
function identity<T>(value: T): T {
  return value;
}

Both achieve the same thing: a function that works with any type while preserving that type through the return value. The mental model transfers directly; only the syntax position changes.

Arrow functions use the same angle-bracket syntax, with one small exception in .tsx files where the parser might confuse <T> with a JSX tag — in that context, use <T,> (trailing comma) or <T extends object> to disambiguate: 

// Regular .ts file — fine
const identity = <T>(value: T): T => value;

// In a .tsx file — trailing comma disambiguates from JSX
const identity = <T,>(value: T): T => value;

2. Calling Generic Functions: Explicit vs Inferred

Java gained limited type inference with the diamond operator (new ArrayList<>()), but TypeScript's inference goes much further. When you call a generic function and pass a concrete argument, TypeScript almost always infers the type parameter from the argument — no angle brackets needed at the call site: 

// Explicit — compiles, but unnecessary
const a = identity<string>("hello");  // T = string, stated explicitly

// Inferred — TypeScript sees the argument "hello" and infers T = string
const b = identity("hello");           // T = string, inferred automatically
const c = identity(42);                // T = number
const d = identity({ x: 1, y: 2 });   // T = { x: number; y: number }

The TypeScript handbook recommends leaning on inference. Writing explicit type arguments is appropriate when inference cannot work (for instance, when the type parameter is not derivable from the arguments, or when you want to override inference for clarity). In practice, you write the angle brackets much less often than in Java.

3. Generic Interfaces and Classes

Both interface and class accept type parameters the same way. Generic interfaces describe shapes; generic classes carry type-safe state: 

// Generic interface
interface Box<T> {
  value: T;
  map: <U>(fn: (x: T) => U) => Box<U>;
}

// Generic class
class Stack<T> {
  private items: T[] = [];

  push(item: T): void {
    this.items.push(item);
  }

  pop(): T | undefined {
    return this.items.pop();
  }
}

const numbers = new Stack<number>();  // explicit
const words   = new Stack();           // inferred when first push supplies T

Generic classes in TypeScript behave structurally: two independent classes that happen to have the same generic shape are assignable to each other — a direct consequence of structural typing introduced in Lesson 2.

4. Constraints with extends

Java bounded type parameters use <T extends Comparable<T>> to restrict which types may fill a type parameter. TypeScript uses the identical keyword — extends — but the bound is any shape, not just a class or interface name: 

// Java — bound to an interface
public static <T extends Comparable<T>> T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

// TypeScript — bound to any shape with a .length property
function getLength<T extends { length: number }>(arg: T): number {
  return arg.length;
}

getLength("hello");          // OK — strings have .length
getLength([1, 2, 3]);        // OK — arrays have .length
getLength({ length: 7 });    // OK — matches the shape
getLength(42);               // Error — number has no .length

Because TypeScript's type system is structural, the bound can be any object shape. There is no requirement that the bound be a named interface — an inline object literal type works, as shown above. This is more flexible than Java's extends, which requires a named class or interface.

5. The keyof Operator

keyof T is a TypeScript operator with no Java equivalent. Given a type T, it produces a union of all the string (or number) literal types that are valid property names on T: 

interface User {
  name: string;
  age: number;
  email: string;
}

type UserKey = keyof User;
// Equivalent to: "name" | "age" | "email"

// The compiler knows that only these three strings are valid
function readProp(u: User, key: UserKey) {
  return u[key];
}

readProp(user, "name");    // OK
readProp(user, "phone");   // Error — "phone" is not a key of User

The union is computed statically from the type — it exists only in TypeScript's type layer and disappears after compilation. At runtime, Object.keys(user) returns a plain string[]; the key-narrowing only happens at compile time.

keyof is one of TypeScript's unique superpowers. Java has no equivalent: you cannot form a type-safe union of an object's property names. In TypeScript, keyof T makes property access generics compile-time safe in a way that Java simply cannot express. It is central to utility types like Pick<T, K>, Omit<T, K>, and Record<K, V>.

6. Type Parameter Constrained by Another Type Parameter

keyof and extends combine into one of generics' most common real-world patterns: a second type parameter that must be a valid key of the first. This lets you write a property-access function that is fully type-safe — the compiler rejects invalid key names at the call site: 

function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: "Alice", age: 30, email: "alice@example.com" };

const name  = getProperty(user, "name");   // type is string ✓
const age   = getProperty(user, "age");    // type is number ✓
const bad   = getProperty(user, "phone");  // Error: "phone" not in keyof typeof user

The return type T[K] is an indexed access type: it looks up what TypeScript knows about property K on T and uses that as the return. This is why getProperty(user, "age") returns number, not string | number | string — the compiler knows exactly which property type corresponds to "age".

7. Default Type Parameters

TypeScript adds a feature Java does not have: type parameter defaults. When a type argument can be omitted by the caller, you can specify a fallback type that TypeScript uses in its place: 

// Without a default: caller must always provide T
function createWrapper<T>(value: T): { wrapped: T } {
  return { wrapped: value };
}

// With a default: T defaults to string if omitted
function createWrapper<T = string>(value: T): { wrapped: T } {
  return { wrapped: value };
}

const a = createWrapper("hello");  // T = string (inferred from arg — same result)
const b = createWrapper(42);       // T = number (inferred from arg)

// Default type params are most useful in class/interface definitions
interface EventEmitter<T = Event> {
  on(event: string, handler: (e: T) => void): void;
}

// Using without a type argument: T defaults to Event
const emitter: EventEmitter = createEmitter();

Default type parameters are particularly common in library code where a generic interface needs a sensible fallback so callers who do not care about specialization can use it without any angle brackets. The React type definitions make heavy use of this pattern: useState<S = undefined>, for instance.

8. Erased at Runtime

Java and TypeScript generics are erased by the time your code runs. This means you cannot use a type parameter in any runtime operation that depends on knowing the concrete type — no instanceof T, no new T(), no reflective inspection of T: 

// This looks plausible but does not compile
function isType<T>(value: unknown): value is T {
  return value instanceof T;  // Error: T only refers to a type, but is being used as a value here
}

// The correct approach: pass a constructor as a runtime value
function isType<T>(value: unknown, ctor: new (...args: any[]) => T): value is T {
  return value instanceof ctor;
}

isType(user, User);   // OK — User is a real runtime value (the constructor)

This is the same limitation Java developers encounter: you cannot write x instanceof T in Java either, for the same reason. The fix is also analogous — pass a Class<T> token in Java, or a constructor reference in TypeScript.

9. Static Members Cannot Use the Class Type Parameter

Static members belong to the class itself, not to any particular instance. Because a class type parameter describes the shape of instances, it is meaningless in the static context — there is no instance T to refer to. Both Java and TypeScript enforce this: 

class Container<T> {
  // Instance members: fine to use T
  value: T;
  constructor(v: T) { this.value = v; }

  // Static members: T is not in scope here
  static count = 0;                     // OK — no T involved
  // static default: T;                 // Error: Static members cannot use T
  // static create(v: T): Container<T>  // Error: T is not defined in static scope
}

// Workaround: introduce a separate type parameter on the static method
class Container<T> {
  static of<U>(value: U): Container<U> {  // Own type param U — independent of T
    return new Container(value);
  }
}

The workaround is the same in both languages: introduce a separate type parameter on the static method itself rather than relying on the class's T.

Unnecessary generics are an anti-pattern. If a type parameter appears only once in a function signature — in one argument position, never in the return type or another argument — it carries no useful constraint. Replace it with unknown or the specific type directly. function log<T>(value: T): void adds nothing over function log(value: unknown): void; it just adds visual noise and confuses readers about what relationship is being expressed.
