1. The Three Core Primitives

TypeScript builds on three JavaScript primitives that map to the most common leaf values you will annotate every day: string, number, and boolean. They are always written in lowercase — this is not a style preference, it is a correctness requirement. 

// Correct — lowercase primitives
let username: string  = "alice";
let score:    number  = 42;
let isActive: boolean = true;

// Also valid with const — type is inferred automatically
const greeting = "hello";   // TypeScript infers: string
const pi       = 3.14159;   // TypeScript infers: number
const done     = false;     // TypeScript infers: boolean

The lowercase keywords are the actual types in the TypeScript type system. Use them in every annotation you write.

2. Never Use the Capitalized Wrapper Types

JavaScript has three built-in wrapper objects — String, Number, and Boolean (capital first letter). They exist for historical reasons and wrap primitive values in a full object. TypeScript exposes these as types, but they almost never represent what you intend.

Do not use String, Number, or Boolean (capitalised) as type annotations. They refer to the rarely-used JavaScript wrapper objects, not the primitive values you actually work with. The TypeScript documentation explicitly warns against them. Always use the lowercase forms: string, number, boolean. 
// Wrong — wrapper objects, not primitives
function greet(name: String): String {   // ❌ do not do this
  return "Hello, " + name;
}

// Right — lowercase primitives
function greet(name: string): string {   // ✓
  return "Hello, " + name;
}

The practical difference matters: a String object is not assignable to a string variable, yet a string primitive is assignable to a String variable — the asymmetry is a source of confusion with no upside.

3. Arrays

TypeScript offers two syntactically equivalent ways to declare an array type. The shorthand form is more common in practice: 

// Shorthand (preferred in most codebases)
let scores:  number[];
let names:   string[];
let flags:   boolean[];

// Generic form — identical meaning, useful inside complex generics
let scores2: Array<number>;
let names2:  Array<string>;

// Inference works as expected
const ids = [1, 2, 3];        // inferred: number[]
const tags = ["ts", "react"]; // inferred: string[]

Both forms are interchangeable. The shorthand T[] is idiomatic for everyday use; Array<T> is sometimes clearer when nested inside another generic.

4. Union Types

A union type declares that a value can be one of several types. The pipe character | separates the members: 

// A value that is either a string or a number
type StringOrNumber = string | number;

function formatId(id: string | number): string {
  return String(id);
}

formatId(42);      // ✓
formatId("abc");   // ✓
formatId(true);    // ✗ — boolean is not in the union

The narrowing requirement

When you hold a union type, TypeScript allows only the operations that are valid for all members of the union. If a method exists on string but not on number, calling it directly on a string | number is a compile error: 

function loudId(id: string | number): string {
  // id.toUpperCase();  ✗ — number has no toUpperCase

  // Must narrow first
  if (typeof id === "string") {
    return id.toUpperCase();  // ✓ — TypeScript knows it's string here
  }
  return String(id);          // ✓ — safe fallback for number branch
}

This is narrowing — TypeScript tracks which branch of a conditional is reachable and adjusts the inferred type accordingly. Narrowing is covered in depth in Lesson 7.

5. interface vs type Alias

TypeScript offers two ways to name an object shape. For most object descriptions they are interchangeable, but they differ in a few important ways:

Feature interface type
Describe an object shape Yes Yes
Extend another type with extends Yes Yes (via intersection &)
Declaration merging (add properties in a second block) Yes No — error
Reopen and extend after initial definition Yes No
Describe a union type (A | B) No Yes
Alias a primitive or tuple No Yes 
// interface — object shape
interface User {
  id:   number;
  name: string;
}

// Declaration merging: a second block adds to the same interface
interface User {
  email: string;    // merged in — now User has id, name, AND email
}

// type alias — object shape (equivalent for basic use)
type Point = {
  x: number;
  y: number;
};

// type alias — union (interface cannot do this)
type Status = "active" | "inactive" | "pending";

// type alias — primitive alias
type UserId = number;
The heuristic: use interface by default for object shapes. Reach for type when you need a union type, a primitive alias, or a tuple. In practice: if your annotation starts with { }, lean toward interface; if it involves | or a non-object value, use type.

6. Optional Properties and null Handling

Optional properties with ?

Appending a ? to a property name marks it as optional, meaning it may be present or absent. The type of an optional property is automatically widened to include undefined. 

interface Config {
  host:    string;
  port:    number;
  timeout?: number;   // may be number or undefined
}

const cfg: Config = { host: "localhost", port: 3000 };  // ✓
// timeout is absent — that's allowed

function buildUrl(cfg: Config): string {
  const t = cfg.timeout ?? 5000;  // nullish coalescing for the undefined case
  return `${cfg.host}:${cfg.port} (timeout ${t}ms)`;
}

strictNullChecks makes null explicit

With strictNullChecks: true (included in strict: true), null and undefined are not assignable to every type. You must declare them explicitly in a union and narrow before using the value: 

// Without strictNullChecks (avoid this)
let name: string = null;   // TypeScript would allow it — dangerous

// With strictNullChecks (the correct setting)
let name: string | null = null;   // must be explicit in the union
name = "alice";                   // ✓
name = null;                      // ✓
name = undefined;                 // ✗ — undefined is not in string | null

function greet(name: string | null): string {
  if (name === null) {
    return "Hello, stranger";
  }
  return "Hello, " + name;  // ✓ — TypeScript knows name is string here
}

The non-null assertion operator ! tells TypeScript you are certain a value is not null or undefined. Use it sparingly and only when you have external knowledge the type system cannot see: 

const el = document.getElementById("root")!;  // asserting el is not null
el.innerHTML = "mounted";                      // ✓ — no null-check required

7. Comparison: Java Types vs TypeScript Types

If you are coming from Java, several familiar concepts either change meaning or disappear entirely in TypeScript:

Java TypeScript equivalent Notes
int, long, float, double number All numeric values share one type. No integer/float distinction.
String (capital S) string (lowercase) TypeScript's string is a primitive, not a wrapper object.
boolean boolean Same name, same semantics.
Optional<T> T | null or T | undefined No wrapper type — nullability is expressed directly in the union with strictNullChecks.
int[] number[] or Array<number> Two syntaxes, identical meaning.
Object object or Record<string, unknown> Rarely useful in annotations; prefer a named interface.
