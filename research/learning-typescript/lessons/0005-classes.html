Classes in TypeScript

~25 min Module 2 — The Type System Lesson 5 of 13

1. Access Modifiers: public, protected, private

TypeScript uses the same three access modifier keywords you know from Java: public, protected, and private. The semantics map closely — public is accessible everywhere, protected is accessible within the class and its subclasses, and private is accessible only within the declaring class. Unlike Java, public is the default in TypeScript; you do not need to write it explicitly. 

// Java
public class Animal {
    public String name;
    protected int age;
    private String secret;
}

// TypeScript — public is the default, no keyword needed
class Animal {
  name: string;          // implicitly public
  protected age: number;
  private secret: string;

  constructor(name: string, age: number, secret: string) {
    this.name = name;
    this.age = age;
    this.secret = secret;
  }
}

The syntax is familiar enough that Java developers often skip straight to writing class-heavy code — and that is where the critical differences surface.

2. TypeScript private Is Compile-Time Only

This is the most important thing to understand about TypeScript access modifiers: they are enforced only by the compiler, not at runtime. When TypeScript compiles to JavaScript, all private and protected annotations are erased. The resulting JavaScript has no memory of those restrictions.

This means that bracket notation — which TypeScript's type checker does not allow on a typed reference — still works at runtime against the plain JavaScript object: 

// TypeScript source
class BankAccount {
  private balance: number = 0;

  deposit(amount: number) {
    this.balance += amount;
  }
}

const account = new BankAccount();
account.deposit(100);

// TypeScript compile error — good:
// account.balance;  // Error: Property 'balance' is private

// But at runtime (after compilation), bracket notation bypasses the check:
(account as any)["balance"];  // 100 — no error at runtime!
Key Point
TypeScript's private keyword is a compile-time guard only. It prevents accidental access in your editor and during compilation — but it does not create any runtime enforcement. Any caller can bypass it with bracket notation or a cast to any. If you need real runtime privacy, use #field instead.

3. Hard Privacy with #field

JavaScript (and TypeScript) natively supports truly private fields using the # prefix — called private class fields. These are enforced by the JavaScript engine itself at runtime, not just by the type checker. No amount of casting or bracket notation can access a #field from outside the class. 

// Java — private fields are enforced by the JVM at runtime
public class BankAccount {
    private double balance = 0;
    // Cannot be accessed via reflection without special permissions
}

// TypeScript — TypeScript private (compile-time only)
class BankAccount {
  private balance: number = 0;
  // (account as any)["balance"] still works at runtime
}

// TypeScript — #field (JavaScript native, truly private at runtime)
class SecureBankAccount {
  #balance: number = 0;

  deposit(amount: number) {
    this.#balance += amount;
  }

  getBalance(): number {
    return this.#balance;
  }
}

const account = new SecureBankAccount();
account.deposit(100);
// account.#balance;           // Compile error
// (account as any)["#balance"]; // undefined at runtime — truly inaccessible

Prefer #field over private when you genuinely need encapsulation guarantees — such as when your class will be serialized, inspected, or used in contexts where the TypeScript compiler is not present.

4. readonly vs Java's final

TypeScript's readonly modifier is the direct equivalent of Java's final for fields. A readonly property can be assigned in the constructor but not anywhere else. Attempts to reassign it after construction produce a compile error. 

// Java — final field
public class Point {
    public final int x;
    public final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }
}

// TypeScript — readonly field
class Point {
  readonly x: number;
  readonly y: number;

  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }
}

const p = new Point(3, 4);
// p.x = 10;  // Error: Cannot assign to 'x' because it is a read-only property

Note that readonly is also a compile-time constraint — the emitted JavaScript contains no enforcement. At runtime, the property is a plain writable JavaScript property. Use Object.freeze() if you need runtime immutability.

5. Abstract Classes

Abstract classes work in TypeScript the same way they do in Java: you cannot instantiate an abstract class directly, and any concrete subclass must implement all abstract methods. The abstract keyword marks both the class and the methods that subclasses must provide. 

// Java
abstract class Shape {
    abstract double area();

    void describe() {
        System.out.println("Area: " + area());
    }
}

class Circle extends Shape {
    double radius;
    Circle(double r) { this.radius = r; }

    @Override
    double area() { return Math.PI * radius * radius; }
}

// TypeScript
abstract class Shape {
  abstract area(): number;  // must be implemented by subclasses

  describe(): void {
    console.log("Area:", this.area());
  }
}

class Circle extends Shape {
  constructor(public radius: number) { super(); }

  area(): number {
    return Math.PI * this.radius ** 2;
  }
}

// new Shape();  // Error: Cannot create an instance of an abstract class
const c = new Circle(5);
c.describe();  // Area: 78.53...

6. The implements Gotcha

In Java, when a class implements an interface, the compiler fills in the declared parameter types from the interface signature. If Greeter declares greet(name: String), your implementing method automatically knows its parameter is a String.

TypeScript does not work this way. implements only checks that the class satisfies the interface contract — it does not propagate type information into the method bodies. Inside the class, parameters are untyped unless you annotate them explicitly. 

// Java — interface parameter types flow into the implementing class
interface Greeter {
    void greet(String name);
}

class FriendlyGreeter implements Greeter {
    public void greet(String name) {
        // 'name' is automatically String — no annotation needed
        System.out.println("Hello, " + name.toUpperCase());
    }
}

// TypeScript — implements does NOT infer parameter types
interface Greeter {
  greet(name: string): void;
}

class FriendlyGreeter implements Greeter {
  greet(name) {
    // With strict mode, 'name' is implicitly 'any' here — NOT inferred as string!
    // TypeScript compile error under strictNullChecks / noImplicitAny:
    // Parameter 'name' implicitly has an 'any' type.
    console.log("Hello, " + name.toUpperCase());
  }
}

// Correct TypeScript — annotate the parameter yourself
class FriendlyGreeter implements Greeter {
  greet(name: string): void {
    console.log("Hello, " + name.toUpperCase());
  }
}
Java Developer Warning
TypeScript's implements is a shape-check, not a type-inference trigger. Writing implements Greeter tells the compiler "verify that this class satisfies Greeter" — it does not automatically annotate your method parameters with the interface's types. Always annotate parameters explicitly in implementing classes, even when the interface already defines them.

7. Structural Class Comparison

As covered in Lesson 2, TypeScript uses structural typing — and this applies fully to classes. Two completely unrelated classes with the same shape are interchangeable from the type checker's perspective. You do not need a shared base class or interface for TypeScript to accept one in place of the other. 

// Java — this does NOT compile; Dog and Cat are unrelated types
class Dog { String name; }
class Cat { String name; }

Dog d = new Cat();  // Compile error: incompatible types

// TypeScript — this compiles fine; same shape = compatible types
class Dog {
  constructor(public name: string) {}
}

class Cat {
  constructor(public name: string) {}
}

// Dog and Cat are completely unrelated — no extends, no shared interface.
// TypeScript accepts this because their shapes are identical.
const d: Dog = new Cat("Whiskers");  // OK!

This behavior surprises Java developers regularly. If you need nominal-style safety (accept a Dog but never a Cat, even if they look alike), you need a branded type or a discriminant field — both of which are advanced patterns covered later in the course.

8. Parameter Properties — No Java Equivalent

TypeScript offers a shorthand that Java has no equivalent for: parameter properties. When you prefix a constructor parameter with an access modifier or readonly, TypeScript automatically declares a field with the same name and assigns the argument to it. This eliminates the Java boilerplate of declaring a field, then assigning it in the constructor body. 

// Java — three separate steps: declare field, accept param, assign
public class Person {
    private final String name;
    private final int age;

    public Person(String name, int age) {
        this.name = name;
        this.age = age;
    }
}

// TypeScript — verbose equivalent (works but is unnecessary)
class Person {
  private readonly name: string;
  private readonly age: number;

  constructor(name: string, age: number) {
    this.name = name;
    this.age = age;
  }
}

// TypeScript — parameter property shorthand (idiomatic)
class Person {
  constructor(
    private readonly name: string,
    private readonly age: number,
  ) {}
  // TypeScript generates the field declarations and assignments automatically.
  // The constructor body is empty — nothing else is needed.
}

const p = new Person("Alice", 30);
// p.name is inaccessible from outside (private)
// p.age is inaccessible from outside (private)

Parameter properties work with any access modifier: public, protected, private, readonly, or any combination. They are the idiomatic way to define simple value-holding classes in TypeScript.

9. No Need for Static Utility Classes

Java forces nearly all code into classes, which leads to a common pattern: a class with nothing but static methods, serving as a namespace for related utilities. TypeScript does not require this. Because TypeScript modules are first-class namespaces, you can export plain functions and objects directly from a file. The static utility class antipattern has no purpose in TypeScript. 

// Java — everything must live in a class
public class MathUtils {
    public static int clamp(int value, int min, int max) {
        return Math.max(min, Math.min(max, value));
    }
    public static double lerp(double a, double b, double t) {
        return a + (b - a) * t;
    }
}
int result = MathUtils.clamp(15, 0, 10);

// TypeScript — plain module-level functions (idiomatic)
export function clamp(value: number, min: number, max: number): number {
  return Math.max(min, Math.min(max, value));
}

export function lerp(a: number, b: number, t: number): number {
  return a + (b - a) * t;
}

// Caller imports only what they need
import { clamp } from "./math-utils";
const result = clamp(15, 0, 10);

Classes in TypeScript exist for encapsulation, inheritance, and instances that carry mutable state. If your class would have no instance methods and no constructor — just static methods — replace it with module-level functions.
