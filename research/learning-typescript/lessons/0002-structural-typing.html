Structural Typing — The Java Instinct to Unlearn

~20 min Module 1 — Foundations Lesson 2 of 13
Primary source TypeScript for Java/OOP Programmers — typescriptlang.org/docs/handbook/typescript-in-5-minutes-oop.html

1. How Java Thinks: Types by Name

If you learned to code in Java (or C#, or another classical OOP language), you carry a deep instinct about types: a value belongs to a type only if it was explicitly declared to be that type. This is called nominal typing.

In Java, two classes with identical fields are not interchangeable unless one explicitly extends the other or they share a common interface. The type system tracks names and inheritance chains, not structure. 

// Java
class Dog {
    String name;
    void speak() { System.out.println("Woof"); }
}

class Cat {
    String name;
    void speak() { System.out.println("Meow"); }
}

// This does NOT compile in Java — Cat is not Dog,
// regardless of how similar they look.
Dog d = new Cat();  // ERROR: incompatible types

The Java compiler enforces this even if Cat and Dog have identical fields and methods. Name matters. Declaration matters. Shape does not.

2. How TypeScript Thinks: Types by Shape

TypeScript takes the opposite approach: structural typing. The type checker asks only one question — does this value have all the properties the type requires? If yes, the value is compatible. Where it came from, what class it was instantiated from, and what name you gave that class are all irrelevant. 

// TypeScript
class Dog {
  name: string;
  constructor(name: string) { this.name = name; }
  speak() { console.log("Woof"); }
}

class Cat {
  name: string;
  constructor(name: string) { this.name = name; }
  speak() { console.log("Meow"); }
}

// TypeScript: this works fine.
// Dog and Cat have the same shape, so Cat satisfies a Dog variable.
const d: Dog = new Cat("Whiskers");  // OK!

There is no inheritance link between Dog and Cat, yet TypeScript accepts the assignment. Both classes have a name: string property and a speak() method — their shapes match, so they are compatible.

In TypeScript, shape wins. The type checker does not care what you called your class. If a value carries all the properties a type requires, it is that type — whether or not it was ever declared as such.
Java developers are often surprised to discover that two completely unrelated classes are silently interchangeable in TypeScript. This is not a bug — it is the language's core design. Expect it everywhere. Nominal-style safety (type X only when declared X) requires extra patterns like branded types, which come much later.

3. Types as Sets of Values

A helpful mental model: every type in TypeScript is a set of values. A variable typed as Dog can hold any value that belongs to the Dog set — any object that has at least the properties Dog describes.

This means a single value can belong to multiple types simultaneously. An object with properties name, speak, and fly belongs to the Dog set (has name + speak), the Cat set (also has name + speak), and some hypothetical Bird set (has fly). Sets can overlap freely. 

// TypeScript — a value in multiple types at once
type Named   = { name: string };
type Audible = { speak(): void };

class Parrot {
  name: string;
  constructor(name: string) { this.name = name; }
  speak() { console.log("Squawk"); }
  fly() { console.log("Flap"); }
}

const p = new Parrot("Polly");

// p belongs to Named — it has .name
const n: Named   = p;   // OK

// p belongs to Audible — it has .speak()
const a: Audible = p;   // OK

// p belongs to both at once — no contradiction
const na: Named & Audible = p;  // also OK

4. Empty Types Accept Everything

One immediate consequence of the set model: an empty type — a type with no required properties — places no constraints on a value. Every possible value already satisfies an empty shape, so every value belongs to the empty-type set. 

// TypeScript
class Empty {}

// An empty class has no shape requirements to fail.
// Any object with any properties satisfies it.
const e1: Empty = { name: "Alice", age: 30 };  // OK
const e2: Empty = new Date();                   // OK
const e3: Empty = () => 42;                    // OK (functions are objects)

// Compare this to Java: new Empty() in Java is just new Empty() —
// nothing else can be assigned to an Empty variable.
// In TypeScript, empty means "no requirements" = "accepts everything."

This is surprising if you expect empty to mean "nothing allowed." In the set model, empty type = the set of all values with at least zero properties = every value.

5. TypeScript Types Disappear at Runtime

In Java, type information is preserved at runtime. You can call obj.getClass(), use instanceof reliably across the hierarchy, and use reflection to inspect annotations and field types.

TypeScript has no equivalent. All type information is fully erased when your code is compiled to JavaScript. The output is plain JavaScript — there is no trace of your interfaces, type aliases, or generic type parameters at runtime. 

// TypeScript source
interface Point { x: number; y: number; }

function log(p: Point) {
  console.log(p.x, p.y);
}

// Compiled JavaScript output — interface is gone
function log(p) {
  console.log(p.x, p.y);
}
// TypeScript — runtime type checking must use JavaScript means only
function isPoint(val: unknown): val is Point {
  // You cannot ask "is this a Point?" at runtime directly.
  // You must check properties manually:
  return (
    typeof val === "object" &&
    val !== null &&
    "x" in val &&
    "y" in val
  );
}

There is no getClass(). There is no generic reflection over TypeScript types. At runtime, you have JavaScript. Plan accordingly.

6. You Do Not Need Classes

Java forces almost all code into classes. TypeScript does not. Because structural typing cares only about shape, a plain function is just as valid as a method on a class. In fact, free functions are idiomatic TypeScript — they are simpler, easier to test, and do not carry the overhead of class instantiation. 

// Java style — everything in a class
class MathUtils {
    public static int add(int a, int b) {
        return a + b;
    }
}
int result = MathUtils.add(2, 3);
// TypeScript — free function, no class needed
function add(a: number, b: number): number {
  return a + b;
}

const result = add(2, 3);  // 5

Classes still exist in TypeScript and are useful for encapsulation, but they are a tool, not a requirement. You will write many TypeScript files with no class at all.
