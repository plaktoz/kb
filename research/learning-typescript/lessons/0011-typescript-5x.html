Standard Decorators

TypeScript 5.0 shipped standard decorators as a stable feature, implementing the TC39 decorator proposal. Unlike the old experimentalDecorators flag, standard decorators require no special tsconfig option — they are just on by default.

A decorator is a function that wraps a class or class member. Here is a @loggedMethod decorator that logs calls to any method it is applied to: 

function loggedMethod(originalMethod: any, context: ClassMethodDecoratorContext) {
  const methodName = String(context.name);

  function replacement(this: any, ...args: any[]) {
    console.log(`Entering ${methodName}`);
    const result = originalMethod.call(this, ...args);
    console.log(`Exiting ${methodName}`);
    return result;
  }

  return replacement;
}

class Greeter {
  @loggedMethod
  greet(name: string) {
    console.log(`Hello, ${name}!`);
  }
}

const g = new Greeter();
g.greet("world");
// Logs: Entering greet → Hello, world! → Exiting greet

You can stack multiple decorators on the same target. They are applied bottom-up — the decorator closest to the class member runs first, the outermost runs last: 

@first   // runs second (outermost)
@second  // runs first (closest to the method)
greet(name: string) { ... }

Decorator factories are functions that return a decorator, letting you pass configuration at the call site: 

function loggedMethod(label: string) {
  return function (originalMethod: any, context: ClassMethodDecoratorContext) {
    return function (this: any, ...args: any[]) {
      console.log(`[${label}] Entering ${String(context.name)}`);
      return originalMethod.call(this, ...args);
    };
  };
}

class Greeter {
  @loggedMethod("DEBUG")
  greet(name: string) {
    console.log(`Hello, ${name}!`);
  }
}
The old experimentalDecorators flag and the new standard decorators are incompatible systems. If experimentalDecorators: true is set in your tsconfig, TypeScript uses the legacy behavior and will not accept standard decorator syntax. If your codebase or a library relies on the old decorator API, you must choose one or the other — you cannot mix them in the same compilation.

const Type Parameters

Before TypeScript 5.0, when you passed an array literal to a generic function, TypeScript inferred a wide type (string[]) rather than a narrow tuple. The only workaround was a manual as const at every call site: 

// Before: infers string[], not ["a", "b"]
function first<T>(arr: T[]) { return arr[0]; }
const x = first(["a", "b"]); // type: string

// Caller had to write:
const x = first(["a", "b"] as const); // type: "a"

TypeScript 5.0 lets you add a const modifier directly on the type parameter. The compiler then infers the narrowest possible type automatically — no as const required at each call site: 

// After: const modifier on the type parameter
function first<const T extends readonly unknown[]>(arr: T) {
  return arr[0];
}

const x = first(["a", "b"]); // type: "a" — narrow, no as const needed

This is especially useful for utility functions that build configuration objects, route definitions, or any API where callers want narrow literal types without extra boilerplate.

Multiple extends in tsconfig

Previously, a tsconfig.json could only extend a single base config. TypeScript 5.0 allows extends to accept an array of base configs. Later entries in the array override earlier ones: 

// tsconfig.json
{
  "extends": [
    "@tsconfig/strictest/tsconfig.json",
    "@tsconfig/node20/tsconfig.json"
  ],
  "compilerOptions": {
    "outDir": "dist"
  }
}

This makes it easier to compose community-maintained base configs (like those from tsconfig/bases) without manually duplicating their options into a single file.

All Enums Are Now Union Enums

In earlier TypeScript, only enums with literal values (strings or simple numbers) were treated as union enums — unions of their member literal types — enabling type narrowing on individual members. Computed enum members were excluded, which created inconsistent behavior.

TypeScript 5.0 makes all enums union enums. This means you can now narrow on any enum member, and TypeScript reports an error if a switch statement or conditional does not cover all members: 

enum Direction {
  Up,
  Down,
  Left,
  Right
}

function move(dir: Direction) {
  if (dir === Direction.Up) {
    // TypeScript knows dir is Direction.Up here
  } else if (dir === Direction.Down) {
    // TypeScript knows dir is Direction.Down here
  }
  // Exhaustiveness checking now works for all enums
}

This brings enums in line with discriminated unions for the purposes of control-flow analysis and exhaustiveness checking.

moduleResolution: "bundler"

Modern build tools like Vite, esbuild, and webpack handle module resolution differently from Node.js. They allow extensionless imports (import './utils' instead of import './utils.js') and support package.json exports fields for subpath mapping.

TypeScript 5.0 introduces moduleResolution: "bundler" specifically for these environments. It lets TypeScript model the bundler's behavior accurately — accepting extensionless relative imports without requiring the .js extension that moduleResolution: "node16" demands: 

// tsconfig.json — for a Vite project
{
  "compilerOptions": {
    "module": "ESNext",
    "moduleResolution": "bundler"
  }
}
// With moduleResolution: "bundler" — both of these are valid
import { add } from './math';       // extensionless ✓
import { add } from './math.js';    // with extension also ✓

// With moduleResolution: "node16" — this would be an error
import { add } from './math';       // must write './math.js' ✗
If you are building a project with Vite, esbuild, or webpack, use moduleResolution: "bundler" — it matches what your build tool actually does and avoids spurious errors about missing .js extensions. Pair it with verbatimModuleSyntax: true (covered below) for a well-configured modern setup.

verbatimModuleSyntax

TypeScript 5.0 introduced verbatimModuleSyntax as a cleaner, more predictable replacement for the older importsNotUsedAsValues and preserveValueImports flags. The rule is simple:

  • import type { Foo } — the type keyword signals a type-only import. TypeScript erases this import entirely from the compiled output. It will never appear in the .js file.
  • import { Bar } — no type keyword. TypeScript keeps this import in the output as-is, assuming it may have a runtime side effect or that Bar is a value, not just a type. 
// Source (.ts)
import type { User } from './types';   // type-only — will be erased
import { createUser } from './api';    // value import — will be kept

// Compiled output (.js)
import { createUser } from './api';    // only this survives

With verbatimModuleSyntax enabled, TypeScript enforces that you are explicit: if you import something that is only used as a type, you must write import type. Forgetting to do so causes a compile error, which prevents accidental runtime imports of type-only modules. 

// tsconfig.json
{
  "compilerOptions": {
    "verbatimModuleSyntax": true
  }
}

// This is now an error if `User` is only used as a type:
import { User } from './types';       // Error: use `import type` instead
import type { User } from './types';  // Correct

Performance Improvements

TypeScript 5.0 delivered significant build toolchain improvements alongside the language features:

  • 10–20% faster compilation — the TypeScript team rewrote internal data structures (moving from namespaces to modules) and restructured the compiler pipeline, yielding measurable speed gains on real-world projects.
  • 59% smaller npm package — the published typescript package on npm dropped from ~63 MB to ~26 MB. This speeds up npm install in CI environments and reduces disk usage across projects.

These gains are automatic — no config changes are needed. They apply to any project that upgrades to TypeScript 5.x.
