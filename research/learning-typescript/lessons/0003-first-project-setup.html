1. Installing TypeScript

TypeScript is distributed as an npm package. The most common approach for a new project is to install it as a local dev dependency so every contributor uses the same version pinned to your package.json. A global install is convenient for quick experiments but can cause version mismatches across projects.

Global install (quick experiments)

# Install the TypeScript compiler globally
npm install -g typescript

# Verify the install
tsc --version

Local install (recommended for real projects)

# Inside your project directory
npm init -y
npm install --save-dev typescript

# Run tsc via npx so it uses the local version
npx tsc --version

With a local install, the tsc binary lives in node_modules/.bin/tsc. You can also add a build script in package.json so npm run build always uses the project-local compiler.

2. Writing Your First .ts File

A TypeScript file is just JavaScript with type annotations layered on top. Start by annotating a simple function — add a type to each parameter and a return type after the closing parenthesis. 

// src/index.ts

function greet(name: string): string {
  return "Hello, " + name;
}

console.log(greet("TypeScript"));

The : string after each parameter and the : string after (name: string) are the only additions compared to plain JavaScript. If you call greet(42), TypeScript reports an error at compile time — before the code ever runs.

3. Compiling with tsc

The TypeScript compiler converts .ts files into plain JavaScript that any runtime (Node.js, browsers) can execute. In the simplest case, pass the file directly: 

# Compile a single file
tsc src/index.ts

# This produces: src/index.js
node src/index.js
# → Hello, TypeScript
Even when tsc reports type errors, it still emits a .js output file by default. This means you can accidentally deploy broken code if you rely on the file being present as a signal of success. Always check the exit code, or set "noEmitOnError": true in your tsconfig to suppress output on failure.

4. Why tsconfig.json Matters

Compiling single files with tsc filename.ts does not scale. For any real project you need a tsconfig.json — the configuration file that tells the compiler which files to include, where to write output, and which rules to enforce. Think of it as the TypeScript equivalent of pom.xml or build.gradle: it defines the build contract for the entire project so every developer and every CI run uses identical settings.

Once tsconfig.json exists in the project root, you simply run: 

# Compile the whole project using tsconfig.json
npx tsc

# Or watch for changes and recompile automatically
npx tsc --watch

5. The Recommended Starter tsconfig.json

The options below cover the most important compiler settings for a modern Node.js project. You can generate a baseline with npx tsc --init and then adjust, or start from this file directly. 

{
  "compilerOptions": {
    "target": "ES2020",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "sourceMap": true,
    "declaration": true,
    "esModuleInterop": true
  },
  "include": ["src/**/*"],
  "exclude": ["node_modules", "dist"]
}
Option What it does
target Which JavaScript version to emit. ES2020 supports modern syntax while remaining broadly compatible.
module Module system for emitted code. nodenext enables native ESM for Node.js 12+.
outDir Where compiled .js files are written. Keeps source and build artifacts separate.
rootDir Root of your TypeScript source files. Mirrors the src/ structure inside dist/.
strict Enables the full suite of strict type-checking options (see below).
sourceMap Emits .js.map files so debuggers map runtime errors back to TypeScript lines.
declaration Emits .d.ts type declaration files — essential if publishing a library.
esModuleInterop Allows default imports from CommonJS modules (import fs from 'fs' instead of import * as fs).

6. Why strict: true Is the Single Most Important Setting

"strict": true is a shorthand that activates a bundle of checks in a single line. The two most impactful are strictNullChecks, which makes TypeScript treat null and undefined as distinct types that must be handled explicitly, and noImplicitAny, which disallows parameters or variables whose type would silently default to any. Together, these two checks eliminate the largest categories of real-world runtime errors. Always start a project with strict: true — retrofitting it onto an existing codebase later is painful.

The full list of checks enabled by strict: true includes:

  • strictNullChecks — null and undefined are not assignable to other types
  • noImplicitAny — parameters without a type annotation raise an error instead of defaulting to any
  • strictFunctionTypes — function parameters are checked contravariantly
  • strictBindCallApply — .bind, .call, and .apply are type-checked
  • strictPropertyInitialization — class properties must be assigned in the constructor
  • noImplicitThis — this in functions must have an explicit type
  • useUnknownInCatchVariables — caught error variables are typed as unknown, not any

7. Project Structure: src/ → dist/

The rootDir / outDir pair enforces a clean separation: TypeScript source lives in src/ and compiled JavaScript lands in dist/. Add dist/ to your .gitignore — build artifacts belong in CI, not version control. 

my-project/
├── src/
│   └── index.ts        ← TypeScript source (what you edit)
├── dist/
│   ├── index.js        ← compiled output (generated by tsc)
│   ├── index.js.map    ← source map (generated when sourceMap: true)
│   └── index.d.ts      ← type declarations (generated when declaration: true)
├── tsconfig.json
└── package.json

8. Running the Compiled JavaScript

After npx tsc succeeds, run the output file with Node.js directly. There is no TypeScript runtime — node executes plain JavaScript that the compiler produced. 

# Compile
npx tsc

# Run the output
node dist/index.js
# → Hello, TypeScript

During development you may prefer ts-node or tsx, which compile and run a .ts file in one step without writing to dist/. For production, always compile first and run the compiled output — that is what your users execute.
