1. Getting Started: Skip the Manual Config

TypeScript supports JSX natively, but in practice you should never configure the compiler by hand for a new project. Two scaffolding tools handle everything for you: 

# Next.js — TypeScript is the default
npx create-next-app@latest my-app

# Vite — choose the React + TypeScript template
npm create vite@latest my-app -- --template react-ts

Both tools ship a tsconfig.json with the correct "jsx": "react-jsx" setting, the right lib entries, and path aliases pre-wired. Starting from scratch with tsc --init is unnecessary and error-prone for React projects.

Once scaffolded, rename any file from .js to .tsx to enable JSX syntax with full type checking. Files that contain no JSX can use .ts.

2. Typing Props with an Interface

The idiomatic pattern is to define an interface for a component's props and then destructure directly in the function signature. TypeScript checks every caller against that interface at compile time. 

// Button.tsx
interface ButtonProps {
  label: string;
  onClick: () => void;
  variant: "primary" | "secondary";
}

function Button({ label, onClick, variant }: ButtonProps) {
  return (
    <button className={variant} onClick={onClick}>
      {label}
    </button>
  );
}

// Usage — TypeScript enforces all three props are present and correct:
<Button label="Save" onClick={() => save()} variant="primary" />

// TypeScript error — "variant" is missing:
<Button label="Save" onClick={() => save()} />
Do not type the component itself as React.FC<ButtonProps>. That pattern adds an implicit children prop you may not want and obscures the return type. Annotating props directly in the function signature gives clearer types, better inference, and less boilerplate.

3. Optional Props with ?

Append ? to any prop name in the interface to make it optional. TypeScript will treat the prop's type as T | undefined inside the component, which forces you to handle the absent case explicitly. 

interface AlertProps {
  message: string;
  title?: string;          // optional — may be undefined
  onDismiss?: () => void;  // optional callback
}

function Alert({ message, title, onDismiss }: AlertProps) {
  return (
    <div className="alert">
      {title && <strong>{title}</strong>}
      <p>{message}</p>
      {onDismiss && (
        <button onClick={onDismiss}>Dismiss</button>
      )}
    </div>
  );
}

// Valid — only the required prop:
<Alert message="Disk space low" />

// Also valid — all props supplied:
<Alert message="Disk space low" title="Warning" onDismiss={handleDismiss} />

4. useState with an Explicit Type Parameter

When you call useState, TypeScript infers the state type from the initial value. That works perfectly when the initial value reveals the full type: 

const [count, setCount] = useState(0);       // inferred: number
const [name, setName]   = useState("Alice"); // inferred: string

But when the initial value is null, [], or {}, inference cannot determine the full type — it would lock you into null forever, or infer never[] for the array. Supply the type parameter explicitly: 

interface User {
  id: number;
  name: string;
  email: string;
}

// Initial value is null — TypeScript needs the full union:
const [user, setUser] = useState<User | null>(null);

// Initial value is [] — TypeScript needs to know what goes in the array:
const [items, setItems] = useState<string[]>([]);

// Initial value is {} — same problem:
const [filters, setFilters] = useState<Record<string, string>>({});
Always provide an explicit type parameter to useState when the initial value is null, an empty array [], or an empty object {}. Without it, TypeScript infers a type that is too narrow and you will hit errors the moment you try to set real data.

5. Typing Refs with useRef

useRef takes a generic type parameter for the DOM element it will point to. Pass null as the initial value so React can manage the assignment during mount. 

import { useRef, useEffect } from "react";

function SearchBox() {
  // Type parameter = the DOM element type; initial value = null
  const inputRef = useRef<HTMLInputElement>(null);

  useEffect(() => {
    // inputRef.current is HTMLInputElement | null
    // The optional chain handles the null case safely:
    inputRef.current?.focus();
  }, []);

  return <input ref={inputRef} type="text" placeholder="Search..." />;
}

The generic parameter tells TypeScript exactly which properties and methods are available on inputRef.current. Use the matching HTML element type: HTMLButtonElement, HTMLFormElement, HTMLDivElement, and so on.

6. Event Handler Types

React's synthetic events are generic types parameterised on the element that fires them. TypeScript uses this to give you accurate access to event.target and event.currentTarget properties. 

import { useState } from "react";

function ContactForm() {
  const [email, setEmail] = useState("");

  // input onChange
  function handleEmailChange(event: React.ChangeEvent<HTMLInputElement>) {
    setEmail(event.target.value); // event.target is HTMLInputElement
  }

  // form onSubmit
  function handleSubmit(event: React.FormEvent<HTMLFormElement>) {
    event.preventDefault();
    console.log("Submitting:", email);
  }

  // button onClick
  function handleReset(event: React.MouseEvent<HTMLButtonElement>) {
    event.currentTarget.blur();
    setEmail("");
  }

  return (
    <form onSubmit={handleSubmit}>
      <input
        type="email"
        value={email}
        onChange={handleEmailChange}
      />
      <button type="submit">Send</button>
      <button type="button" onClick={handleReset}>Clear</button>
    </form>
  );
}

The three event types you will reach for most often:

  • React.ChangeEvent<HTMLInputElement> — input, textarea, select onChange
  • React.FormEvent<HTMLFormElement> — form onSubmit
  • React.MouseEvent<HTMLButtonElement> — button and div onClick

7. The Children Prop: React.ReactNode

When a component accepts children, add a children prop typed as React.ReactNode. This type is a broad union that covers every value React can render: JSX elements, strings, numbers, arrays, fragments, portals, booleans, and null. 

interface CardProps {
  title: string;
  children: React.ReactNode; // any valid React output
}

function Card({ title, children }: CardProps) {
  return (
    <div className="card">
      <h2 className="card-title">{title}</h2>
      <div className="card-body">{children}</div>
    </div>
  );
}

// All of these are valid children:
<Card title="Info">Plain text content</Card>
<Card title="Form"><ContactForm /></Card>
<Card title="List">{[1, 2, 3].map(n => <span key={n}>{n}</span>)}</Card>

Use React.ReactElement instead when you need to enforce that only a single JSX element can be passed (no strings, no null). This is less common but useful for slot-based APIs.

8. Generic Components for Type-Safe Lists

Function components can be generic, just like any other TypeScript function. This lets you write reusable components that stay fully typed over whatever data they receive. 

// A list component that works with any item type,
// as long as each item has a numeric id.
function List<T extends { id: number }>({
  items,
  renderItem,
}: {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}) {
  return (
    <ul>
      {items.map((item) => (
        <li key={item.id}>{renderItem(item)}</li>
      ))}
    </ul>
  );
}

// TypeScript infers T = { id: number; name: string } from usage:
const users = [
  { id: 1, name: "Alice" },
  { id: 2, name: "Bob" },
];

<List
  items={users}
  renderItem={(user) => <span>{user.name}</span>}
/>

// TypeScript error — passing a string where a number is expected:
<List
  items={[{ id: "x", name: "Alice" }]}  // ERROR: string is not assignable to number
  renderItem={(user) => <span>{user.name}</span>}
/>

The constraint T extends { id: number } means TypeScript will reject any item type that lacks a numeric id — while still inferring the full shape of T and passing it through to renderItem.
