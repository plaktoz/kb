The Five Principles

~10 min Module 1
Primary source https://ui.shadcn.com/docs — the five explicit design principles behind every architectural decision in shadcn/ui

shadcn/ui is not a grab-bag of components. Every decision — why you copy code instead of installing a package, why it uses Tailwind, why it works well with AI editors — traces back to five stated principles. Learn these five, and the rest of the library starts to explain itself.

The five principles are not marketing copy. They are the architectural constraints that determined every design choice in shadcn/ui. When something about the library surprises you, one of these principles is almost always the explanation.

1 — Open Code

When you add a shadcn/ui component, its source code lands directly in your repository. You own it outright — there is no upstream version to wait for, no API boundary to work around, no PR to submit. If you want to remove the hover animation on Button, you open the file and delete it.

This is a deliberate inversion of the conventional library model. Most UI libraries hide their internals behind a versioned package. shadcn/ui exposes them by design, treating editability as a first-class feature.

2 — Composition

Components are built from smaller, focused primitives rather than monolithic widgets. A Dialog is assembled from a DialogTrigger, DialogContent, DialogHeader, and so on — each piece exported separately so you can use exactly the parts you need.

Because the source lives in your project, you can also compose pieces in ways the original author never anticipated. The composition principle means you extend by assembling, not by overriding a deeply nested prop.

All components are built to be accessible — WCAG-compliant, screen-reader friendly, and keyboard-navigable — because accessibility is baked into the Radix UI primitives that shadcn/ui wraps.

3 — Distribution

shadcn/ui distributes components through a flat-file schema and a CLI. When you run shadcn add button, the CLI reads a registry definition and writes the component files directly into your project. Nothing is installed as a runtime dependency; the component is your code from that point forward.

The flat-file schema also means the distribution mechanism is transparent. You can inspect exactly what will be written before it lands, and the CLI respects your project's existing path aliases and style configuration set during shadcn init.

4 — Beautiful Defaults

Components ship with sensible visual defaults so a freshly added button looks polished without any extra configuration. The styling is powered by Tailwind utility classes, which are straightforward to read and override — changing a background color means swapping a class name rather than fighting a theme object or CSS specificity.

CSS variables underpin the color system, so a single change to --primary in your stylesheet propagates to every component that references that token. Beautiful defaults are a starting point, not a cage.

5 — AI-Ready

Because you own the source, an AI coding assistant can read your actual component implementation. It is not guessing from documentation or reasoning about a black-box package — it sees the real file, with your real customisations, and can suggest targeted edits.

This is not a retrofitted feature. It is a direct consequence of the Open Code principle: when implementation details live in your repository rather than inside a node_modules folder, every tool that reads your codebase gains full visibility into your UI layer.

A common misconception is that "AI-Ready" is a separate, special feature you enable. It is not. AI tooling works well with shadcn/ui because Open Code puts the source in your repo. The two principles are the cause and the effect, not two independent switches.

How the Principles Work Together

The five principles are not independent. Open Code makes Distribution meaningful (copying code into your project only matters if you can actually edit it). Distribution makes Composition practical (flat files are easy to assemble and reorganise). Beautiful Defaults lower the cost of starting, and AI-Ready makes iterating faster once you have something working.

Understood together, they explain why shadcn/ui feels different from other UI libraries — not just in what it gives you, but in the kind of ownership it asks you to take on.
