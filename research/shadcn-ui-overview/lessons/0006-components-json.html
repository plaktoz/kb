components.json — The Decisions You Can't Undo

~10 min Module 3
Primary source https://ui.shadcn.com/docs/components-json — explains every field in components.json, which settings are locked at init, and what each one controls

When you run shadcn init, the CLI writes a file called components.json to your project root. It is a short JSON configuration that tells the CLI everything it needs to know about your setup: where to put components, what style you chose, whether you are using TypeScript, and how to resolve path aliases.

Most of those settings can be adjusted later without drama. Three of them cannot. Understanding which three — and why — is the entire point of this lesson.

What components.json looks like

A freshly generated file looks roughly like this: 

{
  "$schema": "https://ui.shadcn.com/schema.json",
  "style": "new-york",
  "rsc": true,
  "tsx": true,
  "tailwind": {
    "config": "tailwind.config.ts",
    "css": "app/globals.css",
    "baseColor": "zinc",
    "cssVariables": true,
    "prefix": ""
  },
  "aliases": {
    "components": "@/components",
    "utils": "@/lib/utils",
    "ui": "@/components/ui",
    "lib": "@/lib",
    "hooks": "@/hooks"
  }
}

Every field has a job. The table below gives a quick tour.

Field-by-field reference

Field What it controls Changeable later?
style Visual design language for all components — new-york (sharp, tighter spacing) or default (softer, more rounded) No
tailwind.baseColor The neutral palette (e.g. zinc, slate, gray) baked into CSS variable values that every component references No
tailwind.cssVariables Whether components use CSS custom properties (true) or inline Tailwind utility classes (false) for theming No
rsc Whether to generate React Server Component-compatible files Yes
tsx Whether to output .tsx (TypeScript) or .jsx (JavaScript) files Yes
tailwind.config Path to your Tailwind config file Yes
tailwind.css Path to the CSS file where shadcn writes its CSS variable definitions Yes
aliases.* Where the CLI puts component files, utils, and hooks — defaults map to @/components/ui/ Yes (but reset up early)

The three locked decisions

style — visual design language

style is not a Tailwind class — it is a template selector. Every component the CLI copies into your project is rendered from one of two template sets: new-york or default. Those templates embed different spacing, border-radius, and shadow choices directly into the component source code. Once components are in your project, swapping the style would require re-adding every single one from scratch.

The default style is deprecated. Always pin "style": "new-york" when running init. If you accidentally choose default, you will need to delete all your components, change this field, and re-add them — there is no migration path.

tailwind.baseColor — the neutral palette

baseColor determines the exact HSL values written into your globals.css for tokens like --background, --foreground, --muted, and --border. Every component uses these tokens. Changing baseColor after the fact means manually replacing all those variable values in globals.css — the CLI will not do it for you.

tailwind.cssVariables — theming mode

When cssVariables is true, every component references color tokens like bg-background and text-foreground — short utility classes that point to CSS custom properties. When it is false, components are written with hard-coded Tailwind utilities like bg-zinc-950. The two outputs are structurally different: you cannot flip this setting without re-adding every component.

Use cssVariables: true. It is the only mode that makes dark mode painless — you swap the values of the custom properties in a .dark selector and every component updates automatically.

style, baseColor, and cssVariables are locked at init because they are baked into the source code of every component file written to your project. The CLI does not patch existing files. Changing any of these after the fact means deleting all your components and starting the add step over from scratch.

Path aliases — set them up early

The aliases section is not locked in the same way, but it needs to be correct before you run init. The CLI uses these paths when writing import statements inside every component it generates. The default — @/components/ui/ — works automatically if you used create next-app with the default import alias. If your project uses a different alias (or none at all), update both tsconfig.json and this section before adding any components.

All components also import from @/lib/utils, which is where shadcn writes its cn() helper function. That path must resolve correctly too, or every component will fail to compile.

What to do if you got a locked setting wrong

There is no shadcn migrate command. The recovery path is manual and straightforward, even if tedious:

  1. Delete the files in components/ui/.
  2. Edit components.json with the correct style, baseColor, or cssVariables value.
  3. Update the CSS variable definitions in globals.css (re-run init or edit manually).
  4. Re-add every component you had previously: pnpm dlx shadcn@latest add button card input ...

For a project with ten or twenty components this is a half-hour task. For a project with fifty components and customized variants, it is a painful afternoon. Make the three decisions once, upfront.

Check your understanding

Which of these settings in components.json cannot be changed after init?

You are about to run shadcn init on an imaginary project: a personal dashboard with a dark mode toggle and about thirty components planned.

Write out the three lock-in decisions you would make — style, baseColor, and cssVariables — and give a one-sentence reason for each choice. Then explain what you would have to do if you later discovered you had chosen the wrong baseColor.
