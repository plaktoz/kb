STRIDE — The Developer’s Primary Threat Framework

Module 2 — Frameworks Lesson 4 of 12 ~15 min read

Primary source Microsoft Azure Security: Threat Modeling Tool Threats — learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-threats

What Is STRIDE?

STRIDE is a mnemonic developed at Microsoft in the late 1990s by Loren Kohnfelder and Praerit Garg. It gives you six threat categories — one per letter — that cover the most common ways a web application can be attacked or abused. Today it is the most widely taught threat identification framework for software developers and is the default framework in both Microsoft’s Threat Modeling Tool and OWASP’s Threat Dragon.

The six categories are: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, and Elevation of Privilege. Each category corresponds to a fundamental security property your system is supposed to uphold. When a threat violates one of those properties, it falls into the matching STRIDE bucket.

STRIDE does not tell you about every possible attack — it gives you six questions to ask about every data flow in your system. Asking the same six questions consistently is what makes it powerful.

The Six STRIDE Categories

The table below is your primary reference. For each category you get: the full name, the security property it threatens, a plain-English definition, and a concrete web app example you can visualise immediately.

Letter Threat Type Security Property Violated Web App Example
S Spoofing Authentication An attacker steals a user’s session cookie and replays it to the server, logging in as that user without knowing the password.
T Tampering Integrity An attacker sits between the browser and the server on an unencrypted Wi-Fi network and silently changes the quantity field in a submitted order form from 1 to 100.
R Repudiation Accountability A user places an order, then disputes the charge and claims they never placed it. Because the app has no audit log recording who placed the order and when, there is no way to prove the claim either way.
I Information Disclosure Confidentiality A misconfigured API endpoint returns all user records instead of just the authenticated user’s own record, leaking names, emails, and hashed passwords to anyone who calls it.
D Denial of Service Availability An attacker sends thousands of login requests per second to /api/login without rate limiting, saturating the server’s CPU and making the endpoint unavailable to legitimate users.
E Elevation of Privilege Authorization A regular user discovers that navigating directly to /admin/users returns the admin dashboard because the server only checks authentication (are you logged in?) but not authorization (are you an admin?).

Each Category in Depth

S — Spoofing (Authentication)

Spoofing means pretending to be someone or something you are not. The security property it threatens is authentication — the system’s ability to verify that an identity is genuine. In web apps, spoofing attacks target the mechanisms that establish identity: session tokens, JSON Web Tokens, API keys, and OAuth flows. An attacker who can spoof a legitimate user or service bypasses every access control that depends on knowing who you are.

Common spoofing vectors include: stolen or forged session cookies, credential stuffing (replaying leaked username/password pairs), open redirect attacks that impersonate a trusted redirect URL, and DNS spoofing that points a domain at an attacker-controlled server.

T — Tampering (Integrity)

Tampering means maliciously modifying data — either in transit across a network or at rest in a database or file system. The security property threatened is integrity: the guarantee that data has not been altered by an unauthorised party. Even a small, targeted modification (changing a price from $1 to $0.01, flipping an isAdmin flag from false to true) can have large downstream consequences.

Defences against tampering include: TLS for data in transit, cryptographic signatures or HMACs for critical data, parameterised queries (preventing SQL injection that overwrites rows), and input validation on the server side — never on the client side alone.

R — Repudiation (Accountability)

Repudiation occurs when a user can convincingly deny having performed an action because the system lacks the audit trail to prove otherwise. The security property is accountability (sometimes called non-repudiation). This category is about the gap between what happened and what can be proven to have happened.

Repudiation threats become legal and financial problems fast. A user who successfully disputes a legitimate charge triggers a chargeback. An employee who deletes a record and denies it creates a compliance failure. The fix is durable, tamper-evident logging: record who did what, when, from which IP, on which resource — and store those logs somewhere the subject of the log cannot modify them.

Repudiation is the most overlooked STRIDE category. It means your system cannot prove that a user did or did not do something — which matters for debugging, legal disputes, and fraud detection.

I — Information Disclosure (Confidentiality)

Information disclosure means exposing data to parties who should not have access to it. The threatened property is confidentiality. This is perhaps the broadest STRIDE category: it covers data leaks via API responses that return too much, verbose error messages that reveal stack traces or database schemas, unencrypted data at rest, improperly scoped access tokens, and directory listings on web servers.

A useful heuristic: every data flow in your system is a potential information disclosure threat. Ask “what is crossing this boundary and who can intercept or read it?” for every arrow on your data flow diagram.

D — Denial of Service (Availability)

Denial of Service (DoS) threats target the availability of your system — the guarantee that legitimate users can use it when they need to. Attacks range from volumetric floods (sending more traffic than the server can handle) to algorithmic complexity attacks (crafting inputs that trigger worst-case behaviour in your code) to resource exhaustion (opening thousands of database connections without releasing them).

For web developers, availability threats are often not exotic attacks but rather missing guardrails: no rate limiting on public endpoints, no pagination on queries that can return millions of rows, no timeouts on external API calls. These are design-level gaps, which is exactly why you want to catch them in threat modeling before they reach production.

E — Elevation of Privilege (Authorization)

Elevation of Privilege (EoP) means a user gaining capabilities beyond those they were granted. The threatened property is authorization: the system’s ability to enforce what an authenticated identity is allowed to do. Authentication and authorization are distinct: knowing who you are does not automatically tell the system what you can do.

Web app EoP examples include: accessing another user’s resources by changing an ID in a URL (Insecure Direct Object Reference), exploiting a mass-assignment vulnerability that lets a regular user set role: "admin" in a POST body, and path traversal attacks that allow a low-privilege user to read files outside their permitted directory.

How to Use STRIDE in Practice

STRIDE is most effective when applied systematically to each element in your Data Flow Diagram (DFD). The standard workflow is:

  1. Draw your DFD for the feature you are analyzing. Mark every process, data store, external entity, data flow, and trust boundary.
  2. Pick an element — start with a data flow arrow, since that is where most web app threats live.
  3. Ask all six STRIDE questions about that element. “Could this data flow be spoofed? Could it be tampered with? Could its occurrence be repudiated? Could it disclose information? Could it be disrupted? Could it be used to gain higher privileges?”
  4. Write one specific threat statement per “yes” answer. Specific means: name the attacker action and the target component. “SQL injection via the email parameter overwrites rows in the users table” is specific. “Tampering” alone is not.
  5. Move to the next element and repeat. Cover every element in the DFD before moving on to mitigation.

The power of the checklist is that it forces you to consider categories you would not naturally think of. Most developers instinctively think about tampering and information disclosure. STRIDE reminds you not to skip spoofing, repudiation, availability, and privilege escalation.

Why STRIDE Is the Right Starting Framework for Web Developers

Several competing frameworks exist — PASTA, LINDDUN, VAST, OCTAVE — and we will cover the most relevant ones in later lessons. STRIDE is the recommended starting point for web developers for three reasons:

  • It maps directly to web app attack surfaces. Every major OWASP Top 10 vulnerability fits neatly into one or more STRIDE categories. Injection attacks are Tampering. Broken access control is Elevation of Privilege. Security misconfiguration often leads to Information Disclosure. STRIDE gives you a vocabulary for what you are already defending against.
  • It is designed for developers, not security specialists. Microsoft created STRIDE to be used by developers during design — not by a dedicated red team after the fact. The questions are simple enough to ask in a sprint planning session without deep security expertise.
  • It integrates with free tooling. Both OWASP Threat Dragon and Microsoft’s Threat Modeling Tool use STRIDE as their default threat classification system. Learning STRIDE first means you can immediately use the tools that auto-generate threat lists from your DFDs.

STRIDE is not perfect. It does not cover privacy threats well (that is LINDDUN’s strength), it does not prioritise threats by business risk (that is PASTA’s strength), and it does not account for insider threats with unusual richness. But for a junior web developer building their first threat model on a web feature, STRIDE covers the ground that matters most and is learnable in an afternoon.
