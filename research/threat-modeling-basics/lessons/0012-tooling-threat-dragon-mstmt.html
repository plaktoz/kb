OWASP Threat Dragon and Microsoft TMT — Getting Started

Module 4 — Outputs and Tooling Lesson 12 of 12 ~12 min read

Primary sources OWASP Threat Dragon — owasp.org/www-project-threat-dragon  ·  Microsoft Azure Security: Threat Modeling Tool Getting Started — learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-getting-started

Why Use a Dedicated Threat Modeling Tool?

In the earlier lessons of this module you learned what a completed threat model looks like: a data flow diagram, a structured list of threats, a mitigation register, and an executive summary. You can produce all of those artifacts using nothing more than a whiteboard, a spreadsheet, and a word processor. Many teams do exactly that.

Dedicated threat modeling tools add one thing that no generic tool can: a rule engine that reads the element types in your DFD and auto-generates a threat checklist based on known attack patterns. Instead of asking “have I remembered to check for Denial of Service on this data flow?” for every arrow in the diagram, the tool generates that question for you. The result is a faster starting checklist and fewer gaps caused by human forgetfulness.

Two tools dominate the free tier: OWASP Threat Dragon and the Microsoft Threat Modeling Tool (commonly abbreviated Microsoft TMT or MSTMT). This lesson covers both in enough depth that you can open either one today and produce your first machine-assisted threat model.

OWASP Threat Dragon

What It Is

OWASP Threat Dragon is a free, open-source threat modeling application maintained under the OWASP umbrella. It was created to be simple enough for a developer to use without a security background and flexible enough to support multiple threat frameworks beyond STRIDE.

You can access Threat Dragon in three ways, depending on your setup:

  • Browser demo: Go to threatdragon.com and start a model immediately in your browser. No account or install required for local work — models are saved to your browser’s local storage or exported as JSON files.
  • Desktop installer: Download the Electron-based desktop app for Windows, macOS, or Linux from the OWASP GitHub releases page. The desktop app lets you save models to the local file system and integrates with GitHub for team workflows.
  • Docker container: Run docker pull owasp/threat-dragon to host a local instance, useful for teams who want a shared server without relying on the public demo site.

The Rule Engine

The core feature of Threat Dragon is its rule engine. When you draw a DFD and label your elements — process, data store, external entity, data flow, trust boundary — the engine evaluates each element against a set of built-in rules and generates a list of candidate threats. For example, placing an unencrypted data flow between two processes will trigger Information Disclosure and Tampering threats automatically.

The generated threats appear in the element’s properties panel. Each threat entry includes a title, a threat category, a description, a suggested mitigation, and a status field (“Open,” “Mitigated,” or “Not Applicable”). You edit and supplement these entries directly in the tool, then export the final model.

Supported Frameworks

Threat Dragon supports six threat frameworks, selectable at model creation time:

  • STRIDE — the default, best for web apps (Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege)
  • LINDDUN — privacy-focused (Linkability, Identifiability, Non-repudiation, Detectability, Disclosure of information, Unawareness, Non-compliance)
  • CIA — Confidentiality, Integrity, Availability
  • DIE — Distributed, Immutable, Ephemeral (resilience-focused)
  • PLOT4ai — AI/ML system threats
  • STRIDE per element — a stricter variant that maps STRIDE categories to specific DFD element types

Output Formats

When you are done, Threat Dragon gives you two output formats:

  • JSON threat model file: A structured .json file containing the full DFD, every element’s properties, and all threat entries with their statuses. This file is source-control-friendly — it can be committed to your repository alongside your code, diffed between versions, and reviewed in a pull request.
  • Printable report: An HTML or PDF rendering of the full threat model, suitable for sharing with stakeholders who do not use the tool directly.

Microsoft Threat Modeling Tool

What It Is

The Microsoft Threat Modeling Tool (Microsoft TMT) is a free Windows desktop application published by Microsoft. It has been available since around 2008 and is one of the most mature free tools in the category. Microsoft describes it as “designed for non-security experts,” with the explicit goal of making threat modeling accessible to developers during the design phase of a project rather than as a security review after the fact.

Microsoft TMT is Windows-only. If you are on macOS or Linux, you will need a Windows virtual machine or switch to Threat Dragon.

How It Works

Like Threat Dragon, Microsoft TMT centers on a DFD editor. You drag stencils onto a canvas — processes, data stores, external entities, and data flows — and draw trust boundaries as dashed rectangles around them. The tool includes a library of pre-built stencils for common Azure services (App Service, SQL Database, Key Vault, Service Bus, and dozens more) as well as a generic template for non-Azure architectures.

Once the diagram is drawn, you click “Analyze” and the rule engine generates a STRIDE threat list based on the element types and trust boundary crossings in your diagram. The generated threats are far more granular than most manual checklists — a single diagram with a handful of elements can produce 30–60 auto-generated threats.

Threat Status Tracking

Each generated threat has a status that you set as you work through the list:

  • Not Started — the default; no one has reviewed this threat yet
  • Needs Investigation — flagged for further research or discussion
  • Mitigated — a control is in place; you record what the mitigation is
  • Not Applicable — the threat does not apply to your context; you record why

This status workflow maps directly to the mitigation register format described in Lesson 11. Exporting the report from Microsoft TMT gives you a formatted document with all threats and their statuses, which serves as a ready-made mitigation register.

Azure Templates

One of Microsoft TMT’s strongest features is its Azure integration. If your application runs on Azure infrastructure, you can select an Azure-specific template when starting a model. The stencil library then includes cloud service shapes that carry Azure-specific threat rules — for example, a threat about misconfigured Azure Storage access policies, or a threat about missing Azure Key Vault access logging. This level of cloud-provider-specific threat generation is not matched by generic tools.

How to Use Auto-Generated Threats

Both tools generate threats from DFD element types using pattern-matching rules. Understanding what the rule engine can and cannot do is essential to using these tools well.

The rule engine knows about structure: “this is a data flow crossing a trust boundary, therefore it could be intercepted (Information Disclosure) or modified in transit (Tampering).” The rule engine does not know about content: it does not know that your data flow carries medical records rather than anonymous preferences, or that your process is accessible to unauthenticated users, or that a particular trust boundary crosses an air gap between an on-premises server and a cloud service.

The right mental model is: auto-generated threats are a starting checklist, not a complete threat register. They ensure you have not forgotten to ask the obvious questions. But every generated threat needs a human review to decide whether it applies in your specific context, and every context-specific threat that the rule engine cannot derive needs to be added manually.

In practice, a good threat modeling session using one of these tools looks like this:

  1. Draw your DFD. Label elements correctly — the rule engine quality depends entirely on accurate labeling.
  2. Run analysis. Skim the generated threats quickly to remove the ones that clearly do not apply (mark them “Not Applicable” with a brief reason).
  3. Work through the remaining generated threats one by one, adding mitigation notes for each.
  4. Add manual threats for context-specific risks the tool cannot know: business logic flaws, specific data sensitivity concerns, known integration quirks, insider threat scenarios.
  5. Export the report and review it against your acceptance criteria.

Do not rely entirely on auto-generated threats. Tools generate threats based on DFD element types — they cannot know your specific business logic, the data your app handles, or the context that makes some threats more relevant than others.

Other Tools Worth Knowing

Threat Dragon and Microsoft TMT are the two most accessible free tools, but the threat modeling tooling ecosystem is broader. The table below covers four more tools you may encounter in job listings, project documentation, or team discussions.

Tool Type Best for Access
pytm Threat modeling as code (Python library) Teams who want threat models checked into source control as Python scripts and generated automatically in CI Free, open source; pip install pytm
draw.io Diagramming tool with threat modeling shape libraries Teams already using draw.io for architecture diagrams who want to add threat annotations without switching tools Free browser app at app.diagrams.net; desktop installer available
IriusRisk Enterprise threat modeling platform Larger teams who need a centralized tool with role-based access, compliance mapping, and ticketing integrations Community Edition free; paid tiers for enterprise features
Threat Composer Structured threat statement builder (AWS Labs) Teams who want a lightweight, structured way to write well-formed threat statements without a full DFD tool Free, open source; hosted at awslabs.github.io/threat-composer

For the majority of junior web developers starting out, Threat Dragon or Microsoft TMT is the right choice — both have guided interfaces, auto-generation, and export. The other tools become relevant as your team’s maturity and workflow requirements grow.

Getting Started: A Five-Minute Walkthrough

OWASP Threat Dragon

  1. Open threatdragon.com in your browser. Click Local Session to start a model stored in browser local storage (no account required).
  2. Click New Model. Give it a title, choose STRIDE as the threat framework, and click Create.
  3. On the diagram canvas, drag a Process shape, a Data Store shape, and two External Entity shapes onto the canvas. Draw Data Flow arrows between them. Add a Trust Boundary box around the internal components.
  4. Click any element to open its properties panel. Give it a name matching what it represents (e.g., “Registration API”). The Threats tab in the panel shows auto-generated threats for that element.
  5. Review the generated threats. For each one, either add a mitigation note and mark it Mitigated, or mark it Not Applicable with a reason.
  6. When done, click Report to download a printable HTML report, or Save to export the JSON model file.

Microsoft Threat Modeling Tool

  1. Download and install the tool from the Microsoft Learn page. Windows only.
  2. Click Create a Model. Select the SDL TM Knowledge Base template for generic apps, or the Azure-specific template if your system runs on Azure.
  3. Draw your DFD using the stencils in the left panel. Drag elements, draw data flows, and add trust boundary rectangles.
  4. Click View → Analysis View to run the rule engine and see the generated threat list.
  5. Work through the threat list. Set the status of each threat (Not Started → Mitigated or Not Applicable) and add mitigation notes.
  6. Click Reports → Create Full Report to export a Word or HTML document with the full threat model.

Knowledge check

What is the primary advantage of OWASP Threat Dragon over Microsoft TMT?

Open OWASP Threat Dragon at threatdragon.com (or download Microsoft TMT if you are on Windows). Recreate the user registration DFD from Lesson 8: Browser → Registration API → User Database → Email Service, with one trust boundary around the backend components.

Then answer the following three questions based on what the tool auto-generated:

  1. List 2–3 threats the tool auto-generated. Include the threat title and STRIDE category.
  2. Did the tool catch any threat you had not already identified when working through Lesson 9? If so, which one?
  3. Did the tool miss any threat you had already identified manually? If so, which one, and why do you think the rule engine did not generate it?
Finished the exercise? Ask your tutor: “I’ve listed the auto-generated threats from my DFD in Threat Dragon. Can you help me decide which ones are most relevant for a user registration flow and which I should add manually based on the business context?”
