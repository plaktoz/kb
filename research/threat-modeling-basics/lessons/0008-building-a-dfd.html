Step 1 — Building Your Data Flow Diagram

~15 min Module 3 — The Process

Primary source: Agile Threat Modelling — Martin Fowler https://martinfowler.com/articles/agile-threat-modelling.html
Covers what to include in a DFD for agile teams: components (services, databases, UIs), users (internal, external, privileged), directional data flows, trust boundaries, and assets — anything whose loss causes financial, reputational, or legal harm.

Secondary source: Microsoft Threat Modeling Tool — Getting Started https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-getting-started
Documents the standard DFD stencil conventions: square = external entity (user or external system), circle = process (web server, API), parallel lines = data store (database, file system), red dotted line = trust boundary.

What is a data flow diagram?

A data flow diagram (DFD) is a visual map of how data moves through a system. It shows the components involved, the data that travels between them, and the points where control or ownership changes hands. That last part — the trust boundaries — is what makes a DFD the right starting point for threat modeling.

Before you can reason about what an attacker might do, you need to be able to see where data enters your system, what processes touch it along the way, where it is stored, and where it leaves. A DFD makes all of that visible on a single page. Once it is drawn, the question "where could something go wrong?" becomes much easier to answer because you can point to a specific arrow or a specific boundary crossing.

A DFD is not an architecture diagram. Its purpose is to make trust boundaries and data flows visible — if you cannot see where data crosses a trust boundary, you cannot reason about what can go wrong there.

Architecture diagrams show deployment topology: servers, load balancers, Kubernetes pods, cloud regions. That information is useful for operations, but it is not what you need for threat modeling. What you need to know is simpler and more specific: who sends what data to whom, and where does the level of trust change? A DFD answers those questions directly. It strips away infrastructure detail and focuses on the thing that matters for security: data movement and ownership.

The four DFD element types

Every DFD is built from exactly four kinds of element. Learning these four shapes is the entirety of the notation — there is nothing else to memorize.

DFD Element Symbol Example in a web app What to ask about it
External Entity Square or rectangle [ ] Browser, mobile client, third-party payment API, admin user Is this entity trusted? Can it send malformed or malicious data?
Process Circle or oval ( ) Web server, authentication service, background job, email sender What does this process do with the data? Could it be subverted or bypassed?
Data Store Two parallel lines || || User database, session store, file system, cache Who can read or write here? Is this data encrypted at rest?
Data Flow Arrow with direction → Login request, API response, database query, email delivery Is this flow encrypted in transit? Is it authenticated? Can it be intercepted or replayed?

The notation is deliberately minimal. Some teams use slightly different shapes (rectangles instead of squares for external entities, for example), and that is fine — consistency within your team matters more than strict adherence to a standard. What cannot vary is the meaning: every element must be clearly identifiable as one of these four types.

Trust boundaries: the most important concept in a DFD

A trust boundary marks the point where control or ownership changes. The most common examples in web applications are:

  • The boundary between the public internet (user-controlled) and your server (your-controlled)
  • The boundary between your web server and your internal database network
  • The boundary between your application and a third-party API you call
  • The boundary between an authenticated user session and an unauthenticated one

Trust boundaries are drawn as dotted lines cutting across the data flows that cross them. The dotted line is not a wall — data does flow across it — but it is a signal to the threat modeler: every data flow that crosses this line is a candidate for attack. Data entering your system from the internet crosses a trust boundary. Data leaving your process and entering a database crosses a trust boundary. These crossing points are where most real-world vulnerabilities are exploited.

When you are new to DFDs, a practical heuristic is: draw a trust boundary wherever you would check permissions or validate input. If you are already doing input validation at a particular point, that is because some part of your team already sensed the trust boundary there, even if it was never made explicit.

A concrete example: a login flow

The following is a text-art DFD for a simple login flow. The notation uses [ ] for external entities, ( ) for processes, and || || for data stores. The trust boundary is marked explicitly.

DFD: Login flow (text notation) [ User (Browser) ] | | login request (username + password) | [crosses trust boundary: internet → server] v - - - - - - - - - - - - - - - - (Trust Boundary: Internet / Server) - - - | v ( Web Server / Auth Process ) | \ | credential query \ session token v v || User DB || [ User (Browser) ] (password hash)

Reading this diagram, even as plain text, surfaces several security questions immediately:

  • Is the login request sent over HTTPS? (Is the data flow encrypted?)
  • Is the password hashed before storage in the User DB, or stored in plaintext?
  • How is the session token generated — is it cryptographically random?
  • Can the credential query be manipulated by the web server to return rows it should not (SQL injection)?

None of these questions required reading any code. They came directly from looking at the diagram and asking "what could go wrong at this arrow?" and "what could go wrong at this trust boundary crossing?"

Assets: what are you protecting?

In threat modeling, an asset is anything whose loss, exposure, or corruption causes harm. "Harm" is intentionally broad — it can be financial (fraudulent transactions), reputational (a breach headline), legal (a GDPR violation), or operational (a service outage that costs revenue).

Common assets in web applications include:

  • User credentials — usernames and passwords; if exposed, attackers can impersonate users
  • Personally identifiable information (PII) — names, email addresses, phone numbers, home addresses; regulated in many jurisdictions
  • Session tokens — if stolen, an attacker gains the privileges of the authenticated user without needing their password
  • Financial data — payment card numbers, bank account details, transaction records
  • API keys and secrets — if leaked, an attacker can impersonate your server to third-party services
  • System availability — the ability of your service to respond to legitimate requests

When drawing a DFD, annotate it with the assets that live in each data store and flow through each data flow. A database labeled ||User DB|| becomes more useful to a threat modeler when it is labeled ||User DB (credentials, PII)|| — the label tells you immediately what the stakes are if this component is compromised.

Practical tips for junior developers

The most common mistake when building a first DFD is trying to model the entire application at once. That produces a large, tangled diagram that is hard to reason about and even harder to maintain. Here is how to avoid it:

  1. Start with a whiteboard sketch. Use sticky notes, a whiteboard, or a shared drawing tool. The goal is to think, not to produce a polished artifact. A photograph of a whiteboard is a perfectly valid DFD.
  2. Focus on one feature or one user story. Pick the most sensitive one — authentication, payment, or anything that touches user data — and model that first. A DFD covering "user login" is more useful than a DFD attempting to cover the entire application.
  3. Keep it simple. Three boxes and two arrows is enough to start threat modeling. Add detail only when you find a question you cannot answer without it.
  4. Draw the trust boundaries before you draw the components. Ask first: where does trust change in this feature? Then place your components on either side of those boundaries. This forces trust to be a first-class concern rather than an afterthought.
  5. Label assets explicitly. When you draw a data store, write the most sensitive data it holds next to its symbol. When you draw a data flow, note whether it carries credentials, tokens, or PII. This labeling makes threat identification in the next step much faster.

Don’t try to model your entire application in one DFD. Start with one feature or one user story. A focused, incomplete model is more useful than an exhaustive one you never finish.
