Step 2 — Identifying and Capturing Threats

~15 min Module 3 — The Process

Primary source: Agile Threat Modelling — Martin Fowler https://martinfowler.com/articles/agile-threat-modelling.html
Describes how agile teams apply STRIDE systematically to each data flow in a DFD, treating each STRIDE category as a checklist question rather than an exclusive bucket.

Secondary source: OWASP Threat Modeling https://owasp.org/www-community/Threat_Modeling
Covers multiple elicitation techniques — STRIDE, attack trees, kill chains — and emphasizes capturing threats before prioritizing them, ensuring no candidate threat is discarded prematurely.

The goal: systematically ask “What can go wrong?”

With your DFD drawn and trust boundaries marked, you have a map. The next step is to walk that map and ask a single question at every arrow: what can go wrong here? The challenge is doing this systematically enough that you don’t miss anything important, and loosely enough that you don’t constrain your thinking too early.

STRIDE is the tool that provides this discipline. For every data flow arrow on your DFD, you run through all six STRIDE categories and ask whether each one applies. You are not looking for one threat per arrow — you are asking six distinct questions per arrow, and any of them can yield one or more threats. The DFD you built in Lesson 8 is your worksheet; each arrow is a row you work through in turn.

This is not a creative exercise in the sense of imagining novel attack scenarios from scratch. It is a structured walkthrough that ensures you cover every category for every data flow. The creativity comes in articulating the specific threat once STRIDE has pointed you at a category — “Spoofing applies here; what exactly could an attacker spoof and how?”

STRIDE per element: applying the checklist to each data flow

The technique is called STRIDE per element. Take each arrow in your DFD — each data flow — and step through all six STRIDE categories one at a time. For each category, ask: “Could an attacker exploit this flow in a way that fits this category?” If yes, write it down as a specific threat statement (more on the format in the next section). If no, move on.

The following table shows three examples using the user registration flow from Lesson 8:

Data Flow STRIDE Category Specific Threat Statement
Browser → Registration API Spoofing Attacker forges a legitimate user’s registration request to create an account under their email
Browser → Registration API Tampering Attacker modifies the POST body to set their account role to “admin” during registration
Registration API → User DB Information Disclosure Verbose SQL error message reveals the database schema to an unauthenticated attacker

Notice that the first two rows cover the same data flow with different STRIDE categories. This is expected and correct: a single arrow can and often does have threats in multiple — or all six — STRIDE categories. You are not assigning one category to each flow; you are asking each category as a question about each flow.

STRIDE categories are not mutually exclusive. A single data flow can have threats in all six categories. Applying STRIDE is a checklist to ensure you ask each question — not a constraint that limits you to one threat per flow.

Work through the DFD methodically: pick the first arrow, run all six STRIDE questions, write down any threats that apply, then move to the next arrow. Some teams use a whiteboard grid with arrows as rows and STRIDE categories as columns, marking each cell that yields a threat. Others use sticky notes, one per threat. The medium does not matter; the coverage does.

Writing good threat statements

A threat statement is only useful if it is specific enough to act on. The format that works is:

[Attacker action] + [entry point or data flow] + [target component]

This three-part structure forces you to name what the attacker does, where they enter the system, and what they are trying to reach or damage. Without all three parts, the threat is too vague to evaluate or mitigate.

Compare these two phrasings of the same threat:

  • Vague (not useful): “Information Disclosure”
  • Specific (useful): “Attacker intercepts session token from browser to server over HTTP”

The first phrasing just names a STRIDE category. It tells you nothing about where the threat occurs, how an attacker would exploit it, or what the impact is. The second phrasing names the attacker action (intercepts), the entry point (the browser-to-server data flow over HTTP), and the target (the session token). A developer reading it knows immediately what to investigate: “Is this flow over HTTP? Should it be HTTPS? If so, this threat is real and we need to fix it.”

More examples of the format in practice:

  • “Attacker replays a captured registration request to the Registration API to create duplicate accounts” (Spoofing + Tampering, Browser → Registration API)
  • “Attacker sends a malformed email address to the Registration API to trigger an unhandled exception that exposes a stack trace” (Information Disclosure, Browser → Registration API)
  • “Attacker floods the Registration API with concurrent requests to exhaust the database connection pool and deny service to legitimate users” (Denial of Service, Browser → Registration API)

Each statement names what the attacker does, where it happens, and what the consequence or target is. That three-part specificity is the standard to aim for.

Capture everything, filter nothing yet

The identification step has one rule: write everything down. This is not the step where you decide what is realistic or what is worth fixing. It is the step where you ensure that every candidate threat is visible to the team before any of them are dismissed.

The practical tool for this is one threat per sticky note — physical sticky notes on a whiteboard, or digital equivalents in a tool like Miro or FigJam. Each sticky note holds exactly one threat statement. The act of writing it on its own note gives it equal standing with every other threat, and makes the physical act of prioritizing (which happens in Lesson 10) a matter of sorting and grouping notes rather than editing a shared document where deletions disappear silently.

Capture every threat you can think of before filtering any out. The prioritization step (Lesson 10) is where you decide what to fix — not here. Premature filtering causes teams to miss real threats.

The most common mistake at this stage is self-filtering: a developer thinks “that would never happen in practice” or “we already do X so that’s not a real threat,” and never writes it down. The problem is that this judgment is made without evidence, before the team has evaluated the threat formally. If a threat is real but was never written down, it cannot be formally dismissed — it simply falls through the cracks. Write it down. If it is truly irrelevant, the prioritization step will surface that clearly and you can close it there, with a documented reason.

Aim for quantity at this step. A session that produces 30 threat statements — many of them low severity, some of them duplicates, a few of them highly important — is more valuable than a session that produces 8 “curated” threats, because the curated session has already lost the threats that seemed unimportant to whoever was filtering.

Alternative approaches

STRIDE is not the only technique for identifying threats. Two other approaches are worth knowing, particularly as you grow in experience.

Kill Chains approach threat identification from the attacker’s perspective, stepping through the sequence of actions an attacker takes from initial access to final objective. The classic formulation is reconnaissance → weaponization → delivery → exploitation → installation → command-and-control → actions on objective (Lockheed Martin’s Cyber Kill Chain). This perspective is useful for understanding multi-step attacks where no single component appears vulnerable in isolation — the threat only becomes visible when you model the full sequence. Kill chain analysis tends to be more useful for mature teams analyzing complex systems than for beginners working through their first threat model.

Attack Trees represent threats as hierarchical decompositions: a root node names the attacker’s goal (e.g., “Steal user credentials”), and child nodes name the ways to achieve it, each of which can be further decomposed into their sub-methods. Attack trees are powerful for deep analysis of a specific high-value target — you can model AND-conditions (attacker needs X and Y) versus OR-conditions (attacker needs X or Y) and reason about which paths are most feasible. The cost is that building a thorough attack tree takes significant time, making them better suited to post-threat-model deep dives than initial identification sessions.

For a junior developer conducting their first threat model, STRIDE is the right starting point. It is structured enough to prevent blank-page paralysis, systematic enough to provide coverage, and lightweight enough to complete in a single working session. The alternative techniques become valuable additions to your toolkit once you are comfortable with STRIDE’s output.

Using GenAI for brainstorming

Generative AI tools can serve as a useful brainstorming partner during threat identification. The basic approach: write a brief, accurate description of the system or feature you are modeling, then ask the model to produce a STRIDE-prompted threat list. A prompt like “Here is a user registration flow: Browser sends a POST request to a Registration API, which writes to a User Database and sends a welcome email via an Email Service. List potential threats using each STRIDE category for each data flow” will produce a reasonable starting list in seconds.

This is most valuable for getting unstuck — when a team has been staring at a DFD for 20 minutes and the sticky notes are still blank, a generated list gives you something to react to. Reacting to a list (“yes, that’s real,” “no, we already mitigate that with X,” “that’s interesting, we hadn’t thought of that angle”) is cognitively easier than generating from nothing.

The critical constraint: every suggestion must be verified against your actual system. A language model has no knowledge of your specific architecture, your existing controls, your technology stack, or your deployment environment. It will produce threats that are generic, some of which will not apply to your system, and it will miss threats that are specific to your system’s unusual design choices. Treat generated output as a draft checklist to react to, not as a finished threat model. The judgment — which threats are real for this system, which are already mitigated, which need investigation — must come from the team that knows the system.
