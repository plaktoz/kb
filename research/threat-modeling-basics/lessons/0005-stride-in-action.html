STRIDE in Action — Walking Through a Web App DFD

Module 2 — Frameworks Lesson 5 of 12 ~15 min read

Primary source Microsoft Azure Security: Threat Modeling Tool Getting Started — learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-getting-started

A Worked Example DFD

The best way to learn STRIDE is to apply it to a concrete system rather than to abstract definitions. We will use a minimal login flow as our example — simple enough to reason about in one sitting, but representative of real-world threats.

Here is the Data Flow Diagram (DFD) for a basic login request: 

[Internet User] ──login request──> (Web Server) ──DB query──> ||User Database||
                    ^
                    | TRUST BOUNDARY (internet / server zone)

The notation used above follows the standard DFD shorthand:

  • Square brackets [ ] — external entity. Something outside your system that initiates or receives data. You do not control it.
  • Parentheses ( ) — process. A component of your system that receives, transforms, or forwards data. You own its code.
  • Double bars || || — data store. Persistent storage: a database, a file system, a cache. Data at rest lives here.
  • Arrows ──> — data flows. Every arrow is a potential threat vector.
  • Trust boundary — a line where data crosses from one zone of trust to another. The internet-to-server boundary is the most important one in most web apps.

The trust boundary in this diagram sits between the internet user and the web server. Data arriving from the internet has not been validated. It could have been crafted by anyone. Everything that crosses that line deserves scrutiny.

Applying STRIDE to a Data Flow

Now apply STRIDE systematically to the data flows in the diagram above. For each flow, work through all six STRIDE categories and write a specific threat statement for any category where an attack is plausible.

The table below shows three worked examples — two threats on the User → Web Server flow and one on the Web Server → Database flow:

Data Flow STRIDE Category Specific Threat Statement
User → Web Server Spoofing Attacker uses stolen session cookie to impersonate another logged-in user
User → Web Server Tampering Attacker modifies the login POST body to inject SQL into the username field
Web Server → Database Information Disclosure Misconfigured DB permissions expose all user records to the application service account

Notice that each threat statement is concrete. It names an attacker action, an entry point, and a target. The next section explains why that specificity is the difference between a useful threat model and a useless one.

Vague vs. Specific Threat Statements

The most common mistake in STRIDE exercises is writing the category label as the threat statement. “Tampering” is not a threat statement — it is a category. Your team cannot act on a category label. They need to know what is being tampered with, where the tamper can happen, and how.

A good threat statement has three parts:

  1. The attack technique — what the attacker actually does (SQL injection, session replay, path traversal).
  2. The entry point — where the attack enters the system (the login form, the /api/users endpoint, the file query parameter).
  3. The target component and implied consequence — what gets compromised as a result (the users table, another user’s account, the admin dashboard).

Compare these two statements side by side:

Quality Statement Why
Vague Tampering Names the category only. The developer does not know which input, which component, or which data.
Specific Attacker injects SQL via the username field on the login form, overwriting rows in the users table Names the technique (SQL injection), the entry point (username field, login form), and the target (users table). Actionable.

A specific threat statement names the attacker action, the data flow, and the target component. “SQL injection from internet to login form” is actionable. “Tampering” is not.

A useful test: could a developer read your threat statement and write a unit test or mitigation ticket without asking a follow-up question? If not, the statement is too vague.

Threat Modeling as a Team Sport

One of the most practical lessons from the Microsoft Threat Modeling Tool Getting Started guide is an observation about who spots what. Ricardo, a developer on the example team, built the DFD. He knew the system well and captured the intended flows accurately. But when Ashish, a tester on the same team, reviewed the diagram, he found gaps Ricardo had missed.

This is not a criticism of Ricardo. It is a structural feature of how developers and testers think:

  • Developers model how the system works. They think about the happy path: user authenticates, query runs, response returns. Their mental model is built around correct behaviour.
  • Testers model how the system fails. They think about edge cases, unexpected inputs, and boundary conditions. Their mental model is built around incorrect and adversarial behaviour.

This difference in perspective is why threat modeling is most effective as a group exercise. Bring developers who know the code, testers who probe for failure modes, and — if available — someone with a security background who knows common attack patterns. Each perspective surfaces threats the others will miss.

If you cannot assemble a group, at minimum do a second pass on your own DFD after a break, deliberately wearing a “tester hat”: ask yourself how each component could be made to fail, not just how it is supposed to work.

Auto-generated Threats Are a Starting Point

Tools like OWASP Threat Dragon and Microsoft’s Threat Modeling Tool (TMT) can auto-generate threat lists from your DFD. You draw the diagram, mark the element types (external entity, process, data store, data flow), and the tool produces a checklist of STRIDE threats based on those element types.

This is genuinely useful. It means you get a baseline list quickly, and you do not miss obvious threats just because you were tired or distracted. For a junior developer running their first threat model, the auto-generated list is a significant help.

Auto-generated threats from tools like Microsoft TMT or Threat Dragon are a starting checklist — they will miss context-specific threats that only your team knows about.

However, the auto-generated list is not the final answer. Tools generate threats from structural patterns: “this element type is a data store, therefore it has these typical threats.” They do not know:

  • That your particular data store holds PII subject to GDPR, raising the stakes on information disclosure threats.
  • That your application allows file uploads, which opens attack surface the DFD element type alone does not convey.
  • That your authentication flow uses a third-party OAuth provider, adding trust boundary complexity the tool cannot infer.
  • That a specific business rule in your app (e.g. users can set their own discount codes) creates an EoP path unique to your domain.

The right workflow is: generate the automated list, then review it together as a team, then add the context-specific threats the tool could not know. The automated list is your floor, not your ceiling.

Knowledge check

Which threat statement is specific enough to act on?

Draw a simple DFD in text form for a web app feature of your choice — registration, search, or checkout. Use the following notation:

  • → for data flow arrows
  • [ ] for external entities
  • ( ) for processes
  • || || for data stores

Once you have your diagram, pick one data flow arrow and apply STRIDE to it. Write two specific threat statements for that flow. Each statement must name:

  1. The attack action (what the attacker does)
  2. The entry point (where the attack enters)
  3. The target component (what gets compromised)
Finished the exercise? Ask your tutor: “Can you review my two threat statements and tell me whether they are specific enough to be actionable, and what a developer would do to mitigate each one?”
