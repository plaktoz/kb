From Process to Artifact

The earlier lessons in this course covered the process of threat modeling: drawing data flow diagrams, running STRIDE across each element, scoring threats, and choosing a response. This lesson is about the artifacts that process produces. When you finish a threat modeling session, what should you actually have on disk?

The OWASP Threat Modeling Cheat Sheet identifies five canonical outputs. Together they form a durable record that a new team member, an auditor, or your future self can open in six months and immediately understand what risks this system carries, what decisions were made, and what remains to be done.

Understanding these outputs matters for two reasons. First, they are the deliverable — what you hand to a tech lead, a security reviewer, or a compliance team to demonstrate that threat modeling actually happened. Second, they create a feedback loop: outputs that are wrong or stale are evidence that the system has drifted and threat modeling needs to run again.

The Five Canonical Outputs

1. The Data Flow Diagram

The DFD is the visual foundation of the entire threat model. It shows every process, data store, external entity, trust boundary, and data flow in the scope you defined. Everything else — the threat list, the threat register, the attack surface map — is derived from or anchored to the DFD. If the DFD is wrong, every downstream output is suspect.

A finished DFD should be saved as an image or editable file alongside the rest of the threat model documentation. When using a tool like OWASP Threat Dragon or Microsoft’s Threat Modeling Tool, the tool file is the DFD. Commit it to source control so it changes in lockstep with the code it describes. A DFD that lives only on a whiteboard photograph or in someone’s personal folder is not a deliverable — it is a memory.

2. The Ranked Threat List

This is the exhaustive list of every threat you identified during the STRIDE analysis, each scored by likelihood, impact, and overall risk (as covered in Lesson 10). The list is sorted by score so the highest-risk threats appear at the top. This ordering tells the team where to spend effort first when mitigation work is prioritised in a sprint.

Every threat in the list should be a specific, named threat — not a category label. “SQL injection in the email parameter of POST /api/register overwrites rows in the users table” is a ranked threat entry. “Tampering” is not.

3. Response Strategies

For every threat on the ranked list, you record a response decision: mitigate (add a control to reduce likelihood or impact), eliminate (remove the feature or flow that creates the threat), transfer (shift responsibility to a third-party service or contract), or accept (document the risk and consciously decide not to act on it now). The response must be recorded even when the decision is to accept. Undocumented acceptance is not a strategy — it is an oversight that looks identical to work that was never done.

4. Mitigation Requirements

A response of “mitigate” generates a mitigation requirement: a specific, testable control that a developer can implement and a tester can verify. The OWASP Threat Modeling Cheat Sheet recommends anchoring mitigation requirements to a published standard rather than writing freehand descriptions, for two reasons. First, standards are already testable: OWASP’s Application Security Verification Standard (ASVS) numbers each requirement, which means you can reference “OWASP ASVS v4 requirement 3.3.3” and anyone on the team knows exactly what “done” looks like. Second, standards are maintained: if the standard is updated, your requirement inherits the update.

MITRE’s Common Weakness Enumeration (CWE) is the other common reference. CWE numbers describe the underlying weakness class (CWE-89 is SQL Injection, CWE-307 is Improper Restriction of Excessive Authentication Attempts). Citing a CWE in a mitigation requirement connects your threat model to a shared vocabulary used by static analysis tools, bug trackers, and vulnerability databases.

A mitigation requirement that says “add authentication” is not actionable enough. Reference a specific standard: “Implement session token rotation per OWASP ASVS v4 requirement 3.3.3.” That is something you can test and verify.

5. Formal Documentation

The four outputs above should be consolidated into a single document — or a small set of linked documents — that is accessible to everyone who needs it: developers, tech leads, security engineers, and auditors. The Microsoft Threat Modeling Tool exports a report containing threat title, STRIDE category, priority, status (Not Started / Needs Investigation / Mitigated / Not Applicable), and mitigation notes. That structure is a reasonable template even if you are not using Microsoft’s tool.

The documentation should be stored in source control alongside the code it describes — ideally in a threat-model/ or docs/security/ directory at the root of the repository. This means the threat model is reviewed in pull requests, updated when code changes, and visible to the whole team. A threat model that exists only in a shared drive accessible only to security engineers is not a living document — it is a filing cabinet that will go stale.

The Threat Register

In practice, the ranked threat list and the response strategies are usually combined into a single table called the threat register. The threat register is the living heart of your threat model: one row per identified threat, all the information you need to track it from identification through to resolution.

The threat register is the living heart of your threat model. It is not a one-time document — update it when you add features, when incidents occur, and when the architecture changes.

The columns recommended by OWASP and Microsoft together produce a register that is both analytical and operational:

Column Purpose
Threat A specific, named threat statement identifying the attacker action, the targeted component, and the consequence.
STRIDE Category The primary STRIDE category: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, or Elevation of Privilege.
Likelihood Numeric or qualitative score (e.g. 1–3) for how probable exploitation is.
Impact Numeric or qualitative score (e.g. 1–3) for the damage if exploited.
Score Combined risk score used to rank threats (e.g. Likelihood × Impact).
Response The chosen response strategy: Mitigate, Eliminate, Transfer, or Accept.
Mitigation Note For Mitigate responses: the specific, testable control, ideally referencing OWASP ASVS or MITRE CWE.
Status Current progress: Not Started, Needs Investigation, Mitigated, or Not Applicable.

The status column is what makes the threat register operational rather than merely analytical. When a developer addresses a threat, they update the status to Mitigated and add a note referencing the commit or pull request. This transforms the register into a traceable record of what was decided, what was done, and when.

The Attack Surface Map

The OWASP Attack Surface Analysis Cheat Sheet describes a companion artifact to the threat register: the attack surface map. Where the DFD shows how data flows between components, the attack surface map catalogs every entry point into the system — every place where an attacker could interact with or inject data.

Entry points to document in an attack surface map include:

  • All public-facing UI forms (login, registration, contact, search, file upload)
  • All HTTP API endpoints, including their methods and authentication requirements
  • HTTP request headers that the application reads and acts on (e.g. Authorization, X-Forwarded-For, Content-Type)
  • Files read from disk, including configuration files and user-uploaded content
  • Database connections, including any third-party databases or data feeds
  • External service integrations (payment processors, email providers, OAuth providers)
  • Background jobs, cron tasks, and message queue consumers

The attack surface map and the threat model are intentionally coupled. According to the OWASP Attack Surface Analysis Cheat Sheet, any change to the attack surface — adding a new API endpoint, enabling a new file upload type, integrating a new external service — should trigger a new threat modeling session for the affected scope. Conversely, a new threat modeling session should prompt a review of whether the attack surface map is still accurate. They are twin lenses on the same system.

In a small project, the attack surface map can be a simple list in the same document as the threat register. In a larger system, it might be a structured table with columns for entry point type, URL or identifier, authentication required, and notes. The important thing is that it exists, is maintained, and is used as a change-detection mechanism.

The Validation Checklist

Before you consider a threat model “done,” run through a validation checklist. The OWASP Threat Modeling Cheat Sheet provides questions to confirm completeness. The goal is to catch gaps before they reach a security reviewer or, worse, production.

  1. Does the DFD accurately reflect the current system? Are all processes, data stores, external entities, data flows, and trust boundaries present and correctly labelled?
  2. Have all threats been captured and assigned a response? Is every STRIDE category applied to every data flow and process in the DFD?
  3. Are response decisions justified? Is there a written rationale for each threat accepted or transferred, not just mitigated?
  4. Are mitigations specific and measurable? Does every “Mitigate” entry reference a testable control or a published standard requirement?
  5. Is the attack surface map complete? Does it account for all entry points, including background jobs, webhooks, and third-party integrations?
  6. Is documentation accessible? Is the threat model stored where the whole development team can find and update it, not siloed with a single person or team?
  7. Is there a plan for keeping the threat model current? Is there a trigger condition — architecture change, new feature, security incident — that will prompt the next review?

A threat model that passes this checklist is not necessarily perfect — but it is complete enough to be useful and honest enough to be trusted. The sign-off question to ask yourself is: “Could a developer who was not in the room reconstruct the security reasoning behind this system from these documents alone?” If the answer is yes, the outputs are sufficient.

What the Complete Package Looks Like

A finished threat model for a single web feature typically lives in a source-controlled directory containing:

  • A DFD file (tool export, SVG, or embedded diagram in the README)
  • A threat register (Markdown table, spreadsheet, or tool-generated report)
  • An attack surface map (list or table, may be a section within the same document)
  • A short narrative document covering: scope and assumptions, the analysis approach used, key decisions (especially accepted risks), and a validation sign-off

The Microsoft Threat Modeling Tool generates all of these in a single report export: threat title, STRIDE category, priority, status, and mitigation notes per threat, plus a copy of the DFD. That report can be stored in a docs/security/ directory and updated in-place as mitigations are completed and the architecture evolves.

Whether you use a tool or assemble the documents by hand, the format matters less than the habits: keep it in source control, update it when the system changes, and make sure the team knows where it lives.
