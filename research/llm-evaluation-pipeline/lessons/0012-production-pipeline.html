Three-Tier Cadence Architecture

Running evals in production is not a single decision — it is a layered system of checks operating at different frequencies and costs. Hamel Husain describes three tiers that every mature LLM product should implement, each triggered at a different moment in the development lifecycle.

Tier Method Cadence Cost
1 — Unit tests Deterministic and fast scripted checks Every CI commit Cheapest — no model calls
2 — Sampled trace eval Human review or LLM judge on sampled production traces Daily or weekly Medium — judge API or human hours
3 — A/B testing Live traffic split between current and candidate model On significant changes to mature products Most expensive — real users, engineering overhead

The progression from tier 1 to tier 3 mirrors increasing confidence requirements: a CI gate is cheap enough to run on every push, a human or model eval on sampled traces is reserved for regular quality monitoring, and a live A/B test is warranted only when you need real-world signal before committing to a major change.

Within tier 2, Husain advocates for binary good/bad labels over granular numeric scores. Granular scores sound more informative, but they introduce inter-rater disagreement and make it harder to set action thresholds. A binary pass/fail decision is faster to make, easier to calibrate across reviewers, and directly actionable. When datasets are imbalanced — far more good outputs than bad — track model-vs-human agreement using precision and recall rather than simple accuracy, which can be misleadingly high in lopsided distributions.

One principle cuts across all three tiers: never stop looking at data. Husain is explicit that sampling should continue over time rather than be treated as a one-time exercise. Even when no systemic failure is obvious, ongoing data review surfaces edge cases, distribution shifts, and emerging failure modes that would be invisible to automated metrics alone.

Dataset Bootstrapping and the run_experiment() Pattern

The Anyscale guide describes a repeatable structure for running LLM evaluations: a single run_experiment() function that sequences three stages every time an experiment is executed.

  1. Dataset creation — assemble manually labeled or synthetically generated question-answer pairs that represent your use case.
  2. Generate responses — run the current pipeline configuration over every item in the dataset and collect the outputs.
  3. Evaluate responses — score each output by calling evaluate_responses() with a trusted evaluator LLM.

Wrapping these three stages in a single function makes experiments reproducible, comparable, and easy to trigger from CI. The same function runs during development, on a scheduled cadence, and as a regression gate before any configuration change ships.

The cold start problem: synthetic Q&A bootstrapping

New applications rarely have labeled evaluation data at launch. The practical solution is to prompt an LLM to generate question-answer pairs directly from your existing text chunks or documents. This synthetic dataset does not replace human-labeled gold data, but it provides an immediately useful starting point that can be progressively refined as real production traces accumulate.

A key constraint governs dataset portability: evaluation results cannot be transferred between use cases. A dataset built for a technical support bot is not a valid proxy for a legal document summarizer, even if both involve retrieval-augmented generation. Domain-specific datasets are essential — evaluation quality is bounded by the specificity and coverage of the underlying test cases.

Sequencing system parameter changes

When optimizing a RAG-based pipeline, the Anyscale guide recommends evaluating system parameters in a deliberate sequence rather than simultaneously. Each change should be isolated and measured before the next one is introduced: chunking strategy, then embedding model, then number of retrieved chunks, then LLM choice, then prompt engineering, then reranking. This ordering prevents conflating the effects of multiple simultaneous changes, which makes it impossible to attribute a score change to any single decision.

Routing strategy: match model cost to query difficulty

Not every query requires the most capable — and most expensive — model. Anyscale found that GPT-4 was the most reliable evaluator, while smaller open-source models exhibited a notable bias: they scored their own outputs generously. This asymmetry motivates a routing strategy: route hard queries to GPT-4 and simple queries to a cheaper model. In the Anyscale experiments, Mixtral-8x7B approached GPT-4 quality at approximately 25 times lower cost, making it a compelling option for the bulk of straightforward requests.

Evaluator Drift and Human Calibration

An evaluator — whether human or model-based — is itself a component that can degrade over time. Eugene Yan calls this evaluator drift: the gradual divergence between what your judge labels as good or bad and what your human standards team would label today. Drift can occur for several reasons: the judge's underlying model is updated, the distribution of production inputs shifts, labeling guidelines evolve, or new failure modes emerge that were not covered when the evaluator was originally calibrated.

The remedy is ongoing human calibration. Periodically re-sample a fresh set of examples from production, have humans label them, and compare those labels against what the current judge produces. If agreement drops below an acceptable threshold, the judge needs retraining, prompt revision, or replacement. This process is not a one-time setup — it is a recurring maintenance task woven into the production eval cadence.

Prompted judges vs. finetuned judges: a practical split

Yan draws a clear distinction between two judge architectures that serve different roles in a production system.

Prompted LLM judges (e.g., GPT-4 with a carefully engineered rubric) offer broad generalizability across evaluation types. They can be adapted to new evaluation criteria by changing the prompt without retraining, making them well-suited for development-time evaluation where requirements shift frequently.

Finetuned evaluators excel on in-domain tasks where they were trained. However, they function as task-specific classifiers: when applied to a different evaluation scheme — even a superficially similar one — they suffer catastrophic performance drops. Their strength is speed and cost efficiency, not flexibility.

The recommended split: use prompted LLM judges during development when evaluation criteria are still evolving; deploy finetuned classifiers in latency-sensitive production guardrails where inference speed and cost matter more than flexibility. Combining both gives you adaptability where you need it and efficiency where you cannot afford to wait.

Eval infrastructure is not just a quality gate — it is simultaneously a data curation engine for fine-tuning and a debugging tool for understanding where your pipeline fails. Building it as a first-class system from the start means every future improvement is grounded in real, accumulated evidence rather than intuition.
A common mistake is to treat evaluator calibration as a one-time setup. Teams invest effort in aligning human and model labels at launch, then assume that alignment holds indefinitely. It does not. Model updates, shifting input distributions, and evolving quality standards all erode agreement silently — you will not notice until you re-measure. Schedule periodic re-calibration from the beginning; do not wait for a visible quality drop to prompt it.
