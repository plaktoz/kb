DeepEval: An Open-Source Pytest-Native Evaluation Framework

DeepEval is an open-source evaluation framework that plugs directly into pytest (Python) or Vitest (TypeScript), letting you write LLM test cases alongside your regular unit tests. Because evals live in the same repository and run in the same CI pipeline as the rest of your code, there is no separate evaluation harness to maintain or synchronize.

The core primitive is the LLMTestCase. Every test case requires two mandatory fields:

  • input — the prompt or query sent to the LLM
  • actual_output — the response your LLM produced

Two optional fields are used in most real evaluations:

  • expected_output — a reference answer for correctness comparison
  • context — retrieved passages or grounding documents, essential for RAG evaluation

For multi-turn conversations, DeepEval provides a ConversationalTestCase that captures the full dialogue as a list of Turn objects, each carrying a role and content field — the same shape as the messages array in the Chat Completions API.

GEval: Define Evaluation Logic in Plain English

The primary metric in DeepEval is GEval, described as "a research-backed metric" that evaluates outputs "on any custom metric with human-like accuracy" using an LLM judge internally. The key design decision is that you write the evaluation criteria in plain English rather than hand-coded comparison logic — GEval translates those criteria into judge prompts automatically.

Every metric score ranges from 0 to 1. You set a threshold value to define the pass/fail boundary. A correctness metric with a threshold of 0.5 passes any output scoring above the midpoint and fails anything below it. The judge model is fully swappable: DeepEval integrates with OpenAI, Anthropic, Gemini, Azure OpenAI, and Ollama.

A minimal GEval correctness metric:

from deepeval.metrics import GEval
from deepeval.test_case import SingleTurnParams

correctness_metric = GEval(
    name="Correctness",
    criteria="Determine if the 'actual output' is correct based on the 'expected output'.",
    evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.EXPECTED_OUTPUT],
    threshold=0.5,
    model="gpt-4o"
)

To execute the test suite: deepeval test run test_example.py

Agents, Traces, and Online Monitoring

DeepEval handles agentic workloads beyond single-turn evaluation. For agent evaluation it captures execution traces and applies TaskCompletionMetric to the full trajectory — scoring whether the agent accomplished its goal, not just whether any single output looks good. At the component level, individual spans such as retrievers, tool calls, and sub-agents can each be scored separately within a trace. For production environments, attaching a metric_collection to traces enables continuous online monitoring without changing your test files.

Cutting Judge Costs: How Few-Shot Calibration Makes GPT-3.5 Viable

Running every evaluation through GPT-4 is accurate but expensive. Databricks investigated whether a cheaper model could serve as a reliable judge for RAG pipeline evaluation, and the results were striking: GPT-3.5 with few-shot examples achieves comparable ranking accuracy to GPT-4 at 10x lower cost and 3x faster speed.

The critical qualifier is with examples. GPT-3.5 without a grading rubric produces "very inconsistent results and is completely unusable." The capability gap between the two models is not the problem — calibration is.

The One-Example-Per-Score Rule

Providing one graded example per score level dramatically stabilizes GPT-3.5 output. If your rubric has four levels (0–3), you supply four annotated examples — one demonstrating each level. This anchors the model's interpretation of the scale and prevents it from drifting toward arbitrary intermediate values between runs.

Databricks also recommends using low-precision integer scales — specifically 0–3 or 1–5 — rather than 0–100 or 0–10 ranges. Fine-grained scales invite inconsistency: a judge cannot reliably distinguish a 67 from a 71. Small integer scales with one anchored example per level produce far more reproducible results.

Human Alignment Numbers

LLM judges calibrated this way match human graders on more than 80% of judgments and fall within a one-point margin on more than 95%. The outlier is Comprehensiveness — the least-aligned metric across the three standard RAG dimensions, because it is the most subjective. When a question has multiple valid levels of detail, humans and LLMs disagree more than on any other quality dimension.

Composite Scoring and Routing: Maximizing Quality Within Budget

Weighted Composite Scores for RAG

A single scalar score rarely reveals what is wrong with an output. Databricks recommends a three-metric composite for RAG evaluation, with weights that reflect what users actually care about:

Metric Weight What it measures
Correctness 60% Is the answer factually accurate relative to the retrieved context?
Comprehensiveness 20% Does the answer address all relevant aspects of the question?
Readability 20% Is the answer clearly written and easy to understand?

Correctness dominates at 60% because factual accuracy is the dimension that breaks user trust fastest when wrong. Comprehensiveness and readability each take 20%, acknowledging their importance to user experience without letting them override the accuracy signal. Comprehensiveness is also weighted conservatively because it has the lowest human-LLM alignment — the most subjective dimension warrants the least authority in an automated score.

Routing Strategy: Right Model for the Right Query

Not every query needs GPT-4. A practical routing strategy assigns judge models based on query difficulty:

  • GPT-4 for hard or ambiguous queries — where the correct answer is genuinely uncertain, context is complex, or edge cases are likely to matter
  • GPT-3.5 with few-shot examples for clear-cut queries — where the rubric applies straightforwardly and a calibrated cheaper model is sufficient

This routing approach captures most of GPT-4's judgment quality where it matters while redirecting the majority of routine evaluations to the far cheaper model. The cost reduction compounds quickly at scale: if 70% of queries are clear-cut, routing them to GPT-3.5 cuts the average cost per eval by roughly 7x.

GPT-3.5 with one graded example per score level matches GPT-4 ranking accuracy at one-tenth the cost and three times the speed. Without a rubric and examples it is completely unusable. The difference is not the model — it is the scaffold. Calibration, not capability, is the variable that controls cheap judge quality.
A common misconception is that a finer-grained numeric scale produces more precise evaluations. The opposite is true. Scales from 0–100 or 0–10 invite arbitrary scores that judges cannot reproduce consistently across runs. Use low-precision integer scales (0–3 or 1–5) with one annotated example per level. More granularity without calibration is noise, not signal.
