What Is pass@k and Why Does It Matter?

Text-matching metrics like BLEU were originally designed for machine translation, where a reference human translation provides a surface to compare against. Applied to code generation, the same logic seems appealing: generate a solution, compare it word-for-word to a reference implementation, assign a score. Fast, cheap, reproducible.

The problem is that code is not text. Two functions can look completely different — different variable names, different loop structure, different algorithmic approach — and still produce identical outputs for every possible input. Conversely, two functions can share most of their tokens and diverge catastrophically on a single edge case. Lexical similarity tells you almost nothing about whether the code works.

The HumanEval benchmark was built to address this gap. Instead of asking "does the output look like a reference solution?", it asks "does the output pass the tests?" Each problem in HumanEval presents a docstring describing a function to implement. The model generates a function body. Correctness is determined by executing a suite of unit tests against the generated function — not by comparing tokens.

The metric that makes this tractable at scale is pass@k. Rather than generating a single solution and hoping it is correct, you generate k candidate solutions for each problem and count the problem as solved if at least one of those candidates passes all unit tests. This shifts evaluation from a single-shot question ("did the model get it right?") to a coverage question ("can the model get it right within k attempts?").

Formally: generate k samples per problem; a problem is solved if any sample passes all unit tests; pass@k is the fraction of problems solved under this rule.

HumanEval Results: What Repeated Sampling Reveals

The HumanEval paper evaluated Codex — an early code-generation model — and the results illustrate both the power of pass@k and the failure modes that lexical metrics would never catch.

Metric Codex score What it measures
pass@1 28.8% Probability that a single generated solution passes all tests
pass@100 70.2% Probability that at least one of 100 solutions passes all tests

The gap between 28.8% and 70.2% is the headline finding. Repeated sampling is a highly effective strategy for code generation. The model can produce a correct solution for most problems — it just does not always produce one on the first try. For applications where you can afford to run several candidates through tests and select the passing one, this is a substantial capability multiplier.

The paper also documented specific failure modes that no lexical metric would catch:

  • Long chains of operations in docstrings — when a function specification requires composing several steps, models struggled to maintain correctness across the full chain. A BLEU comparison against a reference would give partial credit for getting some steps right; unit tests give no credit unless every step is correct.
  • Binding operations to variables — models sometimes performed the correct computation but assigned the result to the wrong variable, or forgot to return it. The output text looked plausible; execution revealed the error.

These failure modes are invisible to surface-level metrics. The model produced code that resembles correct code. Only running the tests surfaces the bug. This is why the paper concluded that functional correctness via test execution is far more reliable than BLEU for code evaluation — and that BLEU showed no meaningful correlation with actual code correctness.

Benchmark Validity Pitfalls: The DROP Investigation

Building a reliable evaluation pipeline requires more than choosing the right metric. Every stage of the pipeline — tokenization, normalization, stop condition, scoring logic — can introduce bugs that corrupt results. The investigation into the DROP benchmark score on the Open LLM Leaderboard is a case study in how subtle implementation errors compound into misleading rankings.

DROP is a reading-comprehension benchmark that requires discrete reasoning over passages, often involving numeric answers. The Hugging Face investigation found that small technical choices could catastrophically skew results:

  • Stop token choice (. vs. \n): Different stop conditions changed how much of a model's response was captured before scoring began. A model that generated a well-formatted multi-line answer could have that answer truncated or padded differently depending on which stop token the evaluation harness used.
  • Numeric normalization bugs: Better models that followed prompt formatting guidelines more closely generated longer, more fully explained responses. These longer responses bypassed the normalization logic in the scoring code — which was written with shorter responses in mind — causing better models to score lower than weaker models.

The effect was not marginal. Over 50% of examples had to be re-run after the evaluation errors were identified. The cost of replication — in compute time and engineering attention — was substantial. And in the intervening period, published leaderboard rankings had inverted the true ordering of model quality for this benchmark.

What to scrutinize in every evaluation pipeline

The DROP case generalizes. Every pipeline stage is a potential source of silent corruption:

  • Tokenization: How are prompts and responses tokenized? Does the model see the same format it was evaluated on?
  • Normalization: How are answers cleaned before comparison? Numeric normalization, case folding, whitespace stripping — each rule can create unexpected interactions with model outputs.
  • Stop conditions: Does the evaluation harness stop generation at the right point? Over- or under-truncation affects what gets scored.
  • Scoring logic: Is the comparison function symmetric? Does it handle edge cases (empty strings, unicode, very long outputs) without silent failures?

The investigation also identified a practical early-warning technique: correlation checks. By plotting benchmark scores against an independent proxy measure — a simpler metric you trust, or human ratings on a sample — you can detect when the pipeline is producing results that diverge from ground truth before those results become published rankings.

Community-wide transparency proved essential to catching the DROP errors. When enough practitioners compared notes, the anomaly (better models scoring lower) became undeniable. Evaluation is not a solved problem you set up once; it requires ongoing scrutiny and openness about implementation details.

For code generation, the only reliable ground truth is execution. pass@k operationalizes this: generate k candidates, run the tests, count problems where at least one candidate passes. Codex's jump from 28.8% pass@1 to 70.2% pass@100 shows both the value of the metric and the leverage available from repeated sampling.
BLEU is sometimes applied to code generation because it is fast to compute and requires no test infrastructure. This is a mistake. BLEU measures token overlap against a reference solution — but there is rarely a single correct implementation, and two syntactically similar functions can diverge completely on edge cases. The HumanEval paper found that BLEU showed no correlation with actual code correctness. A high BLEU score is neither necessary nor sufficient for a function to pass its tests.

Write unit tests for a pass@k evaluation of Fibonacci

You are building a pass@k evaluation for the prompt: "Write a function that finds the Nth Fibonacci number." Write three unit tests that would form the basis of this evaluation — one covering the happy path, one covering an edge case, and one covering a boundary condition. Each test should be a plain assertion that would pass if the function is correct and fail if it is not.

  • Happy path: a typical input with a known-correct output
  • Edge case: an input at or near zero where the sequence definition matters (e.g., fib(0) or fib(1))
  • Boundary condition: a case that stresses the implementation — a large index, negative input handling, or type behavior
