Guardrails AI — Guards, Validators, and the Hub

The Guardrails AI Lifecycle

Guardrails AI is a full-lifecycle AI reliability platform. Rather than addressing only one moment in an AI system's lifespan, it covers the entire journey from initial data preparation through live production enforcement. The platform organises this into three distinct phases:

  1. Synthetic data generation — the Snowglobe engine creates synthetic datasets used to stress-test models before they ever see real users.
  2. Pre-deployment evaluation — edge-case datasets are generated to probe model behaviour under difficult or unusual inputs, catching problems before go-live.
  3. Production runtime enforcement — live guardrail policies intercept LLM inputs and outputs, catching policy violations, hallucinations, and data leakage as they occur.

The runtime enforcement layer is built around the Guardrails Hub — a centralised registry of deployable guardrail policies. Instead of writing every check from scratch, developers pull pre-built validators from the Hub and compose them into Guards.

The Guardrails AI platform is designed to be applied at all three phases of the model lifecycle — not just at runtime. The Hub acts as a shared registry that makes the runtime phase composable and reusable across projects.

Validators and Guards — Core Concepts

Validators

A Validator is a single, pre-built risk measurement. Validators are available through the Guardrails Hub and cover a wide range of concerns — detecting toxic language, checking for competitor mentions, enforcing regex patterns, and more. Each Validator is a self-contained check with a defined pass/fail contract.

Guards

A Guard is the container that assembles one or more Validators into a deployable pipeline. The Guard exposes the validate() (or callable) interface that application code uses, and it defines what happens when any of its Validators fails. Validators are the building blocks; Guards are the assembled guardrail.

To create a Guard, you call Guard().use(...), passing one or more Validators and their failure-action configuration. Multiple .use() calls can be chained, or several validators can be passed together — both approaches compose them into the same Guard.

Think of a Validator as a single test and a Guard as a test suite. The Guard runs its Validators in order and decides what to do when one fails — the Validator only knows how to detect the problem, not how to respond to it.

OnFailAction — Controlling Failure Behaviour

Every Validator is configured with an on_fail parameter that specifies what the Guard should do when that particular check fails. The OnFailAction enum provides the available choices:

Action Behaviour Typical use
OnFailAction.EXCEPTION Raises a Python exception, halting execution immediately. Strict enforcement where any violation must be surfaced to the caller.
OnFailAction.FILTER Silently removes or replaces the invalid content without raising an error. Data pipelines where partial output is preferable to a hard failure.

Other actions also exist in the library. The choice of action is a design decision tied to context: user-facing chatbots often benefit from the visibility that exceptions provide, while automated data pipelines may prefer silent filtering to maintain throughput.

OnFailAction.FILTER swallows failures silently, which makes debugging harder. If you use it in a data pipeline, make sure you have separate logging or metrics in place to track how often content is being filtered — otherwise violations can go unnoticed for a long time.

Code Examples

Basic Validation with a Single Validator

The example below creates a Guard that enforces a US phone number format using RegexMatch. If the validated string does not match, the Guard raises an exception. 

from guardrails import Guard, OnFailAction
from guardrails_ai.regex_match import RegexMatch

guard = Guard().use(
    RegexMatch, regex="\(?\d{3}\)?-? *\d{3}-? *-?\d{4}", on_fail=OnFailAction.EXCEPTION
)

guard.validate("123-456-7890")  # passes

Composing Multiple Validators

Guards become more powerful when multiple Validators are composed. The Guard below applies two checks — competitor mention detection and toxic language detection — each configured independently with its own threshold and failure action. 

guard = Guard().use(
    CompetitorCheck(["Apple", "Microsoft"], on_fail=OnFailAction.EXCEPTION),
    ToxicLanguage(threshold=0.5, on_fail=OnFailAction.EXCEPTION)
)

Both Validators must pass for the Guard to consider the content valid. Each can be tuned independently — a strict threshold for toxic language, for example, while using a more permissive setting elsewhere.

Structured Pydantic Output

Guards are not limited to validating plain text strings. Using Guard.for_pydantic(), you can enforce structured output against a Pydantic model, ensuring the LLM's response conforms to a defined schema rather than returning free-form text. 

from pydantic import BaseModel

class Pet(BaseModel):
    pet_type: str
    name: str

guard = Guard.for_pydantic(output_class=Pet, prompt=prompt)
raw_output, validated_output, *rest = guard(llm_api=openai.completions.create)

The Guard wraps the LLM call, parses the response, validates it against the Pet schema, and returns both the raw output and the validated, typed object.

Deploying as a REST Service

Guardrails can be deployed not just as an in-process library but as a standalone REST service. A single command starts the service: 

guardrails start

Once running, the service exposes an HTTP API that any application can call — decoupling the guardrail logic from the application process entirely. Integration is straightforward through two paths:

  • The Guardrails client — a purpose-built SDK that communicates with the running service.
  • The standard OpenAI SDK — by redirecting the base_url to point at the Guardrails service endpoint, existing OpenAI-compatible code can run through Guardrails with minimal changes.

Running Guardrails as a service is particularly useful in microservice architectures where multiple applications need shared guardrail policies, or when guardrail compute should be isolated and scaled independently of the main application.

The REST service deployment mode means Guardrails can act as a drop-in proxy in front of any OpenAI-compatible endpoint. Redirecting base_url is all that is needed — no changes to the rest of the application code.
