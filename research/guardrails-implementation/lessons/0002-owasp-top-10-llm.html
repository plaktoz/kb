What Guardrails Defend Against — OWASP Top 10 for LLMs

~20 min Module 1 — Foundations: What Are Guardrails? Lesson 2 of 12
Primary Source OWASP Top 10 for LLM Applications
https://owasp.org/www-project-top-10-for-large-language-model-applications/

The Open Worldwide Application Security Project (OWASP) cataloged the ten highest-risk vulnerabilities specific to LLM-based applications. Understanding these risks is the first step to understanding why guardrails exist and what they are protecting against. Each risk on this list has a direct counterpart — a guardrail type you can build into any production AI system.

The OWASP Top 10 for LLM Applications

The ten risks below are ordered as OWASP lists them. Read each description carefully — you will use them in the exercise at the end of this lesson.

1. Prompt Injection

Crafted inputs manipulate the LLM into following attacker-controlled instructions. According to OWASP, successful prompt injection can lead to "unauthorized access, data breaches, and compromised decision-making." This is the most widely exploited LLM-specific attack vector and affects both direct user inputs and indirect content the LLM reads from external sources (documents, web pages, tool outputs).

2. Insecure Output Handling

When an application passes LLM outputs directly to downstream systems — browsers, databases, shells — without validation, the output becomes an attack surface. OWASP notes this may cause "downstream security exploits, including code execution." An LLM asked to produce JavaScript might generate malicious scripts; an LLM writing SQL might produce injection payloads.

3. Training Data Poisoning

If training or fine-tuning data is tampered with, the resulting model can produce responses that "compromise security, accuracy, or ethical behavior." Attackers who can influence training datasets can embed backdoors or biases that surface only under specific conditions.

4. Model Denial of Service

Unusually resource-intensive inputs — extremely long prompts, recursive reasoning chains, adversarially complex queries — can exhaust compute resources, causing service disruptions and elevated costs. This mirrors classic denial-of-service attacks but exploits the LLM's compute profile rather than network bandwidth.

5. Supply Chain Vulnerabilities

LLM applications depend on a supply chain: pre-trained model weights, fine-tuning datasets, third-party plugins, and libraries. Compromised components anywhere in this chain can trigger system failures and data breaches. An attacker who poisons a popular open-source embedding model affects every application that downloads it.

6. Sensitive Information Disclosure

LLMs can inadvertently expose data from their training sets, system prompts, or retrieved context. Inadequate output filtering risks exposing protected data including personally identifiable information (PII), credentials, or confidential business information embedded in context windows.

7. Insecure Plugin Design

Plugins and tools that extend LLM capabilities introduce a new attack surface. OWASP warns that plugins handling untrusted inputs risk "severe exploits like remote code execution." When an LLM calls a plugin that writes files, sends emails, or queries databases, any injection in the LLM's output becomes an instruction to that plugin.

8. Excessive Agency

When an LLM is given too much autonomy — the ability to call APIs, execute code, send messages, or modify data without human oversight — unchecked autonomy leads to "unintended consequences, jeopardizing reliability, privacy, and trust." The LLM may take actions its users or developers never intended, either through misunderstanding or through prompt injection that redirects its tool use.

9. Overreliance

Systems and users that accept LLM outputs uncritically create security and decision-making vulnerabilities. When developers build pipelines that automatically act on LLM output without verification, a single confident but wrong (or manipulated) output can cascade through a system. Overreliance is partly a human-process risk, not only a technical one.

10. Model Theft

Unauthorized access to proprietary model weights or architectures risks competitive harm and exposure of sensitive data that may have been used in training. Attackers may use model extraction techniques — querying a model systematically to reconstruct its behavior — or directly exfiltrate model files.

Every one of the ten OWASP LLM risks maps to at least one guardrail type. Guardrails are not abstract best-practice suggestions — they are the concrete technical defenses that correspond directly to these documented attack categories.

Mapping OWASP Risks to Guardrail Types

The table below shows how each risk connects to a guardrail type. Some risks require more than one layer of defense. The "guardrail type" column uses labels you will practice with in the exercise.

# OWASP Risk Primary Guardrail Type Notes
1 Prompt Injection Input filter A secondary LLM detector or pattern-matching filter screens inputs for injection attempts before they reach the main model
2 Insecure Output Handling Output filter Output validation guardrail checks and sanitizes LLM responses before they are passed to downstream systems
3 Training Data Poisoning Supply chain audit Data validation and provenance checks on training/fine-tuning datasets before they are used
4 Model Denial of Service Rate limiter Rate limiting and input-length guardrails prevent resource exhaustion from pathological queries
5 Supply Chain Vulnerabilities Supply chain audit Integrity checks, signed artifacts, and dependency audits across model weights, plugins, and libraries
6 Sensitive Information Disclosure Output filter PII detection and output filtering block protected data from appearing in responses
7 Insecure Plugin Design Input filter + output filter Validate both the LLM's instructions to plugins (output filter) and plugin responses passed back to the LLM (input filter)
8 Excessive Agency Permission/scope control Constrain which tools the LLM can invoke; add human approval gates for high-impact actions
9 Overreliance Monitoring/logging Log LLM decisions, surface confidence signals, and add human-in-the-loop checkpoints for high-stakes outputs
10 Model Theft Rate limiter + monitoring/logging Rate limiting on inference endpoints and anomaly detection on query patterns deter extraction attacks
A common misconception is that prompt injection is the only LLM-specific security risk. In reality, OWASP documents nine other categories — several of which (Excessive Agency, Insecure Output Handling, Insecure Plugin Design) become more dangerous as LLMs gain tool-use and agentic capabilities. Guardrail design must cover the full list, not just the most publicized attack.

Why This Matters for Guardrail Design

The OWASP list establishes a shared vocabulary for LLM application security. When you build a guardrail, you should be able to name which risk (or risks) from this list it addresses. If you cannot point to a specific risk, the guardrail may be redundant or misdirected.

Three risks deserve special attention as AI systems move toward greater autonomy:

  • Excessive Agency grows more dangerous as LLMs are given more tools. An LLM that can only generate text has limited blast radius; an LLM that can send emails, execute code, and call external APIs has enormous blast radius if not properly scoped.
  • Prompt Injection scales with the amount of external content the LLM processes. Retrieval-augmented generation (RAG) systems that ingest web pages, documents, or user data are continuously exposed to indirect injection payloads embedded in that content.
  • Insecure Output Handling is frequently overlooked because the LLM itself is not malicious — but its output can be used as an attack vector against downstream systems that trust it unconditionally.
