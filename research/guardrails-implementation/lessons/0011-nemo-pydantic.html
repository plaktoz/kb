NeMo Guardrails: Programmable Rails for LLM Applications

NVIDIA NeMo Guardrails is an open-source Python library for adding programmable guardrails to LLM-based applications. It allows developers to block, alter, or validate unsafe, off-topic, malicious, or policy-violating user inputs and model responses — without restructuring the underlying application or retraining the model.

The library sits as a layer around your existing LLM calls. You define policies in configuration files; NeMo intercepts requests and responses and applies those policies transparently. Your application code barely changes.

Key Features

Feature What it does Mechanisms
Content Safety Screens inputs and outputs for unsafe content LLM self-checking, NVIDIA safety models, community models (e.g. LlamaGuard), third-party APIs
Jailbreak Protection Detects attempts to bypass system instructions Heuristic detection, self-check methods, specialized NIMs
Topic Control Keeps conversations within defined boundaries Dialog rails and topical rails defined in Colang
PII Detection / Masking Identifies and redacts personally identifiable information Microsoft Presidio, Private AI, GLiNER integrations
Agentic Security Validates tool calls in agent workflows Multi-agent workflow support via LangGraph
Extensibility Add custom logic and third-party integrations Custom Python actions and third-party API hooks

How NeMo Guardrails is Built

NeMo Guardrails is built around three components that work together:

  1. YAML configuration files — declare which rails are active, which models to use for checking, and how to connect to external services.
  2. Colang conversational flows — a domain-specific language for defining dialog patterns, topic rails, and what the bot should do when a rail is triggered.
  3. Python SDK — the LLMRails class wraps your LLM configuration and exposes a generate() method that automatically applies all configured rails.

The LLMRails API

Using NeMo Guardrails in Python requires only two lines to get started: 

from nemoguardrails import LLMRails, RailsConfig

# Load configuration from a directory containing config.yml and Colang flows
config = RailsConfig.from_path("./guardrails_config")

# Wrap your LLM with the configured rails
rails = LLMRails(config)

# Call generate — rails are applied automatically before and after the LLM call
response = rails.generate(messages=[
    {"role": "user", "content": "Tell me how to bypass authentication."}
])

print(response)

The generate() method accepts the same message format as OpenAI-compatible APIs. Internally, NeMo intercepts the call, runs input rails (checking the user message), forwards to the LLM if the input passes, then runs output rails on the response before returning it.

Colang Topic Rail Example

Topic control rails are defined using Colang conversational flow syntax. A topical rail specifies what topics the bot is allowed to discuss, and what to say when a user goes off-topic: 

# config.yml (excerpt)
rails:
  input:
    flows:
      - check off-topic

---
# flows.co (Colang)
define flow check off-topic
  user ask off topic
  bot say off topic refusal

define bot say off topic refusal
  "I can only help with cooking-related questions. Please ask me about recipes, ingredients, or techniques."

define user ask off topic
  "What is the weather today?"
  "Can you write code for me?"
  "Who won the election?"

Deployment Options

NeMo Guardrails can run in several modes:

  • In-process Python library — import and call directly within your application. Lowest latency, no extra network hop.
  • HTTP server — deploy as a standalone service exposing OpenAI-compatible endpoints. Other services call it over the network without knowing guardrails are applied.
  • Kubernetes — configurations are portable; the same YAML and Colang files used in local development deploy directly to production Kubernetes clusters.
Key insight: NeMo's portability is a practical advantage. The same configuration that runs locally during development deploys unchanged to production Kubernetes. You are not maintaining separate rule sets for different environments.

Pydantic: Type-Driven Boundary Validation

Pydantic is Python's most widely used data validation library, driven by type annotations. The core idea is simple: define a class that inherits from BaseModel, declare fields with type hints, and Pydantic handles coercion and validation automatically when data enters your system.

Pydantic operates as a boundary enforcement layer. Data enters, gets validated against your declared schema, and either passes through (possibly transformed to the declared type) or raises a detailed ValidationError.

Defining a BaseModel

from pydantic import BaseModel, field_validator
from datetime import datetime

class ChatRequest(BaseModel):
    message: str
    user_id: str
    session_token: str
    timestamp: datetime          # ISO 8601 string → parsed to datetime automatically
    max_tokens: int = 512        # field with a default value

    @field_validator("message")
    @classmethod
    def message_must_not_be_empty(cls, v: str) -> str:
        v = v.strip()
        if not v:
            raise ValueError("message must not be empty")
        if len(v) > 2000:
            raise ValueError("message must not exceed 2000 characters")
        return v

# Valid input — Pydantic coerces the string "128" to int 128
req = ChatRequest(
    message="What temperature for roasting chicken?",
    user_id="u-42",
    session_token="tok-abc123",
    timestamp="2026-08-20T14:00:00Z",
    max_tokens="128"             # string coerced to int in lax mode
)

Type Coercion: Strict vs. Lax Mode

Pydantic supports two validation modes that control how strictly it enforces types:

  • Lax mode (default) — allows safe coercions. A string '123' is coerced to int. Bytes keys are coerced to str. ISO 8601 strings are parsed into datetime objects. The value passes through transformed to match the declared type.
  • Strict mode — rejects any value that does not already have the exact declared type. A string '123' passed to an int field raises a ValidationError immediately — no coercion is attempted. 
from pydantic import BaseModel

class StrictModel(BaseModel):
    model_config = {"strict": True}
    count: int

# This will raise a ValidationError in strict mode
try:
    StrictModel(count="42")     # string, not int — rejected
except Exception as e:
    print(e)
# Output: 1 validation error for StrictModel
# count
#   Input should be a valid integer [type=int_type, ...]
Key insight: Strict mode is the right choice at system boundaries where silent coercion would mask type bugs. If upstream code is sending strings when your schema expects integers, you want to know immediately — not have Pydantic quietly fix it for you.

ValidationError: Structured Failure Details

When validation fails, Pydantic raises a ValidationError containing structured information about every field that failed — not just the first one. Each error entry includes:

  • loc — the field location (including nested paths for nested models)
  • type — the error type code (e.g., string_too_long, int_type)
  • msg — a human-readable description of what failed
from pydantic import BaseModel, ValidationError

class RequestModel(BaseModel):
    user_id: str
    max_tokens: int

try:
    RequestModel(user_id=None, max_tokens="not-a-number")
except ValidationError as e:
    print(e.error_count(), "errors")
    for err in e.errors():
        print(err["loc"], "→", err["msg"])

# Output:
# 2 errors
# ('user_id',) → Input should be a valid string
# ('max_tokens',) → Input should be a valid integer

Because ValidationError is machine-readable, you can catch it, extract the structured errors, and return them directly in an API error response — giving callers precise field-level feedback without writing any custom error-formatting logic.

Additional Pydantic Capabilities

  • Custom validators — use @field_validator or @model_validator to add domain-specific logic beyond built-in type checks (e.g., ensuring a message is not empty, validating a token format).
  • JSON Schema emission — call Model.model_json_schema() to generate a JSON Schema from the model definition. Useful for API documentation and integrating with external tooling.
  • TypedDict and dataclass support — Pydantic can validate standard library types, not just classes that inherit from BaseModel.
Caveat: Pydantic validates structure and types, but it does not understand intent. A message field that passes type validation may still contain a prompt injection attack. Pydantic is a boundary enforcement layer — it is not a semantic guardrail. Combine it with tools like NeMo Guardrails or Guardrails AI for content-level protection.

Choosing the Right Tool: NeMo vs. Guardrails AI vs. Pydantic

These three tools address different problems and work best at different layers of your system. They are not mutually exclusive — in a production LLM service you will often use all three.

Tool Primary concern Where it operates Best for
NeMo Guardrails Conversational policy enforcement Wraps the LLM call (input + output) Topic control, jailbreak prevention, PII masking, multi-turn dialog safety, agentic tool-call validation
Guardrails AI Structured output validation and correction Post-LLM output processing Ensuring LLM outputs match a declared schema, auto-retrying malformed responses, field-level output validation
Pydantic Data schema validation at system boundaries API input/output, inter-service data contracts Validating request payloads, enforcing type contracts between services, generating JSON Schema for docs

Decision Guidance

  • Use Pydantic at every API boundary where structured data enters or leaves your service. It is lightweight, fast, and zero-configuration for simple cases. Think of it as your first line of defense against malformed requests.
  • Use Guardrails AI when your LLM must return data in a specific schema and you need the library to detect deviations and optionally auto-correct or re-prompt. It is output-focused.
  • Use NeMo Guardrails when you need policy-level control over what topics a conversational LLM can engage with, when you need jailbreak protection, or when you are building multi-agent systems where tool calls must be validated before execution.
  • Use all three together for a defense-in-depth approach: Pydantic validates the incoming request structure, NeMo applies conversational rails around the LLM call, and Guardrails AI validates that the LLM's output conforms to your schema before returning it to the caller.
