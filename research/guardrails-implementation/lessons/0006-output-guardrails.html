G-Eval: Scoring LLM Responses Against Criteria

Before a response reaches the user, you can run it through an automated scoring pass. The G-Eval pattern, documented in the OpenAI Cookbook, assigns each response a numeric score from 1 to 5 against a set of criteria you define. If the score falls at or above a configured threshold, the response is blocked; if it scores below the threshold it proceeds to the user.

G-Eval structures its evaluation around three concepts:

  • Domain — the application context the scorer is evaluating (e.g., customer support, medical advice).
  • Criteria — the specific property being measured (e.g., toxicity, off-topic content, factual accuracy).
  • Steps — the chain-of-thought instructions the evaluating model follows to arrive at a score.

This three-part structure makes G-Eval extensible: you swap in a new domain/criteria/steps tuple for each quality dimension you care about, without rewriting the scoring infrastructure. The scorer itself is typically a separate, cheaper LLM call that runs synchronously before the response is returned.

G-Eval turns vague quality goals ("don't be harmful") into a measurable, automatable gate: score the output, compare to a threshold, block or pass. The domain/criteria/steps structure keeps the policy readable and version-controlled alongside your application code.

Azure AI Content Filtering: Harm Category Taxonomy

Azure OpenAI's built-in content filtering system intercepts both prompts and completions, running them through neural classifiers. Every piece of text is evaluated across four harm categories, and within each category is assigned one of four severity levels.

Category What it covers Severity levels
Hate and Fairness Attacks based on race, gender, religion, nationality, and other protected attributes Safe · Low · Medium · High
Sexual Anatomical or romantic content, sexual abuse, and exploitation
Violence Physical harm, weapons, terrorism, and glorification of violent acts
Self-Harm Eating disorders, bullying, self-injury, and related content

The four severity levels — safe, low, medium, and high — form an ordinal scale. You configure per-category thresholds: content at or above the configured severity triggers the filter action (block or annotate). A conservative deployment might block anything rated low or above in the violence category, while a research tool might allow medium and only block high.

Annotate-Only vs. Block Mode

Azure content filters can operate in two modes for each category independently:

  • Block mode — content that meets or exceeds the threshold is suppressed. The API returns an HTTP 400 error rather than a completion. The user receives no model output for that request.
  • Annotate-only mode — content passes through to the caller, but the API response is annotated with filter results. The finish_reason field is set to content_filter to signal that filtering ran, and content_filter_results contains the per-category scores. Your application receives the content and can decide what to do with it.

Annotate-only mode is useful during the design phase of a deployment: you collect real distributions of severity scores before committing to blocking thresholds. It is also appropriate when your application needs to show the user why content was flagged rather than silently suppressing it — you read the annotations and generate a contextual explanation.

Special-Purpose Filters

Beyond the four harm categories, Azure provides additional filters that target structural risks rather than offensive content:

Prompt Shields

Prompt Shields detect two specific attack vectors: direct jailbreak attempts (where a user crafts a prompt designed to bypass the model's safety training) and indirect prompt injection (where malicious instructions are embedded inside documents or data the model is asked to process). Because these attacks arrive through the input channel, Prompt Shields run on prompts as well as completions.

PII Detection and Masking

The PII filter detects personally identifiable information — names, addresses, identification numbers, contact details — that appears in LLM output. In masking mode, the detected spans are replaced before the response reaches the caller. This matters for any application that processes user data and must comply with privacy regulations: the model may inadvertently surface PII from its training data or from documents passed in the context window.

Groundedness Detection

The groundedness filter flags LLM output that is not supported by the source documents provided in the prompt. This is a direct hallucination detection mechanism: if the model makes a factual claim that cannot be traced back to the grounding documents, the filter surfaces that divergence. It is especially relevant for retrieval-augmented generation (RAG) applications where accuracy against a retrieved corpus is a hard requirement.

Protected Material Detection

The protected material filter detects when the model reproduces verbatim or near-verbatim content from copyrighted sources — song lyrics, published articles, or licensed code. This reduces intellectual property risk when the application might otherwise relay copyrighted text directly to users.

Handling finish_reason: content_filter

When the content filtering system blocks or annotates a completion, the API signals this through the finish_reason field on the choice object. A value of content_filter tells your application that filtering ran and affected the response. Contrast this with normal completion endings: stop means the model finished naturally, and length means it hit the token limit.

Reading finish_reason alone is not sufficient. You also need to inspect content_filter_results to understand which category triggered and at what severity, so your application can respond with a context-appropriate message.

Check whether filters actually ran. If the Azure content filter service is unavailable at request time, content is not blocked — it passes through. However, the response will contain a content_filter_error object rather than normal content_filter_results. An application that only checks finish_reason will miss this condition entirely and treat an unfiltered response as a filtered-and-clean one. Always verify that content_filter_results is present and contains no error object before trusting that filtering ran successfully.

Best Practices Summary

  1. Always read finish_reason on every completion response.
  2. If finish_reason is content_filter, do not surface the raw response — return a graceful fallback to the user.
  3. Inspect content_filter_results for the per-category severity breakdown.
  4. Confirm that content_filter_results contains no content_filter_error object, which would indicate the filter service itself did not run.
  5. Define explicit fallback behavior for your use case — the right response to a blocked medical query differs from the right response to a blocked entertainment query.
