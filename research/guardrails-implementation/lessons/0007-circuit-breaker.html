The Circuit Breaker Pattern

⏱ ~20 min Module 3 — Software/System Guardrails · Lesson 7 of 12
Primary source: Martin Fowler — Circuit Breaker
https://martinfowler.com/bliki/CircuitBreaker.html

The Problem: Cascading Failures

In distributed systems, services depend on other services. When a downstream dependency — a database, a third-party API, a microservice — becomes slow or unresponsive, the callers waiting for responses accumulate. Threads block. Connection pools exhaust. The slowdown in one service cascades upward and sideways, eventually degrading the entire system.

The naive approach — retrying immediately on failure — often makes things worse. A struggling service bombarded with retries has no opportunity to recover. What's needed is a way to detect that a dependency is unhealthy and stop calling it until it recovers. That is exactly what the circuit breaker provides.

The pattern wraps a protected function call in an object that monitors for failures. When failures hit a configured threshold, the breaker "trips" and subsequent calls return errors immediately — bypassing the failing operation entirely — giving the downstream service space to recover while protecting thread pools and other limited resources in the caller.

The Three-State Machine

A circuit breaker is a state machine with three distinct states. Understanding how transitions occur between them is the core of the pattern.

State Behavior for callers What triggers a transition out
Closed Calls pass through to the protected operation normally. Each failure is counted. A successful call resets the failure count to zero. This is the healthy, default state. Failure count reaches the configured threshold → transition to Open.
Open All calls fail immediately without attempting the operation. The breaker raises an error (e.g., CircuitBreaker::Open) rather than touching the downstream service. Callers receive fast failures instead of hanging indefinitely. A configured reset timeout elapses → transition to Half-Open.
Half-Open Exactly one trial call is allowed through to test whether the downstream service has recovered. All other simultaneous calls still fail immediately, preventing an overwhelming flood of requests onto a service that may still be fragile. Trial call succeeds → reset failure count, transition to Closed.
Trial call fails → transition back to Open.

Reading the State Machine

The typical lifecycle of a circuit breaker event looks like this:

  1. The breaker starts in Closed. Calls flow normally. Occasional failures are counted but do not trip the breaker.
  2. A dependency becomes unresponsive. Failures accumulate. The count crosses the threshold. The breaker trips to Open.
  3. Fast failures are returned to callers. The downstream service is no longer bombarded with requests and has time to recover.
  4. After the reset timeout, the breaker enters Half-Open. One probe call is sent to the downstream service.
  5. If the probe succeeds, the breaker resets to Closed and normal operation resumes. If it fails, the breaker snaps back to Open and the timer restarts.

Example (Ruby)

The structure of a circuit breaker implementation illustrates how the pattern is applied. The breaker stores the protected block and checks state before each invocation: 

cb = CircuitBreaker.new {|arg| @supplier.func arg}

When the breaker is Open, calling cb raises CircuitBreaker::Open immediately rather than invoking @supplier.func. The caller can catch that specific error and execute a fallback strategy.

Key insight: The circuit breaker does not fix a broken downstream service — it protects the rest of the system from being dragged down while that service is broken. Fast failure is a feature: callers know immediately that a dependency is unavailable and can execute fallbacks, rather than exhausting resources waiting for a response that will never come.

When to Use the Circuit Breaker

The pattern is most valuable wherever a call can hang or fail in ways that consume limited resources:

  • Remote and network calls — HTTP requests to external APIs, database connections, or inter-service calls within a microservices architecture are the primary use case. These calls can be slow to time out and have unpredictable failure modes.
  • Cascading failure prevention — when a single supplier going unresponsive can propagate failures to all its consumers and beyond, a breaker provides a firebreak.
  • Thread pool protection — threads blocked waiting for a slow dependency cannot serve other requests. A breaker that trips fast frees those threads immediately.
  • Asynchronous systems — in event-driven architectures, the circuit can be tripped when a downstream queue fills up, preventing producers from overwhelming a consumer that has fallen behind.

Key Operational Considerations

Monitoring

A breaker changing state is a signal, not just a safety mechanism. When the circuit trips to Open, it is telling you that a downstream system is in trouble. Operations teams need visibility into breaker state changes — dashboards, alerts, and logs that surface trips and resets in real time. Without this, the breaker silently masks an outage that the team should be investigating.

Manual Override

Operations staff should be able to manually trip or reset a circuit breaker. In practice this means: tripping a breaker early when maintenance on a downstream service is planned (rather than waiting for natural failure accumulation), and manually resetting a breaker when an operator has verified that the downstream service has fully recovered, without waiting for the reset timeout to expire. These manual controls are critical for production operations.

Fallback Strategies

The value of fast failure is realized only when callers have a plan for what to do when the breaker is Open. Common fallback strategies include:

  • Queuing requests — store the request locally and replay it once the circuit closes, appropriate when the operation is not time-sensitive.
  • Serving stale data — return a cached response from the last successful call, appropriate when approximate data is better than no data.
  • Graceful degradation — return a simplified response, a default value, or a user-facing message explaining that the feature is temporarily unavailable.

The right fallback depends on the operation's semantics. The important thing is to decide on the fallback at design time, not during an incident.

Common misconception — the circuit breaker is not a retry mechanism. Retries and circuit breakers serve opposite purposes: retries try harder; circuit breakers stop trying. Used together without coordination, they compound problems — a retry loop inside a circuit breaker inflates the failure count rapidly and can cause premature tripping. Design the two mechanisms to be aware of each other: retries should be limited and exponentially backed off; the circuit breaker should sit outside the retry loop, not inside it.

Application to LLM APIs

The circuit breaker is the foundational software guardrail for any backend service making outbound calls — and it is especially important for AI applications that call external LLM APIs.

LLM API endpoints exhibit exactly the failure modes the circuit breaker is designed for: they can become slow under load as inference queues grow, they can be rate-limited or throttled, and they can become temporarily unavailable during provider incidents. A single slow LLM call can hold a server thread for tens of seconds; without a breaker, concurrent user requests will exhaust the thread pool long before any timeout fires.

In practice, a circuit breaker around an LLM API call should be paired with:

  • A timeout on the individual call (so the breaker failure counter is actually incremented).
  • A fallback strategy — returning a cached response, routing to a secondary provider, or presenting the user with a clear "service temporarily unavailable" message.
  • Alerting when the breaker trips, so the engineering team knows the provider is degraded.

Together, these practices ensure that a provider outage degrades a single feature gracefully rather than causing the entire application to hang.
