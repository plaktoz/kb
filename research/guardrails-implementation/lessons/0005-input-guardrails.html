Input Guardrails — Topical Filtering and Jailbreak Detection

⏱ ~20 min Module 2 — AI/LLM Guardrails Lesson 5 of 12
Source OpenAI Cookbook — How to Use Guardrails  ·  developers.openai.com/cookbook/examples/how_to_use_guardrails

Two Places to Draw the Line

Guardrails for LLM systems fall into two broad categories based on where in the pipeline they act.

Input guardrails intercept a user's message before it ever reaches the main LLM. Their job is to stop problematic requests at the gate. Three primary concerns live here:

  • Topical filtering — rejecting queries that fall outside permitted subjects.
  • Jailbreak detection — catching attempts to override system instructions or extract unsafe behaviour from the model.
  • Prompt injection prevention — blocking embedded instructions in user content that try to hijack the assistant's behaviour.

Output guardrails act on the LLM's reply before it is delivered to the user. They cover different concerns: hallucination and fact-checking, brand moderation, and syntax or schema validation. Output guardrails are the subject of the next lesson.

This lesson focuses entirely on the input side — specifically the topical guardrail pattern and the async execution strategy that keeps latency manageable.

The Topical Guardrail: Secondary LLM Call

A topical guardrail works by sending the user's message to a secondary LLM call whose sole job is to decide whether the request falls within permitted subjects. This secondary call uses a purpose-built system prompt that instructs it to respond with exactly one of two tokens:

  • allowed — the request is on-topic; pass it through to the main LLM.
  • not_allowed — the request is off-topic or violates policy; return a rejection response to the user instead.

By constraining the guardrail's output to a binary schema (allowed / not_allowed), the calling code can parse the result deterministically — no ambiguous free-text to interpret, no risk of the guardrail itself producing unsafe content.

The secondary LLM used for the guardrail is typically a smaller, faster model than the one powering the main conversation. Its task is simple enough that a smaller model handles it well, and using a lighter model reduces both cost and latency.

Core pattern: A secondary LLM call, given a tightly scoped system prompt, returns allowed or not_allowed. The main LLM only runs if the guardrail returns allowed.

Async Execution: Hiding Latency

The obvious concern with adding a guardrail call is latency: a sequential pipeline (check first, then call the main LLM if clear) adds the guardrail's round-trip time to every interaction.

The async execution pattern solves this by firing both calls at the same time:

  1. The guardrail check is launched concurrently with the main LLM call.
  2. Both run in parallel.
  3. When results arrive: if the guardrail was triggered, return the guardrail's rejection response. Otherwise return the main LLM's response.

As one description of the pattern puts it: "If your guardrails get triggered you send back their response, otherwise send back the LLM response."

The total wall-clock time is roughly the slower of the two calls, not the sum. In practice, the main LLM call usually dominates — meaning the guardrail check is effectively free from the user's perspective.

Async key insight: Running the guardrail and main call concurrently means adding an input guardrail does not necessarily double your latency. Total wait time ≈ max(guardrail time, main call time).

The Accuracy / Latency / Cost Tradeoff

No guardrail configuration is free. Choosing a model and calibrating its sensitivity involves three competing factors:

Factor Consideration
Accuracy Fine-tuning or adding few-shot examples to the guardrail prompt improves detection of edge cases. A larger model generally makes fewer classification errors.
Latency / Cost Smaller models reduce overhead — they respond faster and cost less per call. The async pattern partially offsets latency, but cost still scales with model size.
Threshold Setting the guardrail too aggressively increases false positives — legitimate queries that get blocked. Too loosely, and harmful requests slip through.

The tension is real: a larger guardrail model is more accurate but adds latency and cost; a smaller model is faster and cheaper but may miss edge cases. The async pattern mitigates the latency dimension, but the accuracy/cost tradeoff remains a deliberate design decision.

False positive risk: Over-aggressive guardrails block legitimate user requests. As the source puts it, "more false positives leads to a fractured user experience." Tuning the guardrail's sensitivity is not a one-time setup — it requires ongoing evaluation against real traffic patterns.
