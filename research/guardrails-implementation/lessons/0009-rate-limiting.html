Rate Limiting — Algorithms and When to Use Each

⏱ ~20 min Module 3 — Software/System Guardrails Lesson 9 of 12
Source ByteByteGo — Rate Limiting Fundamentals  ·  blog.bytebytego.com/p/rate-limiting-fundamentals

Why Rate Limiting Is a Guardrail

Rate limiting controls how frequently users or services can access a resource. When requests exceed defined thresholds, they get throttled or blocked. This makes rate limiting one of the most versatile guardrails in a software system — it acts at the infrastructure layer rather than the application layer, meaning it intercepts excess load early in the request lifecycle before it can cause downstream harm.

There are three distinct reasons to reach for a rate limiter:

Benefit How It Helps
Security Defends against denial-of-service (DoS) attacks by rejecting excess calls before they overwhelm your servers.
Cost Control Caps usage of paid third-party APIs — payments processors, health record systems, LLM providers — so that a runaway client or bad actor cannot generate unbounded charges.
Server Health Rejects excess load early in the request lifecycle, protecting databases, queues, and downstream services from saturation.
Rate limiting is a perimeter guardrail: it does not fix bad requests, it simply refuses to process more of them than the system can safely handle. Acting early — before the request touches application logic — makes it cheap to enforce and hard to bypass.

Core Concepts

The Limit / Window / Identifier Triad

Every rate limiter is built from three elements. Understanding these is prerequisite to choosing and configuring any algorithm:

  • Limit — the maximum number of requests allowed. This is the ceiling you are enforcing (e.g., 100 requests, 1 000 tokens).
  • Window — the time period over which the limit applies: per second, per minute, per hour, per day, per week. The window determines the granularity of enforcement.
  • Identifier — what distinguishes one caller from another. Common identifiers are a user ID (authenticated caller) or an IP address (unauthenticated traffic). The identifier is what makes a rate limiter per-user rather than global.

These three values together define the policy: for example, "no single user ID may make more than 60 requests per minute." Changing any one element changes the behaviour substantially.

Response Types When the Limit Is Exceeded

When a caller crosses the threshold, the rate limiter can respond in one of three ways:

  • Blocking — the request is rejected outright with an HTTP 429 Too Many Requests response. The caller must wait before retrying.
  • Throttling — the response is deliberately slowed down rather than refused. The caller experiences degraded latency as a signal to back off.
  • Shaping — over-limit requests are deprioritised and queued rather than dropped immediately. Traffic is reshaped toward an acceptable output rate.

HTTP 429 is the standard signal for blocking. Well-behaved clients should honour it — and ideally read the Retry-After header to know how long to wait.

The Five Main Algorithms

Rate limiting is not a single algorithm. Each approach makes different trade-offs between memory, accuracy, and how it handles traffic bursts.

Algorithm Mechanism Best For Weakness
Fixed Window Counter Counts requests within a fixed, non-overlapping time slot (e.g., 12:00–12:01). Counter resets at the end of each slot. Low-complexity systems needing simple quotas, such as daily usage limits. Burst vulnerability at window boundaries — a caller can send the full quota at the end of one window and the full quota again at the start of the next.
Sliding Window Log Stores the exact timestamp of every request. At evaluation time, timestamps outside the sliding window are discarded; the count of remaining timestamps determines whether the request is allowed. Systems where precision matters and fairness is paramount. High memory usage — every request timestamp must be stored, which is expensive at scale.
Sliding Window Counter Blends two adjacent fixed-window counters using a weighted formula to approximate the count within a rolling window. No per-request timestamp storage needed. Systems needing a balance of accuracy and memory efficiency. Approximate — the weighted blend is not perfectly precise, so edge cases near the boundary may be slightly off.
Token Bucket Each caller holds a bucket of tokens. Tokens replenish at a steady rate. Each request consumes one token. If the bucket is empty, the request is rejected. APIs that should allow short bursts of traffic while still capping sustained throughput. Tuning complexity — bucket capacity and refill rate must be calibrated carefully or the policy behaves unexpectedly.
Leaky Bucket Requests enter a queue and drain out at a constant rate — like water leaking from a bucket at a fixed drip speed. Excess requests that overflow the queue are dropped. Scenarios demanding a uniform, predictable output rate, such as streaming pipelines. Strictly drops legitimate bursts — even valid spikes are shed if the bucket overflows.
The Fixed Window Counter has a well-known boundary exploit. If the window resets at the top of each minute and the limit is 100 requests, a caller can send 100 requests at 12:00:59 and another 100 at 12:01:00 — 200 requests in two seconds, each window technically within its limit. Sliding window approaches exist specifically to close this gap.

Choosing the Right Algorithm

The right algorithm depends on what your system needs to protect against and how much complexity you can absorb in operations:

  • Use Fixed Window when you need simplicity above all else — daily API quotas, coarse billing limits, or internal service caps where boundary exploits are not a meaningful threat.
  • Use Token Bucket when callers legitimately produce bursty traffic — for example, a developer's app that sends a flurry of requests when the user takes an action but is quiet otherwise. Tokens accumulate during idle periods and can be spent in bursts, so the algorithm tolerates natural traffic patterns while still capping sustained overuse.
  • Use Leaky Bucket when the downstream system requires a smooth, constant input rate — streaming ingestion pipelines, message queues with fixed throughput budgets, or real-time processing stages that cannot absorb spikes.
  • Use Sliding Window (Log or Counter) when fairness matters most and boundary-burst exploits are a real concern — for instance, a public API where well-funded attackers might deliberately time their traffic to straddle window boundaries.

In practice, many production systems combine approaches: a Token Bucket per user for burst tolerance, plus a Fixed Window counter for billing quotas, plus a global Leaky Bucket at the ingress layer for traffic shaping. Each layer addresses a different failure mode.

Exercise — Design a Rate Limiting Strategy

Design a rate limiting strategy for a public AI API with two tiers:

  1. Free tier — casual users who should be allowed occasional queries but not sustained high-volume traffic.
  2. Paid tier — developers building applications who need burst tolerance but where cost control still matters.

For each tier, address all three questions:

  1. Choose an algorithm and justify why it fits this tier's usage pattern.
  2. Specify concrete values for all three elements of the triad: the limit, the window, and the identifier you would use to distinguish callers.
  3. Describe what happens when a user exceeds the limit — do you block, throttle, or shape? What HTTP response does the caller receive?
