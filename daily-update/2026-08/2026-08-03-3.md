## 📁 Category Ingestion Breakdown

### 🚀 Technology — Loop Engineering

- **[The human role shifts from operator to architect](../../wiki/technology/loop-engineering-agent-loop-design.md)**: Loop engineering — coined June 2026 after a viral post by Peter Steinberger — replaces manual prompting with designed control systems built from six elements: Trigger, Context, Action, Verification, Memory, and Escalation. Every well-designed loop must define all six; skip any one and you have a script, not a loop.

- **[Four canonical loop types, ranked by autonomy](../../wiki/technology/loop-engineering-getting-started-loops.md)**: Anthropic's official taxonomy classifies loops by trigger and stop condition: turn-based (human-initiated), goal-based (evaluator model enforces success criteria), time-based (`/loop` locally, `/schedule` in the cloud), and proactive (fully autonomous). Each tier requires progressively stronger verification discipline to compensate for reduced human oversight.

- **[Five building blocks — skip one and the system breaks](../../wiki/technology/loop-engineering-designing-systems-that-prompt-ai-agents.md)**: The Ralph Technique (Geoffrey Huntley's originating pattern — a plain `while` loop, one task per fresh context) is the simplest valid loop. Production loops require five building blocks: Automations, Worktrees, Skills, Connectors (MCP), and Sub-agents. The Adoption Maturity Ladder maps 5 levels from Level 0 (manual prompting) to Level 4 (auto-merge on green).

- **[Discovery, Handoff, Verification, Persistence, Scheduling — all five mandatory](../../wiki/technology/loop-engineering-guide-safe-autonomous-agents.md)**: A production-grade loop reference that names four specific failure risks: **verification debt** (unattended mistakes), **comprehension rot** (code ships faster than understanding grows), **cognitive surrender** (accepting output without judgment), and **token blowout**. The non-negotiable rule: "the agent that generated the change should not grade its own homework."

- **[180% more code, 30% more shipped — the MIT paradox](../../wiki/technology/loop-engineering-future-of-software-development.md)**: Anthropic reports 80%+ of merged production code is AI-authored; Google reports ~75% of new code AI-generated by 2026. Yet an MIT/Forbes study found that AI agents producing 180% more code volume yielded only 30% more production-ready software. The valuable human skills going forward: specification writing, verification design, architecture judgment, and review at scale.

- **["Humans on the loop" — not in it](../../wiki/technology/humans-agents-software-engineering-loops.md)**: Kief Morris introduces three stances: humans outside (vibe coding, no oversight), humans in (bottleneck — inspecting every output), and humans on (maintaining the harness that governs agents). The on-the-loop model unlocks an **agentic flywheel** where agents eventually evaluate and improve their own harness with human review gates.

### 🚀 Technology — Spec-Driven Development

- **[Specs as super-prompts — 50% error reduction](../../wiki/technology/spec-driven-development-ai-coding-assistants.md)**: Academic paper arguing that AI coding tools have made specification quality — not coding speed — the bottleneck. Human-refined specs reduce LLM-generated code errors by up to 50%. Three tiers of rigor: Spec-First (lowest overhead), Spec-Anchored ("the sweet spot — divergence breaks the build"), and Spec-as-Source (automotive industry already here: Simulink → certified C code).

- **[The disciplined middle path between vibe coding and waterfall](../../wiki/technology/spec-driven-development-thoughtworks-2025.md)**: Thoughtworks defines SDD as specifying external behavior (I/O, preconditions, invariants, state machines) rather than implementation details. The central debate: is the spec or the generated code the authoritative artifact? The author's position — specs drive generation, but executable code remains the source of truth.

- **[EARS notation + 4-phase loop: Specify → Plan → Tasks → Implement](../../wiki/technology/sdd-ai-agents-ears-notation-2026.md)**: SDD addresses three AI agent failure modes: intent drift, context decay, and unverifiable output. EARS notation provides five structured patterns that make requirements AI-parseable (e.g., `WHEN [trigger] THE system SHALL [response]`). The practical rule: store specs in the repo under `specs/NNN-feature-name/`, keep each to 1–3 pages, and "spec the negative space" — out-of-scope notes are as important as requirements.

- **[Tool evaluation: Kiro, Spec-Kit, Tessl — and the Verschlimmbesserung risk](../../wiki/technology/spec-driven-development-kiro-spec-kit-tessl.md)**: Birgitta Böckeler finds the term "SDD" already semantically diffused. The real risk: elaborate tooling can amplify hallucinations rather than curb them (*Verschlimmbesserung* — making something worse while trying to improve it). Large context windows don't guarantee AI agent compliance; agents frequently ignored or over-applied spec instructions regardless of context size.

- **[Specs aren't waterfall — they're elevated, living artifacts](../../wiki/technology/spec-driven-development-isnt-waterfall-brooker.md)**: Marc Brooker's key reframe: Waterfall's failure was late feedback, not documentation. SDD moves iteration up the abstraction ladder — humans govern the outer loop (spec refinement and trade-off resolution) while AI handles the inner loop (code generation). Historical progression: switches → gates → instructions → code → **specs**.

- **[SDD is iterative — one use case per cycle](../../wiki/technology/spec-driven-development-iterative-agile.md)**: Simon Martinelli's AI Unified Process (AIUP): define → refine behavior → implement/generate → validate → adjust. The key quote: *"Code is cheap. Understanding is expensive. Wrong software is built faster than ever."* With AI generating code from specs, any ambiguity in the spec propagates directly into every generated artifact.

- **[Vibe for ideation, spec for execution](../../wiki/technology/vibe-coding-vs-spec-driven-development.md)**: Head-to-head comparison across six dimensions: startup speed, long-term velocity, maintainability, team suitability, technical debt risk, and scalability. Verdict: vibe coding wins on speed for prototypes and experiments; SDD wins for production systems, regulated industries, and multi-stakeholder environments.

- **[DDSE — the governance-first alternative to SDD](../../wiki/technology/ddse-vs-spec-driven-development.md)**: Decision-Driven Software Engineering (DDSE) uses CI/CD-enforced Technical Decision Records rather than specs as its source of truth. The decision matrix: use SDD for speed and early delivery; use DDSE for enterprise scale, audit requirements, and provable governance. DDSE's Contract Decision Records enable parallel front-end/back-end delivery — SDD has no equivalent.

- **[Prompts as first-class delivery artifacts — the REASONS Canvas](../../wiki/technology/structured-prompt-driven-development.md)**: Thoughtworks' SPDD treats prompts as version-controlled, reviewed artifacts alongside code. The REASONS Canvas (Requirements, Entities, Approach, Structure, Operations, Norms, Safeguards) is the canonical implementation blueprint per story. The governing rule: when behavior needs to change, update the canvas before changing code.

### 🚀 Technology — Agile Foundations & History

- **[Waterfall's real flaw: late feedback, not documentation](../../wiki/technology/waterfall-process.md)**: Fowler's crisp definition — Waterfall does one activity (e.g., design) for all features before moving on; iterative does all activities for one feature at a time. The origin myth: "waterfall" never appears in Winston Royce's 1970 paper — the cascade diagram was misread.

- **[YAGNI: ~2/3 of planned features fail to move their intended metrics](../../wiki/technology/yagni.md)**: Fowler's four cost categories for presumptive features: cost of build (wasted effort), cost of delay (deferred valuable work), cost of carry (complexity), and cost of repair (early builds need rebuilding). YAGNI does not apply to refactoring or self-testing code — those are the enablers that make deferral safe.

- **[Evolutionary design is viable — if you have the enabling practices](../../wiki/technology/is-design-dead-martin-fowler.md)**: XP transforms design from planned to evolutionary. The enabling trio: Automated Testing, Continuous Integration, and Refactoring — these flatten the cost-of-change curve. YAGNI applies because premature flexibility makes code harder to change in all directions except the anticipated one.

- **[Agile emerged as a direct reaction to requirement instability](../../wiki/technology/agile-methodology-fowler-new-methodology.md)**: Fowler's two foundational distinctions: adaptive (iterative) vs. predictive (plan-driven); and people-first vs. process-first. "Software construction is nearly free — almost all effort is design." Measurement-based management fails in software because critical success factors resist quantification.

- **[Skipping specs is the single biggest unnecessary risk](../../wiki/technology/painless-functional-specifications-why-bother.md)**: Spolsky (2000): designing in prose takes minutes; designing in code takes weeks. A spec aligns QA, marketing, developers, tech writers, and managers simultaneously. Root cause for skipping specs: people dislike writing — not a technical problem.

- **[Functional specs: living documents with nongoals and open issues](../../wiki/technology/painless-functional-specifications-part-2-whats-a-spec.md)**: Functional spec = what from the user's perspective. Technical spec = internal implementation. UX decisions must be finalized before technical architecture is chosen. Single author per spec ensures coherent voice. Nongoals explicitly bound scope. All open issues must be resolved before coding begins.

- **[Stakeholders cannot mentally simulate software from written descriptions](../../wiki/technology/up-front-requirements-limits.md)**: James Shore's project failure: stakeholders signed everything — prototypes, screenshots — yet still received the wrong product. Non-technical stakeholders "smile and nod" without genuinely evaluating what they're approving. The fix: ship real working software early with an explicit expectation of iteration.

- **[Specification by Example: the most accessible requirements tool](../../wiki/technology/specification-by-example.md)**: Fowler traces the term to a 2002 XP/Agile Universe workshop. Examples highlight specific points; general rules must be inferred — SBE cannot stand alone. The double-check principle: expressing intent in both code and tests using different methods surfaces errors automatically.

- **[BDD's living documentation pattern across 50+ projects](../../wiki/technology/specification-by-example-book.md)**: Gojko Adzic's case studies from startups to global enterprises. Executable acceptance tests serve double duty as living documentation. Dan North: "The closest I've seen to a BDD book." Won the 2012 Jolt Award for Best Book.

- **[BDD formulation: translating examples into Given/When/Then](../../wiki/technology/bdd-books-formulation.md)**: Seb Rose and Gáspár Nagy (SpecFlow creator) bridge discovery workshops and automated tests via Gherkin scenarios. The formulation step is where stakeholder examples become executable living documentation.

- **[The Art of Agile Development, 2nd ed. — Agile Fluency Model](../../wiki/technology/art-of-agile-development-second-edition.md)**: James Shore's complete rewrite diagnoses the core failure: most "Agile" organizations don't practice real Agile. Four-part arc: Improving Agility → Focusing on Value → Delivering Reliably → Optimizing Outcomes. New chapters on DevOps, scaling, and remote teams.

- **[SDD academic origins: TDD + Design by Contract as complementary spec types](../../wiki/technology/specification-driven-development.md)**: Wikipedia's canonical entry places SDD within Documentation-Driven Development alongside Model-Driven Development. The 2004 Ostroff/Makalsky/Paige paper combined SDD with TDD, treating tests and contracts as distinct but complementary specification types — each catches failure modes the other misses.

### 🚀 Technology — RAG Architecture

- **[RAG: external memory at inference time, no retraining required](../../wiki/technology/rag-architecture-implementation-and-evaluation.md)**: Retrieval-Augmented Generation supplements an LLM with task-specific external data retrieved at inference time, addressing hallucination and knowledge staleness. Two-phase pipeline: ingestion (embed + index) and inference (retrieve → augment prompt → generate). Key evaluation metrics: retriever accuracy/relevance and generator faithfulness/correctness. RAG beats fine-tuning for real-time or frequently updated knowledge domains.

## 🧠 Emerging Connections

Today's loop engineering and spec-driven development notes share an unexpected structural parallel with the vault's existing [[RAG Architecture Implementation and Evaluation]] note: **RAG and SDD solve the same root problem at different layers of the stack.** RAG externalizes factual memory into a mutable vector store so an LLM's reasoning doesn't have to carry stale or proprietary knowledge. SDD externalizes intent into a versioned spec so an AI coding agent's implementation doesn't have to infer unstated requirements. Both architectures apply the same principle — **Separation of Memory and Reasoning** — at different abstraction levels: RAG at inference time, SDD at development time. The implication: the most robust AI-assisted engineering workflows may eventually combine both layers: specs defining *what* to build (SDD outer loop) + RAG giving agents access to *organizational context* (domain knowledge, past decisions) without prompting it manually.
