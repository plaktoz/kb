# Agentic manual testing

source_url: https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/

---

The defining characteristic of a coding agent is that it can *execute the code* it writes — this is what makes coding agents far more useful than LLMs that simply produce code without any way to verify it. Code generated by an LLM should never be assumed to work until it's actually been run. Coding agents can confirm their code works as intended, or iterate further until it does.

Getting agents to write unit tests — especially test-first, red/green TDD — is a powerful way to ensure they've exercised the code they're writing, but it isn't the only worthwhile approach. Passing tests doesn't guarantee code works as intended; anyone who's worked with automated tests has seen cases where tests pass but the code fails obviously in production — crashing on startup, failing to display a crucial UI element, missing a detail the tests didn't cover. Manual testing remains no replacement — seeing a feature work with one's own eyes before shipping it matters, and getting agents to manually test code frequently reveals issues automated tests missed.

## Mechanisms for agentic manual testing

How an agent should "manually" test code depends on what the code is. For Python libraries, `python -c "... code ..."` lets an agent pass a string of Python code directly to the interpreter, including imports — coding agents are familiar with this trick and will sometimes use it unprompted. Other languages have similar mechanisms, or an agent can quickly write a demo file to compile and run (often in `/tmp` to avoid accidental commits). For web JSON APIs, agents can exercise endpoints using `curl`; telling an agent to "explore" often results in it trying out a range of API aspects, quickly covering a lot of ground. When manual testing surfaces something broken, the fix should follow red/green TDD so the case ends up covered by permanent automated tests.

## Using browser automation for web UIs

Interactive web UIs have historically been hard to test from code, but the past decade has brought major improvements in automating real browsers, uncovering problems in realistic settings that unit tests miss. Coding agents know how to use these tools well.

**Playwright**, Microsoft's open-source library, offers a full-featured API across languages and can automate any popular browser engine — simply telling an agent to "test that with Playwright" is often enough. Tools built specifically for coding agents include `agent-browser` by Vercel (a CLI wrapper around Playwright) and Willison's own project **Rodney**, which uses the Chrome DevTools Protocol to directly control Chrome. A `rodney --help` invocation (via `uvx`, auto-installing on first use) gives an agent everything it needs to both understand and use the tool, including taking screenshots the agent can then evaluate with its own vision. Rodney and similar tools support running JavaScript on a loaded site, scrolling, clicking, typing, and reading the accessibility tree.

Issues found and fixed via browser automation, like other manual tests, can be folded into permanent automated tests. Many developers have historically avoided extensive automated browser tests due to their reputation for flakiness — small HTML tweaks causing frustrating waves of failures — but having coding agents maintain such tests over time greatly reduces the friction of keeping them current as designs change.

## Have them take notes with Showboat

Manual testing by agents can also produce artifacts documenting the code and how it was tested. Willison built **Showboat** to facilitate documents capturing the agentic manual-testing flow. Its `showboat --help` command teaches an agent what it is and how to use it; the three key commands are `note` (appends a Markdown note), `exec` (records a command, runs it, and records the output — discouraging the agent from writing what it "hoped" happened instead of what actually happened), and `image` (adds an image, useful for Rodney screenshots). This pattern has worked well for documenting agent work during sessions, and Willison hopes to see similar patterns adopted more widely.
