# Yagni

## Summary

YAGNI ("You Aren't Gonna Need It") is an XP-originated principle advising against building software capabilities presumed needed in the future. It contrasts with the late-90s emphasis on careful upfront planning.

## Core Argument

When teams build "presumptive features" (code supporting functionality not yet in use), they incur real costs even when the feature eventually proves useful:

- **Cost of build** — wasted effort if the feature is never needed
- **Cost of delay** — other valuable features are deferred
- **Cost of carry** — added complexity slows all subsequent work
- **Cost of repair** — features built early may need rebuilding as the team learns

Research suggests roughly two-thirds of planned features fail to improve their intended metrics, making the expected value of presumptive work generally negative.

## Key Distinctions

Fowler emphasizes that YAGNI does *not* apply to:
- Refactoring and improving code malleability
- Self-testing code and continuous delivery practices
- Changes that don't add complexity

It *does* apply to both large visible features and small abstractions: "any abstraction that makes it harder to understand the code for current requirements is presumed guilty."

## Practical Heuristic

When tempted to build something early, mentally simulate the refactoring needed to add it later. Often this reveals the future cost is modest — or surfaces a lightweight change now that reduces later effort without adding meaningful complexity.

> "Yagni is not a justification for neglecting the health of your code base. Yagni requires (and enables) malleable code."
