# LLM Security

LLM security is the discipline of identifying and mitigating risks arising from large language models deployed as applications — distinct from traditional software security in that the attack surface is probabilistic, exploits are social-engineering-adjacent rather than binary, and the primary attacker entry point is the same natural-language interface that gives the system its value.

## Why GenAI Security Differs from Traditional Security

Traditional penetration testing operates on a binary pass/fail model: an exploit either reproduces or it doesn't. Generative AI systems are probabilistic — the same input can produce different outputs across runs, making the reproducibility assumption that underlies traditional remediation workflows invalid [[genai-red-teaming-owasp-prompt-injection]]. The security goal shifts accordingly: where traditional security aims at zero vulnerabilities, GenAI security aims at blast-radius containment — reducing the severity and scope of inevitable failures rather than eliminating them. This containment mindset applies equally to prompt injection (architecturally unavoidable given how LLMs process natural language), hallucination (an inherent property of probabilistic models), and agentic misbehavior (which emerges from optimization pressure without adequate oversight). The OWASP GenAI project — grown to 600+ contributors across 18+ countries since its 2023 origin as the LLM Top 10 — reflects the community's recognition that the attack surface extends well beyond the model itself to the entire deployment stack [[owasp-top-10-llm-applications]]. Red teaming GenAI systems requires replacing the binary exploit model with probabilistic assessment: running thousands of adversarial probes and measuring attack success rates gives developers quantitative risk data before deployment, rather than a binary verdict. AI systems trained to be helpful respond to persuasion, urgency, role-play, pretexting, and refusal suppression in ways that mirror social engineering — making AppSec teams without a social-engineering mental model significantly under-equipped [[genai-red-teaming-owasp-prompt-injection]].

## Prompt Injection: The Primary Threat

Prompt injection — crafting inputs that override a model's original instructions to redirect its behavior — is ranked the #1 LLM application risk by OWASP and is considered architecturally unavoidable with current model architectures [[owasp-llm01-prompt-injection]]. Two variants exist: direct prompt injection (user-facing input manipulation) and indirect prompt injection (malicious instructions embedded in data the model processes, such as resumes, CRM entries, or web-scraped content). Indirect injection is the harder production problem because it bypasses the user-facing input layer entirely — a model asked to summarize a malicious document can be redirected mid-task without the user or developer seeing the injection, and [[genai-red-teaming-owasp-prompt-injection]] documents demonstrated attacks that hijack LLMs, extract user data, and redirect users to malware via prompt-to-SQL injection across multiple tested models. Advanced attack patterns documented by researchers include ASCII/Unicode smuggling (invisible characters carrying hidden instructions that bypass guardrails), context window exhaustion (flooding context so early-session guardrails are forgotten), the Crescendo attack (incrementally escalating a conversation from benign to harmful over many turns), and TAP (Tree of Attacks with Pruning), which demonstrated over 80% jailbreak rates on leading LLMs using iterative tree-of-thought refinement. [[adversarial-prompting-llm-attacks]] and [[adversarial-attacks-llms-lilian-weng]] document the broader landscape: role-playing frames, urgency injection, refusal suppression, pretexting, context poisoning (corrupting RAG databases upstream), and adversarial suffixes (token strings that activate restricted-content neural pathways) all exploit the same core property — LLMs' responsiveness to contextual framing — that makes them useful.

## Guardrails Architecture

Application-layer guardrails are the primary technical response to LLM security risks — configurable, auditable detective controls that can be updated independently of the underlying model. The canonical architecture distinguishes input guardrails (validating user prompts before the model sees them, catching prompt injection, jailbreaks, and off-topic requests) from output guardrails (validating model responses before delivery, checking for PII leakage, toxicity, hallucination, and competitor mentions) [[llm-guardrail-patterns-input-output]]. The key operational insight for production deployment is the async guardrail pattern: running guardrail checks and the main LLM call in parallel rather than sequentially, discarding the main response only if the guardrail fires — this avoids adding latency to every successful request. NVIDIA NeMo Guardrails extends this to a full conversation-layer architecture with five rail types (input, output, dialog, execution, and retrieval), a domain-specific language (Colang) for defining control flow, and layered jailbreak detection combining fast heuristics with LLM-based judgment and specialized NVIDIA NIMs [[nvidia-nemo-guardrails-llm-safety]]. The "shared vulnerability" problem constrains purely LLM-based guardrail designs: a guardrail model trained on the same data as the production model can be fooled by the same attacks, which is why combining LLM-based checks with rules-based pattern matching — each catching what the other misses — is the defense-in-depth standard. Gradual rollout (annotation-only mode before enabling hard blocking) is the operational discipline that prevents premature over-refusals from degrading user experience while calibrating false positive and false negative rates on real traffic [[llm-guardrail-patterns-input-output]].

## Agentic Security and Excessive Agency

The security risks of agentic AI systems are categorically more severe than those of text-only chatbots because the potential consequences of misbehavior change from harmful text to real-world actions. [[owasp-llm08-excessive-agency]] identifies excessive agency — over-permissioned models taking harmful autonomous actions without adequate human oversight — as a distinct risk category requiring the same least-privilege reasoning applied to traditional system accounts. Write actions (database writes, email sends, file system operations, financial API calls) carry irreversibility properties that read actions do not, and the blast radius of a compromised agent operating with write permissions is qualitatively different from a chatbot producing a harmful response. [[defensive-coding-ai-agents-owasp-asvs]] documents that AI coding agents trained on internet-scale code will replicate both good and bad security practices from existing codebases, meaning that unguided agents actively propagate existing vulnerabilities; the mitigation is front-loading security guidance via OWASP ASVS at the planning phase — injecting relevant checks before code is written rather than running vulnerability scans after generation. For multi-agent systems, cascading failures are the specific failure mode to plan for: one agent going off-course causes downstream agents operating on its outputs to follow, amplifying rather than correcting the initial error. Retrieval-augmented generation (RAG) introduces a distinct agentic attack surface: adversarially-crafted content embedded in retrieved documents can inject instructions into the model's context, a threat that [[nvidia-nemo-guardrails-llm-safety]] addresses with dedicated retrieval rails that inspect documents before they reach the LLM.

## The OWASP LLM Top 10 Framework

The OWASP Top 10 for LLM Applications provides the most widely-adopted risk taxonomy for production LLM deployments. Beyond prompt injection (#1) and excessive agency (#8), the framework covers: insecure output handling — unvalidated LLM outputs fed to downstream systems enabling XSS, SSRF, or privilege escalation (#2); training data poisoning — tampered training data introducing biases or backdoors that persist into production (#3); supply chain vulnerabilities — compromised datasets, pre-trained models, or third-party components in the pipeline (#5); sensitive information disclosure — PII, credentials, or proprietary data extracted via prompting (#6); insecure plugin design — insufficient access controls in LLM plugins enabling unauthorized actions or code execution (#7); overreliance — uncritical acceptance of hallucinated outputs causing cascading failures in downstream systems (#9); and model theft — unauthorized extraction of proprietary models via API attacks, model inversion, or weight theft (#10) [[owasp-top-10-llm-applications]]. The 2026 update (OWASP GenAI LLM Top 10) extends coverage to agentic AI systems and RAG architectures, reflecting the expanded attack surface of modern deployments. The "treat system prompts as public by default" design principle encapsulates the most practical operational guidance: system prompts will leak in mutated form under adversarial probing, so sensitive information (credentials, internal policies) should never be embedded in them — assume exposure and design for harmless leakage [[genai-red-teaming-owasp-prompt-injection]].

## Red Teaming and the Application Layer Priority

Most teams should focus red teaming effort on application-layer threats rather than model-layer risks: model-layer issues (hallucinations, hate speech, PII from training data) tend to improve over time with model updates, while application-layer threats (indirect prompt injection, tool misuse, data exfiltration, privilege escalation) arise from deployment architecture and are within the team's control [[genai-red-teaming-owasp-prompt-injection]]. White-box testing (with model access) is significantly more effective than black-box testing for AI systems — without access to model internals and ground-truth data, findings cannot be reliably validated, and black-box AI red teaming is largely limited to obvious surface-level issues. PyRIT (Microsoft) is the leading open-source tool for automated LLM red teaming, specifically designed for the multi-turn, context-accumulating nature of GenAI attacks [[pyrit-microsoft-ai-red-teaming-framework]]; Garak (NVIDIA) is the complementary open-source framework for systematic probe generation. Google's AI Red Team, drawing on Mandiant and TAG threat intelligence, reinforces the containment framing: many AI attack findings lack a simple fix and should feed ongoing R&D rather than one-off patches — conventional security controls (locking down systems, minimizing blast radius, layering defenses) remain meaningfully effective against many AI-specific attacks, since many AI attacks remain detectable using conventional methods [[genai-red-teaming-owasp-prompt-injection]].
